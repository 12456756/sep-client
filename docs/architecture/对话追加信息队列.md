# 对话追加信息队列

每个对话任务独立保存 FIFO 队列，最多等待 10 条，不计正在运行或等待重试的本轮。成功入队必须先写盘；切换页面不会中断执行。超出上限返回 `CONVERSATION_QUEUE_FULL`，使用统一弹窗显示“任务队列已经满了”，输入与附件保留。

## 分层与接口

- `conversation:continue`（既有 `task:continue` 通道）提交消息 ID、文本、附件引用和知识库选择。重复 ID 复用已接受的消息；同一 ID 携带不同输入时拒绝。
- `conversation:queue` 读取队列或显式继续处理，只接受当前账号的对话任务。
- `ConversationQueueService` 通过账号、企业、任务组成的串行写链处理容量、落盘、启动、结束、重试与终止；不等待模型运行结束。
- `ConversationQueueStore` 通过 `ScopePath` 和原子文件保存任务目录下的 `conversation/queue.json`。损坏且无有效备份时返回失败，不能覆盖为空队列。
- `TaskRuntime.hasConversationRun(taskId)` 是新增的只读运行状态查询。任务结果发布后，worker 和工作目录锁仍可能正在释放，因此队列必须同时检查运行器是否仍持有任务。
- `TaskRuntimeOptions.onConversationSettled` 在执行器清理完成、清除启动标记后通知队列，并携带任务所属账号。准入队列中的员工失效也必须通知结束。

## 执行与恢复

消息先标记为 active 并持久化，再交给运行器。运行器为本轮使用预先分配的 runId，真正运行前重新校验授权。文本、附件快照引用、知识库选择分别保存，不读取后来消息的输入。

执行失败或启动失败时暂停队列，保留失败项与后续等待项。显式重试为失败项创建新的 runId，先重试该条，再处理后面的消息；重试项不占用等待容量。

终止操作与队列写操作串行执行，取消当前和等待信息，保留已有执行结果。终止后重新发送可开启新一轮。存在运行中、等待或失败项时不能切换员工。

退出时中止本会话调度信号；登录恢复后才重新启用服务。异步返回须同时校验信号和账号。启动或重新登录发现未完成队列时，恢复为暂停；之前 active 的消息转为待重试，已明确完成的消息不重放。用户确认继续后再处理。

## 前端

输入框上方显示可展开的“等待处理 n/10”，列出文本与附件名。暂停时显示“继续处理”或“重试并继续”，不为成功发送弹窗。正在提交的标识与幂等 ID 保存在账号所属的对话状态中，页面切换后继续复用。

重试会重新执行失败的输入；已有工具审批和副作用核实规则继续生效。此队列不会使关闭客户端后的模型任务继续在系统后台运行。
