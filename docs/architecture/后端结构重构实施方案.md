# 客户端后端结构重构实施方案

> 适用范围：Electron 主进程后端（`electron/` + `pi-extension/`），共 45 个文件、约 6105 行 TypeScript。
> 本轮不改动渲染进程（`src/`）代码与 IPC 契约。
>
> **本文档是行为基准。** 原有的《后端结构重构方案》与《客户端后端任务运行框架方案》已删除且不再遵循，
> 并发规则、状态机语义、错误码语义此前只存在于代码中。第 2 章的缺陷清单与第 7 章的并发不变式
> 共同承担基准职责，Phase 0 必须先把它们落成可执行断言。
>
> **当前实现说明（2026-09-10）：** 八个重构阶段已经完成。本文件后续各阶段记录保留作历史依据；
> 当前目录、命名和职责以第 3.2 节及根目录 `AGENTS.md` 为准。旧记录中的 `workflow`、
> `TaskExecutionCoordinator` 等名称不再是代码契约，也不应通过兼容层恢复。

## 0. 设计原则与工作准则

### 0.1 三条设计原则

1. **每个模块只有一个改变的理由。** 判断标准不是文件大小，而是"一次需求变更会不会同时改它的两个部分"。
2. **依赖单向流动。** 控制层 → 服务层 → {数据层, 执行层} → 公共层。反向引用一律禁止，用接口 + 注入倒置。
3. **每种判断只有一个定义点。** 本次重构最大的收益来源：当前 scope 校验有 10 份、副作用工具清单有 3 份、
   脱敏正则有 2 份、原子写有 3 份、路径推导有 4 份。

### 0.2 四条工作准则

| # | 准则 | 含义 |
|---|------|------|
| W1 | **冗余代码直接删除，不予保留** | 已确认无引用的代码不搬迁、不注释保留、不留 `@deprecated` 兼容层。归并重复实现时删掉旧实现，不留 re-export shim。清单见第 6 章。 |
| W2 | **使用标准日志打印，在需要日志的地方设置** | 全后端只有一个日志入口 `common/logger.ts`，禁止裸 `console.*`。日志点由第 5 章的规范决定，不靠个人习惯。 |
| W3 | **先修缺陷，后做重构** | Phase 1 在**结构一行不动**的前提下修完第 2 章全部 9 个缺陷。结构调整从 Phase 3 才开始。 |
| W4 | **单次提交只做一件事** | 任何提交不得同时改结构和改行为。行为修正单独成 commit 并在信息里写明修的是哪个缺陷编号。 |

W3 是本方案与初版的最大差别。理由：C1（任务永久卡死）、C2（工作区锁永久泄漏）、C3（停机数据丢失）、
C5（审批可能批准错误的工具调用）是**当前已存在的线上缺陷**，与重构无关。让它们等待一轮多阶段重构才修复
不合理；且它们一旦在重构中期发作，会与结构改动的回归混淆，难以定位。

## 1. 现状问题总览

按你提出的三个关注点归类。

### 1.1 控制层不成层

`electron/main.ts` 837 行，27 个 `ipcMain.handle` + 1 个 `ipcMain.on` 全部写在模块顶层：

- **不可测**：注册发生在 import 副作用里，测试无法在不启动 Electron 的情况下调用任何一个 handler。
- **10 个模块级可变全局**：`mainWindow`、`taskCoordinator`、`taskCoordinatorInitialization`、`taskManager`、
  `taskRunStore`、`workflowStore`、`taskMetadataStore`、`activeInstances`、`subscriptionRuntime`、
  `authenticationCleanupPromise`。加 6 个手写惰性单例（`ensureXxx`）维护它们。
- **3 种错误信封**：`authError()`（`main.ts:66`）、`taskError()`（`main.ts:144`）、以及 `main.ts:413`
  一处裸对象 `{ message, statusCode: 401 }` 和 `main.ts:430` 的 `{ statusCode: 0 }`。
- **约 10 处逐字复制的 scope 守卫**。
- **`task:create`（438 行）与 `conversation:create`（583 行）近乎重复**。
- 参数校验靠人记得写，没有结构强制。

### 1.2 服务层完全缺失

用例逻辑散落在 IPC 回调内部，没有一个可以脱离 Electron 调用的业务层。最典型的越层：
`TaskManager` 同时是任务仓库、状态机执行者，**并且直接持有 `BrowserWindow` 发 IPC**
（`task-manager.ts:415-426` 的 `notifyTaskUpdate` / `notifyTaskListUpdate`）。一个服务类知道渲染进程的存在。

### 1.3 数据层不成层

4 个 store（`task-store`、`task-run-store`、`workflow-store`、`task-metadata-store`）各自为政：

- **3 套独立的原子写实现**（tmp + rename），行为细节不一致：`task-store` 有 `.bak` 备份与 `quarantine`，
  `workflow-store`（33 行）什么都没有。
- **路径推导重复 4 处**，`workflow-store.ts:11` 自己拼 `task-data/v3/<ent>/<mem>/tasks/<id>/workflow.json`。
- **`task-run-store.ts` 461 行捆了 5 件事**：run 记录、事件日志、消息投影、崩溃恢复、路径推导。
- 脱敏正则 `SENSITIVE_KEY` 与 `sanitizeError`/`sanitizeValue` 在 `task-run-store.ts` 与
  `pi/sdk/pi-coding-agent-adapter.ts:30` 各有一份。

### 1.4 文件夹按来源命名而非按职责

`auth/`、`tasks/`、`pi/`、`runtime/`、`infrastructure/` 混合了控制、服务、数据、领域逻辑。
`tasks/` 里同时有 store、manager、coordinator、domain。新人无法从目录名推断一段逻辑该放哪。

### 1.5 扩展成本实测

以"给任务加标签"为例，今天需要改：`src/shared/types.ts`、`src/shared/ipc.ts`、`preload.ts`、
`main.ts`（handler + 参数校验 + scope 校验 + 错误映射，约 20 行）、store，
共 **6 个文件、4 个必改，`main.ts` 再长 20 行**。重构后的目标见第 9 章。

## 2. 缺陷清单（Phase 1 修复对象）

逐行审查调度、锁、事件链、状态提交四条并发路径后确认的 9 个缺陷。C1/C2/C3 会丢任务或丢数据，
C5 涉及安全约束。**每条独立成 commit**，commit 信息注明编号。

### C1 — `pump()` 按下标 splice 队列，会丢掉无关的排队任务【严重】

`electron/tasks/task-execution-coordinator.ts:297-318`：

```ts
for (let index = 0; index < this.queue.length;) {
  const queued = this.queue[index]
  const task = await this.taskManager.getTask(queued.taskId)            // 挂起点 1
  if (!task || task.activeRunId !== queued.runId) {
    this.queue.splice(index, 1); continue
  }
  const employee = await this.authorizeEmployee(queued.subscriptionId)  // 挂起点 2（网络）
  if (!employee) { this.queue.splice(index, 1); /* ... */ }
  // ...
  this.queue.splice(index, 1)
  void this.startRun(/* ... */)
}
```

`queued` 在 `index` 处捕获，但经过两个 await 后 `this.queue` 可能已被改动——`cancelTask:241` /
`pauseTask:224` 调用的 `removeQueuedTask()` 是**同步 splice**，正好能在 `pump` 挂起时插进来。
恢复执行后 `splice(index, 1)` 删掉的是**另一个**条目。

**后果**：被误删条目对应的 task 仍持有 `activeRunId`，但它永远不会被启动，也永远不会被清理。
任务卡在 PENDING 且无法重试（`admitTask:188` 见 `activeRunId` 非空即抛 `TaskAdmissionError`）。
用户看到一个永久卡死、无法操作的任务。

**修法**：队列条目改为按 `runId` 寻址。取出用 `findIndex(e => e.runId === runId)`，
`removeQueuedTask` 同样按 runId 操作。Phase 1 阶段不拆类，只把下标寻址换成 runId 寻址。

### C2 — 锁获取与 try/finally 之间有裸露区，会永久泄漏工作区锁【严重】

`task-execution-coordinator.ts:350-402`：`releaseWorkspace` 由 `pump():311` 获得后传入 `startRun`，
但 `startRun` 内的 `getPaths()`（360-365）与 `createWorker()`（366-395）**都在 try 之外**。

- `getPaths()` 对非法 taskId/runId 抛 `TaskScopeError`（`task-run-store.ts:374-375, 386`）。
- `createWorker()` 构造 `PiTaskWorker`，同样可能抛。

任一抛出，`finally` 从未进入 → `releaseWorkspace()` 永不调用 → **该工作目录被永久锁死**。
之后所有落在同一目录（含父子目录，`pathsOverlap` 会判定重叠）的任务在 `pump` 里永远 `acquire` 失败，
静默滞留队列，无任何日志。且 `activeByTask` 已在 401 行 set，此后不会被清理。

**修法**：锁的获取与释放必须在同一个词法块内。`startRun` 改为进入函数后立即
`try { /* 全部建仓步骤 */ } finally { releaseWorkspace() }`，不留裸露区。

### C3 — `will-quit` 是同步事件，`stopAll()` 根本没跑完【严重】

`main.ts:833-837`：

```ts
app.on('will-quit', async () => {
  if (taskCoordinator) { await taskCoordinator.stopAll() }
})
```

Electron 不 await `will-quit` 监听器的返回值。进程在 `stopAll()` 的第一个 await 处就继续退出。

**后果**：

- 正在执行的 `bash`/`write`/`edit` 的 `SIDE_EFFECT_UNKNOWN` 事件不会落盘
  （`finalizeRun:487-500` 专门处理这段），下次启动无法判定副作用是否已发生。
- worker 不 dispose，pi 会话文件可能半写。
- `markActiveRunsInterrupted`（`task-run-store.ts:250`）下次启动虽能兜底，
  但拿不到进程内的 in-flight 信息，恢复精度下降。

同一处还有孪生问题：`main.ts:816` 的 `ensureTaskManager()` 未 await，rejection 无人处理。

**修法**：改用 `before-quit` + `preventDefault` 的两阶段退出，并给停机预算设上限：

```ts
let shuttingDown = false
app.on('before-quit', event => {
  if (shuttingDown) return
  event.preventDefault()
  shuttingDown = true
  void withTimeout(stopAllAndDispose(), SHUTDOWN_BUDGET_MS)
    .finally(() => app.exit(0))
})
```

`SHUTDOWN_BUDGET_MS` 建议 5000。必须有界，理由见 C7。

### C4 — `authorizeEmployee` 在调度循环内发网络请求，会阻塞全局准入

`pump():304` 每轮对每个排队条目调一次 `authorizeEmployee`，而它（`main.ts:171-186`）内部是
`getValidAccessToken()` + `GET /client/subscriptions` + `SubscriptionRuntime.prepare()`。
这段代码运行在 `pumping = true` 期间：

- 一次慢或挂起的平台请求 → **所有任务的准入全部停摆**，且没有超时保护。
- `executeTask:137` 已调过一次，`pump` 又调一次 → 每个 run 至少 2 次平台往返；
  因锁冲突重试时还会再调。

叠加时序耦合：`authorizeEmployee` 写全局 `activeInstances`，而注入给 coordinator 的
`resolveEmployee`（`main.ts:155`）读同一个全局。`resolveEmployee` 的返回值取决于
"最后一个写 `activeInstances` 的人是谁"（可能是 `authorizeEmployee`，也可能是 `auth:get-instances`）。
这是时序耦合，不是数据流。

**修法**：Phase 1 只做能力拆分，不建新目录——授权在**入队前**完成一次，
`EmployeeRuntimeConfig` 随队列条目携带，调度循环内改为只读快照，**禁止任何网络调用**；
平台目录读取加 TTL 缓存与单飞（singleflight）去重。Phase 5 再把这两件事正式落成
`service/employee-directory.ts` 与 `service/employee-authorizer.ts`，届时全局 `activeInstances` 删除。

### C5 — 审批响应可能批准错误的工具调用【安全相关】

`electron/pi/approval-broker.ts:46-51`：

```ts
respond(response) {
  let requestId = response.requestId
  if (!requestId && this.pending.size === 1) requestId = this.pending.keys().next().value
  // ...
}
```

场景：请求 A 在 60s 超时被自动拒绝（`:36-38`），紧接着请求 B 进入 pending。
用户此时点了针对 A 的"批准"按钮，而渲染进程送来的响应缺 `requestId`
（`ToolApprovalResponse.requestId` 在 `src/shared/ipc.ts:88` 是可选字段）→ 命中 `size === 1` 分支
→ **B 被批准**。B 可能是一个 `bash`。

这违反项目约束"所有 `bash`/`write`/`edit` 需显式用户批准"——用户批准的不是这一个。

**修法**：`requestId` 必填。缺失时只在"恰好一个 pending **且** taskId/runId 匹配"时才回退，
否则返回 false 并记 warn 日志。

### C6 — 事件序号分配是 O(n²) 文件读，且失败被静默吞掉

`task-run-store.ts:350-371` 的 `appendEvent` 每追加一条事件都调 `getTimeline()`——
完整读取并逐行 `JSON.parse` 整个 `events.jsonl`，只为算下一个 sequence 并做冲突检查。
而 `text_delta` 是**逐 token** 产生的。一个产生 2000 个 delta 的 run 会做 2000 次全文件读取，
且全部串在同一条 `writeChains` 链上，直接拖慢事件到达渲染进程的延迟。

同时 `enqueueEvent`（coordinator:460-469）的链条是 `prior.catch(() => undefined).then(...)`，
`appendEvent` 抛出的 `TaskScopeError` 被完全吞掉：事件既没落盘、没到渲染进程，也没有任何日志。

还有一处：`startRun:433` 用 `await (this.eventChains.get(taskId) ?? Promise.resolve())` 等待事件排空，
但 `enqueueEvent:465-467` 的 `finally` 会在链末尾删掉 map 条目，所以这里可能拿到 `undefined` 而立即返回
——**没有真正的"排空"语义**。

**修法**：持有 per-(task, run) 的内存序号计数器，首次访问时从文件尾部 seek 一次初始化，之后纯内存自增。
链条错误交给日志与错误上报，不再吞。提供显式的 `drain(taskId): Promise<void>`，语义明确。

### C7 — 停机与认证失效链路无界，可以等到 60 秒

`stopAll()`（coordinator:264-282）串行 `await active.worker.abort()` + `await active.completion`。
run 内部可能正卡在 `approvalBroker.request()` 的 60s 定时器上。虽然 `stopAll` 第一行就 `denyAll()`
解除审批等待，但 `enqueueEvent` 的落盘链在慢磁盘上仍无上限。

`invalidateAuthentication`（`main.ts:188-205`）同样：它内部 `await taskCoordinator.stopAll()`，
但**没有任何调用方 await 它返回的 promise**。401 触发后，IPC 处理器仍在用半清理状态继续服务
（`activeInstances` 已清空，但 `taskManager` 的 scope 还没清）。

**修法**：`stopAll` / 停机 / 认证失效全部套 `withTimeout`，超时后走强制路径并记 error 级日志。
认证失效引入显式状态：进入 invalidating 后，scope 守卫对所有需要 scope 的用例直接返回 `AUTH_REQUIRED`，
而不是让它们读到半清理的中间状态。

### C8 — `setCurrentUser` 不走 `mutationChain`，登录切换存在写入丢失窗口

`task-manager.ts:81-126` 的 `setCurrentUser` 直接 `this.currentUser = null` / `this.tasks.clear()` /
`this.tasks = new Map(loadedTasks...)`，全程**不经过** `commit()` 的 `mutationChain`（`:380-392`）。

一个在途的 `commit` 已在 `submit` 外捕获了 `scope`（`:381` 的 `requireCurrentUser()`），
并在闭包里基于**旧** `this.tasks` 计算 `nextTasks`。若它在 `setCurrentUser` 之后才落盘，
就会把旧快照写回旧 scope 的文件——**丢掉切换前最后一批状态变更**。

因为路径按 scope 编码（`task-store.ts:261-265`），这是数据丢失窗口，不是跨租户泄漏。
但登出或 401 时正有任务在跑是完全现实的路径（`invalidateAuthentication` → `clearCurrentUser`）。

**修法**：scope 切换本身作为 `mutationChain` 上的一次操作；引入 `generation` 计数，
`commit` 的 `submit` 内部先校验 generation 未变，否则放弃写入并记 warn 日志。

### C9 — 检查与提交分离（TOCTOU），错误码失真

`task-manager.ts` 混用了两种写法：

- `admitTask`（`:183-195`）、`settleTaskRun`（`:221-242`）把守卫放在 `commit` 的 mutate 闭包**内部**
  ——正确，串行化保护生效。
- `pauseTask`（`:312-324`）、`cancelTask`（`:326-343`）、`deleteTask`（`:345-351`）、
  `addTaskFile`（`:291-301`）先在**链外**读状态判断，再进链修改——两次判断之间状态可变。

实际后果不是数据损坏（闭包内还有 `assertTaskTransition` 兜底），而是**错误码失真**：
链外判断通过、链内 `assertTaskTransition` 抛 `InvalidTaskTransitionError`，被映射成 `INTERNAL_ERROR`
（「操作未能完成。」），而用户实际遇到的是"当前状态下无法执行该操作"。用户看到一个假的内部错误。

**修法**：统一为"守卫只在 mutate 闭包内"一种形态，唯一检查点。
`InvalidTaskTransitionError` 在错误映射里对应 `INVALID_STATE`。
顺带清掉 `task-manager.ts:338-339` 的死赋值（`nextTask.error` 被赋值后立刻被下一行覆盖）。

### C10 — 身份变化不丢平台目录缓存，换账号会看到上一个账号的员工

**Phase 1 修 C4 时引入，Phase 4 期间发现并修复，独立成 commit。**

C4 给 `GET /client/subscriptions` 加了 TTL 15 秒的 `InstanceDirectory` 缓存，但只有
`invalidateAuthentication()` 会 `instanceDirectory.invalidate()`；登录（`main.ts:349-350`）与
登出（`main.ts:394-395`）只清了 `activeInstances` 与 `subscriptionRuntime`。
而 `InstanceDirectory` 的缓存**不按身份分键**。

**后果**：登出后 15 秒内换账号登录，第一次 `authorizeEmployee()` 会从 TTL 缓存里读到
**上一个账号**的订阅列表。平台侧仍用新令牌校验 `getPackageInfo`，所以不是越权执行；
但用户会在列表里看到属于别人的员工，点下去拿到一个无从解释的失败。

**修法**：身份变化只有一个收尾入口。`EmployeeAccess.clear()` 同时丢内存快照、平台目录
TTL 缓存、技能包缓存，登录 / 登出 / 认证失效三条路径共用。

### C11 — 两个通道的错误信封没走唯一映射点，英文文案直送用户且不记日志

**Phase 2 漏做，Phase 4 之后自查时发现，独立成 commit。**

Phase 2 声明"42 处 inline 信封改为 `failure(code)`、两处裸对象全部改走 `error-mapper`"，
但 `main.ts` 里漏了 5 处手写信封：`auth:get-instances` 三条错误分支、
`util:select-directory` 两条。后果三层：

1. **英文文案直送渲染进程。** `src/App.tsx:60` 是
   `setInstanceError(result.error?.message || ...)`，原样显示给用户，
   于是平台异常时看到的是 `Invalid subscription response.` / `Unknown error`。
   与第 4.1 节「`message`（中文，进 IPC，用户可见）」直接冲突。
2. **完全不记日志。** `reportFailure` / `reportAuthFailure` 会记，这 5 处不会，
   `platform-api.ts` 自己也零日志调用——违反第 5.2 节「平台请求失败 → warn」。
   `auth:get-instances` 失败此前在日志里毫无痕迹。
3. 没有错误码，`retryable` 语义丢失。

这不是被前端契约逼出来的：`IpcError` 是 `{ message, statusCode? }`，
`failure()` 的返回值结构上可赋值给它（多出的 `code` / `retryable` 前端忽略即可），
所以不碰 `src/shared/` 也能转（第 11 章）。

**修法**：两个通道的 catch 改为 `reportFailure(通道名, error[, { authenticated: true }])`。
401 触发失效清理的判定原样保留。同时把这条约束交给机器——
`check:boundaries` 新增 enforced 规则 `errors:no-handwritten-envelope`：
`error: {` 只允许出现在 `electron/errors/`。C11 就是"这条只写在文档里、没人盯"的后果。

### 已知限制（本轮不修，仅记录）

- `WorkspaceLockManager` 是纯内存实现（`HeldLock` 不落锁文件），**无法跨进程互斥**；
  代码里也没有 `requestSingleInstanceLock`。两个 Electron 实例共享同一 `userData` 会互相破坏。
  **因此两个工作树不能同时 `npm run dev`。**
- `common/platform/credential-vault.ts`（原 `credentials.ts`）在模块作用域用同步 fs，
  且 import 时就读 `app.getPath('userData')`，Electron 外不可测。它在登录路径上，回归风险最高，
  不混进结构重构，留待下一轮。

### 4.4 编码前置结论（已完成，2026-09-01）

**结论：构建链是干净的，中文文案可以放心落地。** 乱码是一次性的历史事故，损坏范围已完全定界，
且原文全部可从 git 恢复。

#### 判定过程

1. **源文件本身都是合法 UTF-8**（无 BOM，CRLF）。乱码不是文件编码错误，
   而是**文字内容已被替换成错字**——UTF-8 字节被按 GBK 解读后，以新字符重新存回 UTF-8。
   验证：`'选择工作目录'.encode('utf-8').decode('gbk')` 精确得到源码里的 `'閫夋嫨宸ヤ綔鐩綍'`。  <!-- mojibake-sample -->

2. **构建链无关**。`npm run build` 后 `out/main/index.js`、`out/main/chunks/*.js`、
   `out/preload/index.mjs`、`out/renderer/assets/*.js` 全部是合法 UTF-8；
   源码里正确的中文（如 `config.ts` 的 `'主板序列号需要额外的原生模块。'`）在产物中**逐字不变**；
   源码里已损坏的中文在产物中保持同样的损坏形态。electron-vite / Rollup 全程按 UTF-8 透传，
   不做任何转码。**渲染进程产物零乱码。**

3. **损坏时点唯一**：`git log` 逐 commit 统计显示，`763e51e` 及之前所有版本的中文完全正确
   （PUA 字符数为 0），乱码在 `6006e9f`（`feat(enterprise): add silicon-employee workspace...`，
   2026-09-01 14:52）一次性出现。是那次提交的编辑器/工具以 GBK 读入了 UTF-8 文件，
   不是持续性的环境问题。

#### 损坏范围（全仓库精确扫描，共 5 个文件 25 处运行）

判定方法：非 ASCII 连续片段若能按 GBK/cp936 编回字节、再当 UTF-8 读出像源码的中文，
或含私用区（PUA）/片假名字符，即为乱码。**必须把 `€`→0x80 加进 GBK 反查表**——

## 5. 日志规范（W2）

### 5.1 唯一入口

`common/logger.ts` 是全后端唯一日志出口。**禁止裸 `console.*`**，由边界脚本检查
（`common/logger.ts` 与 `undici-polyfill.ts` 除外——后者在 logger 可用之前运行）。

```ts
export type LogLevel = 'debug' | 'info' | 'warn' | 'error'

export interface Logger {
  debug(message: string, fields?: LogFields): void
  info(message: string, fields?: LogFields): void
  warn(message: string, fields?: LogFields): void
  error(message: string, fields?: LogFields): void
  child(scope: string, fields?: LogFields): Logger   // 绑定模块名与常驻字段
}
```

约定：

- **结构化字段，不做字符串拼接**：`log.info('run started', { taskId, runId })`，
  不写 `` log.info(`run ${runId} started`) ``。便于过滤与后续接落盘。
- **每个模块用 `child(模块名)`**，日志自带来源，不再手写 `[TaskExecutionCoordinator]` 前缀。
- **全部字段过 `redact`**：token / cookie / password / secret / apiKey / credential 一律脱敏。
  这条与安全约束直接绑定，不是风格问题。
- 级别语义：`debug` 开发排查（生产默认关）、`info` 正常生命周期节点、
  `warn` 可恢复异常与自动降级、`error` 用例失败或不变式被破坏。

### 5.2 必须打日志的位置

现状 30 处 `console.*` 分布不合理：`pi/sdk/pi-coding-agent-adapter.ts` 用 `console.error`
打了 10 行**纯信息**日志，`pi/pi-task-worker.ts` 5 处同类。以下位置按职责重新设置，
而不是照搬现有调用点。

| 位置 | 级别 | 记录内容 | 理由 |
|------|------|----------|------|
| 应用启动完成 / 组装失败 | info / error | 版本、userData 路径 / 失败原因 | 启动问题现在完全没有痕迹 |
| 停机开始 / 完成 / 超时 | info / info / error | 在跑的 run 数、耗时 | C3 的可观测性；超时说明有 run 没收干净 |
| 认证失效（401 触发） | warn | 触发来源、被中止的 run 数 | C7 的半清理状态需要痕迹 |

### 5.3 明确不打日志的位置

- **`text_delta` 等逐 token 事件**：不逐条打日志（可打聚合计数）。否则重演 C6 那类性能问题。
- **工具调用的参数与返回内容**：可能含用户代码与密钥，只记 toolName 与结论。
- **完整文件路径**：可能含用户目录名，记用途标识；需要路径时只记相对 scope 的部分。
- **任何 token、refresh token、请求头**：绝不记录，即便脱敏后也不记原始形态。

### 为什么是这个顺序

## 12. 命名规整（Phase 8 之后）

八个阶段落完之后做一轮命名规整。判据只有一条：**读名字的人不需要先懂一个理论才能懂这个
文件放什么**。所以动的是行话，不是长度——`atomic-file` / `redact` / `credential-vault`
这类标准术语一个没改，`composition-root`（依赖注入理论）、`admission-queue`（排队论）、
`task-message-projector`（CQRS）这类必须改。

**目录名一个没动**：`bootstrap/ common/ controller/ data/ domain/ errors/ pi/ runtime/
service/` 九个都是平常英文，且分层语义已经由第 3.2 节的依赖方向定死，改名只会让所有
`import` 路径、`check:boundaries` 的五条边界规则、`package.json` 的 test glob 全部跟着动，
换不到任何可读性。

### 12.4 验收

改名会在两个地方**静默**失败，都不是编译器能拦的：

1. **按源码字面量读文件的断言**。`app-lifecycle.test.ts` 与 `sdk-boundary.test.ts` 用
   `readFile(join(root, 'electron', 'bootstrap', 'composition-root.ts'))` 检查启动顺序与
   SDK 边界——路径过期只会在运行时炸，`typecheck` 一片绿。
2. **按后缀发现文件的测试**。`ipc-contract.test.ts` 原来用
   `file.endsWith('.routes.ts')` 枚举路由文件，去掉 `.routes` 之后它一个文件都找不到，
   于是"33 条通道各有一个路由"变成"0 条通道"——**而且是断言通过的方向**。这条是本轮唯一
   真的挂了的测试（两个用例 FAIL），改成 `endsWith('.ts') && file !== 'index.ts'`。

所以判据是全套跑绿，而不是"编译通过"：`typecheck` + `lint`（0 error）+ `test:tasks`(180)
+ `test:invariants`(96) + `check:boundaries`（10 条全 enforced）+ `build` + `poc:01..04`；
产物 PUA 为 0、中文完好、协调器仍是独立动态 chunk（`index.js` 内 `@earendil-works`
引用数 0）。文件搬迁全部用 `git mv`，diff 里是 rename 而不是删加。
