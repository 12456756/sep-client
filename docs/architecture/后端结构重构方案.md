# 客户端后端结构重构方案（初版）

> 状态：在建
>
> 适用范围：`electron/`、`pi-extension/`（客户端内部后端，Electron main 进程）
>
> 上级依据：[客户端后端任务运行框架方案.md](./客户端后端任务运行框架方案.md)（基线）
>
> 创建时间：2026-09-01

## 1. 这份方案是什么，不是什么

**是**：把现有 `electron/` 的目录结构和依赖关系，改造成基线文档第 12 节已经规定好的分层。基线已经定义了目标模块树和职责边界，但代码没有落到那个形状上。本文只解决"怎么从现在的样子走到那个样子"。

**不是**：不重新设计并发规则、状态机、持久化格式或 IPC 语义。这些以基线第 4、6、9 节为准，本次重构**不改变任何运行时行为**。

因此本次重构的成功判据是：**结构变了，行为一个字节都没变**。任何"顺手改一下逻辑"的想法都推到重构之后单独立项。

## 2. 现状问题（实测，非推断）

后端共 6105 行 TypeScript（含测试）。问题集中在一处：`electron/main.ts` 837 行，是事实上的上帝文件。

### 2.1 结构性问题

| 问题 | 实测数据 | 后果 |
|------|---------|------|
| IPC 处理器全部写在模块顶层 | 27 个 `ipcMain.handle` 直接在 `main.ts` 顶层注册 | 处理器无法被单独 import，因此**无法写单元测试** |
| 模块级可变全局 | 9 个：`mainWindow`、`taskCoordinator`、`taskCoordinatorInitialization`、`taskManager`、`taskRunStore`、`workflowStore`、`taskMetadataStore`、`activeInstances`、`subscriptionRuntime`、`authenticationCleanupPromise` | 依赖关系隐式，测试之间互相污染 |
| 手写惰性单例 | 6 个 `ensureXxx()` 函数，每个都是"判空 → 创建 → 赋全局" | 同一模式重复 6 次；创建顺序靠调用顺序偶然保证 |
| 缺失 Application 层 | 基线第 12 节要求的 `application/` 目录**完全不存在** | 用例逻辑（校验 → 授权 → 编排 → 组装返回）全部挤在 IPC 回调里，这是 837 行的直接来源 |
| 错误信封三种形状 | `AuthError`(`code`/`message`/`statusCode`/`retryable`)、`taskError()` 的 `{code,message}`、`auth:get-instances` 里裸的 `{message,statusCode}` | renderer 必须按 channel 分别处理错误，前端无法写统一错误组件 |
| 重复的 scope 校验 | 约 10 个处理器里逐字重复 `const scope = manager.getCurrentUserScope(); if (!scope) return {success:false,error:{code:'AUTH_REQUIRED',...}}` | 漏写一处就是越权读写 |
| 近重复用例 | `task:create`(438 行起) 与 `conversation:create`(583 行起) 逻辑高度重合，代码注释自述保留原因是"当前 renderer 的对话编辑器使用 task:create" | 改一处漏一处 |

### 2.2 隐藏耦合：`authorizeEmployee`

`main.ts:171` 的 `authorizeEmployee()` 每次调用都会发一次 `GET /client/subscriptions`，并且**改写全局** `activeInstances`；而注入给 coordinator 的 `resolveEmployee`（`main.ts:222`）读的正是这个全局。

调用方有 6 个：`task:create`、`task:continue`、`task:switch-employee`、`workflow:create`、`conversation:create`、`task:retry`。

两个后果：

1. 上述每个 IPC 调用都附带一次平台网络往返，延迟与平台可用性绑定在了每一次用户操作上。
2. `resolveEmployee` 返回什么，取决于"最后一个写 `activeInstances` 的人是谁"（可能是 `authorizeEmployee`，也可能是 `auth:get-instances`）。这是时序耦合，不是数据流。

这一条是本次重构必须解开的核心，对应基线的职责边界要求："Application Service 负责用例入口和权限，不直接操作 Pi 内部对象"。

### 2.3 启动期问题

`main.ts:815-825`：`app.whenReady()` 内 `ensureTaskManager()` 未 await，`createWindow()` 与 TaskManager 初始化并发执行，初始化失败时 rejection 无人处理——窗口已经显示，但任务子系统可能是坏的，用户看不到任何提示。

### 2.4 必须原样保留的约束

`main.ts` 里这段边界**不是技术债，是修复**，重构中任何情况下不得破坏：

```ts
// 将 Pi SDK 放在异步边界之后加载：其内置 undici 依赖的 Node API，
// 只有先加载上面的兼容层后，Electron 33 才能提供。
const { TaskExecutionCoordinator } = await import('./tasks/task-execution-coordinator')
```

配套的三件事同样不得动：`electron/main.ts:15` 的 `import './infrastructure/undici-polyfill'` 必须是首个副作用 import；`main.ts:16` 的 coordinator 必须是 `import type`；coordinator 只能在 `ensureTaskCoordinator()` 内部动态 import。破坏它会以 `markAsUncloneable is not a function` 的形式让应用启动崩溃。

### 2.5 附带发现（本次一并记录，修复归入 Phase 0）

- `main.ts:797` 原生目录选择框标题是乱码字面量 `'閫夋嫨宸ヤ綔鐩綍'`，应为「选择工作目录」。**这是用户可见的 bug。**
- `main.ts` 第 4-10、231、294、296、397、436、787、813、817 行的中文注释为乱码（GBK/UTF-8 混写）。
- `electron/preload.ts:65` 用的是 `as ElectronAPI` 类型断言而非类型检查。当前 33 个方法都已实现，所以这是**潜在漏洞而非现存 bug**：将来漏实现一个方法，`tsc` 不会报错，只会在运行时 `undefined is not a function`。改成 `satisfies ElectronAPI` 即可。
- `preload.ts` 的 33 个 channel 字符串与 `main.ts` 各写一遍，无共享常量。
- `package.json` 的 `test:tasks` 用显式文件列表，漏掉了 `electron/tasks/domain/workflow-executor.test.ts` 和 `electron/tasks/domain/workflow-graph.test.ts`——**这两个测试文件从来没被跑过**。
- 仓库根目录有两个构建配置：`electron.vite.config.ts`（42 行，最近一次改动 `c374e3c`）与 `electron-vite.config.ts`（49 行，自初始骨架 `3e687ac` 起未再改动）。electron-vite 默认只解析**带点的** `electron.vite.config.*`，所以带连字符的那份是死文件，改它不会生效。Phase 0 删除。
- `npm run lint` 全仓库不可用：ESLint 9.39.5 要求 `eslint.config.*`，仓库仍是 `.eslintrc.*`。属既有问题，本次不修，但要知道"lint 通过"目前不是有效验收项。

## 3. 目标结构

直接采用基线第 12 节规定的模块树，不做改动：

```text

├── application/          用例入口 + 权限，不碰 Pi 内部对象
│   ├── task-application-service.ts
│   ├── conversation-application-service.ts
│   └── workflow-application-service.ts

│   ├── task-state-machine.ts
│   ├── conversation-runner.ts
│   └── workflow-executor.ts

│   ├── shared-pi-session-runtime.ts
│   ├── workspace-lock-manager.ts
│   └── approval-runtime.ts
```

## 5. 分阶段执行

每个阶段结束都必须跑完整验收（见第 8 节）并单独提交。**任何阶段不允许同时改结构和改行为。**

### Phase 0 — 先建安全网（不动结构）

没有测试覆盖就搬代码，等于盲改。本阶段只做零风险的事：

1. 修 `main.ts:797` 的乱码标题为「选择工作目录」——用户可见 bug。
2. 修 `main.ts` 全部乱码注释（第 2.5 节列表）。
3. `test:tasks` 改为覆盖全部测试文件，让 `workflow-executor.test.ts` 和 `workflow-graph.test.ts` 首次真正运行；若它们本来就失败，先修。
4. `preload.ts` 的 `as ElectronAPI` 改 `satisfies ElectronAPI`。
5. 删除死文件 `electron-vite.config.ts`（见 2.5）。
6. 新建 `electron/ipc/channels.ts` 集中 33 个 channel 字符串常量，`main.ts` 与 `preload.ts` 都引用它。放在 `electron/` 而不是 `src/shared/`：renderer 只通过 `window.electronAPI` 调用，从不需要知道 channel 名字，所以这些常量不属于跨进程契约。**这是纯替换，不改任何 channel 名字。**
7. 补一个 IPC 契约快照测试：断言 `ElectronAPI` 的 33 个成员名与 preload 实际导出的键集合完全一致。后续每个阶段都靠它保证 renderer 侧零感知。

产出：结构未变，但从此有了"行为没变"的机器判据。

### Phase 1 — 纯移动

按第 4 节映射表执行 `git mv`，只改 import 路径，**不改一行函数体**。测试文件跟随源文件一起移动。

审查这一阶段的 diff 时，只需确认：所有非 import 行的改动数为 0。

### Phase 2 — 消除全局与手写单例

用一个组装根（composition root）替换 9 个模块级可变全局和 6 个 `ensureXxx()`：

- 新建 `electron/composition-root.ts`，导出一个 `createBackend()`，返回持有全部 store / runtime / service 实例的对象。
- 依赖显式传入构造函数，不再靠"谁先调用谁先创建"。
- **coordinator 仍然保持异步惰性加载**：组装根提供 `async getTaskCoordinator()`，内部维持 2.4 节的动态 `import`。这条边界是唯一允许保留的惰性单例。
- `app.whenReady()` 内改为 `await createBackend()` 后再 `createWindow()`；初始化失败必须捕获并向用户展示错误，而不是留下一个能开但坏掉的窗口（修 2.3 节问题）。

### Phase 3 — 抽出 Application 层（核心阶段）

1. 建 `application/` 三个服务，把 27 个 IPC 回调里的用例逻辑逐个搬进去。IPC 回调只剩：参数校验 → 调服务 → 返回。
2. 统一错误信封。三种形状收敛为一种，建议以基线第 9.3 节的稳定错误码为准：`{ success: false, error: { code, message, statusCode?, retryable? } }`。**旧字段在 Phase 3 内保留为可选，等前端切换完成后再删**，避免与前端分支硬碰撞。
3. scope 校验抽成单一守卫（对应全局规范「唯一责任点原则」），10 处重复归一。
4. 解开 `authorizeEmployee`（2.2 节）：拆成两件独立的事——
   - 员工目录读取：带 TTL 的缓存，由 `auth:get-instances` 与内部调用共用，不再每次用例都打一次平台；
   - 授权校验：接收目录快照作为**入参**，返回结果，不写任何全局。
   `resolveEmployee` 改为从显式传入的目录读取，时序耦合消失。
5. `task:create` 与 `conversation:create` 的公共部分下沉到同一个应用服务方法，两个 channel 保留为薄入口（renderer 还在用 `task:create`，**不能删**）。

### Phase 4 — main.ts 收敛为注册表

`main.ts` 只剩：polyfill import → 组装根 → IPC 注册表（`channel → handler` 的表驱动）→ 窗口生命周期。目标 150 行内。

### Phase 5 — 拆 coordinator

按 4.1 节的 5 个职责拆出独立类；8 个公开方法签名不变。这是唯一触及并发逻辑的阶段，必须逐条对照基线第 6 节十条运行规则补测试后再动。

### Phase 6 — 补齐持久化与恢复

从 `task-run-store.ts` 拆出 `task-event-store.ts`；建 `conversation-session-store.ts` 与 `recovery/task-recovery-service.ts`。这一步之后，目录形状与基线第 12 节完全一致。

### 阶段顺序为什么是这个

Phase 0-1 零风险、可随时中止；Phase 2 之后依赖关系才变显式，Phase 3 的搬迁才有落点；Phase 5 风险最高，放在有了安全网和显式依赖之后。**Phase 0-4 完成即可宣布重构达到"可继续加功能"的状态**，Phase 5-6 可以按需推进。

## 6. 与前端分支并行开发的协议

本次重构在独立分支进行，同时 `main` 上继续改前端。两边的**唯一交汇面**是 IPC 契约：

| 文件 | 行数 | 内容 |
|------|------|------|
| `src/shared/ipc.ts` | 127 | `ElectronAPI`（33 个方法）与各类返回信封 |
| `src/shared/types.ts` | 329 | 跨进程共享的数据类型 |

合计 456 行，是两个分支唯一必然冲突的地方。规则：

1. **后端分支在 Phase 0-5 内不修改这两个文件。** 结构重构不需要改契约——这正是"结构变、行为不变"的检验。
2. 前端确实需要新增/改字段时，**在 `main` 上单独提一个只改这两个文件的小提交**，后端分支 rebase 过来。反向同理。
3. Phase 3 的错误信封统一是唯一预期会碰契约的改动，采用"新字段可选、旧字段保留"的加法式演进，前端可以按自己的节奏切换，不产生阻塞。
4. `electron/`、`pi-extension/` 归后端分支；`src/`（除 `src/shared/`）归前端分支。互不越界。

### 6.1 两个工作树同时运行的限制（重要）

`main` 与后端分支各有一个工作树，但**两个 Electron 实例不能同时跑 `npm run dev`**：

- 应用状态全部来自 `app.getPath('userData')`，它由**应用名**决定，与源码目录无关。两个实例会共用同一份认证目录、task store、run store、workflow store 和运行时目录。
- 代码里没有任何 `requestSingleInstanceLock`；`WorkspaceLockManager` 是纯内存实现（`HeldLock`，不落锁文件），只能在单进程内协调，**无法跨进程互斥**。

所以：

- 前端在 `main` 上开发，用 `npm run dev:preview`（纯浏览器，`window.electronAPI` 由 `WorkspacePreviewPage.tsx` 的 `previewApi` 全量 mock，**不碰 userData**）。地址 `http://127.0.0.1:5174/?preview=workspace`。
- 后端分支跑 `npm run dev`（真 Electron）。
- 两边都要跑真 Electron 时，**串行**，或先给后端分支加 `userData` 隔离（例如按环境变量改 app name）——这属于新增能力，不在本方案范围内。
- 注意 `vite.preview.config.ts:19-20` 只设了 `host: '127.0.0.1'` 和 `port: 5174`，没有 `strictPort`，所以第二个 `dev:preview` 会静默跳到 5175。

另外每个工作树需要各自 `npm install`（`node_modules` 986 MB），磁盘要留够。
