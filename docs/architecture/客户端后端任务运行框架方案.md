# 客户端后端任务运行框架方案

**文档状态**：开发基线
**适用范围**：Electron 主进程、任务管理、任务调度、Pi 运行时、任务持久化和 IPC 后端
**Pi 版本**：`@earendil-works/pi-coding-agent@0.83.0`
**最后更新**：2026-08-27

本文是客户端后端后续开发的框架约束。后续代码、接口、数据结构和测试必须以本文为准；如果实现需要偏离本文，必须先更新本文并说明原因，不能直接在代码中形成新的隐含规则。

## 1. 核心决策

### 1.1 任务类型

客户端后端只处理两类任务：

1. **对话任务**：用户可以在同一个 task 中连续发送多轮内容，并且可以在任务空闲时切换硅基员工。每一轮是一个独立 run，但一轮结束不等于 task 结束。
2. **任务中心任务**：用户提交一个已经编排好的任务。执行器按照编排定义逐步执行，当前版本要求同一个 task 内严格串行。

### 1.2 共享 Pi Session

一个对话 task 只有一份持久化的 Pi Session：

```text
conversation task
└── one SessionManager / one session JSONL
    ├── user messages
    ├── assistant messages
    ├── tool calls and results
    ├── employee-turn markers
    ├── model/thinking changes
    └── Pi compaction entries
```

不能为每个硅基员工复制一份对话历史。共享历史的唯一 Pi 事实源是该 task 的 `SessionManager` 和对应 JSONL 文件。

需要区分两个对象：

- `SessionManager`：任务级持久化历史，整个对话 task 生命周期内保持不变。
- `AgentSession`：当前员工的内存运行实例，携带当前员工的 `ResourceLoader`、Skill、extension、system prompt、工具权限、模型和事件订阅。

员工切换时只重建 `AgentSession`，重新打开同一个 `sessionFile`；不能创建新的历史文件，也不能复制旧历史到新员工 Session。

### 1.3 订阅运行时并发边界

同一个员工模板或 `subscriptionId` 可以同时服务多个不同 task。不能使用“员工全局锁”、订阅全局锁或 `activeByEmployee` 作为调度边界。

并发控制只允许基于以下实际资源：

- task admission：同一个 task 的执行入口。
- Pi session writer：同一份共享 Session 文件的唯一写入者。
- workspace：实际工作目录及其父子路径范围。
- workflow orchestration：同一个任务中心 task 的唯一编排控制器。

### 1.4 串行规则

- 同一个对话 task 同时只能有一个 active run。
- 同一个任务中心 task 同时只能有一个 active orchestration run。
- 同一个共享 Pi Session 同时只能由一个 `AgentSession` 执行或写入。
- 任务中心 task 内的节点严格串行，不执行 ready 节点并行。
- 不同 task 可以并行，前提是它们的 workspace 不相同且不重叠。
- 相同、父子重叠或 canonicalize 后相同的 workspace 必须串行。
- 等待工具审批仍属于当前 active run，不能释放 task、Session 或 workspace 锁。

### 1.5 SEP 平台契约

平台接口以 [`docs/对接/SEP客户端开发者对接指南-v1.md`](../对接/SEP客户端开发者对接指南-v1.md) 为当前外部契约。旧版 API 文档和交接文档只能作为历史背景；发生冲突时，以该 v1 指南和平台最新规范为准。

任务运行身份必须遵守：

- `subscriptionId` 是订阅、客户端运行时、任务员工选择和 Employment Token 的主键；
- `employeeId` 只表示数字员工模板，用于包和 Skill 等平台接口，不作为一次任务运行的授权身份；
- 新代码和新持久化数据不得使用 `instanceId`、`employeeInstanceId` 或实例级 token；
- `accessToken` 只用于 SEP 普通 API，`employmentToken` 只用于模型网关；二者不能写入任务数据、Session、日志或 renderer；
- 平台目录中订阅消失或不再是 `ACTIVE` 时，禁止创建新 run；已经开始的 run 按实际网关响应进入失败、取消或可恢复状态，不能绕过平台授权继续执行。

## 2. 分层架构

```text
Renderer
  │ contextBridge IPC
  ▼
Main IPC Handlers
  │ 参数校验、owner scope 校验、幂等键校验
  ▼
Task Application Services
  │ 创建 task、提交 run、取消、恢复、切换员工
  ▼
Task Execution Coordinator
  │ admission、锁、队列、状态转换、事件顺序
  ├── Conversation Runner
  ├── Workflow Runner
  ├── Shared Pi Session Manager
  ├── Workspace Lock Manager
  └── Task Persistence Stores
        ├── task metadata
        ├── run records
        ├── execution events
        └── Pi session JSONL
```

职责边界：

- `main.ts` 只负责注册 IPC 和组装服务，不承载任务业务状态机。
- Application Service 负责用例入口和权限，不直接操作 Pi 内部对象。
- Coordinator 负责调度和锁，不负责拼装 UI 数据。
- Pi adapter 负责隔离 SDK 版本差异，不允许业务层到处调用 Pi SDK。
- Store 负责持久化和 owner scope 隔离，不负责决定任务是否可以运行。
- Renderer 只能通过 `window.electronAPI` 通信，不能直接导入 Electron 或 Pi。

## 3. Pi SDK 运行约束

### 3.1 SessionManager 的保存模型

Pi 0.83.0 的 `SessionManager` 是追加式 JSONL 会话树。每条 entry 具有 `id`、`parentId`、`timestamp`，当前 leaf 决定活动分支。

会话可以包含：

- user、assistant、tool result 等消息 entry；
- custom message entry；
- model change 和 thinking level change；
- compaction entry 和 branch summary；
- extension custom entry。

`SessionManager.create(cwd, sessionDir)` 创建指定目录下的 Session，`SessionManager.open(sessionFile, sessionDir, cwdOverride)` 打开指定文件。任务元数据必须保存具体 `sessionFile`，不能只保存目录。

Pi 的 Session 文件为追加式。普通 append 不修改或删除旧 entry。compaction 会追加一条 compaction entry；原始消息仍保留在 JSONL 中。

### 3.2 AgentSession 与员工资源

`createAgentSession()` 返回 `{ session, extensionsResult }`，并可以接收已有的 `SessionManager`。创建时传入的 `ResourceLoader` 决定当前运行实例的 Skill、extension、system prompt 和资源路径。

SDK 没有公开的 `setResourceLoader()`。因此员工切换不得试图在一个运行实例中热替换员工资源。正确步骤是：

```text
wait idle
→ abort/settle old AgentSession if necessary
→ dispose old AgentSession
→ open the same sessionFile with SessionManager.open()
→ create and reload target employee ResourceLoader
→ createAgentSession({ resourceLoader, sessionManager })
→ bind listeners and approval broker
→ write employee-turn marker
→ prompt
```

`AgentSession.reload()` 只重新加载当前实例原有的 ResourceLoader，不是跨员工资源替换 API。`bindExtensions()` 主要绑定运行时回调，也不是员工配置切换 API。

### 3.3 共享 Session 中的员工归属

Pi 普通 message entry 没有业务层 `subscriptionId` 字段。每轮员工开始处理前，必须追加一个隐藏的 `custom_message`，内容包含当前订阅员工、task 和 run 标识；结构化审计字段放入 `details`。

示例语义：

```text
[SEP employee turn]
task: task-123
subscription: sub-1
employee-template: employee-a
run: run-456
```

`custom_message.content` 会进入 Pi context 并参与 Pi compaction；`details` 会持久化但不会发送给模型。不能把员工归属只放在 `details`，否则摘要模型无法看到归属提示。

原始 JSONL 是员工归属的精确审计依据。压缩摘要应通过 `session_before_compact` 的自定义指令要求保留员工职责、关键操作、决策和交接，但模型摘要不提供绝对的逐条保留保证。当前轮员工身份必须每轮重新写入，不能依赖旧摘要推断。

### 3.4 上下文和 compaction

对话 task 的业务层保存完整的消息查询投影和执行事件；Pi Session JSONL 是模型恢复和共享上下文的唯一事实源。业务层不生成摘要、不使用专用摘要模型、不静默截断历史。

`messages.jsonl` 和 execution events 只用于 UI 查询、审计、状态恢复以及 Pi Session 损坏后的降级重建，不能作为正常运行时的第二套模型历史。日常恢复必须打开 task 绑定的同一个 `sessionFile`，禁止把业务消息投影再次批量注入 Pi，否则会造成历史重复、工具调用语义丢失和 compaction 分支不一致。

历史进入 Pi 的方式是正常的 user/assistant/tool 消息和员工标记，不能主要依赖 `context` hook：

- `context` hook 只修改当前 provider 请求副本，不写入 Session JSONL；
- 临时注入内容不会被 Pi 后续 compaction 读取；
- 临时注入会导致每次调用重复拼装，无法成为共享历史事实源。

当 Pi 判断需要压缩时，由 Pi 自己执行自动或手动 compaction。适配层只监听并记录 `compaction_start`、`compaction_end`、失败和恢复事件。

## 4. 持久化结构

任务数据必须按 owner 隔离，并统一使用 v3 目录。建议结构如下：

```text
<userData>/task-data/v3/
└── <enterpriseId>/<memberId>/
    └── tasks/<taskId>/
        ├── task-meta.json
        ├── runs/<runId>.json
        ├── events/<runId>.jsonl
        ├── workflow.json
        ├── artifacts.json
        ├── workspace.json
        └── conversation/
            ├── session.json
            ├── messages.jsonl          # 查询/投影索引，不是 Pi 恢复事实源
            ├── pi-session/
            │   └── <sessionId>.jsonl   # 唯一共享 Pi 历史
            └── pi-agent/               # Pi agent 配置/资源目录
```

如果 Pi 运行需要独立的 agent directory 或 extension 安装目录，必须放在当前 task 的 conversation 目录下或应用管理目录下，不能把 task 历史放进用户外部 workspace。

### 4.1 Task Metadata

任务元数据至少包含：

```ts
interface TaskMetadata {
  version: 3
  id: string
  owner: { enterpriseId: string; memberId: string }
  kind: 'conversation' | 'workflow'
  lifecycle: 'open' | 'closed' | 'archived'
  executionStatus:
    | 'idle' | 'queued' | 'running' | 'waiting_approval'
    | 'paused' | 'interrupted' | 'recovery_required'
    | 'failed' | 'cancelled' | 'completed'
  currentSubscriptionId: string | null
  workspace: { path: string; ownership: 'managed' | 'external' }
  conversationSession: {
    sessionId: string
    sessionFile: string
  } | null
  workflowVersion: string | null
  createdAt: number
  updatedAt: number
}
```

对话 run 成功后：`run.outcome = completed`，但 `task.executionStatus = idle`，`task.lifecycle = open`。只有显式关闭 task 才进入 `closed`。

### 4.2 Run Record

每次用户提交、恢复或任务中心节点执行都创建新的 run ID，不能复用已结束的 run：

```ts
interface TaskRunRecord {
  version: 3
  id: string
  taskId: string
  owner: { enterpriseId: string; memberId: string }
  kind: 'conversation' | 'workflow'
  subscriptionId: string
  employeeId: string
  modelId: string
  runtimeKey: string
  outcome: 'queued' | 'running' | 'waiting_approval' | 'completed'
    | 'failed' | 'cancelled' | 'stopped' | 'interrupted'
  sessionId: string | null
  sessionFile: string | null
  startedAt: number
  endedAt: number | null
  error: string | null
  degradedRecovery: boolean
}
```

### 4.3 Execution Event

事件是任务执行过程的审计记录。每个 run 的 `sequence` 单调递增，写入事件后才能推进对应状态：

```ts
interface TaskExecutionEvent {
  taskId: string
  runId: string
  subscriptionId: string
  sequence: number
  type:
    | 'run_queued' | 'run_started' | 'employee_selected'
    | 'prompt_submitted' | 'message_delta'
    | 'tool_call' | 'tool_approval_waiting'
    | 'tool_approval_decided' | 'tool_result'
    | 'compaction_started' | 'compaction_finished'
    | 'artifact_created' | 'run_completed'
    | 'run_failed' | 'run_cancelled' | 'run_interrupted'
    | 'recovery_started' | 'recovery_finished'
  occurredAt: number
  data: unknown
}
```

事件 payload 不得包含 access token、refresh token、employmentToken、完整敏感认证参数或未经脱敏的密钥。

### 4.4 Pi Session Binding

对话 task 只需要一个共享 binding：

```ts
interface SharedConversationSessionBinding {
  taskId: string
  sessionId: string
  sessionFile: string
  sessionDir: string
  agentDir: string
  generation: number
  status: 'available' | 'active' | 'invalid'
  lastRunId: string | null
  updatedAt: number
}
```

不能把 `subscriptionId -> sessionFile` 作为对话历史模型，也不能保留旧的 `employeeInstanceId -> sessionFile` 模型。`subscriptionId` 只记录在 task 当前选择、run、员工标记和审计事件中；共享历史始终绑定 task。

## 5. 默认 Workspace

未指定 `workDir` 时，创建每个 task 独立的托管目录：

```text
<userData>/task-workspaces/v1/<enterpriseId>/<memberId>/<taskId>/
```

创建 task 或首次运行时确保目录存在，并将 `ownership = managed` 写入 metadata。任务完成、失败、暂停、中断后保留该目录，以支持恢复和产物查看。

删除任务时，托管目录只能在用户确认后移入系统回收站；`external` workspace 永远不能由任务删除逻辑递归删除。

所有路径必须：

1. 先 canonicalize；
2. 检查仍在 owner 允许的范围内；
3. 对符号链接、大小写差异、父子路径做冲突判断；
4. 不把 `sessionFile`、metadata 或 token 存储在 external workspace 中。

## 6. 核心运行规则与并发可靠性

本节是实现并发时必须遵守的运行规则。并发可靠性不是由“使用 async”自动得到的，而是由状态、锁、持久化顺序和单写者不变量共同保证。

### 6.1 规则一：一个 task 只有一个 active execution

**规则**：task 从 `idle/open` 进入 `queued/running` 后，在当前 run 结束、取消、终止或恢复为可继续状态之前，新的提交不能创建第二个 active run。

**执行过程**：

```text
IPC submit
→ 校验 owner/task/expected state/idempotency key
→ 在 task admission 原子检查 executionStatus == idle
→ 写入 run queued 和 run_queued event
→ 更新 task executionStatus = queued
→ 进入 coordinator 队列
```

如果两个 IPC 同时到达，它们必须经过同一个 task admission 串行链。只有一个请求能看到 `idle` 并成功创建 run；另一个返回已有 run 的幂等结果，或返回 `CONFLICT`。不能先在内存判断再异步写文件，否则会出现双 run。

### 6.2 规则二：单 task 单 Pi writer

**规则**：同一个共享 `sessionFile` 同一时刻只有一个 `AgentSession` 运行实例可以执行 prompt、tool loop、compaction 或 append。

**原因**：Pi 的 `SessionManager` 使用同步追加文件，并没有为两个独立实例同时写同一文件提供跨实例协调。即使两个调用都使用 async，也不能依赖文件系统自动合并父子 leaf。

**执行过程**：

```text
task admission 成功
→ 获取 shared session writer lease
→ 打开 SessionManager
→ 创建当前员工 AgentSession
→ 订阅事件并运行完整 prompt/tool loop
→ agent_settled 且事件已落盘
→ dispose AgentSession
→ 释放 writer lease
```

只要 run 尚未 `agent_settled`，就不能切换员工、启动下一轮或让另一个恢复流程打开该 Session 写入。

### 6.3 规则三：固定锁顺序

为了避免死锁，所有执行入口必须按照同一顺序获取资源：

```text
1. task admission
2. workflow orchestration lease（workflow task 必需）
3. shared Pi session writer lease（conversation task 必需）
4. workspace lease
5. tool approval lease（只在等待审批时建立）
```

释放顺序反向执行。任何模块都不能先拿 workspace 再回头拿 task admission，也不能在等待锁时占用 Pi 运行实例。

### 6.4 规则四：状态推进必须晚于事实持久化

任何状态转换都遵守：

```text
写入事实/事件
→ 原子写入 run record
→ 原子写入 task metadata
→ 发布 IPC/UI 事件
```

例如工具执行完成时，必须先保存 tool result 和 `tool_result` event，再将 run 从 `waiting_approval/running` 推进到下一状态。崩溃时宁可状态停留在 `running/interrupted`，也不能先显示完成但没有可恢复的事实记录。

### 6.5 规则五：审批期间锁不释放

工具审批是当前 run 的一部分，不是一个可以脱离任务的 UI 请求：

```text
tool_call
→ 持久化 tool_call event
→ run = waiting_approval
→ 保持 task/session/workspace lease
→ 等待一次性 requestId 的 allow/deny/timeout
→ 持久化 approval decision
→ 继续或阻断 Pi tool loop
```

超时自动拒绝。过期或重复的审批响应必须被忽略，不能作用于新 run。用户终止任务时，先取消审批等待，再 abort Pi，并等待 `agent_settled` 或明确记录无法确认的副作用。

### 6.6 规则六：取消是协作式终止

终止 task 的顺序：

```text
标记 cancel requested
→ 禁止新的 prompt/tool admission
→ 取消 pending approval
→ 调用 AgentSession.abort()
→ 等待 agent idle/settled
→ 保存已发生的消息、工具结果、产物和未知副作用
→ run = cancelled/stopped
→ task executionStatus = idle 或 interrupted
→ 释放锁
```

不能通过直接删除 Session 文件或释放锁来“终止”。已经发生的工具操作必须保留；无法确认是否完成的副作用标记为 `SIDE_EFFECT_UNKNOWN`，不得自动重放。

### 6.7 规则七：恢复流程必须重新竞争锁

应用重启后，启动扫描将持久化为 `running/queued/waiting_approval` 的 run 标记为 `interrupted`，而不是假设它仍在运行。

恢复时必须重新执行完整流程：

```text
读取 task/run metadata
→ 验证 owner scope 和 session binding
→ 按固定顺序重新获取锁
→ 打开同一个 sessionFile
→ 由 Pi buildSessionContext() 恢复上下文
→ 继续或根据策略创建新 AgentSession
```

恢复不能绕过 task admission，也不能根据内存中的旧锁状态直接执行。

### 6.8 规则八：不同 task 的并发判断只看实际资源

两个 task 是否能同时执行，按以下规则判断：

| 条件 | 结果 |
|---|---|
| 不同 task、不同 managed workspace | 可以并行 |
| 不同 task、同一个 workspace | 串行 |
| 不同 task、父子或 canonicalize 后重叠 workspace | 串行 |
| 不同 task、同一 `subscriptionId`、不同 workspace | 可以并行 |
| 同一个 conversation task | 串行 |
| 同一个 workflow task | 串行 |
| 同一 task 的不同 IPC 重试 | 幂等返回或冲突，不得并行 |

员工身份本身不产生全局互斥。

### 6.9 规则九：所有异步资源必须有释放路径

每个 run 都必须在 `finally` 中完成：

- 取消 timer、approval timeout 和 retry timer；
- 解除 Pi 事件订阅；
- dispose 当前 `AgentSession`；
- 关闭或释放 workspace lease；
- 将未完成 run 转换为可查询的最终或中断状态；
- 清理 coordinator 内存索引。

任何异常都不能让 task 永久停留在 `running`，也不能让锁只存在于内存而无法恢复。

### 6.10 规则十：同一认证作用域的刷新必须 singleflight

**规则**：普通 `accessToken` 的并发刷新必须合并为一个 HTTP 请求；同一个 `subscriptionId` 的 `employmentToken` 并发刷新也必须合并为一个 HTTP 请求。不同订阅之间不能错误共享 Employment Token 或刷新 Promise。

**执行过程**：

```text
run 请求有效 token
→ 按 access session 或 subscriptionId 查询 refresh-in-flight
→ 已存在：等待同一个 Promise
→ 不存在：登记 Promise 并发起一次刷新
→ 刷新成功：只更新 main 内存中的 token 和过期时间
→ 刷新失败：所有等待者收到同一分类后的错误
→ finally 删除 refresh-in-flight
```

这条规则避免多个并行 task 同时刷新同一令牌导致重复请求、旧结果覆盖新结果或触发服务端限流。`employmentToken` 不得写入磁盘；普通 refresh token 仍只能通过 `safeStorage` 保存。

## 7. 对话任务生命周期

### 7.1 提交一轮对话

```text
renderer sendMessage(taskId, subscriptionId, text, idempotencyKey)
→ main 校验参数、owner 和 task lifecycle
→ task admission
→ 持久化 user message/submit event
→ 创建 queued run
→ 获取 shared session writer 和 workspace lease
→ 打开共享 SessionManager
→ 校验 subscription 为 ACTIVE 并解析对应 employeeId、包和 Skill
→ 按 subscriptionId 创建隔离的目标员工 ResourceLoader
→ 创建目标员工 AgentSession
→ 写入 employee-turn custom_message
→ session.prompt(text)
→ Pi 追加 user/assistant/tool/compaction entries
→ 转换并持久化可查询事件
→ agent_settled
→ run completed；task executionStatus idle；lifecycle open
→ 释放资源
```

用户下一次发送内容时创建新的 run，但仍使用同一个 task 和同一个共享 Pi Session 文件。

### 7.2 员工切换

员工只能在 task `idle` 时切换。切换不是迁移历史，也不是新建任务：

1. 校验目标订阅仍为 `ACTIVE`，保存 `currentSubscriptionId`；
2. 下一轮运行时使用新员工配置创建 ResourceLoader；
3. 通过 `SessionManager.open()` 打开原 sessionFile；
4. Pi 的 `buildSessionContext()` 恢复共享历史；
5. 写入新员工的 turn marker；
6. 继续执行新一轮 prompt。

运行中切换必须返回 `RESOURCE_BUSY` 或 `CONFLICT`。不能中途替换 system prompt、Skill 或 tool registry。

### 7.3 对话终止和恢复

终止只结束当前 run，不自动关闭 task。恢复会创建新的 run ID；原 run 保持 `cancelled/stopped/interrupted`，并通过共享 Session 继续保留已发生的内容。

## 8. 任务中心生命周期

当前任务中心严格串行，即使未来使用 DAG，也必须在同一个 task 内一次只执行一个 ready node：

```text
创建 workflow task
→ 冻结 workflow definition/version
→ task admission
→ 创建 orchestration run
→ 循环选择依赖已完成的下一个节点
→ 获取节点声明的 subscription/workspace 资源
→ 执行节点
→ 持久化节点结果、产物和事件
→ 更新节点状态
→ 释放节点资源
→ 选择下一个节点
→ 全部必需节点完成后 orchestration completed
```

节点失败时保存失败节点和原因；是否重试必须形成新的 node attempt/run，不得覆盖原始失败记录。恢复时已完成节点不得重复执行，除非 workflow 定义明确要求重试。

## 9. 状态机

### 9.1 Task lifecycle

```text
open → closed → archived
```

对话每轮完成不改变 lifecycle。关闭 task 前必须确认没有 active run。

### 9.2 Task executionStatus

```text
idle
 └→ queued
     └→ running
         ├→ waiting_approval → running
         ├→ paused
         ├→ interrupted
         ├→ failed
         ├→ cancelled
         └→ completed
```

对话成功路径为 `running → idle`，而不是 `running → completed`。任务中心全部节点成功后才使用 `completed`。

### 9.3 稳定错误码

后端至少支持以下错误码：

```text
CONFLICT
RESOURCE_BUSY
DEPENDENCY_NOT_READY
WORKSPACE_UNAVAILABLE
CONTEXT_PREPARATION_FAILED
SESSION_UNRECOVERABLE
RECOVERY_CONFIRMATION_REQUIRED
SKILL_VERSION_UNAVAILABLE
SIDE_EFFECT_UNKNOWN
PERSISTENCE_ERROR
AUTH_REQUIRED
INVALID_ARGUMENT
NOT_FOUND
```

错误必须可序列化、可展示，不得把原始 token、SDK 内部对象或堆栈中的敏感内容发给 renderer。

### 9.4 SEP 平台错误和有限重试

平台调用必须遵守《SEP 客户端开发者对接指南 v1》的状态处理，任务调度器不能无限重试，也不能把一次 HTTP 重试建模成新的用户 run：

| 场景 | 运行时处理 |
|---|---|
| 网关 401 | 重新换取该 `subscriptionId` 的 Employment Token，仅重试当前网关请求一次；再次 401 则 run 失败 |
| 平台普通 API refresh 401 | 清理 main 内存和 `safeStorage` 中的认证凭据，进入未登录状态 |
| 403 | 不重试；刷新订阅目录，run 失败并展示脱敏原因 |
| 404 | 按订阅授权失效处理并刷新目录，不继续创建或恢复 run |
| 429 | 遵守 `Retry-After`，最多两次额外重试，单次等待不超过 60 秒 |
| 5xx 或网络错误 | 指数退避，最多两次额外重试 |
| 流式响应中断 | 保存已收到的事件，将 run 标记为 `failed` 或可恢复状态，不得标记为完成 |

重试等待仍属于当前 active run，继续占用 task、共享 Session 和 workspace lease；取消信号必须能够中断退避等待。每次尝试记录 requestId、状态码、模型 ID、消息数量和耗时，但不记录完整请求、响应或认证头。

普通认证刷新遇到网络错误时不能删除长期 refresh token。平台 `message` 只能脱敏后展示；客户端不得依赖尚未稳定的服务端 `code` 字段进行核心状态转换。

## 10. Session 损坏和降级恢复

恢复策略采用“客户端默认值 + task 创建时快照 + task 级覆盖”：

```ts
type SessionRecoveryMode =
  | 'strict'
  | 'confirm_rebuild'
  | 'auto_rebuild_from_task_history'
```

推荐默认 `confirm_rebuild`。

- `strict`：进入 `recovery_required`，不自动创建替代 Session。
- `confirm_rebuild`：展示可能丢失的员工私有运行状态，经用户确认后使用任务可恢复历史创建新的 AgentSession。
- `auto_rebuild_from_task_history`：原 session 损坏但任务业务历史和员工配置完整时，从消息查询投影、执行事件和产物索引降级重建，并标记 `degradedRecovery = true`。

上述重建仅在原 Pi Session JSONL 已确认无法读取时使用。正常启动、员工切换、任务继续和应用重启恢复，都必须使用同一个 Pi Session 文件，不得从业务投影重复导入历史。

降级时：

1. 保留并隔离损坏文件，不覆盖；
2. 创建新的 session ID、sessionFile 和 generation；
3. 保留原 task、run 和 workspace；
4. 不借用其他员工配置；
5. 不自动重放未确认的工具副作用；
6. 写入 recovery started/finished 事件；
7. 使用 task 已快照的订阅 ID、员工模板、Skill、模型和恢复策略；恢复前重新校验订阅授权。

## 11. IPC 约束

所有 renderer 参数在 main 进程校验：

- taskId、runId、subscriptionId、requestId 必须符合安全 ID 规则；
- workDir 必须经过路径范围校验；
- 用户不能从 renderer 指定任意 sessionFile；
- submit 必须支持 idempotencyKey 或 expected state；
- 取消、审批响应必须绑定 taskId、runId 和 requestId；
- IPC listener 必须在 renderer unmount 时取消订阅。

建议的后端用例接口：

```ts
createTask(request): Promise<TaskResult>
getTask(taskId): Promise<TaskResult>
listTasks(query): Promise<TaskListResult>
submitConversation(taskId, subscriptionId, text, idempotencyKey): Promise<TaskRunResult>
selectConversationEmployee(taskId, subscriptionId): Promise<TaskResult>
cancelTask(taskId, runId): Promise<TaskResult>
closeTask(taskId): Promise<TaskResult>
resumeTask(taskId): Promise<TaskRunResult>
getTaskRuns(taskId): Promise<TaskRunListResult>
getTaskTimeline(taskId, runId): Promise<TaskTimelineResult>
respondToolApproval(requestId, decision): Promise<Result>
```

IPC handler 不直接调用 `session.prompt()`；必须进入 Application Service 和 Coordinator，以确保 admission、锁和持久化顺序一致。

### 11.1 数据上传边界

普通任务正文、本地文件、完整 prompt/response、Pi Session JSONL 和工具输出默认只保存在客户端，不能上传任务中心或通用日志。只有平台接口明确要求且业务流程已获得相应授权时，main 才能发送最小必要数据，例如知识库检索的 query、`subscriptionId` 和检索参数。renderer 不能直接调用 SEP API。

## 13. 测试和验收标准

### 13.1 共享 Session

- 同一个 task 只产生一个共享 `sessionFile`。
- 员工 A、B 切换后读取同一个 JSONL，不产生第二份历史。
- 员工 A、B 使用不同 ResourceLoader、Skill、system prompt 和工具策略。
- 员工切换时旧 AgentSession 已 idle/dispose，旧 extension listener 不再接收新事件。
- employee-turn marker 能在原始 JSONL 中定位每轮员工归属。
- Pi compaction 后原始 JSONL entry 仍可查询。

### 13.2 并发

- 同 task 两个同时提交只创建一个 active run。
- 同 task 一个 run 等待审批时，第二次提交返回冲突。
- 审批响应超时或重复响应不会影响新 run。
- 同一员工不同 task、不同 workspace 可以并行。
- 不同 task 使用相同或父子 workspace 时严格串行。
- 应用退出后 active run 变成 interrupted，重启恢复不会重复运行已完成 run。
- 任何异常都释放 timer、listener、Pi 实例和 workspace lease。

### 13.3 状态和持久化

- 对话 run 完成后 task 为 `open + idle`，可以继续提交下一轮。
- 只有显式 close 才能把 task 设为 `closed`。
- 终止后已经发生的消息、工具结果、产物和未知副作用可查询。
- 状态推进前已写入对应事实和事件。
- Session 损坏时严格遵守 task 快照的恢复策略。
- 日志、事件和 IPC payload 不泄漏 token。

## 14. 后续开发顺序

1. 清理对话模型中按员工保存 Pi Session 的旧字段和旧逻辑，只保留 task 级共享 Session binding。
2. 建立统一 task state machine 和 task admission。
3. 将 coordinator 改为 task/session/workspace 资源边界，删除员工全局互斥。
4. 实现共享 Session adapter：同一 sessionFile、员工切换重建 AgentSession、统一事件订阅和 dispose。
5. 完善事件追加、run 状态原子更新和应用重启恢复。
6. 接入默认 workspace 创建、canonicalize 和父子路径锁。
7. 完善审批、取消、未知副作用和降级恢复。
8. 最后再扩展任务中心 IPC 和 workflow 节点执行。

所有步骤都必须先补测试，再实现行为；测试应优先验证本文件第 6 节的核心运行规则，而不是只验证最终 UI 显示。
