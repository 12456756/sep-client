# 客户端后端架构审查与后续待办

> 状态：历史审查记录。本轮重构已经落地；当前代码结构和命名以根目录 `AGENTS.md` 及实际源码为准。

> 审查日期：2026-09-08  
> 审查范围：Electron 主进程客户端后端，不包含 SEP 平台后端  
> 当前分支：`refactor/backend-structure`  
> 文档目的：记录本轮架构审查结论与后续待办。当前开发顺序仍然是先根据前端完成接口设计，再按接口补齐客户端后端功能。

## 1. 总体结论

当前客户端后端架构的总体方向科学、合理，不需要再次进行整体性重构。

已经建立的主依赖方向为：

```text
renderer
   │ IPC
   ▼
controller
   ▼
service
   ├── data
   └── runtime
          ▼
        pi/sdk

domain / errors / common 为基础能力层
bootstrap 为唯一组装入口
```

本轮重构已经解决了以下关键结构问题：

- Electron 主进程入口不再承载业务逻辑。
- IPC 注册、参数校验和错误转换集中管理。
- 服务层负责用例编排，数据层负责本地持久化，运行时负责任务执行与并发控制。
- Pi SDK 被隔离在 `electron/pi/sdk/`，并通过动态加载规避 Electron 33 与 SDK 依赖的启动兼容问题。
- 主进程向渲染进程推送事件只有一个出口。
- 任务数据按企业和成员隔离。
- 错误码、日志脱敏、原子写、任务队列、工具审批与退出清理已有统一实现。
- 分层规则已由自动化脚本约束，不仅依靠开发约定。

因此，下文记录的问题属于业务闭环、边界契约和可靠性增强问题，不代表现有分层失败，也不建议据此立即启动第二轮大规模架构重构。

## 2. 当前架构中值得保留的设计

### 2.1 单一组装入口

`electron/bootstrap/build-backend.ts` 是客户端后端唯一组装入口，集中创建认证、目录、任务、运行时和持久化依赖。该设计有利于控制初始化顺序，也为后续替换测试实现和增加新服务保留了清晰入口。

### 2.2 IPC 边界集中

`electron/controller/router.ts` 统一负责：

1. 注册 IPC 路由和监听器。
2. 使用 Zod 校验渲染进程输入。
3. 调用服务层。
4. 将异常转换为统一错误信封。

通道名称集中在 `electron/controller/channels.ts`，preload 只暴露有限的 `window.electronAPI` 能力，符合 Electron 客户端的安全边界要求。

### 2.3 运行时职责拆分

任务运行相关能力已经拆分为协调器、队列、worker、事件、审批和工作区锁。`TaskExecutionCoordinator` 保留编排职责，而不再独自持有所有并发状态。这一方向适合本客户端需要同时处理多任务、流式事件、工具审批和中止恢复的场景。

### 2.4 本地数据隔离与恢复

数据路径统一由 `ScopePath` 派生，企业与成员共同构成数据归属范围。任务快照采用原子写和备份恢复，run 与事件记录保留执行历史，能够满足工作记录页和对话恢复的基础需求。

### 2.5 Pi SDK 隔离

`runtime/` 通过端口与 `pi/sdk/` 协作，SDK 只在兼容层安装完成后动态加载。构建产物仍将任务协调器输出为独立 chunk，现有四个 PoC 也覆盖了 SDK 导入、动态令牌、异步工具审批和 401 错误传播。

## 3. 已发现的问题

### 3.1 高优先级：工作流尚未形成完整执行闭环

现状：

- `WorkflowService.create()` 可以校验和保存工作流图。
- `WorkflowService.start()` 最终只是调用普通任务的 `executeTask()`。
- 运行时尚未读取工作流图并按依赖调度节点。
- 尚未实现节点状态持久化、节点输出向后续节点传递、失败传播和节点级重试。
- 创建工作流时只校验了第一个节点的硅基员工，没有逐节点完成授权检查。

影响：

“安排工作”页面可以创建一张看似完整的工作图，但当前客户端后端不能保证按图执行。这个问题必须在安排工作接口确定后，结合前端最终交互一起补齐，避免先实现错误的工作流语义。

建议：

- 先确定前端提交的工作计划、节点、依赖和运行参数结构。
- 再定义工作流执行用例和节点状态模型。
- 实现逐节点授权、依赖调度、输出映射、失败/跳过规则和恢复策略。
- 为完整纵向流程增加集成测试，而不只测试纯工作流图函数。

### 3.2 高优先级：SEP 外部响应缺少统一运行时校验

现状：

- 登录响应在 controller 中进行了部分手工字段检查。
- 刷新访问令牌、获取硅基员工令牌等响应仍主要依赖 TypeScript 类型断言。
- 订阅、技能和安装包响应采用了多套手工兼容逻辑。

影响：

SEP 返回缺字段、字段类型变化或错误格式时，异常可能进入认证状态、运行时或缓存后才暴露，错误位置不稳定，也不利于接口联调。

建议：

- 在 `common/platform/` 为每个 SEP 响应定义 Zod schema。
- SEP API 适配层只返回校验后的客户端领域数据。
- 兼容旧接口的逻辑集中在 schema 转换层，不扩散到 service 和 runtime。
- 无法识别的响应统一转换为可诊断的上游服务错误。

### 3.3 高优先级：部分持久化数据解析过于宽松

现状：

- `TaskRunStore` 主要校验版本、ID 和 owner，没有完整校验 run 的状态、时间、路径和其他字段。
- `WorkflowStore` 只检查 `version` 和 `nodes` 是否为数组，没有重新执行完整工作流节点校验。
- JSONL 事件只校验少量公共字段，事件的 `type` 与 `data` 没有成对校验。

影响：

磁盘数据损坏、版本不兼容或被外部修改时，格式错误的数据可能继续进入服务层和运行时，导致后续出现难以定位的异常。

建议：

- 为 Task、TaskRun、Workflow、Metadata 和 Event 分别建立持久化 schema。
- 数据读取后先校验和迁移，再交给上层。
- 对无法恢复的数据保留隔离文件和明确日志，不静默当成正常空数据。

### 3.4 高优先级：旧数据删除策略不可恢复

现状：

`TaskStore.initialize()` 会删除旧版 `task-data/v2` 和根目录下的 `tasks.json`，没有先归档，也没有迁移记录。

影响：

客户端升级后，如果旧数据仍有业务价值或删除判断出现偏差，用户无法恢复历史任务。

建议：

- 将删除改为一次性、可追踪的迁移流程。
- 旧数据先移动到带版本和时间戳的备份目录。
- 写入迁移完成标记，保证迁移幂等。
- 在新版本稳定一段时间后，再由明确的清理策略删除备份。

### 3.5 中优先级：IPC 事件契约仍然过于开放

现状：

`TaskExecutionEvent` 使用：

```typescript
interface TaskExecutionEvent {
  type: string
  data: unknown
}
```

影响：

不同事件的数据形状只能由消费者自行判断。后端、持久化和前端之间缺少编译期关联，增加工作记录页处理遗漏和运行时错误的概率。

建议：

- 把事件定义成以 `type` 为判别字段的联合类型。
- 为每类事件定义明确 payload。
- 对 SDK 原始事件先在 `pi/sdk/` 归一化，再交给 runtime。
- 持久化读取和 IPC 推送只接受归一化事件。

### 3.6 中优先级：端口隔离仍可进一步收紧

现状：

- service 依赖中仍直接出现 `TaskManager`、`TaskRunStore` 等具体类。
- `RequestContext` 暴露了完整 `Backend`，认证和系统路由可以直接访问多个内部对象。
- 当前边界脚本主要约束 import 方向，不能阻止路由在语义上绕过服务层。

影响：

当前规模下可以维护，但功能继续增加后，service 的单元测试替换成本和 controller 的误用空间会逐渐增大。

建议：

- 新增功能时优先让 service 依赖最小能力接口，而不是继续暴露具体实现。
- 将认证生命周期能力收敛为专门的 `AuthLifecyclePort`。
- 不要求一次性重写现有依赖，可随首页、安排工作等纵向功能逐步收紧。

### 3.7 中优先级：缺少客户端多实例保护

现状：

`WriteChain` 只能保证单进程内的写入顺序，应用没有单实例锁或跨进程文件锁。

影响：

如果用户同时启动两个客户端进程，两边可能并发写入相同用户数据目录，导致任务快照丢失更新或事件记录冲突。

建议：

- 在 Electron 启动阶段使用 `app.requestSingleInstanceLock()`。
- 第二实例启动时聚焦已有窗口，不再创建第二套后端运行时。
- 增加单实例生命周期测试。

### 3.8 中优先级：部分文件读取错误被当成“没有数据”

现状：

`readJsonFile()` 捕获所有读取和解析错误并返回 `null`。文件不存在、权限不足、磁盘 I/O 错误和 JSON 损坏无法区分。

影响：

客户端可能把真实的存储故障表现成空任务列表或找不到记录，用户看不到正确故障原因。

建议：

- 仅将 `ENOENT` 解释为文件不存在。
- JSON 格式错误进入备份恢复或隔离流程。
- 权限、磁盘和其他 I/O 错误转换为 `PERSISTENCE_ERROR`。

### 3.9 中优先级：窗口销毁与推送之间存在小竞态窗口

现状：

`RendererBridge` 先检查窗口是否有效，再调用 `webContents.send()`；窗口可能在两步之间被销毁。

影响：

在退出、重新登录或窗口重建期间，偶发推送可能抛出异常。

建议：

- 推送方法对窗口和 `webContents` 状态进行完整检查。
- 对窗口销毁竞态做有边界的异常处理和测试。

## 4. 与当前接口设计工作的关系

当前优先事项保持不变：先以已完成度较高的前端页面为依据，设计首页和安排工作的客户端 IPC 接口及所需 SEP 接口。

接口设计阶段应吸收本次审查结论：

| 设计对象 | 需要提前确定的内容 | 对应后续实现问题 |
|---|---|---|
| 首页员工列表 | 员工基础信息、状态、刷新策略、缓存语义 | SEP 响应校验、员工目录边界 |
| 员工工作侧栏 | 正在运行、已完成、全部工作的筛选与排序 | Task 查询模型、事件与状态契约 |
| 工作详情跳转 | taskId、runId、页面定位规则 | IPC DTO、TaskRun 数据校验 |
| 安排工作创建 | 单任务或工作流、节点、依赖、执行参数 | 工作流执行闭环 |
| 安排工作启动 | 何时持久化、何时授权、失败如何展示 | service 用例、逐节点授权、错误码 |
| 工作进度更新 | 推送事件类型、节点状态、聚合进度 | 判别联合事件、工作流状态持久化 |
| SEP 缺失数据 | 客户端无法自行获得的数据及其来源 | 新 SEP API schema 与适配器 |

接口确定前，不建议先实现工作流调度器或大幅调整持久化格式，因为前端最终所需的状态、筛选和恢复语义尚未完全确定。

## 5. 推荐处理顺序

### 阶段 A：当前阶段

1. 完成首页接口设计。
2. 完成安排工作接口设计。
3. 明确每项数据由客户端本地、客户端运行时还是 SEP 平台提供。
4. 对 SEP 当前未提供的数据，基于 SEP 数据模型设计新增平台接口。
5. 冻结第一版客户端 IPC DTO、错误码和推送事件。

### 阶段 B：接口确定后

1. 补齐首页聚合查询和员工工作筛选能力。
2. 补齐安排工作的创建、校验和执行闭环。
3. 为 SEP API 响应、IPC DTO 和磁盘数据增加运行时 schema。
4. 将开放事件改为判别联合类型。
5. 增加对应的 service、adapter 和纵向集成测试。

### 阶段 C：功能闭环后

1. 改造旧数据迁移策略。
2. 增加单实例保护。
3. 收紧 service 端口与 RequestContext 暴露范围。
4. 细分持久化错误并完善客户端提示。
5. 补充 Electron 真机冒烟测试。

## 7. 最终判断

当前架构可以作为后续客户端后端开发的基础继续使用。下一步应该围绕前端实际功能建立稳定的 IPC 和数据契约，再按纵向功能补齐 service、data、runtime 与 SEP adapter，而不是重新调整整个目录和分层。

本文件中的问题应作为后续实现清单保留，并在相关接口冻结后逐项转化为具体开发任务和测试用例。
