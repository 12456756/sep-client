## 1. 使用现有员工

2026-10-22 只读核对了平台当前登录账号的「硅基员工 / 我可用」页面，以下两位员工均存在且显示直接授权：

| 步骤 | 员工 | 页面显示的职责 | 本次安排 |
| --- | --- | --- | --- |
| 第一步 | 商品图片策划 | 为主图、详情页和短视频物料提出清晰制作需求 | 在商品视觉职责内，用本轮实际授权的生图工具生成一张商品主图 |
| 第二步 | 商品视频编剧 | 输出商品讲解、测评、口播和场景短片脚本 | 在商品短片职责内，用本轮实际授权的图生视频工具把上一步图片生成短片 |

员工存在和成员有权使用，不等于已确认其当次 runtime 包含可用的图片/视频 profile。实际执行仍检查工具、参数、审批及服务端能力；缺失时应显示具体限制，不假装成功。同一客户端需登录拥有这些授权的账号；如果客户端名称或授权发生变化，以客户端的实际列表为准。

## 2. 运行前准备

1. 使用包含 `8381e85` 的客户端。代码已更新并不意味着旧安装包已更新；在源码目录可用 `npm run dev` 启动当前开发版，已有开发进程则通过其正常流程重启以加载最新主进程代码。
2. 登录客户端，确认能看到「商品图片策划」和「商品视频编剧」。不要使用仅提供界面展示的浏览器预览来验收任务执行。
3. 新建一个空工作目录，例如桌面上的 `sep-media-check-01`，避免同名历史文件造成交付冲突。
4. 进入「安排工作」→「编排」→「自动」。本案例使用自动规划生成媒体需求、来源和交付契约；当前手动表单没有完整的媒体来源/交付字段，不把两步普通文字配置视作同等覆盖。
5. 在输入区域选择可用的编排模型和刚创建的工作目录；为观察审批，访问权限可选「工作区编辑」，取消勾选「自动放行」。这属于本次测试设置，不是产品固定要求。
6. 真实执行会使用实际图片、视频及模型算力。先核对客户端显示的配置与报价，再自行确认生成；本文没有代为发起付费请求。

## 3. 可直接粘贴的目标

```text
请为一款无品牌的米白色陶瓷马克杯制作一张商品主图和一条商品展示短片。

只安排以下两个前后依赖的步骤，使用我现有的员工：

第一步由「商品图片策划」负责：
调用实际图片生成工具，生成一张米白色陶瓷马克杯的商品展示图。
画面是木质桌面、窗边暖光、简洁背景，杯子完整清晰，不出现人物和文字。
优先横向 16:9；如当前配置不支持，采用可用的接近规格并说明。
交付真实 PNG 文件，目标相对路径为 deliverables/mug-main.png。

第二步由「商品视频编剧」负责：
必须依赖第一步的商品主图，使用第一步实际保存的图片资产做图生视频。
镜头缓慢推进，杯口有轻微热气，保持杯子的外观和背景一致。
优先生成约 5 秒的短片；比例和时长按当前工具支持的可用配置调整。
交付真实 MP4 文件，目标相对路径为 deliverables/mug-video.mp4。
第二步明确引用第一步的图片交付物，媒体来源使用各自节点已保存的媒体输出。

图片完成并保存后先等待我确认，不要提前开始视频生成。
我点击“确认，继续”之后再执行第二步；视频完成后自动结束任务。
最终把图片和视频自动保存到本次工作目录。
本次每种产物只做一个版本，恢复和交付纠错时复用原媒体任务及已保存输出。
如果缺少工具、授权或可用参数，请如实说明限制。
```

规格只是为了让首次测试简单，不是固定业务范围。可以把商品替换成自己的实际商品，比例、时长、风格也可按可用能力调整。

## 4. 按界面检查

### 4.1 先检查计划，再运行

点击「开始自动编排」。计划应包含以下意图：

- 先由「商品图片策划」实际生成并交付图片。
- 再由「商品视频编剧」使用该图片进行图生视频；第二步依赖第一步。
- 第一步完成后需要用户确认，第二步完成后不再额外确认。
- 目标包含 PNG 和 MP4 两个实际文件。

如果结果只有需求单、文案或分镜脚本，尚未覆盖本案例的媒体闭环，应点击「重新编排」明确要求实际媒体文件。计划界面目前不提供全部内部媒体字段的编辑和展示，不能仅凭流程图连线证明来源绑定已正确落地；后续实际调用和产物才是进一步证据。

核对后点击「确认并开始工作」。这次确认是启动整个工作；后面的图片确认是另一处执行中的确认点。

### 4.2 图片完成后

- 图片生成和保存成功后，工作进入等待用户确认，界面出现「确认，继续」。
- 工作目录中可找到 `deliverables/mug-main.png`，能正常打开，画面符合要求。
- 第二步仍未开始，不应出现视频生成审批、视频生成中的进度或已提交的视频任务。
- 界面不应把等待确认显示成节点失败，也不需要通过「重试」来放行。

### 4.3 确认后生成视频

点击「确认，继续」，按需要核对并批准视频生成。

- 第二位员工开始执行，使用前面已保存的图片，不需要手动下载后重新上传。
- 执行过程应体现图生视频，而不是独立文生视频或只输出视频脚本。
- 视频生成、下载并保存成功后，任务完成。
- 工作目录中可找到 `deliverables/mug-video.mp4`，使用本机播放器验证可播放，并检查商品外观、场景和运动是否合理。
- 工作详情的最终产物包含图片和视频；尚未实现专用的编排媒体详情面板，不要求这里具备完整内嵌播放器。

仅有“已提交”、任务 ID 或助手文字“已完成”不算验收成功；应以真实文件、保存状态及任务最终状态一起判断。文件格式/哈希检查也不能替代人工检查视频内容。

## 5. 一次有价值的恢复检查

可在第一次显示「等待确认」后，退出客户端并重新打开，再回到同一项工作：

1. 原图片文件仍存在，工作仍是等待确认。
2. 不能因为重开应用而自动生成视频，也不应重新生成图片。
3. 点击「确认，继续」，应继续原流程的第二步。

这项检查不要求额外生成一套产物。不要通过创建新工作或「重新执行整个工作」来验证原任务恢复，因为那会创建新的执行。

若要检查提交后退出的恢复行为，可在已记录原媒体任务 ID 后再单独测试。重开后应恢复查询原任务。当前编排详情不能完整展示全部原 job 与账务关联，严格确认“不重复提交/扣费”需要对照原 job、服务端请求与账务记录，不能只凭肉眼看似相同的图片或视频认定；也不要把模型或报价调用误算成第二次图片/视频生成。

## 6. 判定与记录

| 检查点 | 通过表现 |
| --- | --- |
| 生图 | 第一节点实际生成并保存可打开的 PNG |
| 跨节点引用 | 第二节点使用第一节点的真实图片资产，无需手工导出再导入 |
| 中间确认 | 未确认前第二步不运行；确认后才运行 |
| 自动交付 | 所选工作目录出现计划中的 PNG、MP4 |
| 视频 | 实际文件可播放，内容符合商品要求 |
| 暂停恢复 | 重开同一工作保持确认状态，不重做图片 |
| 完成 | 视频保存成功后任务进入完成状态 |

如失败，记录工作名称或任务 ID、失败阶段、界面错误、是否出现生成审批、是否已有文件及媒体任务 ID（界面可见时）。不记录密码、令牌或完整敏感日志。

常见分辨：

- 员工不在客户端可用列表：先核对登录账号和平台分配，不属于图片传给视频的连接问题。
- 提示没有视频工具或配置不可用：属于当次 runtime/profile 或网关限制，员工名称本身不能证明工具已启用。
- 只有脚本或图片描述：没有实际完成生图/生视频测试。
- 目标已有不同内容：换一个空目录进行新测试，或处理冲突后恢复原任务；不要直接要求重新生成付费资产。
- 图片尚未确认视频就开始：确认点或计划有问题，应记录并停止本次测试。
- 媒体已保存但最终文件缺失：属于自动物化/交付路径问题，保留原媒体任务，优先恢复交付。
