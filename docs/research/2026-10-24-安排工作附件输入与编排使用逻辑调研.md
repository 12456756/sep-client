# 安排工作附件输入与编排使用逻辑调研

日期：2026-10-24。范围：安排工作中的会话、自动编排、手动编排，以及后续继续对话。本文是产品与工程方案，未实现业务代码。

需求补充：用户复制本地文件或截图后，直接在输入框按 Cmd+V / Ctrl+V 即可添加附件，列为首期必做入口。详细实施合同见 [安排工作附件与粘贴上传开发文档](../plans/2026-10-24-安排工作附件与粘贴上传开发文档.md)。

## 1. 结论

当前缺少的是一条完整的附件输入链路，不只是输入框旁少了一个按钮：界面只提交文字，草稿、计划、节点、会话消息和运行入口均没有通用附件引用；执行器也没有把附件作为受控文件或图片传入模型。

推荐采用“原生选择文件 / 输入框直接粘贴 → 企业作用域暂存快照 → 草稿认领 → 提取与规划 → 用户确认节点输入 → 任务私有输入快照 → 节点按绑定读取”的路径。会话和编排复用附件存储及解析能力，分别组织各自的消息和节点输入。

关键决策：

- 一期提供原生多选文件按钮、复制文件/截图后的直接粘贴、文件列表、移除与失败重试；拖拽和仅附件发送放到后续。提交时仍要求文字目标。
- “上传附件”在客户端首先表示本地导入；选择文件不自动上传知识库或媒体服务。执行请求时，相关文字或图片仍会随模型请求传给当前模型提供方。
- 原文件在选择时即复制并计算 SHA-256。后续运行依赖快照，原文件改名、移动或改写不改变已确认输入。
- 规划器继续禁用工具。宿主向规划器提供附件 ID、元数据和有上限的提取内容；不能只给本地路径并期待规划器读取。
- 全局附件是候选材料，节点明确绑定实际输入；不把全部附件正文拼进每个节点的 prompt。
- 普通文档通过任务私有文件及提取结果供 `read` 使用。Pi 0.83.0 的 `prompt(..., { images })` 只解决图片输入，不是通用文档上传协议。
- 上游交付物继续使用现有验收、快照、哈希与直接依赖校验。输入附件与节点交付物是不同来源，不能混用 ID。

## 3. 先区分五类对象

| 对象 | 含义 | 处理原则 |
| --- | --- | --- |
| 输入附件 | 用户这次任务提供的原始文件快照 | 不可变、任务可追溯、按节点授权 |
| 文字材料 | 现有 `confirmedInputs: string[]` | 保留为说明、约束和背景，不能冒充文件 |
| 节点交付物 | 节点执行后生成并验收的结果 | 沿用现有 deliverable 与依赖快照机制 |
| 媒体参考图 | 图片生成/编辑工具可用的 `localAssetId` | 从已验证图片附件显式映射，受媒体工具权限控制 |
| 企业知识库 | 可跨任务检索的长期知识 | 附件不自动入库，需要独立产品行为 |

工作目录仍是用户选定的执行及产出目录。附件快照放在应用私有输入存储中，避免授权整个工作目录后把节点附件范围误当成隔离边界。

## 4. 用户怎么添加和确认

会话、自动编排和手动编排共用附件选择能力。在现有输入区域加入回形针图标按钮，悬停说明“添加附件”，点击后由 main process 打开多选文件窗口。

另一入口是输入框直接粘贴：复制 Finder/资源管理器中的实体文件，或复制截图/图片后，在会话、自动编排目标、手动编排材料或续聊输入框按 Cmd+V / Ctrl+V，立即导入并显示同一附件列表。普通文字、网址、手写文件路径保持文字粘贴；识别到真实文件项才按附件处理，混合图文不得丢字或重复插入。剪贴板导入同样只是本地暂存，发送/确认后才进入模型与编排执行。

优先验证 Electron 33 原生 `paste` 事件中的 `clipboardData.files/items`。磁盘 File 在 preload 内用 `webUtils.getPathForFile` 提取路径，无磁盘图片按限额读取 bytes；File、事件和原始路径不通过公开 bridge 传给 renderer。macOS/Windows 的实体多文件、截图、事件顺序必须实测，不能把 `clipboard.readBuffer('CF_HDROP')` 视为已验证的跨平台文件读取方法。其他聊天软件中的虚拟附件若没有实际 File/bytes，需先保存到本地，不承诺任意来源均可粘贴。

文件列表显示文件名、类型、大小和状态；错误显示具体原因并支持移除/重试。状态应覆盖：导入中、提取中、可用、部分提取、暂不支持、失败。列表不展示原始绝对路径、内部存储路径或 base64。

一期交互规则：

1. 用户选择或粘贴文件，客户端立即复制快照；列表显示处理中。
2. 用户继续写目标，处理中不阻止编辑文字。
3. 必需输入导入失败或解析失败时，阻止依赖它的规划/发送，用户可移除后继续。
4. 自动编排生成后，在节点输入中显示引用的文件，允许用户调整绑定。
5. 手动编排在顶部维护候选附件，在每个节点提供附件和前置交付物选择。
6. 确认启动时冻结附件版本与节点绑定；执行期间不覆盖已经确认的原始输入。

“部分提取”不等于“全部可用”：例如 PDF 只提取到部分页、工作簿公式缺少缓存结果，需要显示范围和缺失项，预检按节点用途判断能否继续。不能把解析失败静默退化为只给模型一个文件名。

仅附件发送一期不开放，沿用非空文字目标校验。若后续支持，需要明确默认任务意图及确认交互，不能通过偷偷创建空目标草稿绕过现有校验。

## 5. 首次发送前没有 taskId，如何存放附件

现有图片导入要求已有任务，但安排工作首次输入时尚无任务；自动规划甚至要等用户写完非空目标才创建草稿。不能直接复用“先传 taskId”的媒体 IPC。

建议引入企业作用域的待认领附件批次：

```text
原生选择文件 / 在输入框粘贴真实文件或图片
  -> 校验当前企业/用户 -> 复制到 owner staging -> 校验类型和大小 -> 计算 hash
  -> 返回 opaque batch token 和附件元数据
  -> 用户提交非空目标 -> createDraft 原子认领 batch
  -> 提取/预检/规划 -> 用户审阅节点输入
  -> confirmStart 收编为 task-owned 输入快照并冻结引用
  -> 成功后才进入运行队列
```

批次 token 只是引用，不是授权凭据。每次操作还必须校验当前 owner、批次状态、有效期和目标草稿归属。renderer 不能提交任意文件路径要求 main process 读取。

`createDraft` 在同一事务语义内认领附件和保存草稿；失败应能重试，不能遗留“文件已认领但草稿不存在”的中间状态。确认启动也需要幂等键：相同确认重复请求不能创建第二份任务或丢失输入。具体存储实现可沿用现有串行化/原子文件写入方式，不要求新增数据库。

选择时就复制文件，而不是确认启动时才读原路径；数据层负责 scope 路径、暂存、原子重命名和最终收编。service 只调用数据端口，不拼接路径。

## 6. 建议的数据合同

下面是领域合同示意，不是现有接口；实现时应加入现有 Zod 与 schemaVersion 迁移。

```ts
type AttachmentRef = {
  attachmentId: string;
  sha256: string;
};

type ExtractionState =
  | { status: 'pending' }
  | { status: 'ready'; textArtifactId: string; parserVersion: string }
  | { status: 'partial'; textArtifactId: string; parserVersion: string; warnings: string[] }
  | { status: 'not-required' } // 原始图片直接走视觉输入
  | { status: 'unsupported'; reason: string }
  | { status: 'failed'; reason: string };

type AttachmentManifest = {
  schemaVersion: 1;
  attachmentId: string;
  owner: ScopeOwner;
  storageOwner:
    | { kind: 'pending'; batchId: string }
    | { kind: 'draft'; draftId: string }
    | { kind: 'task'; taskId: string };
  originalName: string;
  mediaType: string;
  byteLength: number;
  sha256: string;
  blobId: string; // 数据层内部解析，不是 renderer 提供的路径
  extraction: ExtractionState;
};

type NodeInputRef =
  | { kind: 'attachment'; attachment: AttachmentRef; required: boolean; purpose?: string }
  | { kind: 'deliverable'; nodeId: string; deliverableId: string; required: boolean };
```

`ScopeOwner` 复用项目实际企业/用户作用域类型；示例不定义新的身份体系。manifest 是宿主存储记录，IPC 返回裁剪后的 metadata-only view，不能把内部 `blobId`、owner 细节或可访问路径全部暴露给 renderer。

具体扩展位置：

- `ArrangementDraft`：附件清单引用、规划材料版本；`confirmedInputs` 保持文字说明。
- `WorkPlan`：不可变 `attachmentRefs` 及节点 `inputRefs`；计划完整性校验包含附件哈希、节点绑定和合同版本。
- `ArrangementNode`：`inputRefs`，与 `dependsOn` 分开建模。
- 会话消息/运行记录：保存本轮 `attachmentRefs`，运行排队项同样持久化，不能只留在组件 state。
- 附件提取记录：保存 parserVersion、提取范围、警告、分片索引及原件 hash。

文件名不是身份，两个 `合同.pdf` 可以并存；内容 hash 用于校验和作用域内去重，不能替代访问控制。现有 `planHash` 是 `${draft.id}:${draft.revision}:${idempotencyKey}` 风格标识，不能宣称它已经验证附件内容。应单独新增内容摘要，或通过明确版本迁移扩展计划摘要语义。

## 7. 会话如何用附件

首次安排会话仍走现有 draft → preflight → confirmStart 链路，把附件引用一路带入计划和运行。普通 `CreateTaskInput` 入口若保留，也应接收相同的受验证附件引用，避免不同入口产生不同能力。

执行器向 worker 提供宿主生成的输入清单：稳定 ID、文件名、类型、用途、可信只读路径和提取结果路径。用户文字与附件内容分开组织，明确附件内容是业务资料，不是新的系统指令。内部路径只在受控执行上下文提供，不写入普通 UI 消息或日志。

图片分两类使用：

- 需要看图理解、问答或规划：确认所选模型支持图像输入后，适配层调用 `session.prompt(text, { images })`；也可由支持图片的 `read` 工具按需读取。
- 用于生成/编辑工具：转换为当前任务的媒体参考资产，再通过现有媒体能力传入，不把 base64 冒充 `localAssetId`。

Pi 0.83.0 明确提供 `PromptOptions.images`，但当前宿主接口和 worker 没有接通。适配时应让图片只随本轮初始用户输入传入，不能在纠正循环的每次 `nextPrompt` 中无条件重复发送。

继续对话增加“本轮新增附件”。历史消息保留原附件关联，新一轮可显式继续引用历史附件；不要依赖模型碰巧记得文件名。切换员工后重新检查工具、模型与文件授权。运行排队、重试、应用重启和会话恢复都从持久化引用恢复，不能依赖内存文件对象。

恢复时核对快照和提取产物完整性；缺失或 hash 不符时明确暂停相关运行并给出可恢复错误。重建 Pi session 要重建附件上下文，不能只重放文字，也不能为了恢复附件而重放已有工具副作用。

## 8. 自动编排如何规划附件

当前规划器 `allowedTools: []`，保持此约束。由宿主先完成确定性提取，再构造有预算的规划材料：

```text
目标：分析本季度销售并形成经营报告
可用附件：A1 销售.xlsx（工作表、列名、行数、时间范围、缺失/公式说明）
          A2 报告要求.pdf（页数、章节与相关要求摘录）
规则：节点只能引用以上真实 attachmentId；全文通过执行阶段受控读取。
```

规划摘要用于分工和选择输入，不能作为最终分析的数据全集。大表只在规划阶段给结构和统计概览，执行分析仍需读取完整分片，保留原始定位。图片的文件名不代表图片语义：需要视觉理解的规划必须具备视觉能力，或先得到可追溯的图片描述；当前网关是否完整支持此路径需要联调验证。

规划结果必须验证所有引用属于当前草稿和材料版本，拒绝虚构 attachmentId、文件路径和 deliverableId。用户修改附件、解析结果版本或节点输入后递增 draft revision，使旧规划/预检结果失效。

用户标记为“必须使用”的附件如果未分配给任何节点，预检应阻止启动并说明原因；其他未使用的候选附件提示用户确认。附件被分配不代表内容已经读完，执行结果仍需包含必要的来源与覆盖范围。

不要默认插入一个“读取附件”节点。普通读取是消费节点的执行能力；只有确实需要独立清洗、OCR、格式转换或跨节点复用分析结果时，才作为有明确交付物的业务节点。

## 9. 手动编排与 DAG 的规则

手动编排顶部提供候选材料列表，每个节点分别选择附件和前置交付物。现有文字“材料”继续保留；输入框里手写文件名不算有效绑定。

依赖规则明确区分：

- 引用用户附件不产生 `dependsOn`，多个节点可并行读取同一个不可变附件。
- 引用节点交付物，来源节点必须是直接 `dependsOn`；不能绕过 DAG 从任意历史节点取文件。
- 前置节点必须完成、交付物已验收且没有待确认项，才能给下游绑定最终快照。
- 下游可同时需要原始附件和上游结论，必须分别绑定。
- 模型不能修改输入快照；需要加工时写入自己的输出，再声明新交付物。

现有结构化工作合同执行路径和旧手动 prompt 路径都要注入同样的受控输入；只改其中一条会出现“自动能读、手动不能读”的断层。

### 示例一：销售表和报告要求

用户导入 `销售.xlsx`（A1）与 `报告要求.pdf`（A2），目标是生成季度经营报告。

| 节点 | 输入绑定 | 依赖 | 产出与使用 |
| --- | --- | --- | --- |
| N1 销售分析 | A1 必需；A2 中的口径要求必需 | 无 | D1 分析结果，包含 sheet/row/cell 来源、统计口径和异常项 |
| N2 报告撰写 | N1.D1 必需；A2 必需；A1 按需用于核验 | N1 | D2 经营报告，引用已验收 D1 和报告模板要求 |
| N3 质量检查 | N2.D2、N1.D1、A2 | N1、N2 | D3 检查结果，核对数字、要求和缺失说明 |

N1 读取完整表格分片，不能只分析规划摘要。N2 只拿到 D1 时，不应被提示“已经拥有所有原始销售数据”。如果用户希望 N2 核对 A1，需要明确绑定 A1。N3 引用 N1.D1，就必须把 N1 也列为直接依赖。

### 示例二：商品图编辑后图生视频

用户导入 `商品.png`（A3），要求先换背景，再制作短视频。

| 节点 | 输入绑定 | 媒体声明 | 依赖与结果 |
| --- | --- | --- | --- |
| N1 编辑商品图 | 图片附件 A3 | `operation: edit`，源附件映射为当前任务参考图 | 无；产出验收图片 D1 |
| N2 图生视频 | N1.D1 | `operation: image-to-video`，`inputFrom` 指向 N1 的 D1 | 直接依赖 N1；产出视频 D2 |

宿主需要建立 `attachmentId → 当前 taskId 下 localAssetId` 的持久映射，校验图片 bytes/hash 后复用已有 MediaStore。不能把草稿附件 ID 填到媒体工具的资产 ID 参数里，也不能允许模型猜测资产。

同一图片可被多个节点复用，映射需幂等；节点结束或切换时不能让现有 `clearSelection` 清掉其他节点仍需要的参考图。媒体工具只看到当前节点获准使用的资产集合。

N2 沿用现有媒体链路：检查直接依赖、完成状态、最终图片、原始节点证明与 hash，再从输出派生参考图。用户原图 A3 与 N1 编辑后的 D1 不能互相替代。现有 `inputSelection` 的声明不代表已支持任意多图选择，实际解析仍有单一来源约束，扩展需独立验证。

## 10. 文件解析与模型能力

SDK 的 `read` 处理文本或受支持的图片；对其他字节直接按 UTF-8 解码并不等于理解 PDF/Office。不能宣称支持“任意文件”。

| 文件类型 | 建议策略 | 必须说明的限制 |
| --- | --- | --- |
| txt / md / json / csv | 校验编码，保留原件，生成可定位文本/分片 | 大文件预算、非法编码和 CSV 方言需明确处理 |
| png / jpg / webp 等图片 | 校验容器和尺寸；视觉 prompt/read 或媒体映射 | 模型需支持图片；工具支持的格式与 MIME 要匹配 |
| docx | 复用 Mammoth 依赖及关闭外部文件访问的安全配置，生成文本与段落定位 | 转换损失、嵌图和表格结构应记录 |
| xlsx | 复用 ExcelJS，导出 sheet/row/cell、值、公式及缓存结果，按表/行分片 | 不自行重算公式；缓存缺失必须标记，隐藏表处理要明确 |
| pptx | 复用现有 ZIP/XML 解析经验，保留 slide 定位和文本 | 图表、嵌图与复杂排版可能不完整 |
| PDF | 用已有 pdfjs-dist 新建文本提取路径，保留页码及缺失信息 | 现有预览仅传 PDF bytes；扫描件需要 OCR，不能假装已提取 |
| zip / 可执行文件 / 音视频等 | 一期不给出通用可分析承诺 | 若后续支持，单独定义解包、转写、帧提取和安全预算 |

仓库已有 `mammoth`、`exceljs`、`pdf-lib` 和 `pdfjs-dist`，优先复用，不因本方案新增依赖。现有预览转换器有 ZIP 展开预算和表格数量限制，可复用约束与 worker 边界；预览 HTML 不是可直接交给模型的标准提取格式。

保留原件、确定性提取产物与模型摘要三者的对应关系。摘要可以重建，不能替代原件；模型生成的解释也不能伪装成确定性解析结果。

## 11. 权限、安全与限额

附件权限建议扩展为与 `readableDeliveryPaths` 同类的精确只读授权：只允许当前节点读取其绑定原件/提取产物的可信实际路径，不把整个目录加入普通 `allowedPaths`，避免连带授予写权限。

必须承认现有策略边界：`full-local + auto-approve` 会提前放行；共享工作目录内的文件也可能被其他节点读取。因此“节点只分配指定附件”首先是上下文和能力约束，不能在现有无限本地权限下宣称严格沙箱。若产品要求硬隔离，需要另行限制 bash/目录访问或引入隔离执行环境。

为减少误修改，建议保存规范原件与独立运行副本，读取前及运行结束后核对 hash；副本损坏时不得回写规范原件。只读标记和 hash 是宿主保护与检测手段，同用户下的无限本地工具仍可能修改文件，不能据此保证操作系统级不可变性。

导入和读取的宿主校验包括：

- 当前 owner、草稿/任务归属和节点绑定，禁止跨企业/跨任务伪造 ID。
- 文件名只作显示；落盘用内部 ID，阻止路径穿越、符号链接逃逸与检查/读取之间替换。
- 根据文件 bytes 验证 MIME、容器、大小和 hash，不能只相信扩展名或 renderer 数据。
- 原件和快照只读，写入使用临时文件与原子提交；读取或恢复时重新核验完整性。
- 文档提取放在既有适合的 worker/runtime 边界，设置时间、内存、页数、单元格和 ZIP 展开预算。
- 附件内容作为不可信业务数据，不能改变工具策略、角色或系统指令；预览不得执行嵌入脚本或外部引用。
- 日志继续走共享 logger/redaction，不记录原始路径、文件正文、base64、token 或未裁剪异常对象。

限额应作为配置与产品决策。可用试运行起点是每批 10 个文件、单文件 20 MiB、总量 100 MiB，再依据解析耗时调整；这些是建议值，**不是当前平台已支持的规格**。现有媒体图片有自己的字节/像素限制，不能直接当成所有文档限制，也不能绕过其限制。

本地导入与网络发送是两个动作。普通模型请求遵循当前员工/模型的数据发送策略；媒体生成需要向 SEP 上传参考图时，继续走已有报价/审批和上传链路，不能因“本地已选择”跳过审批。

## 12. 持久化、重试和清理

确认计划冻结附件 ID、hash、解析版本和节点绑定。重试使用相同输入版本；用户替换附件应产生新版本并重新预检，不原地修改正在运行的计划。

待认领批次、草稿输入、任务输入分开管理生命周期。移除未提交附件是取消绑定；历史消息里的“隐藏附件”不等于立即删除 bytes。清理只能删除没有草稿、计划、消息、运行和媒体映射引用且没有活跃使用的文件，待认领孤儿可按 TTL 回收。

退出企业或注销后取消相关提取任务并清理内存授权；持久数据继续按 scope 隔离。应用重启不能依赖 `MediaService.selectedReferences` 这类内存选择集合恢复附件，因为该集合并非持久输入账本。

同一原件发生解析失败，重试可重建提取产物，不需要重复让用户选文件。磁盘快照确实缺失或损坏时明确报错，不能偷偷读原路径的新内容代替。

## 13. IPC 与分层改动建议

以下为建议的能力名称，不表示已存在同名 channel；最终命名遵循 `controller/channels.ts` 和现有 preload API。

| 能力 | 输入/输出 | 所属责任 |
| --- | --- | --- |
| 创建/选择待认领附件 | 宿主原生 dialog；返回 batch token、metadata view | controller 校验与对话框；service 校验身份；data 存储 |
| 查询/移除/重试提取 | batch/draft/task 的 opaque ID | controller Zod；service 归属和生命周期；data 原子更新 |
| 附件预览 | 受授权附件 ID，返回受限预览 | 复用预览模式，不能提交任意本地路径 |
| createDraft / updateDraft | attachment refs、节点 inputRefs | 同步扩展 renderer 类型、preload、Zod 和领域合同 |
| preflight / confirmStart | 校验与冻结输入 | service 组织用例，data 收编输入，成功后才 enqueue |
| continueConversation | prompt + 本轮 attachmentRefs | 消息、run、队列与 session 恢复一致 |
| 节点执行 | 内部解析后的受控读取上下文 | runtime 组织 prompt/权限；pi/sdk 接通实际 images |

所有 renderer 输入均不可信；不能把原始 bytes、绝对路径和内部 manifest 当成“前端已经验证过”。data 负责路径，runtime 是应用层接入 `pi/sdk` 的边界，service 不直接引入 SDK。事件投影只展示状态；正式引用和内容校验必须读持久数据，不能拿被脱敏的展示事件当事实来源。

## 14. 预检与验收

预检除现有员工/模型/合同条件外，还应检查附件归属、快照 hash、提取状态、必需输入、引用版本、节点工具权限、视觉能力、媒体 MIME/工具能力及前置交付物约束。必需材料不可用时阻止相应规划或执行，并返回可操作原因。

最低验收场景：

1. 会话首轮选两个同名文件，模型能区分内容；原文件移动后运行仍成功。
2. 继续对话追加文件，重启后历史引用仍有效；切换员工后重新检查能力。
3. 自动编排正确绑定 xlsx/PDF，规划器不调用工具；虚构附件 ID 被拒绝。
4. 手动编排只给指定节点分配文件；直接依赖校验与既有两条 prompt 路径一致。
5. 大表分析读取完整分片并保留定位，不拿摘要替代全量分析；无缓存公式明确报缺失。
6. 商品图可供两个节点复用，媒体映射幂等；编辑结果通过验收后才交给视频节点。
7. 导入取消、超限、不支持格式、部分解析、损坏、跨企业 ID 和符号链接均有明确结果。
8. 确认启动重复请求、运行排队和恢复不丢附件、不重复创建任务、不重放副作用。
9. 普通日志、状态 IPC 和界面不泄漏原始路径、正文或秘密；预览/提取展示仅通过明确授权且有预算的内容接口返回。附件内容不能扩大工具授权。
10. 在受限策略下验证精确只读授权；在 full-local 模式明确展示并测试其既有权限语义。

实现时测试重点是 importer/manifest 的作用域与完整性、IPC 伪造输入、规划引用验证、DAG 绑定、媒体映射以及恢复。依据实际改动运行 `test:renderer`、`test:tasks`、`test:invariants`、`typecheck`、`lint`、`build` 和 `check:boundaries`；修改 `electron/pi/` 或启动/runtime 加载时按仓库要求运行 `poc:01` 至 `poc:04`，并完成 `typecheck`、`build`。

## 15. 分阶段交付

| 阶段 | 可交付行为 | 完成边界 |
| --- | --- | --- |
| P1 基础链路 | 原生多选、复制文件/截图直接粘贴、暂存认领、不可变快照、会话首轮与继续对话、文本/图片、历史与恢复 | 必须真实读到内容；macOS/Windows 粘贴需实测；只有按钮和文件名不算完成 |
| P2 编排输入 | 自动/手动节点绑定、宿主规划摘要、Office/PDF 提取、预检与依赖校验 | xlsx/PDF 分析到报告的完整流程通过；覆盖结构化和旧手动路径 |
| P3 媒体闭环 | 附件图映射媒体资产、编辑到视频、幂等与重启恢复 | 复用现有媒体审批和产物证明，不引入旁路 |
| 后续增强 | 拖拽、仅附件发送、OCR、音视频、更多结构化格式 | 按真实需求评估；明确能力和资源预算 |

用户报告同时覆盖会话与编排，P1 只能作为阶段结果，不能宣称整个问题完成。可在一次版本中合并 P1/P2，但接口和数据合同应先统一，避免两套附件系统。
