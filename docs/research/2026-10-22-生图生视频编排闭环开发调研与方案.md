# 生图、生视频编排闭环开发调研与方案

- 调研日期：2026-10-22。
- 文档状态：参考，作为实现前的调研和设计输入；不替代 `docs/architecture/` 下的后端基线。
- 调研对象：当前 `sep-client` 工作区及 2026-10-21 已确认的图片、视频和编排调用链。
- 目标：详细说明三个主要连接如何开发，并补齐媒体任务从输入到交付的完整闭环。
- 范围原则：复用已有服务和数据存储；优先动态能力协商、可配置上限和向后兼容，避免把当前某个网关或测试 fixture 的数值变成永久产品限制。

## 1. 先说结论

现在的代码已经能让编排节点调用生图、文生视频和图生视频，也能完成授权、报价、审批、异步跟踪、结果下载和本地保存。缺的是“媒体资产如何继续流转”和“媒体结果如何成为编排交付”的连接层。

建议把闭环拆成四个能力层：

1. **媒体资产层**：图片和视频仍由现有 `MediaService`、`VideoService`、`MediaStore`、`VideoStore` 管理，保留原请求身份、哈希、账务和恢复语义。
2. **编排媒体桥接层**：为节点提供任务内资产查询、资产引用转换、导出到工作区、从工作区导入媒体等受控操作。
3. **媒体交付层**：把内部资产映射成编排节点的 `deliverables`，按媒体类型做可配置的完整性和可播放性检查。
4. **用户可见层**：在编排详情里展示节点媒体任务、预览、导出、恢复、审批等待和失败原因，并允许用户继续处理。

开发后应达到的状态是：

```text
用户目标
  -> 自动编排识别需要图片/视频
  -> 节点获得对应员工与媒体能力
  -> 生图或生视频
  -> 资产进入任务媒体库
  -> 可选：转为后续节点的引用输入
  -> 可选：导出为共享工作区文件
  -> 交付验收与哈希记录
  -> 下游节点读取已确认资产/文件
  -> 编排详情展示和用户导出
```

## 2. 当前实现事实

### 2.1 编排已经接通媒体工具

[ArrangementExecutor](../../electron/runtime/arrangement-executor.ts#L373) 为每个节点调用 `media.prepareRun()` 和 `video.prepareRun()`，把返回的工具注入 Pi worker。结构化节点在响应结束前等待媒体任务完成，并在节点结束后再次等待。节点的媒体能力按该节点的 `subscriptionId` 和 `modelId` 授权，不应统一使用整项编排的首个员工。

图片工具有 `media_get_capabilities`、`media_generate_image`、`media_get_job`、`media_cancel_job`；视频工具有 `video_get_job`、`video_generate`、`video_from_image`。工具注册会再次检查 `toolPolicy`，服务侧也会再次检查，不能只依赖 Pi schema。

### 2.2 内部资产已经有稳定身份和完整性保护

图片资产有 `localAssetId`、任务归属、来源、媒体类型、尺寸、大小、哈希、状态和内部相对路径；图片生成结果被标记为 `source: 'output'`，手工导入图片被标记为 `source: 'reference'`。见 [media.ts](../../electron/domain/media.ts#L67) 和 [media-store.ts](../../electron/data/media-store.ts#L366)。

视频输出由 `jobId + outputId` 形成稳定本地资产 ID，保存前校验原始 receipt、大小、哈希、格式和状态。视频内部路径不会通过 IPC 暴露，系统播放器由主进程读取。见 [video-media.ts](../../electron/domain/video-media.ts#L48) 和 [video-store.ts](../../electron/data/video-store.ts#L205)。

这些约束适合继续保留。需要扩展的是“资产用途”和“资产关系”，而不是绕过现有校验直接把内部路径交给模型。

### 2.3 当前人工导出路径不能直接用于编排

图片和视频都有导出能力，但目前由 renderer 发起原生保存对话框，适合用户手工操作，不适合节点自动交付。图片 IPC 在 [routes/media.ts](../../electron/controller/routes/media.ts#L29)，视频导出由视频路由和 `createVideoScopeAdapter()` 完成。

编排的最终交付要求节点在共享工作区写入计划路径，再由 [arrangement-delivery-files.ts](../../electron/data/arrangement-delivery-files.ts#L113) 读取和验收。因此需要一个主进程内部的自动导出服务，不能让节点复用“弹保存对话框”的 UI 路径。

## 3. 连接一：媒体结果自动进入编排交付

这是最优先的连接。没有它，媒体虽生成成功，结构化节点仍可能因没有最终文件而失败。

### 3.1 推荐的职责边界

新增一个编排侧端口，例如 `ArrangementMediaBridge`，由编排运行时注入：

```ts
interface ArrangementMediaBridge {
  listTaskMedia(input: { taskId: string; nodeRunId?: string }): Promise<MediaArtifactRef[]>
  materializeToWorkspace(input: MaterializeMediaInput): Promise<MaterializedMediaFile>
  importWorkspaceMedia(input: ImportWorkspaceMediaInput): Promise<MediaArtifactRef>
  promoteToReference(input: PromoteMediaReferenceInput): Promise<MediaArtifactRef>
}
```

这个端口属于 `runtime -> service/data` 的应用边界。编排执行器只传任务、节点和目标交付信息；它不拼文件路径，不直接读取网关，不直接依赖 `MediaStore` 或 `VideoStore` 的内部目录。

服务层负责：

- 确认任务、节点运行和当前用户 scope 一致；
- 确认资产已保存、未被归档、哈希与 manifest 一致；
- 将图片或视频写入工作区的计划相对路径；
- 使用临时文件、哈希校验和原子 rename，避免验收读到半个文件；
- 冲突时返回清晰结果：已存在且相同可以幂等成功，已存在但不同则拒绝覆盖或要求显式替换；
- 记录来源资产、节点运行、目标路径、复制时间、源哈希和目标哈希。

### 3.2 不要把工作区路径交给模型自行拼接

模型只提交资产 ID 或交付物 ID，例如：

```json
{
  "nodeId": "visual-node",
  "mediaDeliverables": [
    { "deliverableId": "hero-image", "assetId": "out_..." }
  ]
}
```

后端根据已确认计划中的 `deliverables[].path` 解析目标路径。这样可以继续复用 `isSafeDeliveryPath()` 的越界和特殊文件名校验，并避免模型提交绝对路径、符号链接路径或额外文件。

### 3.3 交付物模型建议扩展，而不是另造媒体计划

当前 `ArrangementDeliverable` 适合文档文件。建议增加可选媒体元数据，保持旧计划可解析：

```ts
type ArrangementDeliverable = {
  id: string
  name: string
  format: string
  path: string
  contentOutline: string[]
  acceptanceCriteria: string[]
  artifact?: {
    kind: 'image' | 'video' | 'document' | 'data' | 'other'
    source: 'workspace' | 'media-output' | 'media-reference' | 'either'
    mediaAssetId?: string
    operation?: 'generate' | 'edit' | 'image-to-video' | 'text-to-video'
  }
}
```

`artifact` 应该是提示和验收信息，不应包含供应商 URL、token 或内部绝对路径。旧节点没有 `artifact` 时继续走现有工作区文件流程。

### 3.4 自动导出的时机

有三种兼容方案，推荐由后端优先执行，模型只负责选择资产：

1. **节点结束前自动物化**：模型生成后把资产 ID 写入结束 JSON，后端验收前将资产复制到计划路径。
2. **媒体工具生成时指定交付物 ID**：工具调用直接绑定一个计划交付物，生成保存后立即物化。
3. **独立桥接工具**：增加 `media_materialize_asset` / `video_materialize_output`，供模型在需要时调用。

建议首版支持第 1 种，并保留第 3 种作为复杂流程能力。这样不会让工具参数被单一 UI 设计锁死，也能让文本节点继续只使用普通文件工具。

### 3.5 幂等和恢复

自动导出必须使用稳定键：`owner + taskId + deliverableId + sourceAssetId + sourceHash`。重复执行时：

- 同源同哈希：直接复用并更新验收记录；
- 同资产但目标文件被修改：重新复制或标记“工作区文件已被外部修改”，由策略决定；
- 源资产缺失或过期：不要重新生成，先尝试原任务恢复或要求用户处理；
- 节点重试：优先使用已保存资产和原请求，不重新提交付费请求；
- 编排恢复：先恢复媒体任务，再恢复物化步骤，最后重新验收。

## 4. 连接二：生成图片作为图生视频输入

当前图生视频只接受 `source: 'reference'` 且状态为 `SAVED` 的任务级参考图。生图输出是 `source: 'output'`，所以两步不能直接串联。

### 4.1 推荐的资产语义

不要简单把 `output` 改成 `reference`。两者用途不同：

- `reference`：用户或外部导入，作为输入素材；
- `output`：某次生成任务产生的结果；
- `derived-reference`：由任务内 output 经后端确认后，形成可被其他媒体操作引用的输入副本或逻辑别名。

建议新增资产关系表或 manifest 字段，而不必马上改变现有 `source` 联合类型：

```ts
type MediaAssetRelation = {
  sourceAssetId: string
  derivedAssetId: string
  relation: 'promoted-to-reference' | 'exported-to-workspace' | 'used-as-video-input'
  createdBy: 'user' | 'arrangement' | 'tool'
  createdAt: number
}
```

`promoteToReference()` 应该生成新的派生 ID，保留原 output 的来源、job、output、哈希和 owner，不复制供应商身份，不改变原资产历史。视频 adapter 读取派生引用时仍然只读取已验证的任务本地字节。

### 4.2 推荐的跨节点流程

```text
图片节点生成 output
  -> MediaService.waitForRun 确认 output SAVED
  -> ArrangementMediaBridge.promoteToReference(outputId)
  -> 记录 node-a -> derived-reference 的依赖关系
  -> 视频节点读取 derived-reference
  -> VideoService 上传参考图、报价、审批、提交
  -> 保存视频 output
```

视频节点不需要知道图片节点的内部 jobId，也不应接收绝对路径。它只获得一个任务内、scope 校验过的引用 ID。

### 4.3 依赖和失败语义

如果图片节点生成了多个结果，计划应明确选择规则：第一张、指定 outputId、全部作为候选，或让用户选择。不要让模型通过猜测文件名选择。

如果图片生成部分成功：

- 支持单图输入时，可选择任意已保存输出继续；
- 计划要求全部图片时，等待所有输出或进入 `waiting-user`；
- 某张图片过期、损坏或缺失时，优先恢复原图任务，不自动重新生成同一付费请求；
- 视频提交前再次核对引用哈希，防止前置文件被替换。

### 4.4 兼容策略

建议 `video_from_image` 继续接受现有 `referenceAssets`，同时增加可选的 `mediaAssetId` 或 `inputAssetId`，由 host 内部执行 promote/read，不把 `source` 规则暴露给模型。旧调用继续有效，新调用逐步迁移。

## 5. 连接三：编排详情页接入媒体操作

后端闭环完成后，用户仍需要看见任务状态并处理异常。当前 [WorkDetailPage.tsx](../../src/pages/enterprise/WorkDetailPage.tsx#L210) 只对会话任务挂载 `MediaArtifactsPanel`，编排详情没有媒体面板。

### 5.1 推荐页面结构

编排详情保留现有“步骤进展”和“最终交付”区域，在右侧或节点详情中增加媒体区域：

- 按节点分组显示图片/视频任务；
- 展示生成、跟踪、保存和计费状态；
- 预览已保存图片和视频；
- 导出到用户选择的路径；
- 恢复原任务、重新保存原结果；
- 显示等待审批、授权失效、报价过期和结果过期；
- 显示输入引用关系，例如“由节点 A 的图片成果生成”。

建议复用现有 `MediaArtifactsPanel`、`VideoTaskPanel` 的展示组件，把“任务上下文”和“节点过滤”作为 props，而不是复制一套 UI。

### 5.2 数据接口

增加编排视图聚合接口或在现有 `ARRANGE_GET_EXECUTION` 结果中增加媒体摘要：

```ts
type ArrangementMediaSummary = {
  nodeId: string
  nodeRunId?: string
  imageJobs: MediaJobSummary[]
  videoJobs: VideoJobSummary[]
  assets: MediaArtifactRef[]
  pendingActions: Array<'approve' | 'resume' | 'retry-save' | 'export' | 'select-input'>
}
```

详情页读取的是经过 scope 和字段投影的业务视图，不返回内部路径、供应商 URL、请求 token、完整 prompt 或原始错误对象。

### 5.3 用户操作归属

编排页面可以提供人工导入参考图，但导入后的资产必须绑定当前任务和 owner。用户在详情页点击“恢复”或“重新保存”时，应调用现有原请求恢复方法，不重新生成；点击“重做”需要明确显示会创建新的生成请求，并重新走审批和报价。

## 6. 其他必须补齐的媒体闭环

### 6.1 规划阶段识别媒体任务

规划器当前主要根据员工职责、能力摘要和对话模型生成节点，不携带完整媒体 profile。建议将媒体需求作为“能力声明”加入计划，而不是把供应商模型名硬编码进规划结果：

```ts
type MediaRequirement = {
  kind: 'image' | 'video'
  operation: 'generate' | 'edit' | 'image-to-video' | 'text-to-video'
  required?: boolean
  preferred?: {
    aspectRatio?: string
    resolution?: string
    durationSeconds?: number
    audio?: boolean
    outputFormat?: string
  }
  inputFrom?: { nodeId: string; artifactId?: string }
}
```

规划阶段只记录业务意图；预检阶段再根据员工实时 manifest 解决 profile、规格和工具权限。这样 profile 更新后不需要重新设计规划协议。

### 6.2 启动预检

`preflightDraft()` 应增加媒体检查结果，但不要把暂时不可用等同于永久失败：

- `available`：当前可直接执行；
- `needs-approval`：能力可用，但需要用户审批；
- `needs-user-input`：规格或输入素材尚未选择；
- `temporarily-unavailable`：授权、网关或服务临时不可用；
- `unsupported`：员工 profile 确实不支持该操作。

预检结果需要指出具体节点、操作、所需输入和可替代 profile。启动策略可以由产品决定：必需媒体能力阻止启动，可选媒体能力允许节点进入等待状态。

### 6.3 权限模型不要强绑 `full-local`

当前媒体工具过滤把生成工具与 `full-local` 绑定，导致“允许生图但不允许 bash”无法表达。建议将权限拆成独立能力：

```ts
type TaskCapabilityPolicy = {
  filesystem: 'read-only' | 'workspace-edit' | 'full-local'
  media: 'inspect' | 'generate' | 'generate-and-cancel'
  network: 'disabled' | 'approved-tools'
  approvalMode: 'confirm-each' | 'auto-approve'
}
```

旧 `preset` 仍可映射到新结构，避免旧计划失效：

- `read-only` -> 文件只读、媒体 inspect；
- `workspace-edit` -> 工作区编辑、媒体按单独开关决定；
- `full-local` -> 保留现有最大权限行为。

媒体生成始终保留报价、预算、授权和请求身份校验，即使用户选择自动审批。自动审批只是确认交互方式，不应绕过平台账务和安全检查。

### 6.4 媒体交付验收

当前交付验收统一读取文件并计算哈希。建议增加按 `artifact.kind` 选择的检查器：

| 类型 | 基础检查 | 可选扩展检查 |
| --- | --- | --- |
| 图片 | MIME、非空、哈希、可解析、宽高 | 色彩空间、透明度、尺寸比例 |
| 视频 | MIME、非空、哈希、容器可读取 | 编码、时长、帧率、分辨率、音频轨 |
| 文档 | 现有 Office/PDF/文本检查 | 页数、表格或章节要求 |
| 数据 | 文件存在、编码、哈希 | JSON/CSV schema、列完整性 |

检查上限应采用“全局安全上限 + 运行时可配置上限 + profile 建议值”的三层模型。全局上限可以防止失控，但不应把当前 64 MiB 或某个测试值作为所有视频的永久上限。视频大文件应优先采用流式校验和磁盘配额，而不是简单拒绝。

### 6.5 资产生命周期和清理

媒体库、工作区交付文件和用户导出文件是三种不同生命周期：

- 媒体库资产：由任务和账务记录管理，可恢复原请求；
- 工作区交付：由编排计划和用户工作目录管理，可被下游节点读取；
- 用户导出：用户明确保存到外部位置，应用不再默认管理。

不要因为编排结束就立刻删除媒体库资产。建议保留引用计数、最后使用时间和归档状态，清理策略可按企业配置或磁盘空间触发，并保留恢复所需的元数据。

### 6.6 进度和事件

现有编排事件已经有节点开始、完成、失败、交付校验等类型。媒体闭环建议增加结构化摘要，而不是把供应商原始事件全部推给 renderer：

```ts
type ArrangementMediaEvent = {
  nodeId: string
  nodeRunId: string
  kind: 'image' | 'video'
  jobId?: string
  assetIds?: string[]
  phase: 'preparing' | 'awaiting-approval' | 'submitted' | 'tracking' | 'saving' | 'materializing' | 'ready' | 'blocked'
  retryable: boolean
}
```

这样详情页可以显示“正在生成”“等待确认”“正在保存”“等待用户处理”，但不会暴露 prompt、URL 或内部错误细节。

### 6.7 并发与预算

现有图片服务有并发活动限制，视频也有任务跟踪和恢复队列。编排并行节点可能同时触发多个媒体任务，建议增加任务级预算和并发协调：

- 并发值由运行时、企业策略和网关能力共同决定；
- 超出并发时进入排队或 `waiting-user`，不要误报为模型失败；
- 报价在真正提交前仍需重新确认未过期；
- 任务停止只停止本地调度，是否取消上游由 capability 和单独审批决定；
- 取消不自动承诺退款，账务状态继续通过原请求查询闭合。

范围参数建议由配置或 runtime manifest 提供，并为未来更高分辨率、更长视频和更多输出留出扩展空间。代码层只保留必要的防止内存、磁盘和协议滥用的边界。

## 7. 建议的数据关系

不建议马上把所有媒体字段塞进 `ArrangementNode`。可以增加任务级媒体索引，保持节点计划和媒体任务解耦：

```ts
type ArrangementMediaLink = {
  version: 1
  owner: TaskOwnerScope
  taskId: string
  arrangementRunId: string
  nodeId: string
  nodeRunId: string
  jobId: string
  kind: 'image' | 'video'
  sourceAssetIds: string[]
  outputAssetIds: string[]
  materializedFiles: Array<{
    deliverableId?: string
    path: string
    sha256: string
    size: number
    status: 'PENDING' | 'SAVED' | 'MISSING' | 'CONFLICT'
  }>
  createdAt: number
  updatedAt: number
}
```

这个索引支持：节点详情、跨节点引用、重试恢复、审计和最终交付映射。原始 `LocalMediaJob` 和 `LocalVideoJob` 仍然是账务与供应商恢复的权威记录，不应被编排索引替代。

## 8. 分阶段开发顺序

### Phase 1：内部桥接和图片/视频物化

- 新增编排媒体桥接端口和任务级媒体链接。
- 支持把已保存图片/视频按交付物 ID 原子复制到共享工作区。
- 节点结束 JSON 增加媒体资产引用字段，旧 JSON 继续兼容。
- 将物化结果纳入 `finalDeliveryFile` 和下游依赖校验。
- 增加相同资产重复执行、工作区文件被修改、暂停恢复和权限切换测试。

### Phase 2：跨节点媒体引用

- 增加 output promote/reference 语义。
- 让 `video_from_image` 通过 host 接受任务内派生引用。
- 记录图片节点到视频节点的来源关系。
- 覆盖单输出、多输出、部分成功、结果过期和跨订阅隔离。

### Phase 3：编排详情媒体面板

- 复用会话媒体组件，增加节点筛选和编排任务上下文。
- 增加预览、导出、恢复跟踪、重新保存和等待审批提示。
- 媒体状态和节点状态同步展示，避免页面只显示“节点失败”而没有原因。

### Phase 4：规划和预检增强

- 规划输出媒体需求声明，不绑定具体供应商 profile。
- 预检读取实时 employee runtime，报告操作、规格、工具权限和审批条件。
- 支持可选节点等待、替代员工和用户补充输入。

### Phase 5：媒体质量、配额和运维能力

- 增加图片/视频可解析和可播放验收器。
- 将全局安全上限、企业策略和 profile 能力分层配置。
- 增加任务级预算、并发队列、磁盘配额和资产清理。
- 做真实网关下的端到端验收，不改变原请求恢复和禁止重复提交原则。

## 9. 约束设计：范围放宽，但边界仍然可控

用户希望媒体能力覆盖更宽的图片和视频规格，建议采用以下策略：

1. **以 runtime manifest 为准**：时长、分辨率、比例、帧率、音频、输出格式、参考图数量和输入大小由员工 profile 动态声明。
2. **配置驱动上限**：客户端提供可配置的资源安全上限，默认值留出明显余量；不同企业、环境和网关可以调整，不写死在业务流程中。
3. **流式处理优先**：视频和大图片使用流式下载、哈希和物化，避免把完整文件一次性放入内存。
4. **业务规则与资源保护分离**：不因当前 UI 不支持某个规格就修改后端协议；只在内存、磁盘、耗时和协议安全真正需要时拒绝。
5. **部分成功可用**：多图、多输出和多节点场景允许继续处理已保存结果，只有计划明确要求全部结果时才阻塞整体编排。
6. **可选能力可等待**：网关临时不可用、审批未完成或结果待保存时进入可恢复状态，不直接标记为永久失败。
7. **不把恢复当重做**：所有恢复、重新保存和账务查询都沿用原请求；只有用户明确重做才创建新请求。
8. **保持向后兼容**：旧任务没有媒体字段时继续按工作区文件交付；旧工具调用和旧资产 manifest 仍可读取。

这里的“范围宽”指能力协商和配置可扩展，不代表取消归属、授权、审批、哈希、磁盘和协议安全边界。

## 10. 测试与验收矩阵

### 单元和契约测试

- 资产 promote 不改变原 output manifest，派生引用保持 owner、taskId 和哈希一致。
- 同一资产重复物化幂等；目标文件冲突可识别；写入中断不留下可验收的半文件。
- 图片、视频、参考图、派生引用不能跨 owner、跨 task 或跨 subscription 读取。
- 旧媒体 job、旧视频 job、旧编排计划仍能读取和恢复。
- tool policy 可以独立表达媒体生成权限，不要求开启 bash。
- 预检正确区分 unsupported、temporarily-unavailable、needs-approval 和 needs-user-input。

### 编排运行测试

- 生图节点生成并物化图片，节点完成后下游读取确认文件。
- 图片 output promote 为引用，视频节点用引用生成视频。
- 文生视频直接生成并物化视频。
- 多输出只选择部分结果时，下游按显式资产 ID 运行。
- 生图或视频下载失败时恢复原请求，不重复提交。
- 审批等待、授权变化、用户暂停、应用退出和恢复不会造成重复付费提交。
- 并行节点媒体任务按任务和企业策略排队，状态可恢复。

### UI 和真实环境验收

- 编排详情能看到每个节点的媒体状态、预览、导出和恢复按钮。
- 真实图片网关、真实视频网关、Mock 模式分别验证，不混淆计费状态。
- 大尺寸图片、较长视频、多输出、部分成功和结果过期均能在配置范围内处理。
- 真实员工 manifest 变化后，预检和运行时都能给出可理解的能力差异。
- 最终文件能被下游节点读取，详情页能正确显示来源和哈希状态。

## 11. 完成标准

可以把媒体编排闭环标记为完成，需要同时满足：

- 编排节点可以按实时能力声明调用生图、文生视频和图生视频；
- 生成资产有任务、节点、运行和来源关系；
- 生图结果可以按受控规则作为图生视频输入；
- 图片和视频可以按交付物 ID 自动物化到共享工作区；
- 下游节点能读取已确认的媒体资产或文件；
- 交付验收支持媒体类型，且参数范围来自配置和 profile，不被临时默认值卡死；
- 编排详情页能展示和处理媒体任务状态；
- 暂停、恢复、授权变化和提交不确定场景不重复生成、不丢失账务状态；
- 旧会话、旧编排和旧媒体任务保持可读、可恢复；
- 真实网关端到端测试通过，且完成资源、权限、审批和错误处理验证。
