## 1. 架构概览

sep-client 是一个基于 **Electron + pi-coding-agent SDK** 的桌面客户端。用户本地运行此应用，通过它与 SEP 平台的 AI 员工对话。

### 1.1 核心设计决策

| 决策点 | 选型 | 理由 |
|--------|------|------|
| 架构模式 | Electron (主进程 + 渲染进程) | 跨平台桌面应用标准方案 |
| AI 引擎部署 | pi-coding-agent **进程内**（非 sidecar） | 降低进程间通信复杂度，简化部署 |
| AI 引擎宿主 | Electron 主进程 | 需要 Node.js API（文件、bash、网络） |
| 主↔渲染通信 | contextBridge IPC | Electron 安全最佳实践 |
| 令牌管理 | 主进程独占，safeStorage 加密 | 渲染进程不可见敏感数据 |
| 网关协议 | OpenAI-compatible HTTP (streaming) | pi-coding-agent 原生支持，易于对接 SEP Gateway |

## 2. 进程职责划分

### 2.1 主进程 (electron/main.ts)

**职责**:
- BrowserWindow 生命周期管理
- IPC handlers 注册与路由
- pi session 宿主（PiHost 实例）
- safeStorage 访问（token 加密存储）
- 操作系统 API 调用（文件、bash、网络）

**不做**:
- UI 渲染
- 用户交互逻辑

### 2.2 渲染进程 (src/)

**职责**:
- 用户界面渲染（React）
- 用户交互事件处理
- 通过 `window.electronAPI` 调用主进程服务

**不做**:
- 直接访问 Electron API
- 直接访问 pi-coding-agent SDK
- 持有或操作 token

### 2.3 Preload (electron/preload.ts)

**职责**:
- 通过 `contextBridge.exposeInMainWorld` 暴露受限 API
- 唯一可以同时访问 Electron 和 DOM 的位置

**安全边界**:
- `nodeIntegration: false`
- 只暴露最小必要接口
- 所有参数在主进程侧验证

## 3. 核心模块设计

### 3.1 PiHost (electron/pi-host.ts)

**职责**: pi session 生命周期管理

```typescript
class PiHost {
  startSession(config: SessionConfig): Promise<void>
  stopSession(): void
  sendPrompt(text: string): void
  
  private onAgentEvent(event: AgentSessionEvent): void
  private onToolApproval(request: ToolApprovalRequest): Promise<boolean>
}
```

**关键流程**:

1. **启动 session**:
   ```
   创建 ModelRuntime
   → 注册 sep-gateway provider
   → 创建 DefaultResourceLoader (+ extensions)
   → await resourceLoader.reload()
   → createAgentSession({ resourceLoader, model, ... })
   → session.subscribe(listener)
   ```

2. **事件转发**:
   ```
   session.subscribe() 回调
   → 过滤需要转发的事件类型
   → win.webContents.send('pi:event', event)
   → 渲染进程通过 onPiEvent() 接收
   ```

3. **工具审批**:
   ```
   tool_call 事件触发
   → win.webContents.send('tool-approval-request', data)
   → 渲染进程弹窗
   → 用户 approve/deny
   → sendToolApprovalResponse({ approved })
   → ipcMain.once 接收
   → 返回 { block: !approved }
   ```

### 3.2 SEP Extensions (pi-extension/)

#### 3.2.1 guard.ts — 工具审批拦截

```typescript
export function buildPermissionGuard(config: {
  onToolApprovalRequest: (req: ToolApprovalRequest) => Promise<boolean>;
}): ExtensionFactory {
  return (pi) => {
    pi.on('tool_call', async (event: ToolCallEvent): Promise<ToolCallEventResult> => {
      const toolName = event.toolName;
      
      // 只读工具：直接放行
      if (READ_ONLY_TOOLS.has(toolName)) {
        return { block: false };
      }
      
      // 高危工具（bash/write/edit）：需要审批
      if (HIGH_RISK_TOOLS.has(toolName)) {
        const approved = await config.onToolApprovalRequest({
          toolName,
          input: event.input,
        });
        return approved ? { block: false } : { block: true, reason: 'User denied' };
      }
      
      // 未知工具：默认拒绝
      return { block: true, reason: `Unknown tool: ${toolName}` };
    });
  };
}
```

#### 3.2.2 provider.ts — 动态 token 注入

```typescript
export function buildSepGatewayProvider(config: {
  getAccessToken: () => Promise<string>;
}): ExtensionFactory {
  return (pi) => {
    pi.on('before_provider_headers', async (event: BeforeProviderHeadersEvent) => {
      const token = await config.getAccessToken();
      event.headers['authorization'] = token;  // mutate in place
    });
  };
}
```

**Token 刷新流程**:
```
getAccessToken() 被调用
→ 检查内存中的 accessToken 是否过期
→ 如果过期：从 safeStorage 读取 refreshToken
→ 调用 SEP Gateway /auth/refresh
→ 更新内存中的 accessToken 和 refreshToken
→ 保存新 refreshToken 到 safeStorage
→ 返回新 accessToken
```

### 3.3 CredentialsManager (electron/credentials.ts)

```typescript
export class CredentialsManager {
  async saveRefreshToken(token: string): Promise<void>
  async getRefreshToken(): Promise<string | null>
  
  // 内部使用 electron.safeStorage
  // macOS: Keychain, Windows: DPAPI, Linux: libsecret
}
```

## 4. 数据流

### 4.1 用户发送消息流程

```
[Renderer] 用户输入 "hello"
    │
    └─→ window.electronAPI.sendPrompt('hello')
            │
            │ IPC: 'pi:send-prompt'
            ▼
    [Main] ipcMain.handle('pi:send-prompt')
            │
            └─→ piHost.sendPrompt('hello')
                    │
                    └─→ session.prompt('hello')
                            │
                            │ before_provider_headers 触发
                            ▼
                    [Extension] 注入 Authorization header
                            │
                            │ HTTPS POST /v1/chat/completions
                            ▼
                    [SEP Gateway]
                            │
                            │ SSE stream
                            ▼
                    [pi-agent] 逐 chunk 接收
                            │
                            │ message_update 事件
                            ▼
    [Main] session.subscribe() 回调
            │
            └─→ win.webContents.send('pi:event', event)
                    │
                    │ IPC: 'pi:event'
                    ▼
    [Renderer] onPiEvent() 回调
            │
            └─→ UI 更新（逐字显示）
```

### 4.2 工具审批流程

```
[pi-agent] 返回 bash tool_call
    │
    │ tool_call 事件
    ▼
[Extension guard] 拦截
    │
    └─→ onToolApprovalRequest({ toolName: 'bash', input: {...} })
            │
            │ IPC: 'tool-approval-request'
            ▼
[Renderer] 弹出审批弹窗
    │
    └─→ 用户点击 Approve
            │
            └─→ window.electronAPI.sendToolApprovalResponse({ approved: true })
                    │
                    │ IPC: 'tool-approval-response'
                    ▼
[Main] ipcMain.once('tool-approval-response')
    │
    └─→ resolve(true)
            │
            └─→ extension handler 返回 { block: false }
                    │
                    │ pi-agent 继续执行 bash
                    ▼
[bash tool] 实际执行
    │
    │ tool_execution_end 事件
    ▼
[Renderer] 显示执行结果
```

## 5. 安全设计

### 5.1 进程隔离

| 数据/能力 | 主进程 | 渲染进程 |
|----------|--------|---------|
| refresh token | ✅ 持有（safeStorage） | ❌ 不可见 |
| access token | ✅ 内存中（动态刷新） | ❌ 不可见 |
| pi session | ✅ 唯一宿主 | ❌ 不可访问 |
| Node.js API | ✅ 全权限 | ❌ 无权限 |
| 文件系统 | ✅ | ❌ |
| bash 执行 | ✅ | ❌ |
| IPC | ✅ 发送 + 接收 | ✅ 仅通过 electronAPI |

### 5.2 工具审批策略

| 工具类型 | 默认行为 | 审批超时 |
|---------|---------|---------|
| 只读工具 (read, grep, find, ls) | 自动放行 | N/A |
| 高危工具 (bash, write, edit) | 需要审批 | 60s → 自动拒绝 |
| 未知工具 | 自动拒绝 | N/A |

被拒绝的工具调用仍然会传给 pi-agent（返回拒绝原因），agent 可以继续对话。

### 5.3 Token 管理

- **refresh token**: safeStorage 加密存储，应用重启后仍有效
- **access token**: 内存中，过期自动刷新（expires_in - 60s）
- **日志/事件中禁止打印 token 值**

## 6. 技术约束

### 6.1 版本锁定

| 依赖 | 版本 | 原因 |
|------|------|------|
| `@earendil-works/pi-coding-agent` | `0.83.0` | API 修正已验证，不能随意升级 |
| `@earendil-works/pi-ai` | `0.83.0` | 同上（PoC 测试工具） |

升级前必须重新跑全部 4 个 PoC。

### 6.2 ESM 要求

- `package.json` 必须有 `"type": "module"`
- `tsconfig.node.json` 使用 `"moduleResolution": "node"`（不是 `"bundler"`）

### 6.3 已验证的 API 事实

| API | 行为 | 注意事项 |
|-----|------|---------|
| `createAgentSession` | 返回 `{ session, extensionsResult }` | 必须解构 |
| `DefaultResourceLoader` | 构造需要 `cwd` / `agentDir` | 缺少会崩溃 |
| `resourceLoader.reload()` | 必须显式调用 | 否则 extensions 不生效 |
| `session.subscribe()` | 订阅所有事件 | 没有 `session.on()` |
| `before_provider_headers` | mutate `event.headers` | 返回值被忽略 |
| `tool_call` handler | 返回 `{ block?: boolean }` | async 支持 |

## 7. 扩展点

### 7.1 未来可能的架构演进

| 场景 | 方案 |
|------|------|
| 多 AI 员工切换 | PiHost 支持多 session 实例，通过 employeeId 路由 |
| 离线模式 | 本地 LLM (Ollama) + 动态 provider 切换 |
| 插件系统 | 新增 `pi-extension/plugins/` 目录，动态加载第三方 extension |
| 团队协作 | 多用户共享 session（需 SEP Gateway 支持） |

### 7.2 性能优化方向

- **懒加载 pi session**: 不在应用启动时创建，首次发送 prompt 时再启动
- **事件节流**: `message_update` 高频事件合并后再转发给渲染进程
- **历史消息分页**: 长对话 session 历史只加载最近 N 条
- **背景压缩**: 利用 pi-coding-agent 的 compaction 机制定期压缩历史

## 8. 与 SEP 后端的对接

### 8.1 SEP Gateway 接口

sep-client 通过 `SEP_GATEWAY_URL` 指向的 OpenAI-compatible endpoint 与 SEP 后端通信：

```
POST /v1/chat/completions
Authorization: Bearer <access_token>

{
  "model": "sep-employee",
  "messages": [...],
  "stream": true
}
```

响应：SSE stream (text/event-stream)

### 8.2 认证流程

```
1. 用户在 sep-client 中点击登录
   → 打开系统浏览器，跳转 SEP OAuth 页面
   
2. 用户在浏览器完成授权
   → SEP 重定向到 sep-client:// custom protocol
   → sep-client 接收 authorization_code
   
3. sep-client 用 code 换取 refresh_token
   → POST /auth/token { code }
   → 返回 { access_token, refresh_token, expires_in }
   → refresh_token 存入 safeStorage
   
4. 后续所有请求携带 access_token (via before_provider_headers)
   → 过期自动刷新
```
