# 知识库开发现状调研（通俗版）

调研日期：2026 年 10 月 10 日。代码基线：`bbcd296`，以当前工作区实际实现为准。

这是一份现状说明，不是开发计划的完成声明。本次检查了页面、接口、文档处理、检索、员工对话、部署配置及测试；运行了知识库专项单元测试和两个本地问题复现。没有登录生产服务器、修改线上配置或进行真实文件全流程验收。

## 1. 先看结论

**知识库已经有完整的主要功能框架，也已经接入员工聊天，不是只有展示页面。但还不能把它当成一个已经验收完成、可以放心全面开放的成熟功能。**

可以把它理解成一套“给硅基员工查阅的企业资料库”：管理员放入公司资料，指定哪些员工可以使用；用户提问时，系统先从资料里找相关内容，再交给模型组织回答。

现在这条主线在代码里已经连起来了：

```text
建立知识库 -> 上传资料 -> 后台处理 -> 配置员工授权
                                      |
员工收到问题 -> 查找获准使用的资料 -> 组织回答 -> 保存参考来源
```

不过，本次调研发现几个实际缺口：PDF 解析与当前依赖不兼容、网页下载没有带登录凭证、重试绕过了原有队列、部分检索设置和统计展示与真实行为不一致。这些问题不能用“页面已经做好”或“单元测试通过”来替代验收。

**最准确的阶段判断是：主要开发链路已建立，接下来应以修复、联调和验收为主，而不是继续从零搭框架。** 不给出“完成了百分之多少”，因为功能实现、使用体验和生产验证并不是同一件事。

## 2. 现在已经做到了什么

下表的“已实现”表示已经找到真实代码及接口连接，不表示本次已在浏览器或线上逐项实测成功。

| 能力 | 当前开发情况 | 通俗解释 |
|---|---|---|
| 建立和管理知识库 | 已实现 | 可以新建、改名、改说明、搜索列表和删除 |
| 上传资料 | 已接通真实处理接口 | 不是只记一个文件名，会保存文件并交给后台处理；单文件上限 10 MB |
| 后台处理 | 已实现 | 提取文字、清理、切成小段，再建立检索数据 |
| 查看处理进度 | 已实现 | 可以看到等待、处理中、完成、失败，以及错误原因和处理模型 |
| 手动录入知识 | 已实现，有一致性缺陷 | 可以直接写一段知识、加标题和标签，也可以编辑、删除 |
| 员工授权 | 已实现 | 可以让某个企业雇佣的硅基员工使用指定知识库，也能撤销 |
| 部门授权 | 后端支持，知识库页面不完整 | 后端能按部门限制范围，但知识库授权面板没有完整的新建部门授权操作 |
| 检索 | 已实现三种方式 | 按关键词找、按意思找，或者把两种结果合并 |
| 管理员测试检索 | 已实现，有设置误导 | 输入问题后可查看找到的片段、来源和耗时；不是最终问答质量评测 |
| 接入员工聊天 | 已实现 | 有有效雇佣关系、授权且消息有文字时，会自动检索；默认取 3 段参考资料 |
| 回答的参考来源 | 正常回答的保存和展示链路已实现 | 检索到的候选资料随正常回答落库，聊天历史有“参考来源”展示组件；并未逐条验证实际引用 |
| 检索分析 | 已实现基础页面，统计不完整 | 有检索次数、零结果问题、近期日志和嵌入服务状态，但不能全部当成准确业务指标 |
| 重建索引 | 后端接口已实现，页面未接入 | 换模型或补齐历史向量时可重新生成索引，目前需要调用接口 |
| 失败重试 | 有入口和处理逻辑，可靠性待补 | 用户能点重试，但它没有统一走上传时使用的队列 |

企业端已有三个页面：知识库列表 `/knowledge`、详情 `/knowledge/:id`、检索分析 `/knowledge/:id/analytics`。详情里有文档、文本片段、文档状态和授权管理四个页签。

授权有两个方向的入口：可以在知识库里选员工，也可以在雇佣管理里为员工选择知识库。这里的“员工授权”绑定的是企业的雇佣关系，不是给市场中的员工模板全局开放资料。

### 文件格式要单独说明

| 格式 | 当前实际情况 |
|---|---|
| TXT、Markdown | 有直接读取和处理实现，本次没有做真实上传验收 |
| DOCX | 有文字提取实现，本次没有做真实文件验收 |
| PDF | 页面允许上传，但当前解析调用与已安装依赖不兼容，见第 5 节 |
| 老版 Word `.doc` | 上传接口接受，但使用的是同一套 DOCX 解析逻辑，不能据此认定可靠支持 |
| PNG、JPEG | 有中英文 OCR 实现，即从图片里识别文字；本次未验证识别效果和语言包部署 |
| 扫描 PDF、复杂表格 | 未看到扫描 PDF 转图片再 OCR 的专门流程，也没有表格结构保真的验收证据 |
| 音频、视频 | 未发现知识库导入和转写流程 |

“图片 OCR”不是“模型理解图片内容”：当前仍是先识别成文字，再走文字检索。

## 3. 员工现在怎样使用知识库

以公司报销制度为例，代码中的流程是：

1. 管理员建一个“财务制度”知识库，上传制度文件，或者直接录入制度片段。
2. 系统在后台处理资料。处理结束后，文字片段进入可检索范围。
3. 管理员把这个知识库授权给公司的某个硅基员工，例如财务助理。
4. 用户向该员工询问“差旅报销需要哪些材料”。系统检查用户是否能使用这段雇佣关系，并按员工及部门授权确定检索范围。
5. 系统找出相关资料，把它们作为回答参考交给模型；正常生成的回答会保存这些来源。

这是“先查资料再回答”，也就是 RAG，**不是把公司资料重新训练进模型**。上传文件本身也不等于员工已经能查到：还要完成处理，并配置正确授权。

需要注意以下实际边界：

- **处理完成不一定代表已能按语义检索。** 嵌入服务不可用时，文档也可能显示完成，但只保存了关键词检索数据。后端会记录降级原因，状态面板会显示错误或提示信息。
- **找不到资料或检索报错时，聊天仍可能继续回答。** 当前代码优先保障对话不中断，并允许结合通用知识回答；所以“员工给出了答案”不等于“答案来自企业制度”。
- **只发送附件、不输入文字时，不触发这次知识库查询。** 聊天附件解析和企业知识库导入是两个流程，不能混为一谈。
- **“参考来源”是检索到的候选资料，不是逐条核验过的实际引用。** 当前没有检查回答到底用了哪些片段；来源区也没有原文跳转或完整片段展开入口。工具执行次数达到上限后的兜底回答分支，尚未保存这些来源。
- **不同员工运行入口的接入程度不同。** 正式聊天已接入，复用聊天流程的任务执行也能共享这条链路；员工独立的运行测试接口没有接入。对话调用外部能力时，也不会自动把企业知识库上下文传给能力适配器。因此不能承诺“员工所有运行方式都会查知识库”。

## 4. 权限与部署到了哪一步

### 权限已经有基本边界，但管理体验还没对齐

后台已经要求知识库属于当前企业；新建、修改、删除、上传、片段维护、授权和测试检索等写入或管理操作要求企业管理员。正式检索还检查雇佣关系是否有效、用户是否获准使用，以及知识库授权范围。

但普通企业成员仍能看到知识库入口，页面上的多个管理按钮也没有按角色隐藏。后台会拦截不允许的操作，用户体验可能变成“看得到按钮，点了才报错”。

更重要的是：当前知识库、文档和片段的管理读取主要按“同一企业”校验，**不是每一次直接读取都要求具备该知识库的员工或部门授权**。因此不能把目前的部门检索限制解释为“该部门以外的人完全无法查看原始资料”。如果要放入部门敏感资料，需要先明确并统一阅读权限。

### 技术方案已落到代码，不等于每个环境都已启用

当前代码的主要方案是：

| 组成 | 作用 |
|---|---|
| PostgreSQL | 保存知识库、文档信息、文本片段、授权和日志 |
| pgvector / HNSW | 在数据库里按语义查资料，不用把所有向量都拉到应用内存里计算 |
| Ollama 的 `bge-m3:latest` | 把文字转换成 1024 维检索向量；不是负责最终回答的模型 |
| Redis / BullMQ | 排队处理上传文件，限制并发并自动重试 |
| 本地磁盘或挂载卷 | 保存上传的原始文件；知识库尚未走统一对象存储 |
| sub2api | 员工聊天最终回答的模型调用入口 |

当前知识库嵌入请求是独立访问 Ollama，回答生成走 sub2api。不能按旧文档一概说成“所有知识库模型请求都经过 sub2api”。

仓库已有 pgvector 数据库迁移、重建索引接口和部署说明。不过联调环境的 `docker-compose.dev.yml` 明确绕过了 pgvector 迁移，使用兼容的旧向量存储路径。因此，**不能仅凭代码有 pgvector 就断言所有服务器都在用它。**

生产配置已经包含嵌入服务参数，生产就绪检查也把嵌入服务和知识库队列作为依赖。部署手册还写了暂时停止 Ollama 的操作，以及停用后就绪检查返回 503、发布切换会被阻止的影响。这只说明配置和运维约定存在，**本次没有确认服务当前究竟在运行还是已停用**。

旧计划里出现过 Pinecone、TEI 等方案，也有未同步的勾选项。本报告不拿这些旧计划代替当前代码，更不把过去的测试记录当成本次线上验收结果。

## 5. 本次确认的主要问题

### 5.1 PDF 入口开放了，解析实现却不兼容

项目实际安装的是 `pdf-parse 2.4.5`，解析代码仍把包当成函数直接调用。已用本地已安装包确认：导出是对象，其中提供 `PDFParse` 类；按现有方式调用会得到 `TypeError: p is not a function`。

**影响：用户可以上传 PDF，但按当前依赖和代码组合，后台 PDF 解析会失败。** 这不是仅靠调整嵌入模型或点击重试就能解决的问题。应先修复依赖调用，并用真实 PDF 加回归测试。

### 5.2 文档下载没有带上登录凭证

知识库下载按钮直接用 `window.open` 打开地址；后台下载接口要求 Bearer access token，而 token 存在内存中。新窗口导航不会自动添加这个请求头，后台 JWT 策略也只从 Bearer 头取 access token。

**影响：当前前后端契约下，网页下载入口不能正常完成鉴权。** 仓库已有带认证的通用文件下载方法，知识库尚未复用。本次确认的是代码契约问题，未在浏览器实际点击复现。

### 5.3 重试没有统一经过队列

正常上传经过 BullMQ，处理并发限制为 2，失败最多尝试 3 次。但状态面板的单个和批量重试都调用批量重处理接口，后台直接启动处理函数，没有进入同一队列。

**影响：同时重试很多文件可能绕过并发保护；进程重启时也没有同等的队列持久性保障。** 接口返回的 `queued` 数量并不代表已经写入 BullMQ。

### 5.4 检索测试里有“能调但不生效”的设置

- Rerank 开关会发送 `useRerank`，但检索测试后台未使用这个参数，没有真正执行二次重排序。
- 相似度阈值在纯向量检索中生效，但混合检索接收后没有用于过滤；页面又没有检索策略选择，默认通常进入混合检索。
- 测试返回的策略可能仍是 `auto`，页面却只分成“向量检索”和“全文检索”，未准确表达混合或降级状态。
- 页面把检索得分当成百分比展示，但混合排序分和词法分不是统一的 0 到 1 相似度，**不能把它理解成回答正确率或模型置信度**。

**影响：用户容易误以为设置已生效，或误读检索质量。** 应先让界面与实际策略对齐，再谈调参效果。

### 5.5 分析页不能当成完整业务报表

“从未命中文档”当前实际上检查文档有没有生成文本片段，并没有检查它是否真的被检索命中过。这个名称与计算逻辑不一致。

此外，统计最多取最近 500 条日志，页面趋势来自最近 50 条日志再聚合；测试检索和实际使用也没有在页面充分区分。存在多个授权知识库时，正式检索日志优先记录有返回结果的知识库，无结果的其他库不一定逐个记录。

**影响：这些数值适合初步排查，不适合直接作为完整的 30 天使用量、文档利用率或检索效果结论。**

### 5.6 服务降级时编辑知识，旧向量可能没有清干净

编辑片段时，如果嵌入服务不可用，代码会更新文字和分词，但没有同时清空旧的兼容向量及模型字段。本地直接调用相关字段构建方法，已确认它只返回新的 `tokens`，未返回清空旧向量的字段。

虽然后续会尝试清空 pgvector 列，但兼容路径仍可能留下旧数据。**影响：服务恢复或进入旧存储兼容路径后，检索数据可能与编辑后的文字不一致。** 应补充降级编辑的回归测试。

### 5.7 页面入口和故障提示仍不完整

后台已有重建索引接口，但前端没有对应按钮；分析页却提示用户“执行重建索引”。仅词法入库后显示完成的文档，也不能直接通过“重试失败文档”补齐。

部门授权的新建交互、非管理员按钮限制、请求失败与空数据的区分也需要补齐。来源展示目前还可能显示系统生成的文件名，而不是用户熟悉的原始文件名。

## 6. 本次验证了什么，没验证什么

### 已执行的检查

| 检查 | 结果 | 能证明什么 |
|---|---|---|
| 知识库相关页面、接口和调用链阅读 | 已完成 | 主要能力有真实实现，且员工对话存在调用点 |
| `pnpm --dir backend test -- --runInBand src/modules/knowledge` | 5 个测试套件、14 个用例全部通过 | 已覆盖的权限、缓存隔离、日志和嵌入配置场景通过 |
| 已安装 PDF 包的导出和调用方式检查 | 复现函数调用错误 | 当前依赖与 PDF 解析调用不兼容 |
| 降级编辑的字段构建检查 | 确认未清空旧向量字段 | 服务不可用时的更新分支存在数据一致性缺口 |

专项测试主要围绕企业访问边界、授权查询、向量缓存与兼容回退、正式检索日志、嵌入地址和维度校验。它们使用模拟依赖，不代表真实 PostgreSQL、Redis、Ollama 全链路通过。

### 未验证或覆盖不足

- 本次没有操作生产环境，因此没有确认真实可用知识库数量、文档数量、服务启动状态和实际部署版本。
- 没有在浏览器执行真实上传、下载、授权和问答，也没有做本次页面截图验收。
- 当前未发现知识库页面、上传器、状态面板和授权面板的专项前端测试，也未发现完整知识库生产流程的自动化端到端测试。
- 文档解析、OCR、处理队列、失败重试、分析口径、重建索引及真实混合检索效果缺少对应的专项覆盖。
- 仓库有 20 文档并发压测脚本，但本次没有运行。脚本本身也需要复核：其通过判断未严格纳入上传失败和检索失败，不能只看输出“通过”就认定验收成功。
- 没有测量本次真实检索延迟、并发容量、检索准确性和大文件处理耗时。

### 历史记录能说明什么

仓库保留了两类历史证据，但它们都不足以替代当前验收：

- **2026 年 7 月 31 日的测试报告**记录过建库、手动插入片段和关键词查询。当时走的是关键词降级，对话集成尚未开始，不能作为当前语义检索和聊天引用的验收依据。
- **2026 年 8 月 21 日的开发方案**记录过编译和单元测试通过，同时明确真实上传、向量服务、企业隔离、重启恢复及并发验收仍待完成。该文档里的嵌入部署方案也已与当前 Ollama 方案不同。

截至本次仓库调查，未找到能够证明当前生产环境“真实上传 → 语义检索 → 员工聊天 → 来源展示 → 权限隔离”整体通过的完整验收记录。这表示证据不足，不表示这些环节在所有环境都一定失败。

## 7. 下一步先做什么

### 第一优先级：把承诺给用户的基本操作做实

1. 修复 PDF 解析和带认证下载，增加真实格式样本及下载回归测试。
2. 统一首次处理、单个重试和批量重试的队列入口；测试并发、失败恢复和进程重启。
3. 修复降级编辑后的向量一致性，明确“已处理”和“已向量化”的区别。
4. 对齐管理阅读权限与检索权限，明确部门敏感资料是否应限制直接查看，并按角色收敛页面按钮。

### 第二优先级：让设置和报表可信

1. 移除或禁用未实现的 Rerank 设置，或者真正实现后再开放。
2. 对齐混合检索的阈值、实际策略和分数展示，不再把排序得分当百分比置信度。
3. 修正文档命中统计，拆分测试与正式使用数据，并明确采样和完整聚合的区别。
4. 补上重建索引、部门授权和请求失败提示等管理操作。
5. 决定是否允许“没有企业资料也继续回答”，并让用户能识别本次回答有没有使用知识库。

### 第三优先级：用真实环境完成验收

先用一个测试企业和一小批真实资料验证完整流程，再做跨企业、跨部门和未授权员工的访问检查；验证嵌入服务中断及恢复、失败重试、重启恢复和文件删除。最后使用修正过的并发脚本及固定问题集测处理速度和检索效果。

至少需要拿到这些证据，才适合宣布“已验收可用”：真实文件处理成功、能查到预期答案、不能查到无权访问的资料、引用来源正确、降级状态明确、重试可靠、统计与实际日志一致。

> 知识库的主体已经开发出来，管理员能管理资料和配置员工授权，员工聊天也已经有“先查公司资料再回答”的逻辑。现在不是从零建设阶段，但还没有足够证据认定它已经稳定上线。本次查到 PDF 处理、下载、重试和统计等环节还有实际问题，部分界面设置也没有真正生效。建议先修这些基本问题，再拿真实资料做一次完整验收，而不是继续堆新功能。线上服务是否运行、实际问答效果如何，本次没有远程核验，不能替代生产验收。
