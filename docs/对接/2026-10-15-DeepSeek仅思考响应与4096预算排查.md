## 3. 输出上限为何是 4096

生产配置与模型目录的当前实值：

```text
GATEWAY_DEFAULT_MAX_TOKENS=4096
platform_models[deepseek-v4.1-flash].maxOutputTokens=NULL
platform_models[deepseek-v4.1-flash].contextLength=NULL
```

模型目录该记录 `updatedAt=2026-09-30 05:56:29.103 UTC`。没有从该记录取得供应商输出上限。

生产 SEP 预算规则：

```text
D = GATEWAY_DEFAULT_MAX_TOKENS
M = 模型目录 maxOutputTokens
有效上限 = M ?? D
未传 max_tokens 时 = min(D, 有效上限)
显式 max_tokens > 有效上限时 = HTTP 400 / OUTPUT_BUDGET_EXCEEDED
```

本模型 M 未配置，所以 **4096 同时充当默认值和硬上限**。客户端显式传入的 4096 被保留；不会静默下调更大的显式值，而是直接拒绝。

此处没有使用订阅专属的数值输出上限。订阅授权、企业请求额度等属于其他检查，不能与这条 `max_tokens` 校验混为一谈。若模型目录配置更大的已核实上限，该生产版本允许显式值大于默认 4096；不需要通过全局提高默认值来解除所有模型的限制。

历史请求 `4e4f45bc-bdc1-43b2-a986-a8999ba3b7da`：已在执行表及 green/blue/dev 后端保留日志中按 ID 搜索，未找到对应记录。这类错误可在创建 execution 之前被拒绝，因此执行表没有记录并不异常。代码确认该错误来自 SEP 的模型/平台预算校验，不能据此指向订阅余额不足或供应商拒绝。**当次请求的具体 max_tokens 和当时配置快照无法恢复**；只能确认当前同模型有效上限是 4096，不能把当前值冒充历史快照。

## 5. stop 是否被转换

SEP 的 SSE 转发将原始 chunk 交给客户端，旁路读取 finish_reason 与 usage；没有把 length 改成 stop 的字段重写逻辑，也不按 reasoning/content/tool_calls 字段过滤内容。

但 sub2api 需要从 Responses 终止事件生成 Chat finish_reason：

| a6api Responses 终止信息 | 当前转换结果 |
|---|---|
| 内层 `status=incomplete`，`incomplete_details.reason=max_output_tokens` | `length` |
| 内层 `status=incomplete`，reason 为 `content_filter` | `content_filter` |
| 内层 `status=incomplete`，details 缺失或 reason 未识别 | `stop` |
| 外层事件 `response.incomplete`，内层 status 缺失/不一致，reason 即使是 max_output_tokens | 可能为 `stop`，因为映射只判断内层 status |
| 内层 `status=completed`，只有 reasoning，无正文、无工具 | `stop` |

所以不能笼统认定“中转把所有 length 改成 stop”：标准完整字段会正确映射；**缺失或不一致状态的兼容分支有误报正常结束的风险**。

纯 EOF 或只有 `[DONE]` 而缺少 Responses 终止事件，当前服务会返回 missing-terminal 错误。本次不能归因于“断流自动补 stop”。

转换器支持标准的正文、工具调用、思考 delta 事件。本次无原始 SSE，无法逐片证明 a6api 是否发送了正文/工具片段，也无法排除其采用不兼容事件后被转换逻辑忽略。客户端的“只有 thinking”不能反推 a6api 原始字段一定就是 reasoning_content，因为原始路由是 Responses。

关键代码：

- SEP 生产提交 `backend/src/modules/gateway/gateway.controller.ts:187`：原样 yield chunk。
- sub2api `backend/internal/pkg/apicompat/responses_to_chatcompletions.go:293`：流式 finish_reason 映射。
- 同文件 `:155`：reasoning 事件转换。
- `backend/internal/service/openai_gateway_chat_completions.go:812`：缺终止事件错误。

要确认本次根因，需要 a6api 按重点请求在 2026-10-15 15:58:33 至 15:59:00 的路由记录提供：

1. 实际底层供应商、模型版本、其收到的 max_output_tokens，以及内部是否再覆盖预算。
2. 原始终止 SSE 的外层 type、内层 response.status、incomplete_details.reason；如其内部还调用 Chat 接口，同时提供那个接口的原始 finish_reason。

4. 请求未提供 reasoning 时的默认思考行为，关闭/降低思考的准确参数、合法值，以及与工具调用是否兼容。
5. 当前别名的最大输出上限；是否支持独立思考预算或正文预留。

建议平台后续修复顺序：

1. 补充经过脱敏的终止元数据日志：事件 type、status、incomplete reason、输出预算、usage 分类、是否出现正文/工具；不记录完整提示词或思考正文。
2. 修复不完整终止事件被默认为 stop 的兼容缺口；保留原始终止状态，未知/冲突状态不能伪装正常结束。不应只凭“输出等于预算”强行改成 length。
3. 对未支持的 thinking 参数明确拒绝或告知不支持；确认供应商协议后实现有效映射，避免入口接受但实际丢失。
4. 取得供应商能力证据后，为本模型配置准确的独立 maxOutputTokens，并分开管理默认输出预算和硬上限。不要直接全局无差别调高。
5. 客户端对 reasoning-only 结果设置专门诊断，避免相同预算、相同参数连续五次重复尝试；经确认后再使用调整预算、降低思考或其他恢复策略。
