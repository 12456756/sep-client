# 知识库客户端与平台端开发协作说明

日期：2026-10-10。

本文确定知识库各模块的开发归属、实现方式、接口配合和最终用户流程，不划分开发优先级。依据现状调研与当前两端代码整理。

“当前已有”表示存在代码，不代表已生产验收；“开发要求”和“建议补充”是目标行为，不代表已经实现。

## 1. 总体边界

知识库是员工执行任务时可以查询的资料能力，不是一个需要被自动编排成独立步骤的员工。知识库的内容、权限、解析、索引和检索结果由平台端统一维护；客户端负责把用户操作和员工执行接入到这些能力中。

| 领域 | 桌面客户端 | 平台端/服务端 | 平台 Web 管理端 |
| --- | --- | --- | --- |
| 知识库元数据 | 展示、创建、编辑、删除入口；提交已认证请求 | 持久化、租户隔离、字段校验、审计 | 管理页面和运营入口 |
| 文件与文本 | 选择文件、上传、展示处理状态；编辑手工文本 | 文件存储、解析、OCR、切块、向量化、索引 | 上传、批处理、状态查看 |
| 权限 | 展示可配置对象，提交授权变更 | 计算有效授权、校验订阅/企业/部门关系、即时撤销 | 授权配置和审核入口 |
| 检索 | 在员工对话或节点执行前发起查询，展示参考资料 | 权限过滤、关键词/向量/混合检索、结果排序 | 测试检索和调试参数 |
| Pi 执行 | 将允许的检索结果作为上下文交给本地员工会话 | 不参与本地模型会话，不保存客户端密钥 | 不替代客户端员工执行 |
| 任务与运维 | 展示失败、重试和取消状态 | 队列、重试、幂等、重建索引、监控 | 运维操作和统计 |

客户端不应自行保存一套可用于正式检索的知识库索引，也不应根据本地缓存自行判断用户是否有权访问。平台端返回的权限结果是最终依据。

## 2. 端到端协作原则

1. 用户身份由客户端现有登录态承载，知识库接口使用主进程发起的认证请求；刷新令牌不进入渲染进程、日志或知识库上下文。
2. 所有知识内容的读取、下载和检索都在服务端重新校验权限。客户端缓存只能用于界面展示，不能作为授权凭证。
3. 文件上传成功只表示文件已接收，不表示已经可以检索。客户端必须区分 `PENDING`、`PROCESSING`、`READY`、`FAILED`。
4. 检索结果属于参考资料。只有当员工最终回答实际使用了某条资料时，才应标记为已使用来源；不能把所有候选结果都显示成已引用依据。
5. 检索失败、没有匹配、没有权限和服务不可用必须使用不同状态。企业制度类问题不能在检索失败时静默编造一个“看起来合理”的答案。
6. 知识查询是员工执行中的工具/数据能力，不创建“知识库员工”，也不改变员工选择和自动编排的员工匹配规则。

## 3. 当前状态与需要补齐的协作面

| 能力 | 当前情况 | 协作要求 |
| --- | --- | --- |
| 知识库和文档管理 | 服务端已有 CRUD、上传、下载、删除接口 | 客户端补齐管理界面和统一错误展示，服务端统一租户校验 |
| 文档处理 | 服务端有解析、切块、嵌入和队列代码 | 明确异步任务状态、失败原因和重试接口，不能用同步请求假装完成 |
| 授权 | 已有订阅、部门和知识库授权关系 | 两端统一“订阅/部门交集、多条授权并集”的语义，并在撤销后立即生效 |
| 检索 | 已有关键词、向量、混合检索入口 | 客户端只发送精炼问题，服务端返回实际策略和来源标识 |
| 员工执行接入 | 客户端已有平台 API 包装，但运行时尚未完整接入 | 在本地 Pi 员工执行前调用检索，并控制上下文大小、来源和权限 |
| 资料来源展示 | 检索结果有 `source` 字段，但文档名、版本、页码不完整 | 服务端补充可展示元数据；客户端区分候选来源和实际引用 |
| 运维统计 | 服务端已有部分状态和统计接口 | 统一“请求次数、每知识库命中次数、失败次数”的统计口径 |
| 失败恢复 | 上传队列有有限重试，部分重处理直接同步执行 | 所有耗时任务统一进入队列，写操作支持幂等，客户端支持安全重试 |

## 4. 权限和数据安全

### 4.1 有效授权规则

以下是目标授权规则，不表示现有每个接口都已一致实现。服务端需要统一授权入口，并区分管理权限、员工检索权限和原文下载权限；拥有检索权不自动拥有管理或原文下载权：

1. 当前用户属于目标企业，订阅属于同一企业且处于有效期内。
2. 用户与订阅存在有效成员关系，或用户所在部门满足订阅授权要求。
3. 知识库授权记录匹配当前订阅和部门。订阅级授权适用于该订阅；部门级授权只适用于匹配部门。
4. 当前代码允许 `subscriptionId` 为空的部门授权。是否继续保留这种“部门直接授权”需要双方确认；在确认前，接口文档必须明确它不是客户端自行推断的默认权限。
5. 多条有效授权记录按并集处理；一条授权过期或被删除后，不能继续依赖旧缓存访问。

员工和部门同时出现在授权条件时，应按交集理解：用户必须属于该员工可用的订阅范围，并且部门匹配。不同授权记录之间取并集。

### 4.2 客户端职责

- 只展示服务端返回的可管理或可使用范围，不复制 ACL 规则。
- 所有请求从主进程平台 API 层发出，响应在边界进行结构校验。
- 用户切换员工、恢复历史会话、重新执行节点或重试检索时，都重新请求或确认知识权限。
- 不在日志中记录完整文档内容、访问令牌或刷新令牌。
- 下载文件时使用经过认证的主进程请求，不能依赖 `window.open` 自动携带 Bearer 令牌。

### 4.3 会话切换和撤销

当前本地 Pi 会话可能是共享会话，切换员工或恢复任务时可能残留之前注入的资料。客户端需要在员工切换、任务恢复、权限撤销后的下一次执行前重新构造知识上下文；服务端也必须在每次检索和下载时重新授权。已经返回给模型的历史文本不能通过 ACL 撤回，因此平台端与客户端需要共同决定：撤销后是否允许继续查看历史回答、是否清理本地来源缓存，以及敏感资料是否禁止进入跨员工的下游节点。

## 5. 功能一：知识库管理

### 用户功能

管理员创建、查看、修改和删除知识库，设置名称、描述和使用范围。普通用户只能看到平台端判定为可访问的知识库或员工可用的知识能力，不应通过修改请求参数绕过权限。

### 客户端实现

- 在渲染层提供列表、详情、编辑和删除操作。
- 通过 preload/controller 发送结构化参数，不让渲染层直接访问 `fetch`、令牌或 Node API。
- controller 校验 ID、字符串长度和枚举；service 负责用例编排；`platform-api` 负责调用服务端。
- 删除前显示影响范围，删除后的服务端错误以可操作的状态展示；不要在客户端先假设删除成功。
- 管理界面可以与平台 Web 并存，数据源始终是同一组服务端接口。

### 服务端实现

- 保存企业归属、名称、描述、创建者、更新时间和版本信息。
- 对所有读写接口执行企业隔离和角色授权；不能只在 Web 页面做权限控制。
- 删除时明确是软删除、级联删除文档，还是保留历史引用；返回稳定错误码。
- 对重复提交、并发修改提供版本或 `updatedAt` 检查，避免后保存的客户端覆盖管理员刚才的修改。

### 协作流程

1. 客户端请求列表或详情。
2. 服务端校验身份、企业和权限后返回元数据。
3. 客户端提交创建或修改。
4. 服务端校验并持久化，返回最新版本；客户端以返回值更新界面。
5. 删除成功后，服务端使相关检索和下载立即不可用，并返回清理状态。

### 验收标准

- 不同企业无法通过 ID 读取或修改彼此的知识库。
- 页面刷新后数据与平台 Web 一致。
- 网络超时重试不会产生重复知识库。
- 删除、无权限、并发冲突和服务不可用可以被客户端区分显示。

## 6. 功能二：文件上传与处理

### 用户功能

管理员选择公司制度、产品手册等文件，查看上传及处理状态；失败后查看原因并重试。上传和后台处理是两个阶段，不能只显示一个持续转圈的“上传中”。

### 客户端实现

- 渲染层提供文件选择、文件列表、取消上传、失败重试；文件读取和网络上传由主进程完成。本地文件路径不能直接当作服务端文件地址。
- 提交前根据服务端公布的格式和大小限制校验；当前接口使用 multipart 字段 `file`，单文件限制为 `10 * 1024 * 1024` 字节。服务端仍须再次校验，客户端检查不替代安全检查。
- 上传中显示传输状态；只有上传实现可以获得已发送字节时才展示真实百分比，否则使用不确定进度，不伪造进度。
- 收到文档 ID 后显示“等待处理/处理中/可使用/处理失败”，通过状态接口刷新。建议可见页面从 2 秒间隔开始轮询，逐渐退避至 10 秒；终态、页面关闭或登出后停止。
- 用户取消传输不等于撤销已接收的文档。请求结果不明时先查询接收结果，避免重复上传；删除服务端文档需要单独确认。

### 服务端实现

- 校验身份、管理权、文件大小及真实类型，安全生成存储路径，不信任文件名或 MIME 声明。原始文件保存到受保护存储，不提供绕过权限的公开下载地址。
- 上传请求完成文件接收和记录创建后返回，不在同一 HTTP 请求内等待 OCR、Embedding 全部结束。
- 队列负责解析、清洗、切块、向量化、索引写入，保存状态、阶段、错误码、处理版本和时间；重启后能恢复或判定失效任务。
- TXT、Markdown、DOCX、PDF、图片等按真实解析器和部署环境声明支持范围。调研已指出 PDF 依赖调用不兼容；老版 `.doc`、扫描 PDF、复杂表格和 OCR 效果不能仅依据上传扩展名就宣称支持。
- 区分“文本可检索”和“向量索引就绪”。现有 `READY` 不能独自表达所有索引能力，目标响应需补充就绪与降级信息，避免用户误以为混合检索一定可用。

### 双方配合与验收

上传返回 `documentId` 和处理状态；服务端补齐异步任务标识后，客户端按任务查询进度。文件接收失败由客户端重新上传；文件已接收但解析失败，调用重处理接口，不重新上传同一份文件。以真实文件验收正常处理、超限、损坏文件、解析器不可用、断网、重启恢复和重复点击。

## 7. 功能三：手工知识录入与修改

### 用户功能

管理员直接录入一条制度、FAQ 或业务说明，填写标题、正文和标签，随后编辑或删除；列表需要区分“手工录入”和“文件解析生成”。

### 客户端实现

- 提供文本编辑、保存状态、标签和错误展示；字段限制以双方统一 DTO 为准，不额外维护一套不同的限制。
- 保存失败时保留未提交草稿并标记“未保存”，不得显示为已发布，也不得把本地草稿注入员工的正式知识上下文。
- 保存成功不直接等同于向量更新成功。分别显示内容已保存、索引处理中、可检索或索引失败。
- 文件解析生成的片段默认只读；修改原文件走替换/重新上传，不能让手工编辑被下一次重处理悄悄覆盖。确需编辑生成片段时，先定义覆盖规则。

### 服务端实现与双方配合

文本更新和索引更新使用版本关联：新内容版本提交后，旧向量不得继续被当作新内容的正确索引。可以保留明确标注的上一已发布版本直到新版本发布，或者立即停止旧向量并仅提供新文本的关键词检索；两种策略必须选定并在响应中体现，不能无提示混用。删除同时使文本、向量与缓存不可检索。并发修改返回冲突，客户端提示重新载入或保留草稿，不静默覆盖。

验收必须覆盖“内容更新成功但 Embedding 失败”，确认不会用旧向量错误匹配新内容；重试成功后内容版本与索引版本一致。

## 8. 功能四：员工和部门授权配置

### 用户功能

管理员在知识库详情中选择可使用它的员工雇佣关系及部门，也可从员工授权页面关联知识库。普通成员看到的是自己使用该员工时的有效知识范围，不是平台所有知识库。

### 实现与协作

| 环节 | 客户端/平台 Web | 服务端 |
| --- | --- | --- |
| 获取配置对象 | 请求可管理的员工订阅、部门及已有授权 | 只返回当前企业与当前管理员有权配置的对象 |
| 创建授权 | 提交 `subscriptionId`、可选 `departmentId`，展示范围含义 | 验证对象归属、角色和重复授权；同条条件取交集，不同条取并集 |
| 获取员工有效范围 | 使用当前员工的订阅 ID 请求，不把员工模板 ID 当订阅 ID | 基于用户、企业、部门、订阅有效期计算有效范围 |
| 撤销授权 | 服务端确认后刷新界面和本地展示缓存 | 立即让新检索、读取和下载遵循新权限，清理权限相关缓存 |
| 历史与切换 | 切换员工或恢复会话前重新确认权限 | 不把客户端之前的授权列表作为有效凭证 |

当前订阅授权列表与正式检索的过滤条件需要统一核对，尤其是部门限制、部门直接授权和过期条件。**授权列表只用于展示，正式检索必须再次授权；客户端不能依据“列表非空”直接放行，也不能依据过滤不完整的列表跳过实际可用知识。**

验收使用不同企业、不同部门、过期订阅、撤销授权和伪造订阅 ID；管理员测试检索成功不代表普通成员具有相同权限。

## 9. 功能五：检索服务与管理员测试

### 服务端负责的检索链路

```text
身份与企业校验 → 订阅/部门有效授权 → 限定知识库与有效版本
    → 关键词/向量/混合检索 → 排序与去重 → 来源和执行状态返回
```

- 在检索数据库层或进入候选集前施加企业及知识库过滤，不能先跨企业召回再把无权限内容交给模型过滤。
- `auto` 是服务端策略选择；响应返回实际执行的 `lexical`、`vector` 或 `hybrid`，以及降级原因。
- 关键词分数、向量相似度、混合排序分数不是同一量纲。统一说明 `scoreThreshold` 对各策略的含义，不能把分数展示为“答案正确率”。
- 明确结果去重、相同内容不同版本、同一文档多片段和零结果处理。仅索引已发布的有效内容。
- Embedding 或向量服务不可用时，只有在关键词检索有效且权限正常时才能降级，并明确标记；不能把基础设施故障伪装成“没有资料”。

### 管理员测试功能

客户端和平台 Web 提供问题输入、检索策略、条数、阈值、结果片段、来源、实际策略和耗时。测试入口与正式员工检索复用同一检索核心；若测试使用管理员权限，需要明显标记“管理员测试”，不能用它证明员工授权已配置正确。

当前测试 DTO 存在 `useRerank` 字段，但调研指出其执行效果需要核验。未实际实现前不开放成可用开关。测试和正式接口的阈值默认值当前不同，界面需要显示实际参数，不能在同一个默认设置名称下掩盖差异。

### 结果状态约定（待开发，不是当前字段声明）

| 状态 | 含义 | 用户处理 |
| --- | --- | --- |
| 有结果 | 找到允许使用的资料 | 员工读取参考并回答，显示来源 |
| 无匹配 | 检索正常完成，但没有符合条件的内容 | 调整问题或请管理员补充资料 |
| 无知识授权 | 员工尚未获授权，或当前成员不满足范围 | 联系管理员配置；不泄露无权知识库名称 |
| 资料处理中 | 相关授权范围存在，但资料尚未可检索 | 等待处理或查看失败原因 |
| 已降级 | 例如向量不可用，实际使用关键词检索 | 可继续，但提示检索能力受限 |
| 服务失败 | 网络、数据库或检索服务失败 | 有限重试，失败后保留问题并展示恢复入口 |

现有响应不足以可靠区分所有状态。需要由服务端增加明确状态/错误码，客户端不通过猜测空数组来区分。

## 10. 功能六：员工对话使用知识库

### 用户功能

普通成员选择员工后直接提问，不必手动选择检索策略或复制公司资料。系统按该员工授权自动找参考；回答可以查看实际使用的来源。

### 客户端实现链路

1. 确定当前用户、企业、员工订阅和会话；员工职责判断仍以员工身份信息为依据，不能用知识库内容扩大员工职责。
2. 从本轮问题及必要的追问指代生成精炼查询，例如把“那住宿呢”整理成“公司出差住宿报销标准”；不把整个聊天记录、令牌或无关敏感信息发给检索接口。
3. 通过 service 和平台 API 调用授权检索。授权列表可用于界面展示，但不能替代这次检索请求的服务端授权。
4. 对返回结果去重并控制片段数量和总 token 预算，预算需要给系统提示词、对话和输出预留空间。查询遵守当前 1000 字符上限，不能无提示截断而改变问题含义。
5. runtime 将结果作为本轮有来源标识的参考资料加入 Pi 上下文，不将它们作为系统指令。资料中的“忽略职责/发送密钥/调用工具”等文字不得成为执行命令。
6. 运行员工会话，收集本轮实际引用标识，渲染回答和来源；对引用 ID 做白名单校验，未知 ID 不显示为可信来源。
7. 下一轮追问按新问题重新检索；不能永久沿用第一次检索结果，特别是在员工、企业、授权和资料版本变化后。

### 服务端配合

服务端只提供被授权的检索资料、状态和来源；本地 Pi 会话由客户端运行，不要求服务端再替客户端生成一次答案。平台 Web 自身的员工聊天可以保留其现有服务端执行链路，但两条链路复用同一权限与检索规则，避免重复检索或双重注入。

### 失败时怎么回答

企业专属制度、金额、流程等必须依赖公司资料的问题，无匹配或检索失败时应明确说明无法确认，不以模型常识冒充公司规定。一般知识问题可按员工职责继续回答，但应说明未取得公司知识依据。用户点击重试默认只重试检索；若回答已经生成，再次生成是显式操作，不重复执行有副作用的工具。

### 验收标准

对话不要求用户手工触发检索；追问能关联主题；切换员工后不继承越权资料；恶意文档不能更改系统职责；引用来源来自本轮有效结果。管理员在平台更新资料后，客户端下一轮能按约定版本策略获得最新有效内容。

## 11. 功能七：自动编排中的知识使用

### 用户功能与原则

用户仍然提交任务、确认员工安排并查看各节点结果。知识库在员工执行过程中自动使用，不额外让用户雇佣“知识库员工”，也不生成“搜索知识库”这种必须匹配员工的节点。

### 客户端实现

1. 编排阶段继续按工作职责拆解任务并匹配员工，不把知识检索当成独立职责。
2. 节点执行前，以该节点选中的员工订阅、节点目标和必要上游结果构造查询，不把其他节点的全部上下文一起检索。
3. 每个节点独立进行授权检索，把结果绑定到 `runId`、`nodeId`、员工和本次执行，不复用另一个员工的资料缓存。
4. 把参考资料交给该员工 runtime，当前节点职责和原有员工系统提示词保持有效。
5. 在节点详情中展示检索状态、实际引用和错误。任务取消、重试或改派员工后，旧请求即使返回也不能写入新执行。
6. 明确依赖公司知识的节点在检索失败后进入可恢复的失败/等待状态；不静默跳过后把整个任务标记成功。已有调度状态不支持时，需要扩展状态与恢复操作，不仅增加提示语。

### 服务端配合和数据传播

服务端使用与直接对话相同的授权检索接口，不需要再实现客户端编排调度器。上游回答含有敏感知识时，**“下游员工无权检索原文”不代表它自动有权阅读上游摘录**；客户端与平台端需确认跨节点传播规则。未确认前，不自动向其他员工传播原文片段；敏感任务的输出传播也应按策略限制或阻断。

重试知识检索不等于重跑整个节点。节点已发送邮件、写文件或调用外部业务接口时，不得因检索重试而重复这些副作用。来源记录和节点执行结果一起保存。

## 12. 功能八：来源、原文下载与历史记录

### 用户功能

用户在回答旁看到“引用资料”，可展开对应片段、文档名和定位信息；有下载权限时下载原文。历史回答保留当时使用的版本说明，不把旧回答显示成依据最新制度生成。

### 双方实现

| 能力 | 客户端/平台 Web | 服务端 |
| --- | --- | --- |
| 来源展示 | 为本轮候选分配稳定标识，校验模型输出引用 ID；区分候选与实际引用 | 返回稳定 `chunkId`、知识库 ID、原文 ID、内容版本和可用定位元数据 |
| 实际引用 | 只展示模型明确引用的有效 ID；这不等于已经验证答案与资料一致 | 保证引用指向返回时的版本；需要更强保证时增加引用内容校验 |
| 查看片段 | 通过已认证请求复核权限；无权时不展开本地旧片段 | 每次读取重新校验，返回权限不足、删除或版本变化状态 |
| 下载原文 | 主进程认证下载，安全选择保存路径；Web 用现有认证下载封装 | 流式返回文件或签发短期、受限下载凭证，校验独立下载权限 |
| 历史恢复 | 恢复来源 ID/版本，不未经检查就把旧原文再次注入模型 | 提供当前可访问性；历史保留策略按企业要求执行 |

当前检索结果只有 `content`、`source`、`score`、`knowledgeBaseId`、`chunkId` 等信息，不足以可靠打开原文并定位。文档名、`documentId`、版本、页码/段落/工作表定位为待补字段；不适用时可为空，不能由模型编造页码。

下载原文和查看引用的授权必须分别定义。撤销不能让用户“忘记”已读信息，也不能自动从外部模型历史撤回已发送文本；这类限制需要在企业数据策略中明确。

## 13. 功能九：重处理、重建索引与后台任务

### 服务端实现

- 上传后处理、单文档重处理、批量重处理、知识库重建索引统一进入后台任务系统，不让 HTTP 请求等完整处理链路。
- 用文档/知识库 ID、源版本和任务类型去重。重复点击返回已有任务，不并发重建同一版本。
- 对临时故障有限退避重试；不支持格式、损坏文件、参数错误等确定性故障直接失败。记录可重试性和脱敏错误，不把内部堆栈暴露给用户。
- 构建新索引与发布有效版本分离，不能先删除所有旧索引再等待一次不确定的新建过程；失败保留可用旧版本或明确停止服务，按选定发布策略处理。
- 任务记录包括目标对象、版本、状态、重试次数、时间和结果。建议任务状态为 `queued/running/succeeded/failed/cancelled`，这是待实现任务契约，不替代当前文档状态枚举。
- 删除文档时，运行中的旧任务不得把已删除内容重新写回索引；发布前复核目标存在、版本及有效性。

### 客户端/平台 Web 实现

提供“重试处理”“批量重试”“重建索引”入口、执行范围确认和任务进度。重建与重处理不等同于重新上传。接收任务后允许关闭页面，下次进入继续查询状态；取消本地轮询不等于取消服务端任务，只有服务端明确支持取消时才提供“取消任务”。

### 默认重试建议（需联调确认参数）

| 场景 | 谁重试 | 默认建议与限制 |
| --- | --- | --- |
| 查询/状态读取临时网络失败 | 主进程 API/service | 最多额外重试 2 次，指数退避加抖动，受总体截止时间约束 |
| `429/503` | 调用方 | 遵循 `Retry-After`，不超过总体重试预算 |
| 文档处理依赖临时失败 | 服务端队列 | 最多额外重试 2 次，结束后标记失败并允许人工重试 |
| 上传/创建请求结果不明 | 客户端与服务端配合 | 先查幂等结果；无幂等支持时不盲目自动重放 |
| 参数错误、无权限、损坏文件 | 不自动重试 | 提示修正参数、联系管理员或更换文件 |
| 重建/重处理 | 服务端去重 | 同目标、同版本复用任务，避免客户端和服务端叠加放大次数 |

客户端不重试整个员工执行来补救知识接口故障。所有重试上限、超时和取消行为必须可观测，不能无限转圈。

## 14. 功能十：统计、通知与运维

### 服务端负责

处理成功率、失败类型、队列积压、解析耗时、Embedding 和向量服务健康、检索延迟与零结果率由服务端统计；客户端不通过本地点击量推算全公司指标。正式请求数、测试请求数、每知识库命中次数分别统计，一次跨库查询不能在总请求数中重复计算。

日志关联 `requestId`、任务 ID、知识库/文档 ID 和内容版本，不默认保存完整问题与片段；若确需问题样本分析，要有脱敏、访问范围和保留期限。处理最终失败可通过平台现有通知体系通知企业知识库管理员；基础设施异常再交由平台运维告警，不把每次短暂重试失败都群发。

### 客户端/平台 Web 负责

展示真实处理状态、错误原因、最近更新时间、有效索引版本和重试入口；平台 Web 提供企业管理员与平台运维各自权限范围的分析页面。通知只是提醒，重新进入详情必须请求最新状态。通知连接故障不阻断知识查询，也不触发全局登出。

## 15. 通用规则：认证、错误、超时与取消

- 所有桌面请求通过主进程统一平台 API 封装；需要可信 `Origin` 的接口使用与现有安全配置一致的来源值，不从渲染进程任意接收，不通过关闭服务端校验规避。
- Access Token 过期按现有会话机制刷新，多个请求共享刷新过程；刷新成功后只有限重放原请求。副作用写入重放仍需幂等保障。
- 网络超时、DNS、代理、连接拒绝、服务端 `5xx`、知识权限不足，以及来源校验失败不应直接当作 Refresh Token 失效。只有认证服务明确确认登录会话无法恢复（如刷新令牌过期、被撤销，或账号会话失效）才要求重新登录。
- 服务端应区分认证失效、权限不足和来源错误。客户端不因任意 `401` 无限刷新，也不把第二次业务接口报错直接当作必须登出。
- 主进程为检索、上传和状态请求设置可配置超时及总体截止时间。后台处理依靠任务状态，不通过无限增加 HTTP 超时解决。
- 用户取消、切换企业/员工、退出页面或重新执行时终止对应请求与轮询；使用执行标识丢弃迟到响应，不能把旧企业或旧员工资料写入当前会话。
- 对用户显示可操作错误和 `requestId`；日志记录经过脱敏的底层原因和错误码，不记录令牌、原始文件路径或完整知识内容。

### 建议错误语义（名称需沿用双方既有规范）

| 类别 | HTTP/业务状态建议 | 客户端行为 |
| --- | --- | --- |
| 参数不合法 | `400` + 字段错误 | 保留输入并定位字段 |
| 登录态无效 | `401` + 明确认证错误 | 按会话机制尝试恢复，确认不可恢复后重新登录 |
| 权限/订阅范围不足 | `403` + 范围错误 | 不重试刷新；提示联系管理员 |
| 来源校验失败 | 独立来源错误码，建议 `403` | 配置排查，不触发登出 |
| 对象不存在或已删除 | `404` | 更新列表，保留历史回答的失效提示 |
| 版本冲突/任务冲突 | `409` | 刷新版本或查询已有任务 |
| 文件过大 | `413` | 更换文件，不重复上传 |
| 限流 | `429` | 按等待时间有限重试 |
| 服务暂不可用 | `503` | 显示恢复入口，有限退避 |
| 无匹配、正常降级 | 成功响应中的明确结果状态 | 不伪装成服务器错误 |

这张表是目标契约，不代表当前所有接口已使用这些状态码。错误响应格式沿用平台现有 envelope，新增稳定业务码和关联 ID，不另造一套客户端专用协议。

## 16. 现有 API 与需要补齐的契约

以下路径是控制器相对路径，实际基础地址及统一前缀沿用平台配置，不能在客户端再硬编码一套。存在路由不代表其权限、任务或失败行为已满足本文要求。

| 功能 | 当前已有路由 | 客户端使用方式 |
| --- | --- | --- |
| 列表/创建 | `GET/POST /knowledge-bases` | 管理入口 |
| 详情/修改/删除 | `GET/PATCH/DELETE /knowledge-bases/:id` | 管理详情与编辑 |
| 重建索引 | `POST /knowledge-bases/:id/reindex` | 返回异步任务的行为需要统一 |
| 授权列表/创建 | `GET/POST /knowledge-bases/:id/grants` | 管理员配置 |
| 员工授权范围 | `GET /knowledge-bases/grants/by-subscription/:subscriptionId` | 当前员工范围展示，需要与检索有效授权一致 |
| 撤销授权 | `DELETE /knowledge-bases/grants/:grantId` | 撤销后刷新 |
| 上传 | `POST /knowledge-bases/:knowledgeBaseId/documents/upload` | multipart `file` |
| 文档列表 | `GET /knowledge-bases/:knowledgeBaseId/documents` | 上传记录与管理 |
| 文档详情/删除 | `GET/DELETE /knowledge-bases/:knowledgeBaseId/documents/:id` | 查看状态、删除 |
| 下载原文 | `GET /knowledge-bases/:knowledgeBaseId/documents/:id/download` | 认证下载，不裸用 `window.open` |
| 单文档重处理 | `POST /knowledge-bases/:knowledgeBaseId/documents/:id/reprocess` | 统一异步与去重 |
| 文本列表/创建 | `GET/POST /knowledge-bases/:knowledgeBaseId/chunks` | 手工知识与生成片段区分展示 |
| 文本详情/修改/删除 | `GET/PATCH/DELETE /knowledge-bases/:knowledgeBaseId/chunks/:id` | 按来源类型控制编辑能力 |
| 管理员测试 | `POST /knowledge-bases/:id/test-search` | 不当作普通成员授权验收 |
| 文档状态汇总 | `GET /knowledge-bases/:id/documents/status` | 状态刷新 |
| 批量重处理 | `POST /knowledge-bases/:id/documents/batch-reprocess` | 批量任务 |
| 统计 | `GET /knowledge-bases/:id/analytics?days=30` | 按统一口径展示 |
| 员工正式检索 | `POST /knowledge-bases/search` | 使用当前员工订阅，不接受任意跨企业知识库 ID |

### 当前正式检索结构

```ts
type SearchRequest = {
  query: string // 1–1000 字符
  subscriptionId: string // 有效雇佣关系 ID，cuid，不是员工模板 ID
  topK?: number // 整数 1–20，默认 5
  scoreThreshold?: number // 0–1，默认 0.7
  strategy?: 'auto' | 'lexical' | 'vector' | 'hybrid'
}

type SearchResponse = {
  query: string
  subscriptionId: string
  strategy: 'lexical' | 'vector' | 'hybrid' // 目标语义：实际执行策略
  durationMs: number
  count: number
  results: Array<{
    chunkId: string
    knowledgeBaseId: string
    source: string
    score: number
    content: string
  }>
}
```

这是当前业务结构的整理，不是可直接复制的共享 SDK。客户端现有类型仍允许响应 `strategy` 为 `auto`，双方需要收紧为实际策略，并验证运行时返回；结构校验不能只依赖 TypeScript 声明。管理员测试的 `scoreThreshold` 默认值当前为 `0.5`，与正式接口不同。

### 需要补齐，不能当作已存在接口使用

1. 异步任务查询契约：处理/重建响应返回 `jobId`，任务查询返回目标、阶段、状态、错误和重试信息。具体路由需由服务端按现有任务体系确定，本文不虚构已实现路由。
2. 明确结果状态：无授权、无匹配、未就绪、降级与服务失败可区分；正常业务零结果与真正拒绝访问语义一致。
3. 来源元数据：文档 ID、名称、内容/索引版本和可用定位信息；检索权限不直接意味着可下载。
4. 幂等与并发：创建/上传/重处理的幂等键，修改版本检查；幂等记录绑定企业、用户、操作和请求摘要，过期策略明确。
5. 列表契约：分页、筛选、排序、上限及总数/游标，禁止全量列表无上限增长。
6. 能力与就绪：可上传格式、大小、OCR 可用性、文本/向量就绪、实际降级原因。可使用独立配置接口或扩展详情，最终形式需要确认。
7. 所有新增字段、错误码和响应 envelope 纳入平台 OpenAPI/共享 DTO；客户端同步运行时校验和对应测试。

## 17. 数据与状态一致性约定

| 对象 | 服务端权威信息 | 客户端保存范围 |
| --- | --- | --- |
| 知识库 | 企业、元数据、版本、删除状态 | 界面缓存，不用作授权依据 |
| 文档 | 原文件、处理状态、源版本、文本/索引就绪 | ID、展示状态和必要元数据 |
| 片段 | 内容、来源、版本、有效索引 | 当前执行需要的片段；持久化必须符合敏感数据策略 |
| 授权 | 订阅、部门、有效条件及撤销状态 | 短时展示缓存，正式请求再授权 |
| 后台任务 | 目标版本、执行状态、重试次数和错误 | 任务 ID 与展示缓存 |
| 员工引用 | 稳定来源 ID、当时版本及当前可访问性 | 绑定会话/节点的实际引用记录，不默认保存无限量原文 |

文件状态沿用当前 `PENDING/PROCESSING/READY/FAILED`；任务状态、索引就绪、内容发布状态分开表达，不让一个 `READY` 同时表示文件解析、文本发布、向量健康及模型可正确回答。缓存至少按企业、用户、订阅和版本隔离；登出、切换企业或员工时清理相应上下文。

## 18. 按代码层拆分开发工作

### 桌面客户端

| 层 | 开发内容 | 禁止事项 |
| --- | --- | --- |
| React renderer | 知识库管理、上传状态、授权入口、检索测试、引用与失败恢复 UI | 不直接请求平台、不接触令牌、不读写任意本地文件 |
| preload | 暴露最小类型化管理/查询操作与状态订阅 | 不暴露通用 HTTP、任意路径或令牌 API |
| controller | IPC 注册、Zod 输入校验、标准响应 envelope | 不编排 Pi SDK 或直接处理索引 |
| service | 管理、上传、授权、检索用例和会话协调 | 不引用 Pi SDK，不拼本地持久化路径 |
| platform API | 认证请求、必要来源头、超时/取消、响应校验、错误映射 | 不把访问/刷新令牌返回 renderer |
| data/文件适配层 | 草稿与来源元数据持久化、安全上传/下载文件访问 | 不自行建立正式向量库，不以缓存授予权限 |
| runtime | 员工/节点执行前检索协调、参考上下文预算、引用关联、迟到结果隔离 | 不把知识能力变成员工，不跨员工复用敏感上下文 |
| pi/sdk 适配层 | 通过既有适配边界将本轮资料交给 Pi；验证恢复会话行为 | 不升级 SDK 或绕开现有动态加载边界 |

客户端已有 `getKnowledgeBaseGrants`、`searchKnowledgeBases` 包装，可在现有平台 API 基础上扩展，不需要新增一套网络客户端。Pi 仅由 runtime 经现有适配边界接触。

### 服务端和平台 Web

| 模块 | 开发内容 | 与客户端配合 |
| --- | --- | --- |
| Controller/共享 DTO | 输入、鉴权、分页、错误与 OpenAPI | 提供可验证接口合同与样例 |
| 知识管理 service | 租户、角色、元数据、删除和版本冲突 | 统一桌面与 Web 的数据源 |
| 授权 service | 订阅/部门有效授权、读取/下载/管理分权 | 列表与检索语义一致 |
| 文档处理与队列 | 文件存储、解析/OCR、切块、向量化、有限重试 | 返回稳定文档/任务状态，不依赖客户端常驻 |
| 检索/向量模块 | 权限范围内召回、实际策略、降级与版本过滤 | 返回可解释状态、来源及耗时 |
| 数据库/存储 | 内容、索引、授权、任务、审计和保留策略 | 删除与更新后不留下可继续访问的旧索引 |
| 平台 Web | 企业管理、授权、测试检索、状态、统计和运维入口 | 不在 Web 重写解析或权限逻辑；复用相同 API |
| 运维 | 解析依赖、OCR 语言包、Embedding、向量数据库、队列和监控 | 交付真实就绪检查、错误码和联调环境 |

平台 Web 的企业管理页面与平台运营页面权限不同；不能因为都属于“平台端”就让运营人员默认读取全部企业原文。

## 19. 最终用户使用流程

本节描述开发完成后的目标体验，不表示当前客户端已经提供所有页面。管理员负责准备和授权资料，普通成员直接使用员工；普通成员不需要理解切块、Embedding、向量或检索参数。

### 19.1 谁在哪里操作

| 用户角色 | 入口 | 主要操作 |
| --- | --- | --- |
| 企业知识库管理员 | 桌面客户端“知识库”或平台 Web 企业知识库页面 | 建库、上传/录入、看处理状态、授权、测试、维护 |
| 普通成员 | 桌面客户端员工对话或自动编排 | 提需求、看回答与来源、追问、重试、联系管理员 |
| 平台运维/公司后台管理员 | 各自被授权的后台状态与运维页面 | 看失败任务、依赖服务和脱敏日志，修复环境并重试 |

桌面和 Web 管理入口操作同一份服务端数据，不需要上传两次。管理员角色由服务端判定，普通成员不能因为桌面有按钮就获得管理权。

### 19.2 管理员首次建立“公司报销制度”知识库

| 用户动作 | 客户端行为 | 服务端/平台行为 |
| --- | --- | --- |
| 1. 管理员进入知识库，点击新建，填写“公司报销制度”和说明 | 校验输入并提交；成功后打开详情 | 验证企业管理权限并创建知识库，返回 ID 和版本 |
| 2. 上传《差旅报销制度.pdf》 | 显示上传状态；接收成功后显示“等待处理”而非“已可使用” | 保存文件和文档记录，提交后台处理任务 |
| 3. 等待处理 | 展示“处理中”，按实际返回显示阶段；可离开页面后再查看 | 解析、切块、建立索引，保存结果或明确失败原因 |
| 4. 如果处理失败，查看原因并处理 | 文件损坏提示重新上传；临时依赖故障提供“重试处理”，不要求重复上传 | 对已接收文件重新排队；服务配置问题交管理员/运维修复 |
| 5. 看到“可使用”；若仅关键词就绪，看到能力受限提示 | 显示实际就绪状态，不让用户猜 `READY` 的含义 | 返回文本和向量的真实就绪状态及有效版本 |
| 6. 在授权页选择“财务员工”及适用部门 | 显示员工雇佣关系和部门范围，提交授权并展示保存结果 | 校验关系归属、部门及管理权，创建有效授权 |
| 7. 输入“出差报销需要哪些材料”测试 | 展示命中片段、来源和实际策略；注明是否为管理员权限测试 | 运行检索，返回结果和耗时；测试数据与正式统计区分 |
| 8. 用一个获授权的普通账号选择财务员工验证 | 在正常对话中看到公司资料回答及有效来源 | 重新验证普通成员、订阅、部门和知识库授权 |

**什么时候可以正式使用：** 至少需要资料达到已确认的可检索状态、员工及成员授权有效，并通过一次真实问答验证。仅“上传成功”、仅“管理员测试有结果”或仅“授权保存成功”都不等于整条使用链路可用。

### 19.3 普通成员使用员工回答公司问题

| 用户动作 | 客户端行为 | 服务端/平台行为 |
| --- | --- | --- |
| 1. 选择财务员工，打开对话 | 显示员工身份及可用知识能力，不要求用户选择检索参数 | 提供当前用户对该员工的有效使用范围 |
| 2. 输入“出差报销需要哪些材料”并发送 | 保留用户问题，显示资料查询状态，自动发起当前员工的知识检索 | 按企业、订阅和部门权限检索可用版本 |
| 3. 等待回答 | 把获准片段交给本地员工，并展示生成过程 | 只负责检索和来源，不再替本地 Pi 重复生成回答 |
| 4. 查看回答及“引用资料” | 展示实际引用，不把全部候选都列为依据 | 返回来源 ID、版本和定位元数据 |
| 5. 展开资料或下载原文 | 请求权限复核；只有具备下载权时提供下载 | 重新授权，返回片段/文件或明确拒绝 |
| 6. 追问“那住宿费用的上限呢” | 关联当前主题形成新查询，再检索再回答 | 使用当前权限及有效资料版本检索 |
| 7. 切换到其他员工继续提问 | 切换员工上下文，不把财务员工原文自动带给其他员工 | 对新员工的订阅重新授权 |

用户不需要手动点击“查知识库”。如果问题超出员工职责，仍按员工职责规则拒绝或请求改派；拥有某份知识不代表员工可以承担所有相关工作。

### 19.4 普通成员遇到问题时怎么操作

| 用户看到的情况 | 用户操作 | 客户端与服务端处理 |
| --- | --- | --- |
| “未找到相关公司资料” | 换一种问法，或联系管理员补充资料 | 保留问题；不把正常零结果当网络错误，不编造公司制度 |
| “当前员工没有可用知识授权” | 联系企业管理员配置，或选择已授权且职责匹配的员工 | 不暴露其他部门资料名称，不要求用户重新登录 |
| “资料正在处理” | 稍后重试；管理员可查看处理状态 | 不让普通成员自行重复上传企业原文件 |
| “知识服务暂时不可用” | 在有限自动重试后点击重试，或联系管理员并提供错误编号 | 不清空对话、不直接登出；用 `requestId` 关联排查 |
| “引用已删除或当前无权访问” | 查看历史回答提示，必要时请管理员确认 | 不继续打开本地旧原文，不假装历史答案仍是最新依据 |
| “登录会话已失效” | 重新登录后恢复任务 | 仅在认证机制确认会话不可恢复时出现，不因单次知识请求失败触发 |

### 19.5 用户在自动编排中使用知识库

示例需求：“根据公司制度，整理本次差旅报销材料清单，并形成审核说明。”

| 用户动作 | 客户端行为 | 服务端/平台行为 |
| --- | --- | --- |
| 1. 提交整体需求 | 规划工作节点并匹配承担职责的员工 | 提供现有员工/授权数据；知识库不作为员工候选 |
| 2. 确认员工和节点后启动 | 每个节点执行前按该员工订阅及节点任务查询资料 | 对每次检索独立授权，不因属于同一个任务就共享全部知识 |
| 3. 查看节点进度 | 展示资料查询、执行与输出；不新增需用户雇佣的“知识搜索员工” | 返回各次检索的状态、来源和版本 |
| 4. 查看清单与审核说明 | 在节点结果和最终结果中保留相应实际来源 | 提供来源复核能力；跨节点传播遵循企业策略 |
| 5. 如果节点因资料故障停下，点击恢复/重试 | 只恢复失败环节；改派后重新检索，不重复已经完成的副作用 | 对临时故障恢复服务；授权问题由管理员调整 |
| 6. 取消或重新运行任务 | 中止本次请求并丢弃迟到结果；新执行使用新标识 | 请求取消与后台任务取消分别处理，不承诺能撤回已经完成的动作 |

用户不需要先单独运行“知识库步骤”。最终任务成功必须表示必要节点已完成；不能在资料获取失败时显示整个任务成功。

### 19.6 管理员日常更新与故障修复

| 用户动作 | 客户端行为 | 服务端/平台行为 |
| --- | --- | --- |
| 更新一条手工报销规则 | 显示内容保存状态和索引状态；失败保留草稿 | 按版本更新，避免新文本与旧向量错误混用 |
| 更新一份制度文件 | 使用明确的替换/新版本操作；现有接口未支持替换前，明确上传新文件并由管理员处理旧版 | 不静默把同名文件当替换；发布新版本时使旧版按策略失效 |
| 重试处理失败的文档 | 点击单个或批量重试并查看任务状态 | 复用后台队列，去重并有限重试 |
| 重建知识库索引 | 确认范围后查看后台任务 | 构建及发布索引，失败不把半成品当有效版本 |
| 撤销某员工或部门授权 | 显示已撤销，通知相关界面更新 | 立即拒绝后续无权检索/读取/下载；历史按保留策略处理 |
| 查看失败或零结果统计 | 查看状态和错误编号，联系后台管理员 | 用脱敏日志区分文件问题、授权问题和基础设施问题 |
| 运维修复依赖后恢复 | 管理员重新处理相关失败任务，再做实际问答测试 | 验证依赖就绪、任务成功及有效索引发布，不只验证服务进程启动 |

### 19.7 聊天附件与企业知识库的区别

聊天中上传一个附件，默认只用于该会话或该任务，不自动进入企业共享知识库，也不自动授权给其他员工。是否已支持附件上下文能力应以客户端实际功能为准，不能把本节理解为完成声明。

需要长期共享时，用户明确选择“加入知识库”或由管理员在知识库管理页上传；必须具备管理权，选择目标知识库、完成服务端处理并配置授权。聊天附件的上传成功不能替代正式入库成功。没有管理权的成员可按企业流程申请管理员入库，不在客户端绕过授权。

### 19.8 一句话理解完整流程

```text
管理员：建库 → 上传/录入 → 等待可检索 → 授权员工与部门 → 实际验证
普通成员：选员工 → 提问题/提任务 → 自动查获准资料 → 看回答与来源 → 追问
后续维护：改资料/改授权 → 后台处理与发布 → 下次执行按新版本和新权限使用
```

## 20. 联合验收清单

以下是验收要求，尚未在本轮执行，不是通过记录。双方使用同一测试企业、员工订阅、部门和固定资料集，记录请求、来源版本与实际界面结果。

| 验收项 | 客户端需要证明 | 服务端需要证明 |
| --- | --- | --- |
| 完整闭环 | 建库到普通员工问答无需手动搬运资料 | 文件、授权、索引和检索链路有效 |
| 文件格式 | 不支持格式有明确提示 | 真实 TXT/MD/DOCX/PDF/图片样例按声明处理；扫描件单独验收 |
| 状态正确 | 上传与处理分阶段、无无限等待 | 最终成功/失败可查询，重启后不永久卡处理中 |
| 权限隔离 | 切换员工/企业不复用越权上下文 | 跨企业、跨部门、过期/撤销订阅、下载和来源读取均正确拒绝 |
| 授权一致 | 展示范围不误导正式使用 | 授权列表、正式检索与读取采用一致的有效范围 |
| 索引一致 | 更新失败与发布状态可见 | 新内容不搭配旧向量；删除及旧任务不使资料复活 |
| 无匹配/故障 | 不编造公司事实，不误登出 | 区分正常零结果、无授权、未就绪和服务故障 |
| 重试与幂等 | 重复点击、断网重试不重复执行副作用 | 上传/重处理/重建去重，失败恢复有上限 |
| 对话和编排 | 每轮/每节点正确关联来源、取消后无迟到污染 | 每次授权独立，提供稳定来源及版本 |
| 引用与下载 | 实际引用和候选区分，认证下载 | 返回准确元数据、重新授权；伪造来源 ID 不放行 |
| 安全资料 | 文档注入不能越过员工职责或触发高风险工具 | 内容作为数据返回，存储下载受控，日志脱敏 |
| 统计 | 展示真实口径与参数 | 测试/正式、请求/命中分别计算，降级明确 |

至少补充服务端授权/版本/队列单测与接口集成测试、客户端 IPC/响应校验/runtime 注入与取消测试，以及真实桌面到服务端的端到端验证。Embedding 不可用、网络超时、重复请求和会话切换必须纳入故障注入场景。

## 21. 双方需要定下的产品与协议决策

这些是行为边界，不是开发优先级；未定项不能由一端静默假设。

1. 管理角色与入口：桌面和 Web 是否都开放全部管理操作；原文下载是否独立授权。
2. 授权语义：是否保留部门直接授权；员工+部门的交集、多条记录并集、撤销与过期规则一致。
3. 格式能力：实际支持哪些文件、是否包含 OCR/扫描 PDF/复杂表格，服务端如何公布限制。
4. 内容发布：修改后继续使用上一已发布版本，还是立即切换到新文本并显示向量未就绪；文档替换与旧版失效规则。
5. 无匹配和降级：公司制度类问题如何阻止无依据结论；一般问题何时允许不依赖公司资料继续回答。
6. 敏感数据：允许发送到哪些模型服务、历史回答和片段保留多久、撤销后怎么展示、上下游节点怎么传播。
7. 引用约定：片段标识、版本与定位字段、实际引用格式和校验方式，不能只保存自由文本来源名称。
8. 任务和错误合同：异步任务查询、幂等键、并发版本、总体超时、有限重试、稳定错误码和 `requestId`。
