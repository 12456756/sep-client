# 通知模块故障与服务端修复交接

日期：2026-10-10
交接对象：服务端开发、客户端开发、联调人员

## 1. 结论与检查范围

通知连接失败与登录会话失效是两回事，不能因为通知服务重复拒绝请求就直接让用户退出登录。

本次检查基于以下本地源码：

- 客户端：`D:/github/sep-client`。
- 服务端：`D:/github/SEP-main`。
- 服务端通知 WebSocket 路径：`/ws/notifications`。

已确认来源校验、异常分类、心跳格式、批量推送结构存在对接问题；通知 JWT 密钥与登录模块的配置规则也不一致，但是否已造成线上故障，需要核实部署配置。

这是源码检查结论，不代表已复现线上所有故障。未读取实际密钥，也未完成真实账号、数据库和代理环境下的端到端联调。本文只列本次通知问题所需修复，不扩展为全面重构。

## 2. 为什么以前会自动退出登录

旧客户端存在以下路径：

```text
通知鉴权失败
  -> 客户端强制刷新 Access Token
  -> 通知再次鉴权失败
  -> 客户端触发全局登出
```

这里指明确的鉴权拒绝，并不是任何网络错误都会触发上述路径。

服务端又将 Token 验证、未读数数据库查询放在同一个 `try/catch` 中。因此数据库查询失败也可能返回 `Invalid token`，将内部故障误报为鉴权失败。密钥配置不一致也可能导致刷新后的有效 Token 仍被通知连接拒绝。

### 客户端当前已完成的修复

- 通知 HTTP 接口首次返回 `401`：刷新 Access Token 后重试一次；再次返回 `401` 只报告通知服务不可用，不触发全局登出。
- 通知 WebSocket 首次明确拒绝 Token：强制刷新一次；继续拒绝时按 `1、2、4……最多 30 秒` 间隔重连，不持续强制刷新，不登出。
- 网络、心跳超时、来源校验失败：重连，不按登录失效处理。
- Access Token 自然过期仍走正常自动刷新机制。
- 只有取得登录凭据时确认会话失效，例如 Refresh Token 过期、撤销或刷新明确被拒绝，才要求重新登录；刷新网络超时不等于会话失效。
- 重连认证成功后通过 HTTP 重新获取通知数据，补偿断线期间的变化。
- 通知 WebSocket 握手已补充 `Origin`，使用现有 `config.SEP_WEB_ORIGIN`；不将 Token 放入握手请求头或 URL。

对应客户端：`electron/service/notification-service.ts:50`、`electron/common/platform/notification-socket.ts:278`。以上修复在本地，不能据此认定打包发布版本已包含。

## 3. 必须处理的问题

### 3.1 来源校验：需要客户端与服务端配置配合

**现状与影响**

- 服务端配置非空 `CORS_ORIGIN` 后，缺少或不匹配的 `Origin` 会被关闭连接：`1008 / Origin not allowed`。
- 服务端生产启动要求 `CORS_ORIGIN` 非空。
- 修改前客户端主进程使用 Node `ws`，没有发送 `Origin`，按本次检查的生产代码和配置约束会被拒绝。目前已补充 `config.SEP_WEB_ORIGIN`，实际配置仍须与服务端白名单一致。
- 这是来源校验失败，不是 Token 错误，刷新 Token 不能解决。

**分工**

- 服务端人员确认并提供允许的来源值，确认反向代理会将该请求头传递给应用。
- 客户端已补充 `Origin`；联调时确认 `SEP_WEB_ORIGIN` 的实际值在服务端白名单中，不能因为请求头已添加就认定部署配置一定正确。
- 保留服务端来源校验，不以允许所有来源或关闭校验解决。`Origin` 不替代用户身份验证，Token 仍须单独校验。

**位置**：服务端 `backend/src/modules/notifications/notifications.gateway.ts:49`、`backend/src/main.ts:17`；客户端 `electron/common/platform/notification-socket.ts:89`。

### 3.2 区分鉴权错误与数据库等内部错误

**现状与影响**

通知网关中的同一个 `catch` 将 Token 验证失败、未读数查询失败等异常统一关闭为 `1008 / Invalid token`。客户端会误触发 Token 刷新，日志也无法准确定位故障。

**服务端必须修改**

- 将消息格式校验、Token 鉴权、业务数据查询分开处理。
- 只有 Token 缺失、过期、签名无效等真实鉴权问题才返回约定的鉴权错误。
- Token 有效，但数据库查询或内部处理失败时，返回 `1011 / Internal error`，不能返回 `Invalid token`。
- 记录安全的错误阶段与底层原因；不记录原始 Token、刷新凭据或密钥。
- 失败和断开后清理连接登记及认证定时器。

**位置**：`backend/src/modules/notifications/notifications.gateway.ts:58`，尤其是未读数查询 `:67` 和统一异常处理 `:69`。

### 3.3 修正心跳消息路由

**现状与影响**

- 客户端发送 `{type:ping,timestamp:...}`。
- 服务端使用默认 `new WsAdapter(app)`，而默认适配器按 `message.event` 匹配 `@SubscribeMessage('ping')`。
- 网关自己的消息监听器在认证完成后直接返回，不负责处理 `ping`。
- 因此当前协议无法正常进入心跳处理器。即使连接和鉴权成功，客户端也会因收不到 `pong` 超时重连：约 30 秒发心跳，再等待 10 秒。

**服务端必须修改**

- 在通知网关中让已认证连接的 `type: ping` 正确触发心跳回复，保持现有客户端协议。
- 如果采用自定义适配器解析器，将 `type` 映射到 `event`，需检查其他 WebSocket 网关，避免全局修改影响现有协议。
- 首条 `auth` 消息仍由现有认证流程处理；不要把心跳处理改成绕过鉴权的业务入口。
- 回复继续使用 `{type:pong,timestamp:...}`。

**位置**：服务端 `backend/src/main.ts:54`、`backend/src/modules/notifications/notifications.gateway.ts:57` 和 `:95`；客户端 `electron/common/platform/notification-socket.ts:246`。

参考：Nest `v11.1.28` 官方 `packages/platform-ws/adapters/ws-adapter.ts` 中 `bindMessageHandler` 使用 `handlersMap.get(message.event)`。源码地址：

```text
https://github.com/nestjs/nest/blob/v11.1.28/packages/platform-ws/adapters/ws-adapter.ts
```

### 3.4 批量通知推送完整的已保存记录

**现状与影响**

`createBatch` 保存数据后，推送的是创建参数而非数据库生成的完整记录，缺少客户端必需的 `id`、`createdAt`、`read`。客户端结构校验会拒绝该条通知推送。

后续 `unread_count` 事件通常能触发 HTTP 重新拉取，因此不代表数据库中的通知丢失，但单条实时推送已经不符合协议。

**服务端必须修改**

- 批量创建后，取得每位接收人的实际持久化记录，再逐人推送。
- 推送使用真实数据库 ID、时间和已读状态，不能临时生成不对应数据库的 ID。
- 单条创建与批量创建输出相同的通知结构；不要求客户端放宽校验。

**位置**：`backend/src/modules/notifications/notifications.service.ts:61`，不完整推送在 `:67`；客户端校验定义在 `src/shared/notification-contracts.ts:4`。

## 4. JWT 配置规则：必须核实，是否为当前故障取决于配置

登录签发与 REST 验证优先使用 `ACCESS_JWT_SECRET`，不存在时回退 `JWT_SECRET`；通知 WebSocket 只使用 `JWT_SECRET`。

- 若两者实际不同：有效 Access Token 能调用 REST，却无法通过通知鉴权，刷新也无效。必须统一通知的 Access Token 密钥选择规则。
- 若未设置独立密钥或两者相同：不能把它认定为当前连接失败的原因，不需要为解决本次密钥故障更换现有密钥。
- 无论密钥是否相同，通知入口都应遵循 REST 的 Access Token 验证要求：验证有效期、`type === access`、字符串 `sub` 和有效用户状态，不能只验证签名后读取 `sub`。

**位置**：`backend/src/modules/notifications/notifications.module.ts:15`、`backend/src/modules/notifications/notifications.gateway.ts:61`；对照 `backend/src/modules/auth/auth.module.ts:33`、`backend/src/modules/auth/jwt.strategy.ts:17` 和 `:22`。

核实时只报告密钥配置是否一致，不发送实际密钥内容。

## 5. 保持兼容的协议约定

| 场景 | 消息或关闭行为 | 客户端处理 |
| --- | --- | --- |
| 连接打开后认证 | 客户端发送 `{type:auth,token:<access-token>}` | Token 不放在 URL 中 |
| 认证成功 | 服务端发送 `{type:connected,data:{unreadCount:0},timestamp:...}` | 启动心跳并重新拉取通知 |
| 心跳 | 客户端 `type: ping`，服务端 `type: pong` | 收到回复取消心跳超时 |
| 推送通知 | `{type:notification,data:完整通知,timestamp:...}` | 通过结构校验后处理 |
| 未读数变化 | `{type:unread_count,data:{count:0},timestamp:...}` | 更新数量并同步列表 |
| Token 无效 | 保持 `1008 / Invalid token`；缺失为 `1008 / Authentication required` | 首次强制刷新，再失败只重连 |
| 来源不允许 | `1008 / Origin not allowed` | 不强制刷新 Token，不登出 |
| 服务端内部失败 | `1011 / Internal error` | 重连，不强制刷新 Token，不登出 |

客户端也识别 `4401` 为鉴权拒绝，但本次不要求服务端迁移关闭码。若调整协议，应同时检查平台 Web 客户端兼容性。

完整通知 `data` 必须包含：`id`、`type`、`title`、`message`、`read`、`category`、`severity`、`createdAt`。`createdAt` 为带时区的 ISO 时间；其余关联字段按现有接口提供，不改变通知分类和类型枚举。

## 6. 联调验收清单

| 用例 | 必须达到的结果 |
| --- | --- |
| 合法 Origin + 有效 Access Token | 收到 `connected`，可获取列表和未读数 |
| 缺少或非法 Origin | 返回来源拒绝，不触发 Token 刷新或登出 |
| Access Token 过期，Refresh Token 有效 | 刷新后可重新连接，账号保持登录 |
| 通知重复鉴权拒绝，刷新本身成功 | 不全局登出；重连有退避，不陷入强制刷新循环 |
| 有效 Token + 模拟未读数数据库查询失败 | 关闭码为 `1011`，日志能定位数据库阶段，不返回 `Invalid token` |
| 持续连接至少跨越两个心跳周期 | `ping` 能触发 `pong`，不因协议不一致周期性重连 |
| 批量通知给多个用户 | 每人收到各自真实通知 ID 和完整字段，客户端校验通过 |
| 独立 Access Token 密钥配置 | REST 与通知均能验证同一个有效 Access Token |
| 非 Access Token 或无效用户 | 通知认证被拒绝，不能注册为已认证连接 |
| Refresh Token 真正过期或撤销 | 客户端要求重新登录，正常安全机制保留 |

心跳测试必须经过真实 `WsAdapter` 和 WebSocket 连接；仅直接调用 `handlePing` 或用 `EventEmitter` 模拟网关，无法覆盖本次路由问题。当前 `notifications.gateway.spec.ts` 的模拟测试不足以验证这条链路。

本次交接没有修改服务端代码。客户端已补齐 Origin，相关修复与本文一同提交；服务端修复完成并确认来源配置后，再按上述用例联合验收。
