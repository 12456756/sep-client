# SEP 与客户端：技能包校验职责及对齐说明

核对日期：2026-11-05。本文依据本地 `SEP`、`sep-client` 两个仓库的当前工作区源码。SEP 存在未提交改动，本文不代表这些实现均已部署到生产。网页属于 SEP，不另列为第三方。

**SEP 决定授权、正式生效版本和产物能否下发；客户端验证收到的产物并安全安装、加载。不同边界可以重复验证，但同一安装协议的规则不能互相矛盾。**

“当前实现”描述本地工作区代码；“建议”表示后续对齐方向。两边已取消员工安装产物的 20 MiB/500 文件硬限制，客户端也允许归档目录名与技能名不同及多个技能入口。改动尚未部署或发布。

## 1. 当前流程与成功状态

主链路：SEP 上传归一化并存储包 → 创建/审核技能版本 → 绑定员工 → 按订阅解析生效版本 → 返回运行清单 → 客户端下载、校验、安装 → 固定运行快照并加载技能。

| 状态 | 已经证明什么 | 尚不能证明什么 |
| --- | --- | --- |
| 上传成功 | 已通过上传接口的处理，得到了包哈希、正文、文件数和可能的警告 | 已批准、已绑定到目标员工、兼容客户端 |
| 审核通过 | 版本取得业务审核状态 | 当前订阅选中了该版、下载与安装一定成功 |
| 员工绑定成功 | 某个员工 ID 的能力绑定已写入；部分路径还执行了上架检查 | 同名员工或其他订阅也切换了、企业/订阅选版未覆盖默认版本 |
| 客户端安装成功 | 本次选定的产物通过下载与安装校验 | 未来仍有授权、包内脚本业务逻辑一定正确 |

SEP 已有 `EmployeeReadinessService`：在员工上架及已上架员工的相关绑定变更中，复用产物描述服务，检查批准状态、可安装描述符、安装目录重名等。它没有调用客户端完整 ZIP 安装器，也不是某个订阅全部选版覆盖的验收；不能据此宣称客户端一定可运行。

## 2. 两边职责总览

| 环节 | SEP 负责 | 桌面客户端负责 |
| --- | --- | --- |
| 上传 | 网页展示结果，服务端校验实际上传字节，不信任网页声明的大小、正文和哈希 | 若走本机技能导入，扫描并按该功能规则打包、上传 |
| 格式处理 | 将支持的源归档转为 ZIP；必要时补齐元数据并生成安装产物 | 按协议消费 `single-file` 或 `zip`，验证后安装 |
| 业务权限 | 审批、企业归属、订阅访问权、员工绑定、正式版本选择的权威来源 | 核验当前身份与清单一致，不能靠本地目录绕过授权 |
| 运行清单 | 按订阅解析版本，生成合法描述符、正文哈希及受控下载路径 | 核验 manifest、协商结果、技能身份、批准正文哈希 |
| 下载 | 再查授权、绑定和生效版本，返回确切字节与校验响应头 | 限量读取、检查实际长度和哈希，不接受任意跳转或绕过产物接口 |
| 安装、缓存、执行 | 提供目标客户端能够处理的产物 | 安全解析与落盘、复验缓存、固定快照、限制加载目录，处理已有本地个人版本机制 |

两边都检查路径、大小或哈希，是在保护不同的输入边界。冲突来自对同一语义制定不同标准，不是来自“检查了两次”。

## 3. SEP 的现有实现与改进边界

### 3.1 上传和归一化

`SkillPackageService.store()` 接受 ZIP、TAR、TAR.GZ、TGZ，经 `normalizeArchive()` 转成 ZIP，兼容处理路径分隔符后计算存储哈希。检查涉及路径、重复条目、符号链接、本地头与中央目录名称、解压体积、入口及 UTF-8 正文等。

上传后还有静态扫描及审核相关流程。现有静态扫描不执行包内脚本，也不等于病毒库或沙箱检测；有些内容检查只是警告，上传接口完成不能直接理解为整个审核流程通过。

当前包服务把部分问题作为警告保留：缺失或不规范的 frontmatter、多入口、目录与技能名不同、引用资源未找到等。因此，旧文档“格式有问题就一律拒绝上传”的说法不够准确。

`readInstallablePackage()` 会重新读取并校验存储包，必要时补齐兼容元数据或规范选中入口的文件名；它没有普遍移动目录、移除其他技能入口或补齐缺失资源的行为。不能因为显示兼容警告，就认为这些问题均已修复。

建议继续复用包服务与 `prepareSkillMarkdown()` 处理归一化，并对“最终生成的安装产物”补齐目标协议的兼容检查；网页只提示和展示结果，不另写一套修复算法。

### 3.2 版本与绑定

当前 `resolveEffectiveVersion()` 的优先级为：

1. 有效的企业默认版本。
2. 有效的订阅选定版本。
3. 员工绑定的默认版本。
4. 最新已批准平台版本。

候选版本还受能力 ID、审批状态、scope 和企业归属约束。`getRuntime()` 只枚举当前员工已启用、且能力状态为 `APPROVED` 的 SKILL 绑定。

“同一能力更新版本”与“新建另一个能力后重新绑定”是两件事。企业/订阅选版可以覆盖员工默认版，但不能凭空把能力 A 变成能力 B。排查应核对 `subscriptionId → employeeId → capabilityId → effectiveVersionId`，不能只比较名称或 `1.0.0` 等展示版本号。

建议后台在已有绑定信息旁展示目标员工/订阅 ID、实际生效版本及选择来源，保存后重新读取。不新增第二套优先级，也不靠清客户端缓存解决服务端绑定错误。

### 3.3 运行时与下载

客户端当前请求 `skillArtifactProtocolVersion=1`。SEP 的 `getRuntime()` 对各技能调用 `ClientSkillArtifactService.describe()`，返回正文及 `AVAILABLE` 或 `BLOCKED` 描述符。

产物服务验证包存储身份、包正文与批准版本是否一致，并通过服务端 schema 校验描述符。原先与客户端不同的 20 MiB/500 文件安装预算已移除；字节数、文件数仍须为正的 JavaScript 安全整数。

下载接口会重新验证订阅访问、启用绑定及当前有效版本。清单获取后若权限或选版发生变化，旧下载请求可能得到 404；包不可安装时可返回带 `SKILL_ARTIFACT_BLOCKED` 的 409；临时存储异常按 503 处理。客户端不能把这些结果解释成“改用另一个版本下载”。

现有下载响应包含 `Content-Type`、`Content-Length`、`X-SHA256`，采用 `private, no-store`。建议延续已有接口、鉴权与产物准备流程；上架检查和运行时不能使用两套“可安装”定义。

## 4. 客户端的现有实现与改进边界

### 4.1 清单、授权与来源

`getEmployeeRuntime()` 主动协商技能产物 v1，缺少协议确认或技能 artifact 会失败，不静默退回只下发正文的旧路径。`employee-runtime-contract.ts` 检查技能重复、artifact 身份和下载路径等。

`EmployeeAuthorizer` 再核对订阅目录中的员工 ID 与清单是否一致，以及 `approvedContentSha256` 是否对应运行清单正文。SEP 决定正式版本，客户端不能用“本地最新文件”替换它。

已有本地个人版本机制需要保留：`SkillStore` 能处理显式选择的个人/owner-local 内容，在快照中记录来源及公共基线关系。这不等于改变 SEP 的正式选版，也不能扩展成绕过失败包的兜底策略。排查时要区分服务端批准基线与最终本地执行来源。

### 4.2 下载、安装、缓存与快照

下载层检查受控路径、HTTP 状态、MIME、校验头、流式实际长度和 SHA-256；429 已有有限重试。员工运行时安装不再设置 20 MiB 下载上限。不能只相信声明长度，也不能把网络错误当成格式错误。

`readSkillZip()` 检查中央目录与本地头、条目清单、压缩方式、CRC、UTF-8 名称、路径、符号链接/特殊文件、大小写及 Unicode 路径冲突、入口哈希等，不再设置 500 文件或条目预算。解析器目前支持 ZIP32，不支持 ZIP64；ZIP 格式、JavaScript 安全整数、可用内存及磁盘仍构成技术边界。`approvedEntry()` 再验证 YAML 元数据、描述符安装目录身份和批准正文一致性；不要求归档父目录与技能名一致，不因缺失引用资源拒绝安装。多个入口完整保留，只加载描述符选中的入口。每次下载超时为 10 分钟，调用方取消继续生效。

缓存身份由版本 ID 与产物哈希派生；先写私有暂存目录再发布。复用及加载时还复验文件清单、附件哈希、符号链接。客户端不应跳过这些保护，也不应修改经过哈希认证的字节去“修好”包。

本次准入后会固定技能快照。后台变更不表示已准备的同一次执行应中途换包；验证新绑定应观察重新准入的执行，并核对快照来源，不应把历史任务详情当作当前版本解析结果。

## 5. 已确认的上限和行为差异

以下是本地源码实值，不是本文新制定的正式上限。MiB/KiB 按 1024 换算；入口大小按 UTF-8 字节计算，不是字符数。上传通道预算继续保留，安装产物不再额外按 20 MiB/500 文件拒绝。

| 项目 | SEP 当前行为 | 客户端员工执行当前行为 | 冲突风险 |
| --- | --- | --- | --- |
| 压缩产物字节数 | 包存储最多 100 MiB；安装产物无额外 20 MiB 上限 | 员工运行时描述符、下载和 ZIP 安装无 20 MiB 应用层上限 | 上传预算保留 |
| ZIP 条目与文件数 | 上传总条目最多 10,000；安装产物无额外 500 文件上限 | 无 500 文件/条目应用层上限；解析器仅支持 ZIP32，不支持 ZIP64 | 上传预算及 ZIP32 格式边界保留 |
| 解压总量 | 500 MiB | 无单独的 64 MiB 员工运行时安装上限；仍受 ZIP32、内存和磁盘约束 | SEP 仍可能拒绝超过 500 MiB 的包 |
| `SKILL.md` | 入口和正文处理使用 2 MiB 限制 | 无单独的 500 KiB 员工运行时解析上限 | SEP 仍可能拒绝超过 2 MiB 的正文 |
| 多入口 | 选择根目录或层级最浅入口，同层按名称排序，给 `MULTIPLE_ENTRIES` 警告 | 允许不同安全路径的其他入口，完整保留，仅加载选中入口 | 同一路径的大小写及 Unicode 别名碰撞继续拒绝 |
| 名称与目录 | 不一致给 `DIRECTORY_NAME_MISMATCH` 警告 | 允许归档父目录与技能名不同，保留原始路径和字节 | 描述符安装目录与技能元数据身份仍须一致 |
| 缺失资源 | 包检查给 `RESOURCE_REFERENCE` 警告 | 允许安装，不补造附件 | 实际使用缺失文件时仍可能失败 |
| 元数据不规范 | 可以补齐并给 `METADATA_NORMALIZED` 警告 | 最终入口须通过 schema，内容仍须与批准版本一致 | 应检查补齐后的实际产物 |
| 路径碰撞 | 包检查按 NFKC 检查重复路径 | 还检查大小写别名、隐式父目录拼写冲突、保留缓存清单路径等 | 不能只比较名称正则是否相同 |

客户端“扫描本机技能并上传”使用另一组 `SKILL_IMPORT_LIMITS`：入口 2 MiB、包 100 MiB、解压 500 MiB、文件 10,000。这是导入通道预算，不是员工执行预算。不能概括成“客户端所有技能功能都限制 20 MiB”，也不能只改一个描述符常量就宣称整体对齐。

本次回归验证：两边均接受旧安装上限以上的描述符；实际大于 20 MiB、包含 503 个文件的 ZIP 可安装并复用缓存。生产问题原包经服务端本地重放生成 33,048,086 字节产物，客户端完整安装 442 个文件逐字节一致，重建安装器后复用缓存成功，仅加载选中技能。该重放使用本地网络与授权 mock，未执行包内脚本。

## 6. 格式和哈希：避免误加规则

两边 frontmatter 的主要规则基本一致：`name` 为 1～64 个 Unicode 码点，允许字母、数字、内部空格或非连续连字符，且须满足安全路径组件要求；`description` 非空且最多 1024 字符。`license`、`compatibility`、`metadata`、`allowed-tools`、`disable-model-invocation` 可选，两边均允许其他元数据字段。

不应另加“必须纯英文小写”“必须固定几个章节”“必须有代码块”等安装门槛。SEP 内容质量检查中有些段落、示例和敏感凭据特征只是警告，应保留已有审核语义。客户端与 Pi SDK 已有名称/解析适配，不能因 SDK 的名称警告就改写批准内容。

| 哈希字段 | 对应对象 |
| --- | --- |
| 数据库 `packageSha256` | SEP 上传归一化后存储的 ZIP 字节，可能不同于原 TAR 或重写前本地归档 |
| `approvedContentSha256` | 版本记录 `content` 的字节，与运行清单正文核对 |
| `entrySha256` | 最终下发入口 `SKILL.md` 字节，包含实际元数据、换行 |
| `artifactSha256` | 最终下载产物字节；ZIP 经入口补齐重打包后可能不同于存储包 |

不能要求以上哈希全相等。旧包版本正文可能剥离了 frontmatter，客户端已有受限的等价比较和包正文兼容。后续既不能删除兼容后要求一律原文全等，也不能放宽到忽略真实指令差异。

## 7. 如何对齐，避免两边各改一套

建议沿用现有 v1 链路，不另开下载或安装流程：

1. **先明确语义。** 分开定义上传存储预算和员工安装预算，明确压缩字节、总条目、非目录文件、解压总量、入口大小等。两组预算可以不同，但“上传成功”不能等于“可在目标客户端安装”。
2. **SEP 补兼容性门禁。** 复用 `SkillPackageService`、`ClientSkillArtifactService.prepare()`、`EmployeeReadinessService`，对最终产物检查安装协议。若保留宽上传范围，页面应明确只是存储成功；绑定/发布给客户端和运行时仍须拦截不兼容产物。
3. **客户端保留本地保护。** 共同产物约束应同义；缓存路径、文件权限、暂存发布等是客户端独有职责。SEP 的业务审批和权限选择则不应在客户端再实现另一套权威逻辑。
4. **兼容已发布客户端。** 当前请求只协商 `skillArtifactProtocolVersion=1`，没有上报全部安装预算。建议现有 v1 先按已发布客户端可处理范围收敛；提高预算须明确新协议/能力协商及升级路径，不能单方放宽 v1 常量。
5. **统一规范和测试样例。** 在已有对接文档维护共同规则，两仓库使用同一组合法/非法 JSON、ZIP 样例进行契约测试。是否提取公共包以后再定，不必为文档新增依赖或把 NestJS 模块直接引入 Electron。

建议先补兼容约定与样例，再协调实现和发布。验收需走完“上传 → 绑定 → 目标订阅解析 → 下载 → 客户端安装/加载”，两边分别通过单测不等于闭环已通过。

## 8. 错误与兼容约定

合法 `BLOCKED` 能通过 manifest 解析，但 `EmployeeAuthorizer.authorize()` 在技能准入时仍拒绝它。它与“manifest 结构非法”是两种错误，也不代表客户端自动跳过该技能继续原任务。

现有阻塞原因只有 `INVALID_ENTRY`、`PACKAGE_REQUIRED`、`PACKAGE_UNAVAILABLE`、`PACKAGE_CONTENT_MISMATCH`。artifact 是严格 schema，在 v1 随意添加字段或新 reason 会被旧客户端拒绝。诊断优先进入受控日志或已有错误渠道；扩展协议字段须协调兼容。

| 失败阶段 | 定位责任 | 正确含义与处理 |
| --- | --- | --- |
| 上传包损坏、路径不安全、超上传预算 | SEP | 上传失败，说明约束及实际大小/数量 |
| 可存储但不满足客户端安装规则 | SEP | 明确不可用于目标客户端，不返回不兼容的 `AVAILABLE` |
| 订阅解析到非预期版本 | SEP | 核对订阅、员工、能力、版本 ID 及选版来源 |
| 清单字段不合法 | 客户端 | 记录安全的字段路径、错误类型及约束 |
| 下载时权限或有效版本变化 | SEP + 客户端 | 保留 HTTP 结果，必要时重新取清单重新准入，不能偷偷换包 |
| 哈希、入口身份或缓存复验失败 | 客户端 | 拒绝本次安装/加载，指出具体阶段，不能关闭校验；缺失引用资源仅提示 |

当前 `parseEmployeeRuntimeManifest()` 仍把 Zod 问题折叠成 `Invalid employee runtime manifest.`，字段级诊断是待改进项。建议记录如 `runtime.skills[0].artifact.byteLength` 的受控路径、约束、大小/数量与相关 ID，不输出整份 manifest、技能正文、系统提示词或令牌。

## 9. 回归验收重点

- 同一描述符两边对边界得出一致结果：上限、上限加一、错误类型、未知字段。
- 文件数未超但目录条目超；小 ZIP 解压总量超；入口超过安装预算。
- 单/多入口、大小写与 Unicode 路径碰撞、目录名不匹配、缺失输入资源；输出文件名和外部链接不得误判成必需附件。
- 元数据补齐、CRLF/BOM、存储包与最终产物哈希不同，同时保证批准指令未改变。
- 企业默认、订阅选版、员工默认、平台回退；同名不同员工；清单到下载之间绑定/版本变化。
- 本地个人版本来源、缓存被修改、账号/企业切换、同一次运行快照不会被中途换包。
- 上传、上架检查、运行时描述和真实客户端安装对同一最终产物的结论一致。
