# 客户端自动更新阶段 4 本地发布演练手册

> 状态：在建；阶段 4 本地首批工具已实现，不代表阶段 4 全部完成或生产发布获批。
>
> 核对日期：2026-10-09。
>
> 依据：[自动更新开发方案](./客户端自动更新开发方案.md)、[阶段 3 待验收清单](./客户端自动更新阶段3待验收清单.md)。真实签名操作见 [签名与跨平台验收手册](./客户端自动更新签名与跨平台验收手册.md)。

## 1. 演练边界

本批工具负责版本预演、构建 receipt、双平台产物汇总、本地发布计划，以及本地 fixture 的发布、snapshot rollback 和显式恢复。**无 remote 上传、CI 编排或生产批准入口**；候选更新源 `candidateFeed` 只是配置值，工具不会向该地址上传。

- 原生构建 receipt 必须由 `record-release-build.mjs` 在真实 macOS / Windows 主机执行签名与清单校验后生成；CLI 无跳过签名选项。缺证书、签名或公证验证失败时停止，不以 synthetic 结果冒充 receipt。
- `--commit` 必须是完整的 40 位小写十六进制提交号，是调用方声明的构建来源，**不是独立构建来源证明**。签名成功和 receipt 字段一致也不证明源码、工作树或构建流程已经获批。
- 本地 fixture 可以使用 unsigned synthetic 文件及 `signatureVerified:false` 的模拟 receipt；仅测试流程与恢复逻辑。计划固定为 `mode:local-rehearsal`、`releaseApproved:false`，本地记录也保持 `releaseApproved:false`，不能作为安装或阶段 3 验收证据。
- fixture 必须是用户自有、访问受控的安全本地目录，不能是生产目录、共享下载源或 live feed；来源目录与 fixture 不得互相包含。工具不是恶意并发文件系统的沙箱，不对同用户恶意修改提供完整隔离。
- 单文件临时写入和替换不等于跨文件事务，也不提供 **power-loss durability** 承诺；文件同步不等于断电后目录项、记录和清单必然保持一致。

不要把 `published-local` 解释为正式发布完成，也不要手改 `releaseApproved` 来代替审批。

## 2. 命令映射与前置准备

以下 npm aliases 已全部加入 `package.json`，可直接执行；右栏保留等价的直接入口供核对。本手册不要求修改依赖或自动提升版本。

| npm alias | 直接入口 |
| --- | --- |
| `npm run release:record-build -- ...` | `node scripts/record-release-build.mjs ...` |
| `npm run release:version -- ...` | `node scripts/release-version.mjs ...` |
| `npm run release:collect -- ...` | `node scripts/publish-release.mjs collect ...` |
| `npm run release:plan -- ...` | `node scripts/publish-release.mjs plan ...` |
| `npm run release:init-fixture -- ...` | `node scripts/publish-release.mjs init ...` |
| `npm run release:local -- ...` | `node scripts/publish-release.mjs publish-local ...` |
| `npm run release:rollback -- ...` | `node scripts/publish-release.mjs rollback-local ...` |
| `npm run release:recover -- ...` | `node scripts/publish-release.mjs recover-local ...` |
| `npm run test:releases` | `node --test scripts/record-release-build.test.mjs scripts/release-version.test.mjs scripts/release-notes.test.mjs scripts/release-flow.test.mjs` |

命令从仓库根目录执行。渠道显式选择 `beta` 或 `stable`；环境变量 `SEP_RELEASE_CHANNEL` 若设置，必须与显式参数一致。`stable` 的发布计划拒绝 prerelease 版本。以下示例使用 beta 和 `0.1.3`，只是演示值，不表示该版本已批准；实际运行前选择未尝试过、严格递增的版本。

POSIX shell 示例变量：

```bash
VERSION='0.1.3'
# 仅在当前检出的提交确为本次两平台构建来源时使用；仍是声明，不是证明。
BUILD_COMMIT="$(git rev-parse HEAD)"
# 路径示例须替换为自己控制的目录；BUNDLE 尚不存在，FIXTURE 为空或不存在。
MAC_DIST='/absolute/private/releases/mac/dist/beta'
WIN_DIST='/absolute/private/releases/win/dist/beta'
BUNDLE='/absolute/private/releases/bundle-beta-0.1.3'
FIXTURE='/absolute/private/rehearsals/sep-release-fixture'
```

使用现有已安装依赖，不将源码、真实签名凭据或用户数据复制进 fixture。先运行专项测试并保存真实退出码与摘要；本手册本身不是测试通过记录。

## 3. 版本与说明预演

```bash
npm run release:version -- "$VERSION"
# 等价入口：node scripts/release-version.mjs "$VERSION"
```

预期输出 JSON `dryRun:true`，列出 `package.json.version`、`package-lock.json.version` 和 `package-lock.json.packages[""].version` 的计划变更。工具先核对当前根版本一致，再检查合法规范 SemVer 与严格递增；只改 build metadata 不算递增。**不写源 package/lock、不写 Git、不自动 bump**。

预演不执行构建。需要真实新版本时，由负责版本整合的人另行同步源 package/lock 后，在该版本上构建；不能用 `collect --version` 给旧包重新贴版本号。工具也不会自动修复不一致的锁文件。

说明生成保持原用法和默认 beta：

```bash
node scripts/generate-release-notes.mjs beta /absolute/private/releases/notes \
  --changes-file /absolute/private/releases/changes.txt
```

`--changes-file` 可省略；提供时必须是普通文件、合法 UTF-8 纯文本，最多 64 KiB，拒绝二进制/不允许的控制字符。生成标题仍是 `SEP Client <version> (<channel>)`；说明生成时间不是构建时间。说明不验证签名、公证、上传或发布状态，不能把文案当作这些操作完成的证明。

## 4. 真实原生构建 receipt

本节需阶段 3 的真实签名条件，条件缺失时只做第 9 节 synthetic 测试，不执行“跳过签名”。按签名手册在两台原生构建机分别完成对应渠道的签名构建，保持版本、渠道及声明提交一致；macOS 构建目录必须包含 arm64 和 x64 两组 DMG / ZIP。

macOS，在其构建根目录执行：

```bash
node scripts/record-release-build.mjs beta --commit "$BUILD_COMMIT" \
  --root /absolute/private/mac-build-root
```

Windows 原生主机 PowerShell 示例，`$BUILD_COMMIT` 需设为其真实构建来源声明：

```powershell
node scripts/record-release-build.mjs beta --commit $BUILD_COMMIT --root 'C:\private\win-build-root'
```

`--root` 指向包含 `package.json` 和 `dist/<channel>` 的构建根目录，不是直接指向安装包目录。Windows 还需保留 `dist/<channel>/win-unpacked/<productName>.exe`，供实际主 EXE 签名校验；它不作为安装包汇总条目复制。

成功后，在各自 `dist/<channel>/release-build.json` 得到 `schemaVersion:1` 的 receipt，包含渠道、版本、声明提交、原生平台、`signatureVerified:true` 及文件名、大小、SHA-256、SHA-512。工具实际调用签名与清单验证器，并复核来源文件，不能从另一平台模拟 CLI 的原生校验。

已存在的 `release-build.json` 不会被覆盖。失败时检查签名条件、当前版本及目录完整性；先保留旧报告作为证据，经人工确认后另选独立构建根目录或显式清理旧报告。不得随手手写一个 `signatureVerified:true` 的报告。

## 5. collect：目录装配，不是 live feed 切换

将两平台安装包、关联资源、清单和各自 `release-build.json` 转移到受控的本地输入目录，保持内容不变。必要文件如下，`<version>` 是本次版本：

| 来源 | 必须具备 |
| --- | --- |
| macOS | `SEP-Client-<version>-mac-arm64.dmg/.zip`、`SEP-Client-<version>-mac-x64.dmg/.zip`、`latest-mac.yml`、`release-build.json`；现有 DMG/ZIP blockmap 也须与 receipt 一起保留 |
| Windows | `SEP-Client-<version>-win-x64.exe`、对应 `.exe.blockmap`、`latest.yml`、`release-build.json` |

```bash
node scripts/publish-release.mjs collect beta \
  --version "$VERSION" --commit "$BUILD_COMMIT" \
  --mac "$MAC_DIST" --win "$WIN_DIST" --output "$BUNDLE" \
  --notes /absolute/private/releases/notes/RELEASE-NOTES-beta.md
```

`--notes` 可省略，默认只生成保守的装配说明；自定义说明须为非空合法 UTF-8、最多 128 KiB。汇总工具重新校验 receipt 的身份、清单引用、实际大小与哈希；缺平台、提交不一致或输入变化应停止，不覆盖既有输出目录。

成功结果包含全部安装包及关联资源、两个清单、`release-builds.json`、`RELEASE-NOTES-beta.md`、重新生成的 `SHA256SUMS.txt`。校验和包含 receipt 中的全部非清单产物，包括 blockmap，不能用只列主安装包的旧校验和代替。

**collect 的输出是独立装配目录，不可直接作为 live feed。** 工具在临时目录校验后预留目标目录，再逐文件移入；不是整个目录的一次原子可见切换。其他进程可能看到未完成目录，应等待命令成功退出，再执行 plan；失败时保留错误证据并检查残留，不让客户端指向装配过程中的目录。

## 6. 只读发布计划与 fixture 初始化

```bash
node scripts/publish-release.mjs plan beta \
  --source "$BUNDLE" --version "$VERSION" --commit "$BUILD_COMMIT"
node scripts/publish-release.mjs init --fixture "$FIXTURE"
```

plan 不修改来源文件，输出每个文件的大小、SHA-256、SHA-512 和顺序 `artifact → metadata → manifest`，清单固定最后。`candidateFeed` 不产生网络动作；即使所有 receipt 声称签名通过，也只得到 `local-rehearsal/releaseApproved:false`。`collect/plan/publish-local` 可省略 `--version`，届时读取当前 `package.json`；演练建议显式提供，减少版本歧义。

init 只接受空的本地目录，可创建尚不存在的目录，写入 `.sep-release-fixture.json`，其中 `localOnly:true`。不对已有目录重复初始化；不得手加标记把生产或任意共享目录伪装成 fixture。

发布后布局：

```text
fixture/
  .sep-release-fixture.json
  beta/                         # 本地可变清单/元数据及不可变安装包
  stable/                       # 使用该渠道后创建
  .release-state/
    beta/
      records/<UUID>.json        # 计划、before snapshot 和事务状态
      lock/                     # 仅操作期间存在；崩溃可残留
    stable/
      records/<UUID>.json
```

## 7. 本地发布与 snapshot rollback

```bash
node scripts/publish-release.mjs publish-local beta \
  --source "$BUNDLE" --fixture "$FIXTURE" \
  --version "$VERSION" --commit "$BUILD_COMMIT"
```

正常流程先保存记录与旧 snapshot，再复制不可变安装包/关联资源，核对哈希，更新说明、receipt 汇总及校验和，最后分别提交 `latest.yml`、`latest-mac.yml`，复核完整目录后记录 `published-local`。安装包使用拒绝覆盖的写入方式。

`publish-local`、`rollback-local`、`recover-local` 的 CLI 事务输出仅为摘要，包含 `id`、渠道、版本、声明提交、状态等字段，**不包含 `before` snapshots**。完整 records 保存在 `$FIXTURE/.release-state/<channel>/records/<UUID>.json`，包括计划与恢复快照；stdout 摘要不是完整恢复备份，不要把磁盘快照复制到终端日志或发布说明中。

**两个清单不是跨文件原子提交。** 单文件替换期间可能短暂出现一个平台已更新、另一个尚未更新；失败恢复也逐文件进行，不能宣称绝无短暂不一致。

版本尝试过后，包括失败、恢复或回滚，均不得复用同一渠道版本。只读 version/plan 不消耗版本；一旦本地发布事务写入 records，工具会按该渠道全部历史记录要求更高 SemVer，包括失败记录。报错后也应按操作纪律换更高版本，不因尚未出现成功记录而重发。不得删除/修改记录、覆盖安装包或仅改 build metadata 绕过限制。

保存成功输出中的记录 `id`，在确认该记录对应当前本地发布后回滚：

```bash
RECORD_ID='<本次 published-local 输出中的 UUID>'
node scripts/publish-release.mjs rollback-local beta \
  --fixture "$FIXTURE" --record "$RECORD_ID"
```

rollback 恢复该记录的 `before` snapshot：两个清单以及 `release-builds.json`、对应说明、校验和。原先不存在的可变文件恢复为不存在，不虚构旧版本。结果记录为 `rolled-back-local`；不回滚到任意历史版本，也不接受已经回滚或不再匹配当前状态的记录。

回滚前先校验旧 snapshot 清单及其引用安装包的大小、SHA-512；存在旧 receipt 时，还核对完整产物集合（包括 DMG、blockmap）和 receipt 绑定的清单字节。旧文件缺失或损坏时拒绝手动回滚，不改变当前清单或事务状态；失败恢复与 recover 也在恢复清单前执行此校验，避免暴露无法下载的旧版本。

**snapshot rollback 不删除安装包或关联资源，不降级已升级客户端，不回滚客户端数据。** 更高版本修复仍须选择新版本；本地恢复不处理 CDN 缓存，也不代表远程回滚已实现。

## 8. 失败、崩溃残留锁与显式恢复

| 记录状态 | 含义与处置 |
| --- | --- |
| `publishing-local` / `rolling-back-local` | 未完成操作；进程崩溃时可能保留。确认进程状态，处理残留锁后走 recover |
| `failed-restored-local` | 发布失败，但旧清单及元数据恢复并校验成功；版本已消耗，不以同版本重试 |
| `recovery-required` | 自动恢复或 rollback 未完成；阻止后续发布，需人工确认后显式恢复 |
| `published-local` / `rolled-back-local` / `recovered-local` | 本地事务结果，不是生产批准；历史记录继续参与版本复用检查 |

同一 channel 操作通过 `.release-state/<channel>/lock/` 目录互斥，beta/stable 分开。正常结束会释放锁；**crash 不会自动抢锁或按时间过期解锁**，recover 同样需要获取锁。

1. 停止启动新操作，保存记录、目录清单、脱敏退出码与失败摘要；不要把失败日志里的凭据写进文档。
2. 由人工确认持锁操作的进程已经退出，且没有其他人/进程正在使用该 fixture；不能仅根据锁的年龄判断。
3. 备份对应 channel 的 records 与当前状态，确认 `lock/` 是本次残留且为空，再人工处理。POSIX 可在上述确认后使用 `rmdir "$FIXTURE/.release-state/beta/lock"`；不要用递归删除整个状态目录解除阻塞，非空/异常锁应先调查。
4. 仅有一条未完成事务时执行显式恢复：

```bash
node scripts/publish-release.mjs recover-local beta --fixture "$FIXTURE"
```

recover 校验当前可变文件只能是该事务的旧 snapshot 或计划中的新哈希，然后恢复旧 snapshot，复核后标记 `recovered-local`。没有未完成事务、存在多条未完成记录或状态被外部修改时拒绝，不猜测哪个版本正确。不要自行手改 JSON 或清单来骗过检查；保留证据并调查。

专项测试通过真实子进程在第一份清单替换后退出，确认此时两份清单可能指向不同版本且锁仍保留；带锁 recover 被拒绝。测试等待子进程退出后显式移除空锁，再确认 recover 恢复旧清单。此证据仅覆盖进程退出，不代表断电恢复验收。

断电后记录损坏、目录项丢失或不属于记录的文件变化，不保证可自动恢复。安全停止、人工检查和独立备份仍是必要措施。

## 9. 无证书的 synthetic 演练与验证记录

无证书时先运行现有专项测试；测试在独立临时目录生成 unsigned synthetic 安装包、blockmap、真实对应的文件哈希及 `signatureVerified:false` 的模拟 receipt，测试后清理临时 fixture。不能把这些字节交给真实客户端安装，也不能把 synthetic receipt 描述为通过原生签名校验。

```bash
npm run test:releases
# 等价直接入口见第 2 节命令映射。
```

`release-flow.test.mjs` 包含只读计划、完整产物汇总、渠道隔离、版本复用拒绝、安装包先于清单、故障注入后 snapshot 恢复、显式 recover、rollback 保留安装包及竞争锁拒绝等场景。故障注入通过导出 API 的测试 hook 执行，不是 CLI 的签名跳过或生产故障入口。

新增 loopback HTTP 集成测试在 `127.0.0.1` 的临时端口提供 synthetic fixture，依次发布 `0.1.2`、发布 `0.1.3`、rollback 后恢复 `0.1.2` 清单；每次通过 HTTP 验证两个平台清单的版本，以及匿名请求、HTTP 状态、文件大小与 SHA-512。请求不携带 Authorization 或 Cookie。这只是本地清单可见性和传输完整性验证，**synthetic 文件不可安装**，不证明真实签名、安装升级、客户端降级或远程源验收通过。
