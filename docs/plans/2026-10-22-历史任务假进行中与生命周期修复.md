## 问题

部分旧任务长期显示“执行中”，但没有实际 run、事件或产出；页面还把创建后的全部时间显示成执行时长。用户手动终止后，迟到 heartbeat 或旧事件不能再次激活任务。

## 已确认根因

- `src/features/enterprise/work-mapping.ts` 把所有 `pending` 映射为 `arranging`。
- 进行中筛选和首页数量只看这个映射，没有确认 `activeRunId`、队列登记或 worker 归属。
- `WorkDetailPage` 在缺少真实 `startedAt` 时用 `createdAt` 计算时长。
- 创建成功、准入成功、worker 启动成功和 run 持久化没有分开记录。
- 收尾跨多个异步写入，部分错误可能留下未收敛的任务状态。

## 目标方案

1. 将生命周期投影拆成：未开始、排队、启动中、运行中、等待审批、等待媒体、收尾、启动失败、失联、已暂停、已终止、已完成。
2. 用 `activeRunId + expectedRunId + stateRevision/generation` 判断当前执行归属。
3. 创建和启动分开记录；启动失败持久化 `startFailureCode`、脱敏原因和时间。
4. 无执行证据的旧 `pending` 只显示“尚未启动”，不自动启动、不强改为失败。
5. 已完成 run 但顶层 task 未更新时，只依据匹配的顶层 run 终态修复；编排还要求同一 run 的终态 checkpoint。媒体交付继续由原执行链路确认后再结束 run，巡检不根据供应商成功或单个节点结果推断整个任务完成。
6. 用户终止、归档、删除、新 run 和 scope 切换优先级高于迟到事件。
7. 排队时间、真实运行时间、暂停时间和媒体等待时间分开统计；没有 `startedAt` 时执行时长显示未知。

## 第二阶段：巡检与终态修复

### 已实现

- `electron/domain/task-lifecycle.ts` 提供无 I/O 的分类：未开始、活动、已有终态证据、证据缺失、疑似失联、冲突、受保护。
- runtime 提供 queue、starting、worker、编排、停止收尾的当前归属。每次判定及修复前重新查询，避免使用过期快照；媒体等待中的现有 worker 仍属于活动执行。
- run 增加可选 `executionKind`，checkpoint 增加可选 `lastRunId`，任务增加兼容旧数据的 `stateRevision`。旧字段缺失不推断为普通会话。
- 巡检每 30 秒触发，不重入；每轮最多读取 50 个候选，按轮转游标推进。轮间执行预算为 2 秒，在候选之间检查预算；正在进行的文件读取不强行取消，因此不是硬超时。
- 候选从已加载的当前 scope 任务生成。每项初检读取指定 run 和 checkpoint，修复前再读一次核对；不遍历该任务全部 run。checkpoint 使用只读诊断，不修复或隔离损坏文件。
- `stopAll()` 清理定时器；后续提交执行或续聊时重新启用。首次构造 runtime 时启动巡检，未加载 runtime 的启动阶段不提前引入 SDK。

### 修复准入

仅设置 `SEP_TASK_LIFECYCLE_RECONCILE=1` 时允许写入。默认只分类并记录脱敏诊断日志，尚未提供前端诊断入口。

1. 顶层 `activeRunId` 与 run ID 匹配，run 明确结束，并有有效的起止时间；子节点 run 不能作为顶层完成依据。
2. 普通会话需有明确的 `executionKind=conversation`；编排及类型未知的旧 run 还需同一 run 的终态 checkpoint，且双方结果一致。缺失、冲突或非终态 checkpoint 不自动修复。
3. 本地没有当前执行者。runtime 查询回调是必需条件，调用方不能仅凭磁盘终态执行自动修复。
4. 在任务串行写入链中重新检查 scope / generation、run ID、stateRevision、状态、归档标记和当前执行归属。暂停、用户中断、已完成、已失败任务不被旧证据覆盖。
5. 修复保存 run 的真实起止时间、清除旧准入、增加 revision 和一条修复日志。只有保存成功才发布内存及通知；重复巡检不重复写入。
6. 这是有终态证据的快照修复，允许修复遗漏中间状态的 `pending` / `waiting_approval`。普通执行状态机仍维持原约束。

修复只写任务快照，不修改 run / checkpoint，不启动 worker，不提交模型、工具或媒体任务。关闭开关停止后续自动写入，不撤销已完成的修复。

### 失联处理边界

连续观察 60 秒缺少当前执行归属才分类为 `suspected-lost`。重新观察到活动执行或更换 run 后重新计时；任务创建时间和缺少消息不能作为计时依据。scope 切换清除观察记录。

**疑似失联目前仅诊断，不自动改为 interrupted / failed，也不重试。** 没有 run、没有可信结束时间、只有外部供应商成功或子节点结果时，无法证明整个任务的结果。该限制避免误伤仍在等待媒体交付、审批或结果落盘的任务。
