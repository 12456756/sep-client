## 4. D01：先排查生成成功后保存被中止

### 证据与机制

1. `C:electron/pi/sdk/pi-coding-agent-adapter.ts:267-285` 将 SDK 的工具执行 signal 传给图片 host。
2. `C:electron/service/media-service.ts:313-314` 将工具 signal 和 activity controller 合并为 `parent`；`:385` 使用该 parent 启动异步 `track`。工具已返回，但 tracker 仍持有这个 signal。
3. `C:electron/pi/sdk/pi-task-worker.ts:224-230` 在纯媒体提交成功的 `turn_end` 中调用 `session.abort()`，停止模型后续回合。
4. 已安装 SDK 的 `pi-agent-core/dist/agent.js:200-201` 中，`abort()` 会取消当前运行 controller；`agent-loop.js:453` 将此运行 signal 传给工具。该包位于 `pi-coding-agent/node_modules/@earendil-works/` 下。
5. `C:electron/service/media-service.ts:501-510` 在 tracker 被取消时，把正在保存的状态改成 `SAVE_FAILED`，写入与最新任务一致的停止信息。

这条路径高度支持“模型交接取消了图片下载”的根因假设。已确认的任务事实是生成成功后本地跟踪停止；相同状态也可能由其他取消路径产生，本轮未新增可控时序测试，不能断言该任务一定由交接触发，也不能写成已通过回归确认或已修复。视频 host 有自己的 run/tracker 生命周期，不能仅凭图片链路推断视频同样有此缺陷。

### 修复要求

- 区分工具调用取消、模型回合交接、任务停止、账号范围失效、应用退出。交接仅停止模型继续执行。
- 工具提交阶段仍响应工具取消；job 及编排关联持久化后，由 activity/task 生命周期拥有 tracker 的取消权。不能简单删除全部 signal 检查。
- 交接的所有权切换须覆盖“关联已落盘、工具尚未返回”“下载进行中”“SDK 取消先于后续回调”等时序。
- 显式停止、退出、撤销授权仍须取消网络并收敛，不允许脱离授权无限后台执行。
- 修复后通过原 job 恢复下载；不得为了补文件创建新的生成、报价或扣费请求。原结果过期时明确说明。

### 验收

- 使用真实 SDK + 假网关挂起 content 下载，提交工具返回后触发交接，下载继续到 `SAVED` 且完成自动交付。
- 同样时序下执行用户停止或切换账号，下载必须停止，不能越权写入。
- 普通会话模型结束、编排纯媒体交接、混合文档节点均覆盖。
- 断言原 clientRequestId/job/receipt 不变，提交一次；覆盖无 receipt 的未知提交恢复，不因取消重新生成。

## 5. M01：图片尺寸和模型能力写死

证据：

- `B:backend/src/modules/media-gateway/image-model-contract.ts:1-22`：模型 ID 白名单及共用三尺寸、三质量模板。
- `B:backend/src/modules/media-config/media-config.service.ts:163-225,337-385`：发现建议、配置验证、企业运行时过滤和 V2 能力仍依赖该模板。
- `B:backend/src/shared/media-real.dto.ts:4-20`：真实请求 size 为三值 enum。
- `C:electron/common/platform/real-media-semantics.ts:8-14`：真实参数再次只接受三尺寸。
- `C:electron/common/platform/sep-media-runtime-contract.ts:91-100`：省略 size 时只有三种比例默认映射。
- `C:electron/data/sep-real-media-gateway.ts:12-16`：profiles 响应 schema 同样固定三尺寸。该方法不是员工 runtime 的主要来源，但后续应一并对齐，不能遗漏为兼容陷阱。

优化：

- 首阶段按模型、通道维护经过验证的有限规格列表，开放有证据支持的 16:9/9:16 等尺寸。客户端消费有效规格，不再单独维护三尺寸白名单。
- 质量、生成/编辑、最大张数不能因模型 ID 在目录中就直接认定全部支持。未知模型列为待适配，不能“目录可见即全部可执行”。
- `B:backend/src/modules/media-config/media-model-sync.service.ts:57-105` 会按 compatible 更新 verified，并为新模型建立默认能力；当前 compatible 主要检查本地模板。因此 verified 不应被当作所有规格已实际出图验证的证明。
- `C:electron/common/platform/sep-media-runtime-contract.ts:16,78` 的输入合同允许 maxOutputs 到 8，映射时截为 4；真实请求/receipt 也最多 4。当前属于保守适配范围，不能据此宣称实际支持 8 张；以后扩展张数必须同时调整服务端、报价、响应和工具能力。
- 后续只有确认通道支持自定义尺寸时，再增加范围/步进能力；不要从“16:9”随意构造任意宽高或宣称无限制。
- `R:backend/internal/service/image_billing_size.go:28-61` 已有 2048x1152、3840x2160 等计费分类。这只是代理源码证据，不是部署渠道成功出图证据。
- 保留实际输出宽高与请求规格一致性校验。若通道有合法取整规则，必须作为显式契约描述并记录 requested/effective/actual；不直接取消校验。

回归：新规格贯穿配置验证、runtime、工具、报价 hash、请求 DTO、adapter、receipt、保存与预览；保留旧三规格；不支持规格在上传/报价/生成前拒绝。

## 6. M02：视频规格在能力、请求、发送和对账中冻结

证据：

- `B:backend/src/modules/media-config/media-video-config.service.ts:44-58,110-111`：仅 minimax-h3、4 秒、16:9、720p、24fps、带音轨、MP4、单参考图。
- `B:backend/src/modules/media-gateway/sub2api-video.adapter.ts:118-146,203-209`：先拒绝其他规格，再发送写死的 `seconds=4`、`size=1280x720`、`resolution=720p`、`generate_audio=true` 和 metadata。
- `B:backend/src/modules/media-gateway/media-video-real.service.ts:429-446`：再次冻结校验。
- 同文件 `:332-336`：usage 对账仍要求 model=minimax-h3、duration=4、resolution=720p。只开放提交会让新规格长期停在对账中。

这是首期真实适配范围，不等于当前供应商只支持这些规格。现有前置校验保证请求只能走这套参数，所以当前不是“用户合法选择被 adapter 悄悄改掉”；但扩展时若漏改 adapter，会产生这个风险。

优化：

- 能力、报价、提交字段转换、结果验证、usage 对账必须按同一持久化规格处理。模型差异留在现有 adapter 中，不让 renderer 组装供应商字段。
- 建立已验证的规格组合；时长、分辨率、比例、音频不能仅取各自数组的笛卡尔积，避免出现每个字段单独支持、组合不支持的请求。
- 保留旧 minimax-h3 路径；增加真实支持的新规格后才下发。未实现的模型仍明确标为未适配。
- 真实 V2 runtime 已下发 `audioModes/defaultAudio/defaults`，当前 minimax-h3 为 `[true]`，客户端也会遵守。静音不是简单取消 UI 禁用，需要通道、发送和计费能力一起支持。
- 企业策略取能力交集。默认策略允许 9:16，而首期真实模型仅 16:9，可能导致 runtime 无可用 profile：`B:backend/src/shared/media-video-config.dto.ts:50-62`、`B:backend/src/modules/media-config/media-video-config.service.ts:309-330`。需给出“策略与能力无交集”的原因，不能伪装成模型丢失，也不能擅自扩大管理员授权。

回归：每个新增组合核对实际发送字段、返回元数据和 usage；拒绝非法组合；验证有音/无音、文生/图生、旧新协议及企业策略过滤。

## 7. M03：图片提示词长度前宽后窄

- `C:src/shared/media-host.ts:5`、`electron/common/platform/media-contract.ts:15`、SDK 图片工具 schema 允许 creativeBrief 最长 20000 字符。
- `B:backend/src/shared/media-real.dto.ts:12` 当前 SEP real 图片网关请求仅允许 4000 字符；这不是所有供应商的通用上限。
- 因此 4001..20000 字符可通过工具解析，在真实请求处失败。视频工具为 4000，不应据此把所有历史图片数据也改成 4000。

优化：真实入口立即按有效 `maxPromptLength` 校验，并给出实际长度和上限。初期与真实接口对齐为 4000，未来按模型/adapter 能力扩展。历史 job/session 的读取 schema 保留兼容，不截断用户内容、不自动摘要改写已审批请求。

回归：4000/4001 边界、中文/emoji 的计数口径、普通会话/编排/手动表单一致；越界时零上传、零生成；旧 20000 字符记录仍可读、预览和恢复原请求。

## 9. M05：图片工具的潜在默认规格冲突

证据：`C:electron/service/media-service.ts:231-252` 的工具入口计算出 requested aspectRatio 后，仍可能使用与其无关的 profile.defaultSize；`:297-305` 的 generate 路径又要求二者一致。

触发示例：profile 默认 1024x1024、同时支持 1536x1024；仅传 `aspectRatio=3:2`、省略 size。工具入口可能补为 1024x1024，随后被拒绝。这不是模型不支持 3:2，而是默认值选择冲突。主风险在 Pi 工具入口；现有 `C:src/shared/media-view.ts:27-44` 表单 helper 已有按比例重选尺寸的处理，不能据此认定表单也必然出错。此路径需要专门回归确认，不用全量测试历史通过作为反证。

统一规则：

1. 用户明确给出 size 和比例：同时合法且一致，否则早报错。
2. 只给 size：推导其规范比例。
3. 只给比例：从该比例支持的规格选默认值，禁止带入其他比例的 defaultSize。
4. 都未指定：使用有效 profile 默认值；策略过滤后默认值失效时，重新选择合法默认值。
5. 同一份解析结果用于审批、报价、hash、持久化和提交，不在各层重复“补默认”。

在现有 shared/helper 附近复用纯函数即可，不引入新的配置系统。覆盖所有入口的省略/显式/矛盾参数组合。

证据：

- `C:electron/service/arrangement-service.ts:500-546` 预检覆盖订阅、模型、交付计划和权限，尚未检查当前媒体尺寸、参考限制和输出格式等完整条件。
- `C:electron/domain/arrangement-plan.ts:81-94,129-133` 允许 PNG/JPEG/WebP、MP4/WebM 和 workspace/either 来源。
- `C:electron/runtime/arrangement-executor.ts:423-425` 到执行时才拒绝媒体 workspace 来源。
- 真实图片仅输出 PNG，而 `C:electron/data/arrangement-media-files.ts:171-174` 要求实际 MIME 与目标后缀一致；规划 JPG 交付物会面临生成后物化失败风险。

优化：

- 将经过授权且适度裁剪的媒体能力摘要提供给规划；对推荐但尚未授权的员工标为未知，不能当作可执行证明。
- 预检媒体 operation、规格组合、输入来源、输出 MIME、目标后缀、所需工具、通道和策略交集。
- 区分硬性要求与偏好。用户明确要求 16:9，不得以“最接近”为由静默改为 3:2；偏好允许降级时，计划中显示实际规格和原因。修改已确认计划须更新 revision/hash。
- 首阶段对未支持的 workspace 媒体来源提前阻止计划确认，不必顺带实现完整视频剪辑/FFmpeg 交付工作流。
- JPG/WebM 等非通道原生格式：要么预检说明不可执行，要么规划显式转换步骤，转换前后分别记录产物和验收；禁止简单改后缀。
- 协商失败不自动换更贵模型、重新生成或放宽企业策略。

回归：精确 16:9、允许近似比例、JPG 图片交付、WebM 视频交付、workspace 来源、图生视频缺少参考图；可提前判断的失败必须发生在付费提交前。普通会话通过共享服务获得相同规则和解释。

## 11. M07：本地能力快照、取消和恢复的语义

- `C:electron/service/media-service.ts:130-143` 页面能力缓存命中后不重新 authorize；`:193` 在 prepareRun 更新，`:662` 切换范围清空。页面重复刷新本地快照不等于刷新服务端能力。
- `C:electron/common/platform/sep-media-runtime-contract.ts:76` 将 cancel/recoverByRequestId 固定为 true。
- `B:backend/src/modules/media-gateway/media-real.service.ts:208-210` 真实同步图片不支持取消；receipt 的 `canCancel=false`。客户端 job 级按钮和取消方法已二次检查 receipt，不能误报为现有 UI 一定会成功取消上游。

优化：新增显式能力刷新/按配置版本失效机制，合并同范围同订阅刷新；避免每 5 秒刷新供应商。生成前重新授权并验证配置版本；已提交 job 使用原 profile/请求快照恢复，不能被最新默认值覆盖。

运行时区分“停止本地跟踪”“上游取消”“按请求 ID 找回”，不以通用 cancel=true 暗示可退款或可终止供应商。目录可见、可报价、可生成、可查询、可下载分别给出原因。

回归：页面打开后管理员改规格/撤销授权、旧报价配置变更、新 run 更新能力、旧 job 仍按原请求恢复、同步图片取消按钮不作虚假承诺、账号切换不接收旧刷新响应。

## 12. M08：报价过期被表现成普通失败

- `B:backend/src/modules/media-gateway/media-real.service.ts:24-26,82` 图片报价本地最长 60 秒，实际不超过上游报价过期时间，即 `min(now + 60s, upstream expiresAt)`。保留过期校验是正确的计费保护，问题在于用户审批超时后的恢复体验。
- `C:electron/service/media-service.ts:352-374` 先报价再等人工审批，审批后再次判断有效期，过期直接失败。
- `C:electron/data/sep-real-media-gateway.ts:160-167` 对部分非 2xx 状态统一投影为 SERVICE_UNAVAILABLE，未保留 QUOTE_EXPIRED/CONFIG_CHANGED 等业务原因。

优化：保留报价 TTL 与审批，增加倒计时/过期状态；明确区分尚未提交和可能已提交。仅当证据明确未提交时，使用相同有效请求重新报价，有限次刷新并重新核对预算。价格或规格变化必须重新审批；禁止以旧审批接受涨价。是否允许同价自动续期需明示审批语义，默认不扩大授权。

已有 MAYBE_SENT/receipt 时先查询原 clientRequestId，不能借重新报价创建重复生成。参考图过期则重新上传同一核验资产并重新绑定报价，不修改已经提交的原请求。

回归：审批超过 TTL、上游更短 TTL、续报价涨价、配置变更、参考图过期、提交超时后收到成功；全程断言提交次数和授权金额。

## 13. M09：超时、查询预算和并发限制

证据：

- `C:electron/service/media-service.ts:90-103` 网络操作默认统一 60 秒，包含审批等待使用的 network 包装。
- `B:backend/src/modules/media-gateway/sub2api-image.adapter.ts:113` 同步图片上游执行可等待 180 秒。客户端超时可能先于后台结束，不能据此判定生成失败。
- `C:electron/service/media-service.ts:469-494` 图片跟踪每轮最多 500 次/24 小时，错误重试默认 8 次。
- `C:electron/service/video-tracker.ts:62-65` 视频跟踪默认 120 次/30 分钟；预算是本地停止跟踪依据，不能等同于供应商失败。
- `C:electron/service/media-service.ts:315,527,702` 图片 activities 上限 4，可能包含已交付但仍在对账的 job，进而影响后续提交/恢复。

优化：

- P1：区分审批、短请求、同步提交、下载和总跟踪时限；与后端执行窗口匹配。超时进入“结果待确认/恢复原请求”，不自动重提付费生成。
- P1：错误说明具体阶段、上次尝试、是否可恢复。保留有限次退避，不通过无限增加次数掩盖不可恢复错误。
- P2：生成/下载与账务对账使用各自有限资源额度；对账不长期占满生成名额。图像/视频和跨任务调度保持公平，恢复也有背压。
- 图片同 task 的提交 gate、企业视频并发、预算与审批是业务授权或资源保护，不整体删除。新额度必须可配置且有全局硬上限。

回归：假时钟覆盖超过 60 秒但后台在 180 秒内成功、下载超时续存、查询预算用尽、4 个待对账 job 下的新工作、显式停止/退出及时释放。不能靠真实长时间等待测试这些路径。

## 14. M10：文件限制应对齐，不应无条件取消

| 项目 | 当前范围 | 证据 |
| --- | --- | --- |
| 图片本地资产 | 32 MiB、4000 万像素、单边 32768 | `C:electron/data/media-image.ts:3-5` |
| 真实图片输出 | 25 MiB、PNG 单边 4096、解压后至多 80 MiB | `B:backend/src/modules/media-gateway/media-png.ts:5-43`、`C:electron/data/sep-real-media-gateway.ts:27-33` |
| 视频后台 DTO | 最多 2 GiB | `B:backend/src/shared/media-video.dto.ts:177` |
| 视频实际缓存/adapter/客户端 | 256 MiB | `B:backend/src/modules/media-gateway/video-file-cache.service.ts:13-18`、`B:backend/src/modules/media-gateway/sub2api-video.adapter.ts:50`、`C:src/shared/video-media.ts:162`、`C:electron/data/video-files.ts:7` |

不同用途上限可以不同，但实际可生成/保存的范围必须在有效能力中一致说明。视频 2 GiB DTO 不代表端到端支持 2 GiB；图片本地 32 MiB 不代表真实接口接受 32 MiB。

优化：统一每个用途的常量及跨仓契约 fixture；先对齐到实际可支持范围。扩展大图/长视频前评估流式下载、内存、PNG 解压隔离、磁盘和预览成本，再提高对应限额，不全局替换数值。

必须保留：流字节上限、像素/解压预算、真实文件头、hash、长度及宽高校验，路径和 symlink/hardlink 防护，原子发布与不可变快照，企业/成员/订阅/节点归属。

回归：上限前后各一个字节、超大声明/截断流、PNG 解压超限、视频 DTO 与下载一致、原始文件安全校验。测试用合成流/受控 fixture，不要求保存 GiB 级真实视频。

## 15. M11：多张图/多次同类操作的映射边界

- `C:electron/service/arrangement-media-service.ts:139-146` 按 operation 和 job 数量判断是否复用，未以 mediaRequirementId 细分语义。
- `:164-177` 自动交付对每种媒体类型仅支持单一明确候选，超过一个时转模型选择。
- `:85-91` 前置图片若不能唯一确定就拒绝；这是正确的归属/选择保护。

影响：一次 count=3 的 job 与三次不同需求的 job，不是相同语义；同一节点有多个 generate/edit 需求或多个参考来源时，当前粗粒度关联不利于准确复用。不能直接把原请求防重删掉。

P2 方案：先为每个需求建立稳定映射，关联 requirementId、已解析输入、有效参数、job 和输出选择；历史缺少映射时仍保守恢复，不凭相似 prompt 自动重生成。明确的一对多交付可按已记录映射自动完成；有业务歧义时保留用户/模型选择。

回归：一个 job 多输出、多个同 operation 不同输入、部分成功、恢复其中一个需求、同一资产用于多个许可交付；已有无歧义单图/单视频路径不回退。

## 16. M12：协议与错误也需要为扩展做配套

- `C:src/shared/video-media.ts:6-30`、`C:electron/pi/sdk/pi-coding-agent-adapter.ts:144-162` 的视频枚举只包含 480p/720p/1080p/4k、MP4/WebM，以及时长/fps 的全局上限。
- 当前 runtime 与该工具 schema 基本一致，不构成已发生的具体冲突；将来开放 768p、2k 等新标签时必须一起升级，不能先下发客户端不能解析的值。
- 多处 `.strict()` schema 会拒绝未知能力字段；增加字段也可能破坏旧客户端，不能把“增加可选字段”一律当成向后兼容。
- 真实图片网关缺少与视频同等精细的业务错误投影，容易把规格、报价、格式或过期错误解释为服务不可用，增加模型重试。

方案：对新增字段设计版本协商/分版本投影；旧客户端仍收到旧协议可表达的规格。新客户端对不支持版本明确提示升级，不静默把整个能力隐藏。能力 DTO、工具 schema、表单、持久化读取和 adapter 必须一起评审。

错误应保留脱敏业务 code、field、stage、可否恢复及建议动作；区分不支持、配置过期、授权不足、结果过期、保存失败、未知提交。不要返回密钥、上游 URL、原始响应或完整未脱敏 prompt。

## 17. 建议目标与最小实施边界

有效能力取交集：

```text
已验证模型/通道能力
  ∩ 当前 adapter 实现范围
  ∩ 企业授权与预算策略
  ∩ 当前客户端可表达和安全处理范围
  = 本次请求可执行的能力快照
```

该快照服务规划、表单和工具默认值；服务端仍独立复验。模型不能自行扩大有效能力，也不能通过省略字段绕过约束。

首阶段建议补充的能力信息：

- 图片：已验证 sizes、每比例默认值、qualities/default、maxCount、maxPromptLength、参考图数量/MIME/bytes/尺寸、输出 MIME、取消和恢复能力。
- 视频：已验证规格组合与 defaults/audioModes、参考图限制、输出限制、查询/取消/保留期限；复用已有 V2 字段，不重复造同义字段。
- 通用：configVersion、能力来源和验证范围；对外只投影授权业务信息。

不要求新建独立能力平台或额外依赖。优先改造现有 DTO、config service、adapter 和 shared helper。自定义任意尺寸、多视频模型、自动转码、大文件和多产物映射按明确需求分阶段启用。

## 19. 升级、旧数据与回滚

1. 后台先支持按版本投影的契约，旧协议继续保持原范围；旧请求读取、receipt 查询和 content 下载继续可用。

3. 在测试环境验证新规格的 discovery/pricing 与 adapter；非付费验证不能证明真实出图，真实生成联调单独记录提交和消费。
4. 经授权修改目标 profile 的能力、configVersion 和企业策略；不能只改代码，也不能改写已提交 job 的快照、报价、hash 或 clientRequestId。
5. 历史持久化 schema 不因新入口限制而收窄。旧超长 prompt、多参考记录、新规格 job 均应能被对应版本读取和恢复。
6. 回滚时仅停止新规格提交，保留已提交新规格的查询/下载/结算能力。若旧客户端无法读取新 job，应在灰度阶段隔离受支持版本，不能宣称任意旧包均可直接回滚。
7. 模型重新发现不覆盖管理员能力调整或擅自新增企业授权。连接变更、配置撤销和请求快照变更按已有并发/鉴权规则处理。
