# 接口设计

> 当前实现说明：硅基员工是按订阅和职能识别的独立员工，不包含部门或部门分支字段。
> 本文中早期的部门授权示例以及 workflow 命名仅作历史背景，不得作为 renderer 或 IPC 契约。
> 当前工作类型只有 `conversation` 和 `arrangement`；员工目录只返回订阅、职能、模型和可用状态。

> 文档定位：SEP 客户端顶层接口说明书  
> 当前状态：持续补充中  
> 当前覆盖模块：首页、安排工作  
> 传输边界：渲染进程通过 Electron IPC 调用客户端后端；客户端后端按需调用 SEP 平台接口  
> 设计原则：接口面向前端业务能力，不直接暴露 SEP 数据库模型、客户端文件结构或 Pi SDK 对象

## 1. 文档使用约定

### 1.1 接口编号

接口编号由模块前缀和序号组成：

```text
HOME-xxx      首页聚合与首页交互
EMP-xxx       企业硅基员工目录
WORK-xxx      工作查询与工作详情
ARRANGE-xxx   安排工作流程
EVENT-xxx     客户端主动推送事件
```

后续模块追加到本文档时，沿用同样的编号方式，例如 `ARRANGE-xxx`、`RECORD-xxx`。

### 1.2 接口名称与传输通道

文档中的 `home.getOverview`、`employee.list` 等是业务接口名称，不等同于最终 IPC channel 字符串。最终实现时应在 `controller/channels.ts` 中登记 channel，并在 `preload.ts` 中映射为 `window.electronAPI` 方法。

接口类型分为：

| 类型 | 含义 |
|---|---|
| Query | 读取数据，不改变业务状态 |
| Command | 创建、修改或触发运行 |
| Event | 客户端后端向渲染进程推送的状态变化 |

### 1.3 数据归属

每个接口都必须标明数据来源：

| 数据来源 | 含义 |
|---|---|
| SEP | 客户端无法自行取得，需要调用 SEP 平台接口 |
| Local | 客户端后端本地任务、run、事件或配置数据 |
| Runtime | 当前 Electron 进程中的运行时状态 |
| Aggregate | 客户端后端将多个来源组合成前端视图模型 |

首页接口属于 `Aggregate` 接口。前端不应自行拼接 SEP 原始对象和本地 `ClientTask`。

### 1.4 通用响应约定

IPC 成功响应沿用客户端现有约定，由具体接口声明业务字段；失败统一由客户端错误码和错误信封返回，不在各接口中重复定义错误对象。

```ts
interface IpcSuccess<T> {
  success: true
  data: T
}

interface IpcFailure {
  success: false
  error: {
    code: string
    message: string
    retryable?: boolean
  }
}
```

接口文档中的 `Response` 表示 `data` 内部的业务对象。实际 IPC 是否保留当前项目中的扁平成功结构，由实现阶段统一处理，不改变业务字段语义。

### 1.5 时间、排序与分页

- 接口内部传输时间统一使用 Unix 毫秒时间戳；SEP 适配器负责转换 ISO 时间。
- 列表默认按 `updatedAt` 倒序；同一时间使用稳定的 `id` 顺序。
- 首页员工数量通常较小，但工作列表必须保留 `limit` 和 `cursor` 扩展位。
- 游标由客户端后端生成，前端不得依赖本地文件名或数据库主键排序规则。

## 2. 首页业务边界

首页呈现四类信息：

1. 企业员工规模：公司拥有的有效数字员工数量，以及当前用户可使用的数量。
2. 员工卡片：员工名称、头像、职能、订阅状态、可用性和今日工作量。
3. 员工工作抽屉：点击员工后查看正在进行、历史和全部工作，并可点击工作进入工作记录。
4. 运行变化：任务创建、进度变化、等待确认、完成、失败和删除时自动更新页面。

首页不负责：

- 直接查询 SEP 数据库。
- 直接读取客户端任务文件。
- 解析 prompt 尾部的业务 JSON 作为正式接口协议。
- 自行推断员工与工作的关联关系。
- 自行决定任务状态的业务含义。

## 3. 硅基员工模型结论

### 3.1 当前客户端识别关系

客户端只把平台订阅作为员工运行身份：

```text
DigitalEmployee
  └── subscriptions -> Subscription
```

`subscriptionId` 是客户端选择员工、校验模型和创建 run 的稳定标识；员工名称、职能、版本、
技能和允许模型来自订阅目录。客户端不建立部门、部门分支或部门授权摘要模型。

### 3.2 员工目录字段规则

员工目录返回通用职能和运行所需的授权信息，不返回 `department`、`departmentId` 或 `departments`：

- `roleName` 来自数字员工的 `position` 或平台定义的职能名称。
- `assignedToMe = true` 表示当前成员可以选择该订阅开始工作。
- `availability` 由客户端本地运行状态覆盖目录基础状态。
- 平台返回的员工目录必须在 SEP adapter 中完成 schema 校验和字段归一化。

## 5. 首页聚合接口

### HOME-001 `home.getOverview`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 首页聚合 |
| 类型 | Query |
| 调用时机 | 首页打开、登录完成、账号切换、首页重新进入 |
| 前端效果 | 一次加载首页首屏的企业统计、员工卡片和工作概况 |
| 当前状态 | 客户端后端未实现 |
| SEP 依赖 | `employee.list`、`employee.getEnterpriseSummary` 对应的平台数据 |

#### 请求

```ts
interface HomeOverviewRequest {
  includeWorkSummary?: boolean
}
```

`includeWorkSummary` 默认开启。保留该字段是为了将来在员工目录刷新和首页轻量更新时只请求必要部分。

#### 响应

```ts
interface HomeOverviewResponse {
  enterprise: {
    id: string
    name: string
    totalActiveEmployeeCount: number
    ownedEmployeeCount: number
  }

  employees: HomeEmployeeCard[]

  workSummary: {
    total: number
    active: number
    waitingUser: number
    failed: number
    completedToday: number
  }

  generatedAt: number
}
```

#### 规则

- `totalActiveEmployeeCount` 统计企业下 `Subscription.status = ACTIVE` 的订阅数量，不统计平台全部 `DigitalEmployee` 数量。
- `ownedEmployeeCount` 统计当前用户通过 `EmployeeGrant` 可使用的有效订阅数量。
- `active` 包括 `arranging`、`running`、`waiting-user`。
- `completedToday` 按客户端本地任务的完成时间和客户端时区计算。
- SEP 员工目录请求失败时，不得用旧账号缓存冒充新账号数据；应返回可识别的错误并触发认证/重试语义。
- 本地工作读取失败时，应区分“没有工作”和“持久化故障”。

### HOME-002 `home.getEmployeeWorks`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 首页聚合 |
| 类型 | Query |
| 调用时机 | 用户点击员工卡片，打开员工工作抽屉 |
| 前端效果 | 显示该员工的正在进行、历史和全部工作 |
| 当前状态 | 客户端后端未实现正式接口 |
| SEP 依赖 | 不需要；员工 ID 的有效性由当前目录快照校验 |

#### 请求

```ts
interface HomeEmployeeWorksRequest {
  employeeId: string
  bucket: 'active' | 'history' | 'all'
  limit?: number
  cursor?: string
}
```

#### 响应

```ts
interface HomeEmployeeWorksResponse {
  employeeId: string
  bucket: 'active' | 'history' | 'all'
  works: HomeWorkSummary[]
  nextCursor: string | null
  generatedAt: number
}
```

#### 工作关联规则

一个工作只要满足以下任一条件，就属于该员工：

```text
工作当前执行员工 = employeeId
工作参与员工列表包含 employeeId
工作步骤分配员工包含 employeeId
```

该判断由客户端后端统一实现。前端不能只根据当前执行员工过滤，否则工作流中已经完成或尚未轮到的员工会从抽屉中消失。

#### bucket 语义

| bucket | 包含状态 | 前端标签 |
|---|---|---|
| `active` | `arranging`、`running`、`waiting-user` | 正在进行 |
| `history` | `completed`、`failed`、`paused` | 已完成/历史 |
| `all` | 全部状态 | 全部 |

前端当前文案是“已完成”，但其中还会显示失败和暂停工作。接口使用 `history`，由 UI 决定显示文案，避免接口把失败误定义成完成。

### HOME-003 `home.getWorkSummary`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 首页聚合 |
| 类型 | Query |
| 调用时机 | 首页工作卡片需要补充数据、从通知或深链接打开工作 |
| 前端效果 | 返回单个工作卡片和跳转所需的稳定摘要 |
| 当前状态 | 未实现；当前由前端从 `ClientTask` 和 prompt 推导 |
| SEP 依赖 | 不需要 |

#### 请求

```ts
interface HomeWorkSummaryRequest {
  workId: string
}
```

#### 响应模型

```ts
interface HomeWorkSummary {
  id: string
  title: string
  kind: 'conversation' | 'arrangement'
  status: 'arranging' | 'running' | 'waiting-user' | 'completed' | 'failed' | 'paused'
  progress: number

  currentEmployeeId: string | null
  currentEmployeeName: string | null
  participantEmployeeIds: string[]

  createdAt: number
  updatedAt: number
  completedAt: number | null

  today: {
    created: boolean
    completed: boolean
  }

  flags: {
    hasUnreadResult: boolean
    requiresUserAction: boolean
    hasFailure: boolean
  }

  deliverableCount: number
}
```

#### 规则

- `updatedAt` 必须来自任务或事件的真实最后更新时间，不能继续使用 `completedAt ?? startedAt ?? createdAt` 近似计算。
- `progress` 由客户端后端按照工作类型和步骤状态生成，前端只负责展示。
- 首页摘要不返回完整 prompt、消息、工具输入或事件 payload。
- 不把 prompt 中的 `[SEP_WORK_META]` 作为长期接口协议；它只能作为旧数据兼容读取方式。

## 6. 员工目录接口

### EMP-001 `employee.list`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 企业硅基员工目录 |
| 类型 | Query |
| 调用时机 | 登录后、首页打开、目录 TTL 到期或用户主动重新进入 |
| 前端效果 | 员工卡片、员工头像、职能和可用状态 |
| 当前状态 | 已有基础实现 `auth:get-instances` |
| SEP 依赖 | 现有 `/client/subscriptions`，兼容 `/client/instances` |

#### 响应模型

```ts
interface HomeEmployeeCard {
  subscriptionId: string
  employeeId: string

  name: string
  avatar: string | null
  roleName: string
  functionalCategory: string | null
  description: string | null

  subscriptionStatus: 'active' | 'paused' | 'expired' | 'terminated'
  assignedToMe: boolean
  availableToRun: boolean

  templateVersion: string
  allowedModels: string[]
  skillIds: string[]

  availability: 'ready' | 'working' | 'unavailable' | 'needs-auth'
  lastWorkedAt: number | null
}
```

#### SEP 数据基础

```text
Subscription
DigitalEmployee
EnterpriseMember
EmployeeCapabilityBinding
Capability
SubscriptionSkillVersion
```

#### 规则

- `roleName` 来自数字员工的 `position` 或平台定义的职能名称。
- `availability = working` 由客户端本地运行状态覆盖目录基础状态；SEP 订阅 ACTIVE 不代表当前没有任务运行。
- `assignedToMe = true` 的员工才能出现在首页快速安排工作的可选列表中。
- 平台返回的员工目录必须在 SEP adapter 中完成 schema 校验和字段归一化。

### EMP-002 `employee.getEnterpriseSummary`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 企业硅基员工目录 |
| 类型 | Query |
| 调用时机 | 首页加载或目录刷新 |
| 前端效果 | 顶部显示“公司员工总数”和“我拥有的员工” |
| 当前状态 | 未实现 |
| SEP 依赖 | 需要新增 SEP 客户端接口 |

#### 建议 SEP 接口

```http
GET /client/enterprise/employee-summary
```

#### 响应

```ts
interface EnterpriseEmployeeSummary {
  enterpriseId: string
  totalActiveSubscriptions: number
  currentMemberGrantCount: number
  generatedAt: string
}
```

#### SEP 实现依据

统计应基于：

```text
Subscription.enterpriseId
Subscription.status = ACTIVE
EmployeeGrant.memberId = 当前 EnterpriseMember.id
EmployeeGrant.subscriptionId
```

不应以 `DigitalEmployee` 总数代替企业订阅数量，也不应把其他成员不可用的订阅计入当前用户可选数量。

## 7. 工作查询接口

### WORK-001 `work.list`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 工作查询 |
| 类型 | Query |
| 调用时机 | 首页加载、员工抽屉筛选、工作列表页 |
| 前端效果 | 提供工作摘要列表 |
| 当前状态 | 部分实现为 `task:get-all` |
| SEP 依赖 | 不需要 |

#### 请求

```ts
interface WorkListRequest {
  status?: Array<'arranging' | 'running' | 'waiting-user' | 'completed' | 'failed' | 'paused'>
  employeeId?: string
  createdFrom?: number
  createdTo?: number
  limit?: number
  cursor?: string
}
```

#### 响应

```ts
interface WorkListResponse {
  works: HomeWorkSummary[]
  nextCursor: string | null
  generatedAt: number
}
```

`task:get-all` 可以作为底层实现继续保留，但首页不应依赖其完整 `ClientTask` 结构。工作查询服务负责将任务、元数据、run 和事件投影为 `HomeWorkSummary`。

### WORK-002 `work.getDetail`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 工作查询 |
| 类型 | Query |
| 调用时机 | 用户点击首页工作卡片后进入工作记录或工作详情 |
| 前端效果 | 显示工作步骤、消息、产出文件和完整时间线 |
| 当前状态 | 已有 `task:get`、`task:get-messages`、`task:get-timeline` 等底层接口 |
| SEP 依赖 | 不需要 |

#### 顶层响应建议

```ts
interface WorkDetail {
  summary: HomeWorkSummary
  steps: WorkStepSummary[]
  messages: WorkMessage[]
  timeline: WorkTimelineEntry[]

}
```

现有多个 IPC 接口可以继续作为内部或兼容接口，但顶层说明书把它们归入一个工作详情能力，避免页面承担数据拼装和状态解释。

## 8. 首页实时事件接口

### EVENT-001 `home.onChanged`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 首页实时更新 |
| 类型 | Event |
| 发送方向 | 客户端后端 -> 渲染进程 |
| 前端效果 | 无刷新按钮时自动更新工作卡片、员工忙闲状态和提醒图标 |
| 当前状态 | 部分实现为 `task:updated`、`task:list-updated`、`pi:event` |
| SEP 依赖 | 员工目录变化通常不需要实时 SEP 推送，可按 TTL 刷新 |

#### 事件模型

```ts
interface HomeChangedEvent {
  reason:
    | 'work-created'
    | 'work-updated'
    | 'work-completed'
    | 'work-failed'
    | 'work-deleted'
    | 'employee-directory-updated'

  workIds: string[]
  employeeIds: string[]
  generatedAt: number
}
```

#### 规则

- 任务运行状态由客户端 runtime 产生，不依赖 SEP 轮询。
- `text_delta` 等高频 Pi 事件可以继续走运行记录专用通道；首页只消费聚合后的状态变化，避免首页被每个 token 触发完整重算。
- 页面重载后必须先调用 `home.getOverview`，不能假设事件历史完整。
- 事件必须带有明确的 `reason` 和 ID 列表，不能只发送无类型的 `unknown` payload。

以下能力被首页调用，但不属于首页模块：

| 接口 | 所属模块 | 当前状态 | 首页场景 |
|---|---|---|---|
| `conversation.create` | 对话工作 | 已实现 | 首页快速输入目标并创建对话工作 |
| `task.execute` | 工作执行 | 已实现 | 创建对话工作后开始执行 |

### 10.1 现有接口扩展

```http
GET /client/subscriptions
```

建议返回首页员工目录所需的最小字段：

```text
Subscription.id
Subscription.employeeId
Subscription.name
Subscription.status
Subscription.templateVersion
DigitalEmployee.name
DigitalEmployee.position
DigitalEmployee.functionalCategory
DigitalEmployee.description
DigitalEmployee.avatar
allowedModels
```

客户端只要求返回订阅、员工职能、技能和允许模型；部门授权不是客户端员工模型的一部分。

### 10.2 建议新增接口

```http
GET /client/enterprise/employee-summary
```

用途：返回企业有效订阅总数和当前成员授权数量。

### 10.3 条件性新增接口

如果 `/client/subscriptions` 无法返回完整员工资料，可以增加：

```http
GET /client/subscriptions/{subscriptionId}/profile
```

建议聚合：

```text
Subscription
DigitalEmployee
EmployeeCapabilityBinding
Capability
SubscriptionSkillVersion
```

该接口必须按照当前登录用户和企业范围过滤，不能返回无权限员工的技能、授权或配置。

## 11. 错误与刷新语义

| 场景 | 接口行为 | 首页处理 |
|---|---|---|
| 未登录或 token 失效 | `AUTH_REQUIRED` | 清空当前企业数据，回到登录状态 |
| SEP 暂时不可用 | `SERVICE_UNAVAILABLE` / `NETWORK_ERROR` | 保留可验证的本地工作摘要，员工目录显示不可用状态 |
| 员工订阅不存在 | `EMPLOYEE_UNAVAILABLE` | 不允许发起新工作，历史工作仍可查看 |
| 本地任务数据损坏 | `PERSISTENCE_ERROR` | 不伪装成空列表，显示可恢复错误 |
| 工作不存在 | `NOT_FOUND` | 关闭抽屉或返回工作列表，并清理失效导航状态 |
| 工作状态不允许操作 | `INVALID_STATE` | 保留当前页面数据，提示操作不能执行 |

首页刷新不是用户必须触发的动作：

```text

任务变化 -> home.onChanged
目录 TTL 到期 -> 后台重新获取 employee.list
认证变化 -> 清理旧 scope 后重新加载
```

## 14. 安排工作模块：业务边界与已确定规则

### 14.1 模块定位

安排工作不是一个单独的“创建任务”接口，而是一条从编辑到执行的业务链：

```text
ArrangementDraft
  -> 自动编排或手动编排
  -> 计划校验
  -> 订阅有效期与环境预检查
  -> 用户确认
  -> WorkPlan（不可变快照）
  -> WorkExecution（执行实例）
  -> 节点状态、失败决策和断点恢复
```

三种安排方式最终都形成同一种 `WorkPlan`：

| 安排方式 | 计划来源 | 计划特点 |
|---|---|---|
| `conversation` | 用户选择员工并输入目标 | 多员工共享同一上下文，可在同一工作内切换员工 |
| `auto` | 客户端后端调用 AI 生成 | 生成后用户可以修改员工、节点、依赖、模型和执行设置 |
| `manual` | 用户直接编辑 | 使用真正的 DAG，执行关系由 `dependsOn` 决定，不由数组顺序决定 |

### 14.2 已确定的业务规则

1. 对话式工作允许多个员工参与。员工共享同一个对话上下文；切换员工不创建新工作。
2. 自动编排在用户点击开始后立即调用客户端后端 AI，AI 结果首先进入草稿，用户确认前不执行。
3. 自动编排生成的草稿允许用户修改，修改后必须重新校验。
4. 手动编排必须支持 DAG：无依赖节点可以并行就绪，一个节点可以依赖多个节点，不能存在环。
5. 模型绑定到节点。同一个员工在不同节点可以使用不同模型；每个节点模型都必须单独通过员工订阅的模型白名单校验。
6. 权限是任务级策略。所有员工和所有节点共享同一份任务权限，不能由节点或 renderer 越权扩大。
7. 工作目录是任务级共享工作区，所有员工和 DAG 节点默认使用同一个工作区。
8. 草稿永久保存，只有用户主动删除时才删除；退出客户端、页面切换和异常重启都不能自动删除草稿。
9. DAG 任意节点失败后，整个执行进入等待用户状态；所有分支暂停调度，依赖失败节点的后续节点标记为阻塞。
10. 失败后用户只有两个选择：重试失败节点，或停止整个工作。不允许跳过失败节点，也不允许单独放行独立分支。
11. 客户端正常退出、异常退出或运行时崩溃时，所有正在运行的节点和执行实例都必须落盘为 `interrupted`。
12. 断点恢复从中断节点继续，已完成节点不重复执行；被失败节点阻塞的节点仍保持阻塞，直到失败节点重试成功。
13. 执行前按每个不同的员工订阅检查当前可用性和 `Subscription.endDate`。剩余订阅时间低于系统阈值时，必须在开始前告知用户并阻止启动。

### 14.3 不属于安排工作接口的内容

- Pi SDK session 对象、Employment Token 和 refresh token 不进入任何接口请求或响应。
- `allowedTools` 不接受 renderer 直接提交，由客户端后端根据权限档位计算。
- 工作记录中的完整消息、工具输入和事件时间线属于工作记录接口，不塞入安排草稿列表。
- 前端动画、匹配过程中的内部推理和 UI 临时状态不是接口协议。

## 15. 安排工作核心数据模型

### 15.1 `ArrangementDraft`

草稿是可编辑、可持久化的用户文档。草稿不是正式工作，不进入首页工作统计，也不产生执行记录。

```ts
interface ArrangementDraft {
  id: string
  schemaVersion: 1
  revision: number
  mode: 'conversation' | 'auto' | 'manual'
  status: 'editing' | 'planning' | 'planning-failed' | 'ready' | 'preflight-failed' | 'confirmed'

  title: string
  goal: string
  confirmedInputs: string[]
  sharedSkillIds: string[]

  conversation: ConversationArrangement | null
  nodes: ArrangementNode[]

  workspace: SharedWorkspace
  permissions: RequestedTaskPermissionPolicy

  createdAt: number
  updatedAt: number
  lastPlanning: PlanningSummary | null
}
```

草稿保存位置由客户端后端的 `ScopePath` 派生，至少按 `enterpriseId/memberId` 隔离。接口不暴露真实文件路径。

### 15.2 `ConversationArrangement`

```ts
interface ConversationArrangement {
  participants: Array<{
    subscriptionId: string
    modelId: string
  }>
  activeSubscriptionId: string | null
}
```

这里的 `participants` 是创建工作时的初始参与员工和模型绑定。对话运行期间切换员工仍然共享同一个上下文；运行时可以依据授权结果追加新的参与者记录，但不会改变历史消息归属，也不会创建新的工作 ID。

### 15.3 `ArrangementNode`

```ts
interface ArrangementNode {
  id: string
  subscriptionId: string
  modelId: string
  title: string
  instruction: string
  expectedOutput: string
  dependsOn: string[]
  skillIds: string[]
  requiresUserConfirmation: boolean
}
```

前端的“完成什么、需要什么、产出什么”映射为 `title`、`instruction`/输入内容和 `expectedOutput`；执行关系只由 `dependsOn` 表达。`requiresUserConfirmation` 是节点完成后的业务确认，不等同于工具审批，也不改变任务级权限。

### 15.4 `SharedWorkspace`

```ts
interface SharedWorkspace {
  mode: 'shared'
  path: string | null
}
```

`path = null` 表示由客户端后端为当前用户和工作生成默认工作区。用户选择的绝对路径在主进程中进行规范化、越界检查和敏感路径检查；所有节点使用同一个最终解析路径。

### 15.5 任务级权限策略

产品层权限档位采用 `Pi权限分级方案.md` 的三档模型：

```ts
type PermissionPreset = 'read-only' | 'workspace-edit' | 'full-local'

interface RequestedTaskPermissionPolicy {
  preset: PermissionPreset
  allowedPaths?: string[]
  deniedPaths?: string[]
  commandPolicy?: 'disabled' | 'restricted' | 'confirm-each'
}

interface EffectiveTaskPermissionPolicy extends RequestedTaskPermissionPolicy {
  allowedTools: string[]
  requireApprovalFor: string[]
  commandPolicy: 'disabled' | 'restricted' | 'confirm-each'
}
```

档位到 Pi 工具白名单的固定映射：

| 档位 | 允许工具 |
|---|---|
| `read-only` | `read`、`grep`、`find`、`ls` |
| `workspace-edit` | 上述只读工具 + `write`、`edit` |
| `full-local` | 上述工作区编辑工具 + `bash` |

有效策略还必须经过 SEP 平台能力上限、企业策略、共享工作区路径策略三重约束。`write`、`edit`、`bash` 即使在白名单中，仍按审批策略逐次确认；未知工具默认拒绝。

### 15.6 `WorkPlan`

用户确认后生成不可变的工作计划快照。后续修改必须回到草稿并创建新的工作计划，不能覆盖已经开始执行的计划。

```ts
interface WorkPlan {
  id: string
  schemaVersion: 1
  sourceDraftId: string
  sourceDraftRevision: number
  mode: 'conversation' | 'auto' | 'manual'
  title: string
  goal: string
  conversation: ConversationArrangement | null
  nodes: ArrangementNode[]
  workspace: SharedWorkspace
  permissions: EffectiveTaskPermissionPolicy
  confirmedInputs: string[]

  failurePolicy: {
    onNodeFailure: 'wait-user'
    dependentNodes: 'blocked'
    independentBranches: 'hold'
    allowSkip: false
  }
  recoveryPolicy: {
    resumeFrom: 'interrupted-node'
    rerunCompletedNodes: false
  }

  planHash: string
  createdAt: number
}
```

### 15.7 `WorkExecution` 与节点状态

```ts
type WorkExecutionStatus =
  | 'queued'
  | 'running'
  | 'waiting-user'
  | 'interrupted'
  | 'completed'
  | 'stopped'
  | 'failed'

type WorkNodeStatus =
  | 'pending'
  | 'ready'
  | 'running'
  | 'completed'
  | 'failed'
  | 'blocked'
  | 'interrupted'
  | 'stopped'

interface WorkNodeCheckpoint {
  nodeId: string
  status: WorkNodeStatus
  attempt: number
  startedAt: number | null
  completedAt: number | null
  output: string | null
  error: string | null
  lastEventSequence: number
}

interface WorkExecution {
  id: string
  workPlanId: string
  status: WorkExecutionStatus
  nodeStates: WorkNodeCheckpoint[]
  failureNodeId: string | null
  interruptionReason: 'client-exit' | 'client-crash' | 'runtime-error' | null
  startedAt: number | null
  endedAt: number | null
  updatedAt: number
}
```

## 19. 计划校验、预检查与确认

### ARRANGE-009 `arrange.validateDraft`

#### 请求

```ts
interface ValidateDraftRequest {
  draftId: string
  expectedRevision?: number
}
```

#### 响应

```ts
interface DraftValidationIssue {
  code:
    | 'EMPTY_GOAL'
    | 'NO_NODES'
    | 'DUPLICATE_NODE_ID'
    | 'MISSING_DEPENDENCY'
    | 'SELF_DEPENDENCY'
    | 'CYCLE'
    | 'EMPLOYEE_MISSING'
    | 'MODEL_MISSING'
    | 'INVALID_CONVERSATION'
  path: string
  nodeId: string | null
  severity: 'error' | 'warning'
  message: string
}

interface ValidateDraftResponse {
  valid: boolean
  issues: DraftValidationIssue[]
  checkedRevision: number
}
```

校验规则：

- `manual` 和 `auto` 至少有一个有效节点；`conversation` 至少有一个参与员工。
- 节点 ID 唯一、安全、非空；依赖只能指向当前草稿中的节点。
- 禁止自依赖和环；多个前置节点是合法的 DAG 结构。
- 节点必须绑定员工和模型，但员工是否仍为 ACTIVE、模型是否仍在白名单由预检查负责。
- 依赖数组的排列顺序不表示执行顺序。

### ARRANGE-010 `arrange.preflightDraft`

#### 接口信息

| 项目 | 说明 |
|---|---|
| 所属模块 | 计划预检查 |
| 类型 | Query（带一次性检查快照） |
| 前端效果 | 用户点击确认前，逐项看到员工可用性、订阅剩余时间、模型、技能、权限和共享目录是否满足运行条件 |
| 当前状态 | 未实现 |
| SEP 依赖 | 推荐新增 `POST /client/work-plans/preflight`；目录接口至少要返回 `Subscription.endDate` |

#### 请求

```ts
interface PreflightDraftRequest {
  draftId: string
  expectedRevision: number
}
```

#### 响应

```ts
interface SubscriptionPreflight {
  subscriptionId: string
  employeeId: string
  status: 'ACTIVE' | 'PAUSED' | 'EXPIRED' | 'TERMINATED'
  subscriptionEndAt: number | null
  remainingTimeMs: number | null
  thresholdTimeMs: number
  available: boolean
  passesThreshold: boolean
  reasonCode: string | null
}

interface NodePreflight {
  nodeId: string
  subscriptionId: string
  modelId: string
  employeeAvailable: boolean
  modelAllowed: boolean
  subscription: SubscriptionPreflight
  passes: boolean
  issues: string[]
}

interface PlanPreflight {
  preflightId: string
  draftId: string
  draftRevision: number
  valid: boolean
  canStart: boolean
  subscriptions: SubscriptionPreflight[]
  nodes: NodePreflight[]
  workspace: {
    path: string
    accessible: boolean
    withinPolicy: boolean
    passes: boolean
  }
  permissions: {
    requestedPreset: PermissionPreset
    effective: EffectiveTaskPermissionPolicy | null
    passes: boolean
  }
  blockingIssues: string[]
  warnings: string[]
  checkedAt: number
  expiresAt: number
}
```

预检查的订阅时间规则：

```text
Subscription.status 必须为 ACTIVE
endDate 为空 -> 不受结束时间限制
endDate 已过期 -> 不通过
endDate - 当前时间 < thresholdTimeMs -> 不通过
```

同一订阅只检查一次，多个节点复用同一份检查结果；不把节点预计执行时长累加，也不把余额或 token 伪装成剩余时间。阈值由客户端后端/SEP 策略提供，renderer 不能通过请求参数降低阈值。

预检查结果有有效期。确认接口必须再次做权威检查，不能只相信前端缓存的 `preflightId`。

### ARRANGE-012 `arrange.confirmAndStart`

#### 请求与响应

```ts
interface ConfirmAndStartRequest {
  draftId: string
  expectedRevision: number
  preflightId?: string
  idempotencyKey: string
}

interface ConfirmAndStartResponse {
  workPlan: WorkPlan
  execution: {
    id: string
    status: 'queued' | 'running'
  }
}
```

后端内部按以下顺序执行，并以 `idempotencyKey` 防止重复点击产生多个工作：

```text
读取并锁定草稿 revision
  -> 重新验证 DAG 与员工/模型/权限
  -> 向 SEP 发起权威订阅预检查
  -> 生成不可变 WorkPlan
  -> 创建 WorkExecution
  -> 写入任务、计划和初始执行记录
  -> 入队执行
```

如果权威预检查失败，不创建可运行的执行实例；如果计划已经冻结但入队失败，返回可重试的状态，并保留 `awaiting-start` 计划，不能创建第二份计划。

## 20. 执行、失败与断点恢复接口

以下接口属于工作执行模块，但由安排工作模块产生的 `WorkPlan` 使用。

### WORK-003 `work.start`

```ts
interface StartWorkRequest {
  workPlanId: string
  idempotencyKey: string
}

interface StartWorkResponse {
  executionId: string
  status: 'queued' | 'running'
}
```

`work.start` 适用于 `arrange.confirmDraft` 生成的未启动计划。运行时在每个节点真正开始前仍然检查员工订阅和 Employment Token，不能把预检查当作永久授权。

### WORK-004 `work.retryFailedNode`

```ts
interface RetryFailedNodeRequest {
  workId: string
  nodeId: string
  idempotencyKey: string
}

interface RetryFailedNodeResponse {
  executionId: string
  nodeId: string
  status: 'queued' | 'running'
}
```

只有工作处于 `waiting-user` 且指定节点为 `failed` 时允许调用。重试成功后重新计算 DAG：直接或间接依赖该节点的 `blocked` 节点恢复为 `pending/ready`，独立分支也从 hold 状态恢复调度；已完成节点不重跑。

### WORK-005 `work.resumeInterrupted`

```ts
interface ResumeInterruptedRequest {
  workId: string
  idempotencyKey: string
}

interface ResumeInterruptedResponse {
  executionId: string
  resumedNodeIds: string[]
  status: 'queued' | 'running'
}
```

该接口用于客户端退出、崩溃或运行时异常后的断点恢复：

- `completed` 节点不重复执行。
- `interrupted` 节点创建新的 attempt 并重新入队。
- 失败节点的后继仍为 `blocked`，不因恢复操作被跳过。
- 如果工作同时存在未处理的 `failed` 节点，不能绕过 `waiting-user` 决策，必须先调用 `work.retryFailedNode` 或 `work.stop`。

### WORK-006 `work.stop`

```ts
interface StopWorkRequest {
  workId: string
  reason?: string
  idempotencyKey: string
}

interface StopWorkResponse {
  executionId: string
  status: 'stopped'
}
```

停止是终态操作。尚未开始的节点标记为 `stopped`，正在运行的节点先执行中止并最终落盘为 `interrupted` 或 `stopped`，已完成节点保持完成记录和产出文件。

### WORK-E001 `work.executionChanged`

```ts
interface WorkExecutionChangedEvent {
  workId: string
  executionId: string
  version: number
  status: WorkExecutionStatus
  changedNodeIds: string[]
  failureNodeId: string | null
  reason:
    | 'created'
    | 'node-started'
```

现有 `task:updated` 可以作为兼容事件，但正式首页和工作记录应消费聚合后的执行事件。`pi:event` 仍可用于对话流式文本和工具审批，不应由页面自行推断 DAG 全局状态。

## 21. DAG 状态与执行规则

### 21.1 正常调度

```text
所有依赖 completed/skipped（本设计不允许 skip）
  -> 节点 ready
  -> 获取共享工作区锁和运行资源
  -> running
  -> completed 或 failed
```

无依赖节点可以同时成为 `ready`。但工作目录是共享的，实际并发必须经过工作区锁和工具策略；拥有写入能力的节点不能在未定义冲突策略时并发覆盖同一工作区文件。DAG 的并行语义表示依赖关系允许并行，不保证所有 ready 节点一定同时运行。

### 21.2 失败处理

```text
任一节点 failed
  -> WorkExecution = waiting-user
  -> 所有未开始节点 hold
  -> 直接/间接依赖失败节点 = blocked
  -> 已运行节点按自身结果结束
```

用户只能：

```text
retryFailedNode
stop
```

不提供 `skipNode` 或“只放行独立分支”接口。

### 21.3 中断和重启

```text
进程退出/崩溃
  -> 停止接受新节点
  -> 中止 worker
  -> running node -> interrupted
  -> running execution -> interrupted
  -> 下次启动扫描并补写未完成记录
```

恢复扫描必须幂等，不能把一次中断重复计数为多个 attempt，也不能把未收到完成事件的节点伪装成 completed。

### 22.1 扩展 `GET /client/subscriptions`

现有客户端对接指南已经定义该接口，但当前示例缺少安排工作所需的结束时间和完整授权上下文。建议扩展返回：

```json
{
  "subscriptionId": "sub_1",
  "employeeId": "employee_1",
```

### 22.2 新增 `POST /client/work-plans/preflight`

客户端后端需要一个权威、批量的订阅预检查接口，避免为每个节点重复请求并避免前端目录缓存过期：

```json
{
  "subscriptions": [
    {
      "subscriptionId": "sub_1",
      "modelIds": ["model-a", "model-b"]
    }
  ]
}
```

建议响应：

```json
{
  "thresholdSeconds": 900,
  "subscriptions": [
    {
      "subscriptionId": "sub_1",
      "employeeId": "employee_1",

      "passes": true,
      "reason": null

  ],
```

SEP 后端应基于 `Subscription`、`PlatformModel` 和 `EnterpriseModelConfig` 做实时校验。阈值由服务端策略或双方约定的客户端配置返回，客户端不能通过请求参数绕过。

### 22.3 新增 `POST /client/planning/arrange`

由于企业规划模型可能位于 `EnterpriseModelConfig.plannerModel`，SEP 可以提供只生成计划、不创建正式任务的规划接口；但这不是客户端安排工作成立的必需条件。默认实现由客户端后端通过 `PlanGeneratorPort` 调用配置好的规划模型：

```json
{
  "objective": "整理上个月销售数据并生成复盘报告",
  "confirmedInputs": ["销售数据表", "渠道说明"],
  "candidateSubscriptionIds": ["sub_1", "sub_2"],
  "sharedSkillIds": ["skill_1"]
}
```

返回结构必须是可校验的业务 JSON，而不是自由文本：

```json
{
  "plannerModelId": "planner-model",
  "title": "销售数据复盘报告",
  "goal": "整理上个月销售数据并生成复盘报告",
  "nodes": [
    {
      "id": "node-1",
      "subscriptionId": "sub_1",
      "instruction": "整理并分析销售数据",
      "expectedOutput": "结构化分析结果",
      "dependsOn": [],
      "skillIds": [],
      "rationale": "负责数据整理"
    }
  ],
  "recommendations": [],
  "generatedAt": "2026-09-08T10:00:00.000Z"
}
```

`rationale` 只用于界面展示的简短理由，不得返回模型内部思维链。客户端后端收到后仍必须重新校验节点 ID、员工、模型、技能和 DAG，不能直接信任规划结果。

若未来决定由客户端 Pi SDK 本地完成规划，只需替换客户端后端的 `PlanGeneratorPort` 适配器；IPC 草稿和确认接口不变。

## 23. 安排工作错误语义

| 场景 | 错误码建议 | 行为 |
|---|---|---|
| 草稿不存在或不属于当前 scope | `NOT_FOUND` | 不泄露其他用户草稿信息 |
| 草稿 revision 过期 | `DRAFT_REVISION_CONFLICT` | 不覆盖新版本，返回当前 revision |
| DAG 结构不合法 | `INVALID_ARGUMENT` | 返回节点级 issue，不创建工作 |
| 自动编排失败 | `PLANNING_FAILED` | 草稿保留，允许重新编排 |
| 员工不是 ACTIVE 或授权失效 | `EMPLOYEE_UNAVAILABLE` | 预检查失败，禁止确认启动 |
| 模型不在员工白名单 | `MODEL_NOT_ALLOWED` | 指出节点和模型，禁止确认启动 |
| 订阅剩余时间低于阈值 | `SUBSCRIPTION_EXPIRING` | 告知用户订阅时间不足，禁止启动 |
| 工作区不可访问或越界 | `WORKSPACE_INVALID` | 禁止确认启动 |
| 任务权限超过企业/平台上限 | `PERMISSION_DENIED` | 降低权限或修改设置后重新预检查 |
| 失败节点不可重试 | `INVALID_STATE` | 只能对当前 failed 节点调用重试 |
| 工作被中断 | `EXECUTION_INTERRUPTED` | 使用断点恢复接口继续 |
| 工作已停止或完成 | `INVALID_STATE` | 不允许再次启动原执行实例 |

具体错误码需要加入 `electron/errors/error-codes.ts` 的唯一错误码表，不能在安排工作路由中手写新的错误信封。
