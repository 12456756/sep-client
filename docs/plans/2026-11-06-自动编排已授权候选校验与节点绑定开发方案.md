# 自动编排已授权候选校验与节点绑定开发方案

> 日期：2026-11-06
> 状态：已实施，待验收
> 范围：仅 `sep-client` 客户端

## 1. 背景与问题

自动编排第一阶段使用当前账号已经授权的员工。第一阶段无法完成的步骤会进入第二阶段企业员工目录和第三阶段平台员工目录，模型会输出待申请员工候选。

当前第二、第三阶段存在状态竞态：模型开始规划后，某个员工可能已经被用户授权，但客户端使用的授权员工目录仍是旧快照。模型或客户端能力匹配逻辑会把这个员工放入 `candidateMatches`，前端随后显示“申请员工”。用户点击申请后，平台可能发现该员工已经授权并拒绝重复申请，客户端最终只显示通用错误。

目标是：

- 第二、第三阶段模型完成后，刷新当前账号的授权员工目录。
- 已经授权的候选员工直接绑定到对应步骤并生成执行节点。
- 已授权员工不再保留在申请候选中。
- 前端不显示“某某员工已授权”的额外提醒。
- 前端只显示仍然未授权、确实需要申请的员工。
- 如果所有未解决步骤都已由授权员工补齐，直接进入计划确认/开始页面。
- 授权目录刷新失败时，继续使用本次编排第一阶段已经读取到的旧目录。

## 2. 当前代码事实

主要实现位于 `electron/service/arrangement-service.ts`。

- 第一阶段通过 `loadAuthorizedPlannerEmployees()` 获取授权员工。
- 第二阶段调用 `candidateEmployees.listEnterprise()`。
- 第三阶段调用 `candidateEmployees.listPlatform()`。
- 模型候选位于 `result.candidateMatches`。
- 客户端能力补充候选由 `matchCandidateEmployees()` 生成。
- 两类候选通过 `mergeCandidateMatches()` 合并到同一个 `candidateMatches` 数组。
- 去重键是 `stepId:employeeId`。
- 当前候选结构不记录“模型输出”或“客户端补充”的来源，只记录企业/平台来源、员工 ID、名称和匹配理由。
- 第二、第三阶段按提示词约定只输出申请候选，不生成执行节点。
- 前端 `AutoArrange.tsx` 按 `unresolvedSteps` 和 `candidateMatches` 显示申请项。
- 前端只有在草稿状态为 `ready` 且存在执行节点时显示确认并开始按钮。

因此本方案不新增模型候选来源字段，也不把申请候选直接伪装成执行节点。

## 3. 核心处理规则

### 3.1 授权目录快照

第一阶段开始时保存本次编排使用的授权员工快照，作为后续刷新失败时的回退数据。

第二、第三阶段模型完成后，分别执行一次授权目录刷新：

1. 调用 `employees.refresh()`。
2. 刷新成功时，使用最新的授权员工目录。
3. 刷新失败时，记录警告日志并使用第一阶段快照。
4. 不因刷新失败中断自动编排。
5. 不把刷新失败提示直接展示给用户。

刷新后的授权员工需要经过与第一阶段一致的规划员工构造流程，包括员工 ID、订阅 ID、模型权限、能力信息和媒体工具状态。

### 3.2 候选统一校验

模型返回候选和 `matchCandidateEmployees()` 补充候选已经合并在同一个 `candidateMatches` 中，因此统一按以下规则处理：

1. 使用 `candidate.employeeId` 与授权员工的 `employeeId` 比较。
2. 不使用候选中的 `subscriptionId` 判断最终执行身份。
3. 找到授权员工时，以授权目录中的 `subscriptionId` 为准。
4. 同一个步骤只要已经找到可执行的授权员工，就不再为该步骤展示申请候选。
5. 没有匹配到授权员工的候选继续保留，供前端申请。

### 3.3 已授权员工绑定节点

`candidateMatches` 只有申请候选信息，不包含完整的执行节点信息。因此发现已授权候选后，不能只修改 `canExecute`，也不能在客户端拼造一个不完整节点。

处理方式：

1. 为已授权候选建立内部步骤绑定：

```ts
{
  stepId,
  employeeId,
  subscriptionId: authorizedEmployee.subscriptionId,
}
```

2. 将该绑定加入现有的 `approvedEmployeeAssignments` 约束集合。
3. 使用授权员工阶段的规划逻辑，为绑定步骤生成正式执行节点。
4. 规划器必须使用绑定员工，不得改派其他员工。
5. 节点生成成功后，将节点合并到 `executableNodes`。
6. 从 `unresolvedSteps` 删除已经生成节点的步骤。
7. 从 `candidateMatches` 删除该步骤的申请候选。

这些内部绑定不是平台申请记录，也不创建 `employeeAccessRequests`，因为员工已经授权，不需要申请。

## 4. 第二阶段流程调整

第二阶段当前流程为：加载企业目录、调用模型、合并候选，然后直接进入第三阶段或保存草稿。

调整为：

1. 加载企业候选目录。
2. 调用第二阶段模型。
3. 合并 `result.candidateMatches` 和 `matchCandidateEmployees()` 的结果。
4. 刷新授权员工目录；失败时回退第一阶段快照。
5. 在合并后的 `candidateMatches` 中找出已经授权的员工。
6. 为这些员工创建步骤绑定。
7. 使用授权员工规划阶段生成对应执行节点。
8. 只有节点成功生成后，才从未解决步骤和申请候选中移除该步骤。
9. 对剩余未解决步骤进入第三阶段。

第二阶段发现已授权员工但授权规划没有成功生成节点时，不能静默删除步骤，必须保留该步骤和候选，避免丢失用户任务。

## 5. 第三阶段流程调整

第三阶段使用与第二阶段相同的校验逻辑：

1. 加载平台候选目录。
2. 调用第三阶段模型。
3. 合并模型候选和客户端能力补充候选。
4. 刷新授权员工目录；失败时回退第一阶段快照。
5. 查找已经授权的候选员工。
6. 建立步骤绑定并生成正式执行节点。
7. 成功生成节点后，移除对应未解决步骤和申请候选。
8. 剩余候选才保存到最终草稿。

第三阶段完成后，最终草稿必须满足：

- `nodes` 只包含可执行节点。
- `unresolvedSteps` 只包含尚未能绑定和执行的步骤。
- `candidateMatches` 只包含尚未授权、可申请的员工。

## 6. 前端行为

不新增“某某员工已授权”提示，也不新增授权状态卡片。

后端通过清理 `unresolvedSteps` 和 `candidateMatches` 让现有前端自然得到正确结果：

- 已授权并成功绑定的员工只出现在执行节点中。
- 未授权员工继续显示“申请员工”。
- 已授权员工不出现在申请列表。
- 所有步骤都已经生成节点时，草稿状态为 `ready`。
- `AutoArrange.tsx` 现有的确认并开始入口自动显示。
- 仍有未解决步骤时，草稿状态保持 `awaiting-employee`，前端只显示剩余申请候选。

不通过前端过滤来解决问题，因为前端过滤不能阻止后端保存错误候选，也不能防止重复提交平台申请。

## 7. 申请时的并发保护

编排完成后到用户点击申请之间，员工授权状态仍可能发生变化。因此 `requestEmployeeAccess()` 需要增加最终保护：

1. 点击申请时刷新授权员工目录。
2. 刷新失败时使用当前已有授权快照，符合本方案的回退规则。
3. 如果员工仍未授权，才调用平台申请接口。
4. 如果员工已经授权，不调用平台申请接口。
5. 已授权时转入步骤绑定和节点生成流程。
6. 如果处理后没有剩余申请项，草稿转为 `ready`，前端进入计划确认/开始页面。

这一步用于避免编排完成后的状态竞态导致平台收到重复申请。

## 8. 建议的代码结构

在 `ArrangementService` 内提取一个共享的内部处理函数，避免第二、第三阶段复制逻辑。函数职责建议包括：

- 根据刷新策略取得授权规划员工。
- 在候选中识别已授权员工。
- 生成步骤绑定。
- 调用授权阶段规划生成节点。
- 清理已经解决的 `unresolvedSteps` 和 `candidateMatches`。
- 在规划失败时保留原步骤和候选。

第二阶段和第三阶段只负责提供本轮模型结果、候选目录和阶段上下文，统一函数负责后处理。

建议不要修改 `ArrangementCandidateMatch` 结构，不增加模型候选/客户端候选来源字段；两者当前业务上都属于“待处理候选”，统一校验即可。

## 9. 测试要求

至少增加以下后端测试：

1. 第二阶段返回已授权员工时，生成对应执行节点。
2. 第三阶段返回已授权员工时，生成对应执行节点。
3. 模型候选和客户端补充候选合并后，已授权员工都能被识别。
4. 生成节点使用刷新后授权目录中的真实 `subscriptionId`。
5. 已授权员工不会出现在最终 `candidateMatches`。
6. 所有未解决步骤都被授权员工补齐时，最终状态为 `ready`。
7. 授权目录刷新失败时，使用第一阶段授权快照。
8. 已授权候选生成节点失败时，步骤不会被静默删除。
9. 点击申请前员工刚刚获得授权时，不会调用平台申请接口。
10. 仍有未授权候选时，前端继续显示申请员工入口。

建议重点覆盖 `electron/service/arrangement-service.test.ts`，并补充需要的 `AutoArrange` 渲染测试，确认前端不显示已授权候选且 `ready` 状态显示确认开始入口。

## 10. 验收标准

以下场景均应满足预期：

### 场景 A：第二阶段候选在规划期间获得授权

第二阶段模型选中员工 A，刷新后发现 A 已授权。客户端为对应步骤生成 A 的执行节点，不显示申请 A。

### 场景 B：第三阶段候选在规划期间获得授权

第三阶段模型选中员工 B，刷新后发现 B 已授权。客户端为对应步骤生成 B 的执行节点，不显示申请 B。

### 场景 C：同一候选同时来自模型和能力补充

合并后只保留一条候选记录；授权校验只处理一条逻辑候选，不产生重复申请项。

### 场景 D：所有候选均已授权

最终没有未解决步骤和申请候选，草稿状态为 `ready`，用户直接进入计划确认/开始页面。

### 场景 E：部分候选仍未授权

已授权员工直接形成节点，未授权员工继续显示申请入口，前端不显示已授权员工的申请按钮。

### 场景 F：授权目录刷新失败

使用第一阶段授权快照继续编排，不中断任务，也不额外弹出用户提醒。

## 11. 实施边界

- 本方案只修改客户端。
- 不修改平台接口协议。
- 不修改第二、第三阶段的候选数据结构。
- 不增加“已授权”前端提示。
- 不把已授权员工创建为申请记录。
- 不静默删除无法生成节点的未解决步骤。
- 不修改用户原有的其他工作树改动。
