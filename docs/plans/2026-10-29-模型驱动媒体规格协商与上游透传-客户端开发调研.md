# 模型驱动媒体规格协商与上游透传：客户端开发调研

日期：2026-10-29

状态：客户端实现及本地验证已完成；SEP V3 真实合同联调、账号主体能力与生产验收待完成。本文不代表功能已经上线或任意上游规格已经验证。

配套：[SEP 开发调研](../../../SEP/docs/plans/2026-10-29-模型驱动媒体规格协商与上游透传-SEP开发调研.md)。

## 1. 已确定的产品方向

- 用户明确指定的规格优先；未指定的规格由当前任务模型分析用途、素材和需求后提出，关键信息不足时询问用户。
- 客户端与 SEP 不维护新任务的统一业务默认规格，不从 Profile 默认值、能力数组首项或旧偏好中静默补齐。
- 用户指定值必须原样保留；推荐方案通过结构化参数提交，不只写在创作提示词里。
- 上游不支持时说明字段、原因和可选方案；不自动改规格、换模型或改成脚本动画并宣称同一种交付。
- 身份授权、费用审批、文件安全、报价语义绑定和幂等防重复生成继续由可信主进程与 SEP 执行。

## 3. 现状与改动地图

### 3.1 三个问题要分别修

| 问题 | 已核实的根因 | 不能采用的修复 |
|---|---|---|
| 模型只看到 4 秒、16:9、720p 等 | SEP V2 runtime 固定能力/default；客户端按列表校验并填默认，工具描述又要求只传用户明确规格 | 只改提示词、删除 UI 下拉框或将 capabilities 数组扩大 |
| 编排说员工没有工具 | 规划输入主要是员工说明/技能，不是员工当前真实媒体 runtime；草稿还可能为只读 | 给所有员工写“会生视频”的静态标签，或自动提升任务权限 |
| 请求生视频却交付脚本合成 MP4 | 工具选择与交付验收没有始终绑定“真实模型生成”要求；模型可能把文件扩展名当作交付成立 | 禁止一切脚本、把任何 MP4 都当视频模型产物，或生成失败后静默换实现 |

当前员工会话可通过授权注入媒体工具；不能据此说「所有员工始终都有三个工具」。工具的实际可用性取决于企业/Profile 授权、员工运行时、适配器、任务工具策略和当前会话入口。`read-only` 与规格限制是两件事。

### 3.2 端到端调用链

```text
SEP 员工 runtime/真实授权
→ 客户端平台合同解析与 employee context
→ 会话/编排 prepareRun
→ Pi 工具注册、工具策略与提示词
→ host 解析参数、素材与费用授权
→ gateway quote/submit/query/download
→ 本地 job/store/文件与账务状态
→ UI + 编排交付验收
```

每一段都可能把规格变回默认或静态白名单。因此不能只修改模型提示词或 `videoFormParameters`。

视频 resolution 目前是 `480p/720p/1080p/4k`、format 是 MP4/WebM，时长≤600、帧率≤120；这些不是供应商能力的充分证明。新协议不沿用缺乏独立依据的产品枚举与上界，但仍验证有限正数、字符串长度、对象大小及文件资源安全。

图片 count/引用数量与输出数组索引、文件上限是贯穿协议的约束，不能单独改一个输入 `.max()` 就宣称无限。应区分生成数量的业务值与下载/解析资源控制、适配器当前参考图实现边界；相关边界要明确来源和错误类型。

## 4. 两端统一契约

### 4.1 新旧版本边界

以下为新版本契约设计；客户端已增加版本化分支，SEP endpoint 与双端联调仍待完成，不代表已上线。与 SEP 文档采用同一契约：

- runtime 建议升级为 `protocolVersion:3`，对应版本化媒体请求/quote/receipt/error。V1/V2 原 Schema 保留给历史读取和明确兼容路径，不直接修改其默认语义。
- Profile 保留身份、配置版本、操作/执行模式、适配器就绪状态；`capabilityHints` 标明 `source/observedAt/confidence`，未知可为空；它是建议证据，不是拒绝值列表。
- `defaultProfileId` 是已授权的默认路由，可以保留；`defaults.durationSeconds/defaultSize/defaultQuality` 等业务规格默认不用于新请求。
- 不新增 SEP 规格推理 LLM。当前执行任务的模型完成分析与澄清，现有 quote 优先承担参数完整性和可定价校验，不为本方案另外建设复杂协商服务。

### 4.2 统一数据语义

| 字段 | 规则 |
|---|---|
| `requestedSpec` | 用户要求 + 当前模型建议；用户明确要求不被覆盖，未决定字段可以省略 |
| `parameterSources` | 按字段记录 `user/model/upstream` 与决策引用；记录建议过程，不作为授权凭据。模型不能仅靠自报 user 来源绕过审批 |
| `specRevision` | 澄清、修改规格后递增；可复用现有 revision，旧 quote 不得沿用 |
| `effectiveSpec` | quote 冻结并回显的执行规格；只允许等价格式转换，客户端必须检查与 requestedSpec 同义 |
| `actualSpec` | 文件实测或可信供应商返回，带来源；不能拿 effectiveSpec 代替实测值 |
| `billingDimensions` | 报价和 usage 的实际计价语义，独立于文件实测；不能因输出不符自动声称没扣费 |
| `semanticHashVersion` | 决定规范化/哈希算法；旧任务永远用其原版本 |

图片规格建议覆盖 size/width/height、aspectRatio、count、quality；视频覆盖 durationSeconds、aspectRatio、resolution/width/height、frameRate、audio、outputFormat。字段集合由两端合同冻结，允许可扩展取值但不接受任意上游对象。

下面是模型根据「竖屏商品视频」提出的方案示例，不是默认值或已验证上游能力：

```json
{
  "protocolVersion": 3,
  "profileId": "authorized-video-profile",
  "configVersion": "cfg-current",
  "operation": "text-to-video",
  "referenceIds": [],
  "creativeBrief": "展示商品细节与使用场景，节奏明快",
  "specRevision": 1,
  "requestedSpec": {
    "durationSeconds": 8,
    "aspectRatio": "9:16",
    "resolution": "1080p"
  },
  "parameterSources": {
    "durationSeconds": "model",
    "aspectRatio": "user",
    "resolution": "model"
  }
}
```

### 4.3 缺字段怎样处理

1. 模型读取用户目的、投放位置、参考素材、上下文，保留所有明确约束，再补充有理由的规格方案。不要为了填满参数而编造用户要求。
2. 能合理确定的参数由模型建议并在计划/生成前摘要中可见；不要求每个可推断字段都弹窗确认。影响用途、成本或用户明确要求的歧义应先询问。
3. 请求不完整且缺少计价/上游必需项，host/SEP 返回 `MISSING_SPEC` 与字段原因，模型继续提案或询问；不会先调用付费生成探测默认值。
4. 对上游允许省略、且费用边界已明确的可选字段，保持省略，显示“未指定，由上游决定”。不能在 host/UI/SEP 中补成 24fps、medium、1 张等。
5. `false` 是明确关闭音频，不能当作缺失；非法 `0`、空串、NaN 等报字段错误。禁止 `|| default`、clamp、取数组首项或静默丢弃不支持字段。
6. 参数中尺寸与比例相互矛盾时解释冲突，让模型/用户修订；不能选一个覆盖另一个。等价格式规范化须透明回显，不能变更宽高或时长。

模型建议并不代表任何规格都能成功。未知能力可尝试取得报价；无法映射、价格不可得、上游明确拒绝必须分别说明。上游不支持后的新方案需要回到提案/报价流程，不可悄悄调整原请求。

### 4.4 费用和身份继续受控

- 模型提出参数，可信主进程决定可调用工具并取得既有费用授权；模型不能伪造 `autoApproveMedia` 或修改任务只读策略。
- `auto-approve` 只按原策略处理费用审批，不表示允许换规格、模型、主体或生成方式。
- quote 与 submit 绑定规格、需求版本、Profile/配置、prompt、素材哈希及价格版本；变更参数必须新报价、新请求身份，不复用旧幂等键制造冲突。
- 对未知提交，只查询原请求；不把一个 `retryable` 字段解释成授权再次付费。
- 不改变 renderer → controller → service → data/runtime → pi/sdk 分层。网络、文件路径、凭据处理留在可信边界，不能挪到 renderer。

## 5. 会话与工具选择策略

### 5.1 工具定位及优先级

| 需求 | 首选执行方式 | 必需条件 |
|---|---|---|
| 文生图/参考图编辑 | `media_generate_image`，按素材与意图选择 generate/edit | 主体真实有图片 runtime、允许该操作及费用授权 |
| 文生视频 | `video_generate` | 有文生视频 operation 与对应授权 |
| 图生视频 | `video_from_image` | 有图生视频 operation、可追溯参考素材 |
| 拼接、字幕、剪辑、数据动效、用户明确要脚本动画 | 现有脚本/FFmpeg 等合成或后处理 | 符合用户需求与工具策略，保留制作方式与素材来源 |
| 生成模型不可用或不接受规格 | 说明原因，提出可选方案并继续协商 | 不自动切脚本、模型、员工、规格或发起另一次收费生成 |

优先级来自**需求语义**。明确要求 AI 生成的视频，应优先使用真实生成工具；图表动画等适合程序化制作的任务可以直接用脚本。若只是模糊的「做个视频」，模型根据场景提出制作方案，需要改变交付语义时询问用户。不能设置一个一刀切的“所有视频都必须模型生成”规则。

本项目的本地 relay CLI 是当前开发代理的生图偏好，不等于桌面应用的媒体授权/账务通道。不能把本机密钥、CLI 或脚本回退写成所有应用员工的默认能力。

### 5.2 员工会话

实际入口 [conversation-executor.ts](../../electron/runtime/conversation-executor.ts) 在非 general 会话为 media/video 执行 `prepareRun`，SDK adapter 再结合 tools 与 task policy 注册工具。需要把新版 runtime、可用原因、协商状态传入同一会话，不改变授权过滤的安全职责。

系统提示词与工具描述统一要求：

- 先核对当次 runtime，不能依据岗位名、技能描述或历史对话判断有无工具。
- 把用户规格作为不可静默覆盖约束；模型分析出的建议以结构化参数传递。
- 查询到能力未知不是停止工作的理由；能报价则按合同继续，缺字段则协商。
- 生成成功还需查询完成、下载/保存及交付验收；不得把 tool-call 已发出写成最终完成。
- 上游拒绝后解释字段与原因，替代方案不自动执行；不把所有错误归为权限不足。

### 5.3 通用助手是独立接入项

同一文件当前对 `general` 明确设置 media/video tools 为 `undefined`，并使用原生系统提示词/禁用员工技能。只修改员工提示词不会让通用助手拥有工具。

如果产品目标是通用助手也能生成，需要 SEP 提供**账号/企业真实主体**的授权 runtime、计费与素材作用域，客户端以该主体完成 prepareRun 和费用流程；不能借用任意员工 subscription/token 或假造员工。通用助手仍可继续使用原生提示词框架，通过实际注册工具描述和任务上下文获得媒体政策。

该接入可以单独分期：先完成有授权员工的模型驱动规格流程；账号主体服务未实现前，通用助手如实显示未开通并可引导选择已授权员工。不要把它作为固定规格修复已经自动覆盖的功能。

## 6. 编排改造：让规划、执行和交付看到同一件事

### 6.1 给规划器真实能力，而不只是技能名

入口与当前缺口：

- [arrangement-planner.ts](../../electron/domain/arrangement-planner.ts) 的 `ArrangementPlannerEmployee` 主要包含员工、描述、技能能力，没有完整媒体授权 runtime。
- [arrangement-service.ts](../../electron/service/arrangement-service.ts) 通过 `employeeCapabilities.list` 组目录；[build-backend.ts](../../electron/bootstrap/build-backend.ts) 的现有 provider 主要读取员工技能，不能当成媒体工具是否可用的证据。
- 规划规则有两份：[arrangement-planner-prompts.ts](../../electron/domain/arrangement-planner-prompts.ts) 与 [prompts/arrangement-planner-prompts.md](../../prompts/arrangement-planner-prompts.md)，必须同步更新及测试。

建议在既有员工目录端口中附加最小媒体执行上下文：主体/授权版本、真实模式、可执行 operations/tools、Profile/adapter 就绪状态、能力提示来源，以及 `available/unavailable/unknown` 和具体原因。字段最小化，不能给规划器发 token、连接 URL 或全量配置。

草稿阶段可以执行无副作用的能力/授权查询；草稿只读不等于未来经用户明确授权后的执行节点永远不能生成。规划器应区分「员工有能力」「当前草稿不能提交」「待执行策略需用户选择」，不能因此直接判定全员无工具；真正的执行预检仍必须按最终策略复核。

### 6.2 保留用户硬要求与模型建议

`mediaRequirements.preferred` 等既有字段不能把用户指定的“8 秒、竖屏、必须 AI 生成”都变成可丢弃偏好。建议沿既有 [arrangement-plan.ts](../../electron/domain/arrangement-plan.ts)、[arrangement-planner-media.ts](../../electron/domain/arrangement-planner-media.ts) 扩展：

- `requiredSpec`：用户明确要求及其上下文引用；`proposedSpec`：模型补全建议；对接时合并为 requestedSpec。
- 每项需求保留 requirementId、revision、生成方式要求、输入素材及依赖，避免重规划后关联到错误产物。
- 操作（文生/图生）和素材选择依用户意图与真实引用决定，不因 capabilityHints 第一项改变。
- 预检硬检查真实授权、Profile/适配器、素材归属与依赖文件。静态规格提示不作为阻断白名单；价格和字段完整性在 quote 前按真实合同检查。
- 能力刷新或配置版本变更后重预检，不自动把新 Profile 当成旧请求的替代路由。

### 6.3 缺规格进入等待用户输入

在 [arrangement-executor.ts](../../electron/runtime/arrangement-executor.ts) 与现有工作状态/澄清机制中复用等待输入状态，不新增另一套独立任务调度器：

```text
需求分析 → 建议规格/识别歧义 → 等待用户输入（需要时）
→ 更新需求 revision → 预检/报价/授权 → 生成
→ 保存产物 → 规格与来源验收 → 提交交付物
```

模型已生成方案但未取得必须信息时，不能标完成、生成失败或“找不到员工”。暂停应保留 plan revision、问题、已完成节点与已提交媒体 job。用户回复后只恢复受影响节点，不重新提交已完成/未知的付费请求。

### 6.4 Bridge、素材和交付

主要改动 [arrangement-media-service.ts](../../electron/service/arrangement-media-service.ts)、[arrangement-media-runtime.ts](../../electron/domain/arrangement-media-runtime.ts)、[arrangement-media.ts](../../electron/domain/arrangement-media.ts)、[arrangement-delivery.ts](../../electron/domain/arrangement-delivery.ts) 与 executor/delivery 测试：

- normalize/bridge 保留规格、来源、revision、requirementId，不使用默认表单 helper 补齐。
- 上游图片节点输出按 artifact ID、hash、归属和依赖引用进入图生视频，不能仅传文件名或第一张图片。
- 交付记录关联 receipt/job、真实执行方式、原始与后处理资产、actualSpec、保存位置和验收状态。
- 要求 AI 生成的视频，必须由可信 host 绑定真实上游 job/产物；模型在文本中自报生成来源、脚本产生 MP4 都不能替代证据。
- 生成服务成功但文件未保存、引用缺失、结果不符，分别保留状态和原因；不能仅检查扩展名就通过交付门禁。
- 明确授权的剪辑/字幕/转码可衔接后处理，但保留原件与转换记录，不伪称供应商原生满足所有参数。

## 7. UI、偏好、错误与恢复

### 7.1 真正的用户入口

- 图片：[MediaArtifactsPanel.tsx](../../src/components/workspace/MediaArtifactsPanel.tsx) 有真实创建表单，目前根据静态能力生成选项，单选项会禁用；需改为“用户要求/模型建议/实际生成”可区分的规格编辑和摘要。
- 视频：[VideoArtifactsPanel.tsx](../../src/components/workspace/VideoArtifactsPanel.tsx) 主要展示任务状态和产物；[src/testing/VideoCreationForm.tsx](../../src/testing/VideoCreationForm.tsx) 是测试入口，不能把修改它当作完成生产视频交互。生产视频仍以会话/编排工具流程为主，若补 UI 入口要复用同一 service。
- 编排：[AutoArrange.tsx](../../src/components/enterprise/arrange/AutoArrange.tsx)、[run-settings.ts](../../src/features/enterprise/run-settings.ts) 与工作状态映射须展示待补规格、权限未开通、报价/生成/保存/交付状态。不要把所有等待都标为“等待员工”。
- IPC：[ipc.ts](../../src/shared/ipc.ts)、[media route](../../electron/controller/routes/media.ts) 及现有 video/arrangement controller 负责校验新版输入与输出信封；renderer 不能直接调供应商。

表单可提供建议按钮/示例，但不应加载时自动成为提交值。选项提示允许自定义符合类型的值；缓存中不存在的值不能自动换成列表第一项。上游未映射的格式要解释生成与本地预览/导出的差异，不仅因当前预览器不支持就假称模型不支持。

规格摘要至少显示：用户要求、模型建议及理由、未指定字段、拟用 Profile、费用状态。生成后显示 actualSpec 及与约定差异。无需给用户展示内部哈希或连接信息。

### 7.2 历史偏好不是新默认

[media-preferences.ts](../../src/shared/media-preferences.ts) 与 [media-preference-scope.tsx](../../src/components/workspace/media-preference-scope.tsx) 已按作用域/Profile 保存参数。可以保留历史选择用于查看和“沿用上次”显式操作，但新任务不自动套用。

用户明确说“和上一条一样”时，模型引用上一条具体规格并展示来源，作为此次需求；不得仅凭同一企业/Profile 就注入旧参数。缓存恢复只恢复同一草稿/同一请求已有决定，不把跨任务历史偏好当成用户本次同意。

### 7.3 错误不能吃掉原因

[video-tool-error.ts](../../electron/errors/video-tool-error.ts) 有固定文案引导“不传参数就用 host defaults”，需移除；图片 [media-tool-error.ts](../../electron/errors/media-tool-error.ts) 已有 businessCode/field/stage/recovery，可作为扩展基线，但不能直出原始上游内容。

统一映射语义：

| 错误 | UI/模型动作 |
|---|---|
| `MISSING_SPEC` | 指出所缺字段，提案或询问，保持等待输入 |
| `INVALID_PARAMETER / SPEC_CONFLICT` | 说明格式/冲突；不说员工没有工具 |
| `MEDIA_FORBIDDEN` | 真实授权问题；不自动提升只读权限或借员工身份 |
| `ADAPTER_UNAVAILABLE / ADAPTER_FIELD_UNMAPPED` | 说明 SEP 适配边界；不能说最终供应商拒绝 |
| `PRICE_UNAVAILABLE` | 无法可靠报价，不以零价继续，不等同不支持规格 |
| `UPSTREAM_SPEC_UNSUPPORTED` | 显示脱敏字段、原因与有证据的替代选项，等待重新决策 |
| `SUBMISSION_UNKNOWN` | 查询原请求，保留是否扣费未知；不自动重提 |
| `OUTPUT_SPEC_MISMATCH` | 展示实际结果、可保存安全原件与费用状态，等待接受/修订 |
| `UPGRADE_REQUIRED` | 明确客户端/服务端协议不匹配，不静默回到旧规格 |

建议错误字段与 SEP 对齐：`field/requestedValue/reason/source/stage/retryable/submissionState/billingState/alternatives`。上游的秘密、URL、headers、堆栈及未经审查的正文不进入工具输出或 UI。`retryable` 不能自动授权付费重试。

### 7.4 持久化与恢复

保存每个请求的协议/哈希版本、规格与来源、quote/价格版本、引用内容哈希、连接/配置快照、job/receipt 和实测结果。优先扩展现有版本化 JSON/store，不新建第二套媒体任务系统。

用户变更规格创建新 revision 与报价；旧提交状态未知时先恢复原任务，不能覆盖请求文件再提交。应用重启/账号切换/权限撤销时保留现有 scope 与 epoch 校验；查询恢复不用新版 helper 重算旧请求哈希。不得以本次取消默认值为由破坏停止/取消、并发任务登记或异步清理。

## 9. 两仓库协作与发布

1. SEP 与客户端先锁定版本、字段、错误、安全边界和合同 fixture。不要让客户端先开放自由输入、后端仍按 4 秒冻结收费。
2. SEP 完成适配器映射、动态报价/usage、输出与历史恢复后，客户端才对协商成功的 V3 启用新管线。
3. 客户端保留旧服务器检测；旧协议无法表达的新需求明确要求升级，不按旧 defaults 自动改写。旧界面恢复旧任务与新请求生成是不同路径。
4. 新请求灰度期间核对模型输入、requestedSpec、quote、上游请求、actualSpec、usage 和交付产物。日志只留安全摘要/哈希/追踪 ID，不记录密钥或完整私人素材。
5. 回退仅停止新版本的新提交；已提交请求继续用原版本查询与对账，不能删 job 或用旧参数重放。

上游依赖不能忽略：SEP 已核查 Sub2API 报价目前仍有 480p/720p/1080p、≤600 秒等合同边界，未知分辨率/时长还可能进入其计费默认。客户端不能因为本地取消枚举就宣传任意规格已可用；此时应显示准确的价格/适配原因，而不是继续静默降级。

与旧方案的关系：本方案更新 [2026-10-24 客户端媒体能力方案](./2026-10-24-客户端媒体能力与执行限制优化开发文档.md)、[跨层契约方案](./2026-10-24-媒体能力限制与跨层契约一致性优化.md) 中 host 默认与静态能力列表的方向。此前的授权、文件安全与一致性原则继续保留；历史文件不改写。

编排交付部分与 [2026-10-22 编排媒体闭环方案](./2026-10-22-编排生图生视频闭环详细开发方案.md) 合并推进；错误/费用部分与 [视频错误与账务方案](./2026-10-22-客户端视频提交错误与账务展示修复方案.md) 对齐，避免重复构建状态机。
