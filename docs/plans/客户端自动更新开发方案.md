## 0. 结论先行

### 0.1 推荐方案

采用 `electron-updater` + `electron-builder` + 独立 HTTPS 静态发布源：

```text
构建产物
  ├── macOS DMG（首次安装/人工下载）
  ├── macOS ZIP（自动更新所需产物）
  ├── Windows NSIS EXE（自动更新产物）
  └── latest*.yml（版本清单）
          │
          ▼
独立更新发布源（beta / stable 分目录）
          │
          ▼
electron-updater（主进程）
          │
          ▼
IPC / preload
          │
          ▼
渲染进程顶部更新入口
```

不建议使用普通 SEP 业务 API 承载安装包，也不建议让渲染进程直接请求清单或调用安装能力。

### 0.2 当前真实状态

截至 2026-10-09，仓库的事实状态如下：

| 项目 | 现状 | 结论 |
|---|---|---|
| Electron | `33.4.11` | 已有主进程和 preload 边界 |
| electron-builder | 声明 `^25.1.7`，当前锁定 `25.1.8` | 渠道配置已通过该版本 schema 校验 |
| electron-updater | 未安装 | 尚未具备自动检查、下载、安装能力 |
| builder `publish` | Phase 0 按渠道生成显式配置 | 候选 HTTPS 发布地址已写入配置，远程部署待确认 |
| beta / stable | 业务配置与 builder 配置均按渠道生成；构建产物目录隔离 | 本地发布准备已实现，远程上传与验收待完成 |
| 更新 IPC | 未实现 | 账号菜单中的“检查更新”目前是占位按钮 |
| macOS 签名/公证 | 未配置 | 不能把本地包当作正式自动更新包 |
| Windows 签名 | 未配置 | 正式发布前仍需配置证书和签名流水线 |
| 远程安装包 | 未确认已部署 | 不能直接宣称用户可以在线更新 |

### 0.3 用户最终体验

1. 客户端启动后延迟检查更新，不阻塞登录和首页。
2. 有新版本时，顶部栏出现一个低打扰的更新提示。
3. 用户点击提示查看版本号、更新说明和当前平台。
4. 用户点击“下载更新”，客户端在后台下载并显示进度。
5. 下载完成后，用户点击“立即重启更新”；有运行中任务时先二次确认。
6. 更新失败时保留当前版本，提供重试；更新服务不可用不影响业务功能。

### 0.4 首期明确不支持的情况

- 不强制升级。
- 不在未登录时阻止用户使用客户端。
- 不按用户或企业动态切换 beta / stable。
- 不支持客户端自动降级。
- 不把安装包放到需要业务 Token 的 API 中。
- Linux AppImage 首期继续人工下载，后续单独评估。

## 1. 背景与目标

当前客户端的版本更新方式是：开发者重新打包，用户重新下载 DMG、EXE 或其他安装包，再手动安装新版本。这个流程存在以下问题：

1. 用户不知道是否有新版本。
2. 用户需要自己找到正确的安装包。
3. 用户无法看到版本更新内容和下载进度。
4. macOS arm64、macOS x64、Windows x64 容易下载错误的安装包。
5. 当前客户端没有远程版本清单，也没有更新下载、校验、安装和重启逻辑。
6. 当前打包产生的 `latest.yml`、`latest-mac.yml` 只存在于本地 `dist/`，没有发布到远程静态地址。

本方案的目标是：

> 用户打开客户端后，客户端自动检查对应渠道的新版本；发现新版本时，在客户端内给出低打扰提示；用户点击后完成下载，并在用户确认后自动退出、安装和重启。

### 1.1 首期目标

首期必须完成：

- 启动后检查更新。
- 手动检查更新。
- beta / stable 渠道隔离。
- 显示当前版本和新版本号。
- 显示更新说明。
- 后台下载更新包。
- 显示下载进度。
- 下载完成后显示“立即重启更新”。
- 用户取消或稍后更新后，客户端继续正常使用。
- 更新失败时显示可理解的错误和重试入口。
- macOS arm64 / x64 和 Windows x64 支持更新。
- 更新包来源、版本清单、哈希和签名校验可追溯。

### 1.2 首期不做

以下能力不纳入首期：

- 强制升级。
- 未登录时禁止使用客户端。
- 用户自定义更新服务器。
- 管理后台发布版本。
- 按企业或用户进行复杂灰度。
- 自动降级到旧版本。
- 跨大版本数据迁移框架。
- Linux 自动更新。
- 在业务 API 中传输安装包。

后续确实需要灰度时，应在发布服务或版本清单层增加，而不是把灰度规则写死在渲染页面。

### 2.3 当前发布配置的注意点

当前 `package.json` 已配置 `beta` 和 `stable` 构建脚本；`publish` 由 Phase 0 新增的渠道 builder 配置生成脚本写入，根 `build` 不固定某一个渠道。`electron-builder` 的 `publish.url` 是构建阶段写入更新元数据的发布地址，不能等客户端启动后再由 `runtime-config.generated.ts` 临时决定。

这两个概念必须分开：

| 配置 | 作用 | 是否决定 updater 渠道 |
|---|---|---:|
| `runtime-config.generated.ts` | SEP 业务 API 环境，例如 integration / production | 否 |
| `electron-builder` 的 `publish.url` | `app-update.yml` 和 `latest*.yml` 使用的更新源 | 是 |

因此 `package:beta` 和 `package:stable` 必须在构建时注入不同的 `publish.url`。不能把下面的固定 stable 地址同时用于两个渠道，也不能直接假设 `${channel}` 会被 `electron-builder` 自动替换：

```json
{
  "build": {
    "publish": [
      {
        "provider": "generic",
        "url": "https://download.longdaosep.cn/sep-client/stable/"
      }
    ]
  }
}
```

Phase 0 已采用构建配置生成脚本：接收 `beta | stable`，生成临时的完整 builder 配置，再显式传给 `electron-builder`：

```text
package:beta
  → release:config:beta
  → generate-builder-config beta
  → electron-vite build
  → electron-builder --config .release/electron-builder.beta.json --publish never

package:stable
  → release:config:stable
  → generate-builder-config stable
  → electron-vite build
  → electron-builder --config .release/electron-builder.stable.json --publish never
```

生成配置至少包含：

```json
{
  "publish": [
    {
      "provider": "generic",
      "url": "https://download.longdaosep.cn/sep-client/beta/"
    }
  ]
}
```

生成文件写入已忽略的 `.release/` 目录，更新地址不进入业务运行时配置。已通过当前锁定 `electron-builder 25.1.8` 的 `--help`、类型定义、配置加载和 schema 校验确认临时 JSON 方式；不依赖变量插值。

### 3.4 用户体验规则

1. 自动检查不能阻塞登录页或首页加载。
2. 无新版本时不弹窗、不显示空白更新卡片。
3. 检查失败不应影响登录、对话、任务执行和组织架构查看。
4. 下载更新不应覆盖当前正在运行的安装目录。
5. 关闭更新面板不会取消已经完成的下载。
6. 用户选择“稍后”后，本次启动不重复打扰；下次启动可再次提示。
7. 更新过程中禁止重复点击“下载更新”。
8. 更新说明必须来自可信发布元数据，不能直接渲染任意 HTML。
9. 不因为更新检查失败显示“网络错误”全屏页。
10. 用户当前有运行中的任务时，重启按钮需要显示确认提示。

## 4. 技术方案

### 4.1 推荐技术选型

使用 `electron-updater` 配合 `electron-builder` 产物。

选择原因：

- 与当前 electron-builder 版本和产物格式匹配。
- 能使用已经生成的 `latest.yml`、`latest-mac.yml`。
- 主进程负责更新，符合 Electron 安全边界。
- 支持下载进度、更新错误、下载完成和 `quitAndInstall()`。
- 渲染进程只接收已校验的状态，不直接访问安装包 URL。

新增生产依赖：

```text
electron-updater
```

版本应在实现阶段根据当前 Electron / electron-builder 兼容范围固定，并提交 `package-lock.json`。不得在运行时从网络动态安装依赖。

### 4.2 远程文件布局

推荐使用独立静态域名或对象存储 CDN：

```text
https://download.longdaosep.cn/sep-client/
├── beta/
│   ├── latest.yml
│   ├── latest-mac.yml
│   ├── SEP-Client-0.1.3-mac-arm64.zip
│   ├── SEP-Client-0.1.3-mac-x64.zip
│   ├── SEP-Client-0.1.3-win-x64.exe
│   ├── SEP-Client-0.1.3-mac-arm64.dmg
│   ├── SEP-Client-0.1.3-mac-x64.dmg
│   ├── SHA256SUMS
│   └── RELEASE-NOTES.md
└── stable/
    ├── latest.yml
    ├── latest-mac.yml
    ├── SEP-Client-0.1.2-mac-arm64.zip
    ├── SEP-Client-0.1.2-mac-x64.zip
    ├── SEP-Client-0.1.2-win-x64.exe
    ├── SEP-Client-0.1.2-mac-arm64.dmg
    ├── SEP-Client-0.1.2-mac-x64.dmg
    ├── SHA256SUMS
    └── RELEASE-NOTES.md
```

要求：

- 文件通过 HTTPS 提供。
- `latest.yml` 是 Windows NSIS 更新清单；`latest-mac.yml` 是 macOS ZIP 更新清单。Linux AppImage 首期不接入 updater。
- `latest.yml`、`latest-mac.yml` 和它们引用的自动更新包必须位于同一渠道目录。DMG 只用于首次安装和手动下载，不要求被更新清单引用。
- macOS arm64 / x64 的 ZIP 产物、版本号和架构标识必须以当前 `electron-builder` 实际生成的清单为准；不要手工复制或拼接 `latest-mac.yml`。
- 文件名不能在上传后被重命名。
- 更新清单中的 `sha512`、`size`、`version` 必须和实际文件一致。
- CDN 不应缓存旧的 `latest.yml`；安装包本身可以长缓存。
- 版本发布顺序必须是先上传安装包，再上传清单。
- 回滚顺序必须是先恢复旧清单，再处理新安装包。

### 4.3 渠道映射

当前仓库已经有运行时渠道：

```text
beta   -> integration
stable -> production
```

建议更新源映射：

```text
构建输入 channel=beta
  → electron-builder.publish.url=
    https://download.longdaosep.cn/sep-client/beta/

构建输入 channel=stable
  → electron-builder.publish.url=
    https://download.longdaosep.cn/sep-client/stable/
```

`runtimeConfig.channel` 可以用于业务 API 环境判断和诊断日志，但 updater 的渠道必须在构建时固定，避免测试包给生产用户推送 beta 版本。不要根据登录用户、企业名称或当前 API 返回结果动态切换更新渠道。若后续必须支持同一安装包切换渠道，应另行设计并明确升级风险，首期不做。

| `preload.ts` | 暴露最小更新 API |
| `renderer-bridge.ts` | 转发主进程更新状态事件 |
| `update-state.ts` | 渲染层纯状态机和状态归一化 |
| `UpdateNotice.tsx` | 顶部栏入口、面板、进度和错误提示 |

### 4.5 IPC 契约

新增 invoke 通道：

```text
update:check
update:download
update:install
update:cancel
update:get-state
```

新增 event 通道：

```text
update:state-changed
```

通道和返回值按仓库现有 `IpcCommandResult` / `TaskStatsResult` 风格定义，不直接把 `electron-updater` 的对象暴露给 renderer：

| 通道 | 输入 | 成功返回 | 失败返回 | 说明 |
|---|---|---|---|---|
| `update:get-state` | `undefined` | `{ success: true, state }` | 标准 IPC 错误信封 | 页面初始化和重连时读取快照 |
| `update:check` | `undefined` | `{ success: true }` | 标准 IPC 错误信封 | 结果通过 `update:state-changed` 推送 |
| `update:download` | `undefined` | `{ success: true }` | 标准 IPC 错误信封 | 只允许一个下载任务 |
| `update:cancel` | `undefined` | `{ success: true }` | 标准 IPC 错误信封 | 仅取消当前下载，不删除当前版本 |
| `update:install` | `undefined` | `{ success: true }` | 标准 IPC 错误信封 | 只允许安装已下载且已校验的版本 |

新增类型建议放在 `src/shared/ipc.ts`：

```ts
interface UpdateStateResult extends IpcCommandResult {
  state?: UpdateState
}

interface ElectronAPI {
  getUpdateState: () => Promise<UpdateStateResult>
  checkForUpdate: () => Promise<IpcCommandResult>
  downloadUpdate: () => Promise<IpcCommandResult>
  cancelUpdateDownload: () => Promise<IpcCommandResult>
  installUpdate: () => Promise<IpcCommandResult>
  onUpdateStateChanged: (callback: (state: UpdateState) => void) => () => void
}
```

所有 invoke 路由使用 `z.undefined()` 输入 schema；更新服务不可用时不应伪造成认证失效，因此更新路由使用普通 IPC 错误信封，不触发 `AUTH_REQUIRED`。`update:install` 的运行中任务确认由 renderer 在调用前完成，主进程仍需再次读取状态并拒绝非法状态，不能信任 renderer 传入的“已确认”字段。

建议对外暴露的状态，不包含本地路径、下载 URL、Token 或内部错误堆栈：

```ts
type UpdateState =
  | { status: 'idle'; currentVersion: string }
  | { status: 'checking'; currentVersion: string }
  | {
      status: 'available'
      currentVersion: string
      version: string
      releaseDate: string | null
      releaseNotes: string[]
    }
  | {
      status: 'downloading'
      currentVersion: string
      version: string
      percent: number
      transferred: number
      total: number
      bytesPerSecond: number
    }
  | {
      status: 'downloaded'
      currentVersion: string
      version: string
    }
  | {
      status: 'not-available'
      currentVersion: string
      checkedAt: string
    }
  | {
      status: 'error'
      currentVersion: string
      operation: 'check' | 'download' | 'cancel' | 'install'
      message: string
      retryable: boolean
    }
```

契约规则：

- `percent` 在主进程归一化到 `0..100`。
- `releaseNotes` 只允许纯文本或受限 Markdown 转换后的纯文本。
- `message` 使用用户可理解的固定文案，不透传远程响应、堆栈或请求头。
- 失败状态不得包含 `accessToken`、refresh token、完整下载 URL 或本地敏感路径。
- `install` 不接受任意路径，只安装当前 updater 管理的已下载版本。

下载取消策略：

- 实施阶段先检查锁定版本 `electron-updater` 的类型定义和 `downloadUpdate` 签名，确认是否提供可取消的 `CancellationToken`。
- 如果支持，由 `app-updater.ts` 持有当前下载 token，`update:cancel` 只调用 token 的取消方法，并将状态转为 `idle` 或可重试的 `error`。
- 如果当前版本没有稳定的取消 API，首期不伪造“已取消”能力：UI 隐藏取消按钮或改为“关闭面板，继续后台下载”，待依赖验证后再开放取消。
- 无论哪种实现，取消都不能调用 `quitAndInstall()`，也不能删除用户当前已安装版本。

### 4.6 主进程生命周期

建议在后端和主窗口初始化完成后注册 updater，但检查动作延迟执行：

```text
app.whenReady()
   │
   ├── createBackend
   ├── registerRoutes
   ├── openMainWindow
   ├── createAppUpdater
   └── setTimeout(checkForUpdates, 3000)
```

原因：

- 不阻塞窗口创建。
- 不阻塞登录页和首屏渲染。
- 避免启动时同时占用业务 API 和更新 CDN。
- 即使更新服务不可用，业务客户端仍可正常使用。

建议检查策略：

| 场景 | 行为 |
|---|---|
| 启动后 | 延迟 3 秒检查一次 |
| 检查成功 | 记录本次检查时间 |
| 1 小时内再次启动 | 可跳过自动检查，保留手动检查 |
| 用户点击手动检查 | 立即检查，但防止并发请求 |
| 已有下载任务 | 不重复检查或下载 |
| 网络失败 | 退避重试，不弹模态框 |
| 开发环境 | 不执行真实安装更新 |

运行中任务判定直接复用现有 `getTaskStats()` / `TaskStatsResult`：

```text
update:install
  → taskService.stats()
  → 检查 running / pending / waitingApproval
  → 返回“需要确认”或允许 quitAndInstall()
```

不新增 updater 专用任务计数，也不从 renderer 当前页面列表推断任务是否运行。安装确认所需的最小规则由主进程再次执行，防止页面状态过期。

### 4.7 渲染层状态机

```text
idle
 │
 ├── check ──> checking
 │              │
 │              ├── 无版本 ──> not-available ──> idle
 │              ├── 有版本 ──> available
 │              └── 失败 ────> error ─────────> idle
 │
available
 │
 ├── download ──> downloading
 │                  │
 │                  ├── 完成 ──> downloaded
 │                  └── 失败 ──> error
 │
downloaded
 │
 ├── install ──> 客户端退出并安装
 └── later ────> downloaded / idle，继续使用当前版本
```

以下状态不能由 UI 自己推断：

- 是否真的有新版本。
- 是否已经下载完成。
- 是否允许安装。
- 下载是否失败。

这些状态必须来自主进程 updater 事件。

## 5. 平台策略

### 5.1 macOS

支持架构：

- Apple Silicon：arm64
- Intel：x64

更新产物：

- 更新下载使用 ZIP。
- DMG 用于首次安装和手动下载。
- `latest-mac.yml` 是 macOS 自动更新清单，必须由同一次 `electron-builder` 构建生成，并包含当前架构可用的 ZIP 信息。
- ZIP 必须是与应用签名身份一致的可更新应用包；DMG 能安装不代表 ZIP 自动更新链路可用。
- arm64 和 x64 必须分别在对应架构的已安装客户端上验证，不能只在一台机器上验证清单下载。

发布要求：

1. 使用 Developer ID Application 签名。
2. 对应用进行 notarization。
3. 使用稳定的 Team ID 和 bundle identifier：`cn.longdao.longsilicon`。
4. 更新版本必须使用同一个签名身份。
5. 未签名本地包只用于开发验证，不能作为正式自动更新包。

macOS 用户提示：

- 首次安装时可能需要用户确认打开。
- 自动更新安装前提示会关闭客户端。
- 有运行中的任务时，必须提示任务状态可能受重启影响。

### 5.2 Windows

支持架构：

- Windows x64

更新产物：

- 使用 NSIS 安装包。
- `latest.yml` 是 Windows NSIS 自动更新清单，放在 Windows 渠道目录。
- 安装包和清单必须使用一致的版本号和文件名。
- NSIS 目标必须开启 updater 所需的安装/更新行为；仅生成一个可手动运行的 EXE 不足以证明自动更新可用。

发布要求：

1. 使用 Windows 代码签名证书。
2. 签名证书续期时保持发布身份连续。
3. 安装包需要在普通用户权限下验证安装和更新。
4. 验证 Windows Defender / SmartScreen 对签名包的表现。

Windows 更新体验：

- 优先后台下载。
- 安装通常在退出后完成。
- 不能假设客户端拥有管理员权限。
- 安装失败时保留当前版本可启动。

### 5.3 Linux

首期不实现自动更新。当前 AppImage 仍按手动下载安装包处理。后续如果支持，可单独评估 AppImageUpdate 或发行版包管理方案，不能复用 macOS / Windows 的安装假设。

## 6. 发布流程设计

### 6.1 版本发布流程

```text
1. 修改 package.json version
          │
          ▼
2. 生成对应渠道的 builder publish 配置
   beta / stable 必须显式注入不同 URL
          │
          ▼
3. 运行对应渠道构建
   npm run package:beta
   或 npm run package:stable
          │
          ▼
4. 生成平台安装包和版本清单
          │
          ▼
5. 运行测试、签名、公证、生成校验和
          │
          ▼
6. 上传安装包到渠道目录
          │
          ▼
7. 校验安装包可匿名访问
          │
          ▼
8. 最后上传 latest.yml / latest-mac.yml
          │
          ▼
9. 使用旧版本客户端检查并升级
          │
          ▼
10. 记录发布结果和回滚点
```

### 6.2 版本号规则

采用语义化版本：

```text
MAJOR.MINOR.PATCH
```

示例：

- `0.1.2 -> 0.1.3`：修复和小功能。
- `0.1.3 -> 0.2.0`：可见功能或交互变化。
- `0.x.y -> 1.0.0`：正式稳定版本，需要完整回归。

规则：

- 版本号必须严格递增。
- 不允许重复发布相同版本号的不同安装包。
- 更新清单中相同版本号对应的文件不能覆盖替换。
- 如果安装包内容改变，必须递增版本号。

### 6.3 建议新增发布脚本

```text
scripts/generate-builder-config.mjs
scripts/publish-release.mjs
scripts/verify-update-manifest.mjs
scripts/test-update-feed.mjs
```

职责：

| 脚本 | 职责 |
|---|---|
| `generate-builder-config.mjs` | 根据 `beta | stable` 生成显式 `publish.url`，拒绝未知渠道 |
| `publish-release.mjs` | 检查版本、校验文件、上传渠道目录 |
| `verify-update-manifest.mjs` | 检查清单引用的文件、大小和哈希 |
| `test-update-feed.mjs` | 从远程源下载清单并验证 HTTP、版本和文件可访问性 |

发布脚本必须在上传前失败即停，不允许出现“清单已上传但安装包不存在”的状态。

### 6.4 上传顺序

必须遵循：

```text
安装包 → RELEASE-NOTES → SHA256SUMS → latest.yml / latest-mac.yml
```

不能先上传新清单，再上传安装包。否则旧客户端会立即发现一个不可下载的版本。

### 6.5 回滚

回滚不是删除已经发布的安装包，而是恢复清单：

```text
发现异常
   │
   ▼
停止继续上传
   │
   ▼
将 latest.yml / latest-mac.yml 恢复到上一个稳定版本
   │
   ▼
清除 CDN 清单缓存
   │
   ▼
保留异常安装包，标记为不可继续分发
   │
   ▼
修复后使用更高 PATCH 版本重新发布
```

不要把同一个版本号的坏包替换成好包，因为客户端可能已经缓存了清单或下载结果。

## 7. 安全设计

### 7.1 更新源安全

- 只允许 HTTPS。
- beta / stable 使用固定 allowlist URL。
- 不允许远程接口通过响应修改下一次更新源。
- 不把用户 Token 附加到更新 URL。
- 不把更新下载放到需要登录的业务 API。
- 清单和安装包使用 CDN 或对象存储只读公开地址。

### 7.2 完整性与真实性

更新文件至少需要：

1. HTTPS 传输。
2. electron-builder 清单中的 SHA512。
3. macOS 代码签名和 notarization。
4. Windows 代码签名。
5. 发布目录中的 SHA256SUMS 作为运营审计辅助。

SHA256SUMS 不能替代代码签名。它适合用于人工核验和发布记录，不能单独作为客户端信任根。

### 7.3 渲染进程安全

渲染进程不能：

- 直接导入 `electron-updater`。
- 直接读取更新清单。
- 直接执行安装包。
- 直接调用 `app.quitAndInstall()`。
- 接触下载临时目录或本地安装路径。

渲染进程只能通过 preload 获取：

```text
getState()
check()
download()
install()
cancel()
onStateChanged(callback)
```

### 7.4 日志与隐私

允许记录：

- 当前客户端版本。
- 渠道。
- 平台和架构。
- 检查开始、成功、无更新、失败。
- 下载百分比和结果。
- 安装触发结果。

禁止记录：

- Token。
- 账号密码。
- 完整带签名参数的下载 URL。
- 本地用户目录中的敏感文件名。
- 更新响应中的未知原始字段。

## 8. 异常与边界处理

| 场景 | 预期行为 |
|---|---|
| 无网络 | 静默结束，手动检查时提示网络不可用 |
| DNS 失败 | 不影响业务使用，可重试 |
| 清单 404 | 记录错误，视为暂无可用更新 |
| 清单格式错误 | 进入错误状态，不执行下载 |
| 版本号不递增 | 不提示更新，记录异常 |
| 安装包 404 | 下载失败，提供重试 |
| 哈希不一致 | 丢弃下载结果，不允许安装 |
| 下载中关闭客户端 | updater 保留或清理临时文件，重启后重新判断 |
| 用户磁盘空间不足 | 显示释放空间提示，不影响当前版本 |
| 更新期间任务运行 | 安装前要求确认重启 |
| 下载完成后清单变化 | 以已校验的下载结果为准，不重复覆盖 |
| 用户多次点击下载 | 主进程幂等处理，只允许一个下载任务 |
| 用户手动安装了更新 | 下次检查无新版本 |
| 当前版本高于远程版本 | 不降级 |
| 远程版本相同但文件变化 | 视为发布错误，不自动更新 |
| macOS 未签名包 | 测试环境允许记录失败，正式环境阻止发布 |
| Windows 安装权限不足 | 保留当前版本并给出手动安装提示 |

### 8.1 更新检查不应影响业务

更新器必须与 SEP 业务 API 解耦：

```text
更新 CDN 不可用 ──> 更新提示不可用
                         │
                         └──> 登录、聊天、任务、组织架构仍可用
```

不能因为更新检查失败而触发 `AUTH_REQUIRED`、清空用户会话或退出客户端。

### 8.2 运行中的任务

安装会导致客户端退出。安装前需要检查本地任务状态：

- 没有运行中任务：允许直接确认重启。
- 有运行中任务：显示“重启可能中断当前任务”，由用户明确确认。
- 任务状态已持久化：重启后恢复任务列表和可查看的运行记录。
- 不允许 updater 自己停止或取消远程任务，除非用户在业务界面明确操作。

### 8.3 实施前置条件

在开始 Phase 1 之前，以下事项必须有明确负责人和可验证结果：

| 前置条件 | 需要确认的内容 | 未确认时的处理 |
|---|---|---|
| 下载域名 | `download.longdaosep.cn` 是否最终使用，证书和 DNS 由谁维护 | 只能使用本地 HTTP fixture 验证，不能做正式更新验收 |
| 渠道目录 | beta / stable 的目录权限、上传方式、CDN 缓存刷新方式 | 不允许把两个渠道上传到同一目录 |
| 构建平台 | CI 是否能分别产出 macOS arm64、macOS x64、Windows x64 | 缺少平台产物时该平台标记为不可发布 |
| macOS 证书 | Developer ID Application、Team ID、公证凭据的保管位置 | 只能验证 UI、IPC 和清单，不得发布正式包 |
| Windows 证书 | 代码签名证书、签名服务或 CI Secret 的轮换责任人 | 不得把未签名 EXE 当正式更新包 |
| 发布权限 | 谁可以上传安装包、谁可以上传 `latest*.yml` | 采用最小权限，清单上传权限单独控制 |
| 版本规则 | 版本号递增、beta / stable 晋级和回滚审批 | 不允许覆盖同版本安装包 |
| 数据保留 | 发布日志、SHA256SUMS、旧清单和回滚副本保留多久 | 至少保留当前稳定版和上一个可回滚版本 |

当前没有确认正式远程发布源，因此开发阶段使用本地静态 fixture：

```text
scripts/fixtures/update-feed/
├── beta/
│   ├── latest.yml
│   └── latest-mac.yml
└── stable/
    ├── latest.yml
    └── latest-mac.yml
```

fixture 只能用于检查清单解析、状态机、下载进度和失败处理；不能证明真实 CDN 缓存、签名、公证、NSIS 安装或跨平台重启安装已经可用。

## 9. 分阶段实施计划

### Phase 0：发布链路准备

目标：先让远程文件可被可靠访问。

任务：

- 确认 beta / stable 下载域名或对象存储。
- 确认 `generate-builder-config.mjs` 或独立 builder 配置文件的落地方式，确保 `package:beta` / `package:stable` 不共用发布地址。
- 配置 HTTPS、CORS 或静态文件访问策略。
- 确认 CDN 对 `latest.yml` 的缓存策略。
- 确认 macOS / Windows 签名证书和 CI 构建环境。
- 固定安装包文件命名规则。
- 用当前 `0.1.2` 产物验证目录结构和清单访问。

验收：

- 浏览器或 `curl` 可以匿名获取清单。
- 清单引用的所有文件均返回 200。
- 文件大小与清单一致。
- beta 与 stable 不互相覆盖。

### Phase 0 本地实施结果（2026-10-09）

本次先实现发布准备工具。依据第 8.3 节的前置条件，尚未接入 `electron-updater`、更新 IPC 或 UI，也未上传文件或改变远程生产配置。

已实现：

- `scripts/generate-builder-config.mjs`：只接受 `beta | stable`，将完整现有打包设置复制到 `.release/electron-builder.<channel>.json`，显式写入对应 generic HTTPS 更新源。未知渠道、环境渠道冲突和平台级更新源覆盖都会失败。
- beta / stable 分别输出到 `dist/beta/`、`dist/stable/`；两个目录均使用 `latest.yml` / `latest-mac.yml`，关闭版本号渠道推断和生成其他渠道清单。`npm run package` 默认选择 beta，所有打包命令显式使用 `--publish never`，不会上传。
- macOS DMG 和 ZIP 均显式生成 x64、arm64 产物。现有 `dist/latest-mac.yml` 仅引用 arm64 ZIP，这一旧清单不能作为双架构完整发布验收依据。
- `generate-release-notes.mjs` 支持指定输出目录，校验和与发布说明随构建渠道隔离。
- `scripts/verify-update-manifest.mjs`：校验本地 YAML 清单、版本、路径、文件大小和 SHA512；支持完整平台产物校验。安装包使用流式校验，避免一次读入内存；拒绝首期不支持的非空 web installer `packages` 引用，非法路径错误不会回显可能含凭据的原始 URL。
- `scripts/test-update-feed.mjs`：匿名验证远程清单和引用文件。默认仅接受 HTTPS；本地 HTTP 仅作为显式启用的 loopback fixture。验证不携带业务 Token。
- `scripts/fixtures/update-feed/`：提供 beta / stable 隔离的 Windows、macOS 清单和小型假安装包；仅用于测试，不能用于真实安装。

- 回滚旧清单后，客户端不再发现坏版本。

## 12. 风险与决策记录

### 12.1 为什么不使用普通业务接口检查更新

更新不应依赖用户登录，也不应携带业务 Token。安装包体积较大，业务 API 还需要处理认证、限流、超时和权限，这会扩大故障面。更新清单和安装包应该放在独立的只读静态发布源。

### 12.2 为什么不把自动更新做成强制弹窗

硅基员工平台存在任务执行和工作记录场景。强制退出可能中断用户工作。首期采用“提示 + 用户确认 + 下载后重启”的方式，保证用户掌控重启时机。

### 12.3 为什么 macOS 更新使用 ZIP 而不是 DMG

DMG 适合首次安装和手动分发。自动更新需要可由 updater 处理的应用更新包，当前发布目录应以 ZIP 作为 macOS 自动更新产物，DMG 作为首次安装产物。

### 12.4 当前未签名包的限制

当前本地构建曾出现：

```text
skipped macOS application code signing
```

因此本地包可以用于验证 UI、IPC 和测试更新源，但不能据此宣称正式自动更新链路已经可交付。正式发布前必须配置代码签名、公证和证书保管。

### 12.5 与现有工作区改动的关系

本方案是设计文档，不要求回退或覆盖现有未提交改动。实现阶段应先确认工作区状态，再按自动更新模块的文件边界提交，避免把头像、Logo、组织架构等无关改动混入更新功能提交。
