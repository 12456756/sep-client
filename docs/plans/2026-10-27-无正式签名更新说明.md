# 无正式签名的版本检测与下载更新

## 1. 适用范围

本流程用于尚未接入 Apple Developer ID、公证和 Windows Authenticode 证书时，提供方便且可回滚的过渡更新体验：

1. 已安装客户端从渠道根目录读取 `latest.yml` 或 `latest-mac.yml`，检测是否有更高版本。
2. 用户点击“下载新版”后，由系统浏览器打开对应架构的固定 HTTPS 安装包地址。
3. Windows 用户退出客户端后运行新 EXE；macOS 用户退出客户端后打开 DMG 并覆盖安装。

登录页右上角和登录后的工作台顶栏均提供更新入口。版本检测不依赖业务登录；浏览器打开成功只显示下载提示，不会宣称安装完成或退出正在运行的客户端。本地打包写入 external 模式，正式签名打包才写入 in-app 模式；旧包缺少模式标记时默认采用浏览器下载。

该流程不把 ad-hoc、自签名或未签名产物描述为正式签名产物。生成的 `upload-plan.json` 固定包含 `releaseApproved: false` 和 `signatureVerified: false`，只用于准备上传，不是发布审批、代码签名、公证或安装验收记录。

## 2. 首次启用

旧客户端只有在已经包含本次“检测并打开下载链接”能力时，才能看到后续版本提示。因此需要先人工分发并安装一次新基线版本。此前公开目录中把内部 `0.2.0` 产物改名为 `0.1.2` 的做法不能作为自动更新基线，也不能继续复用 `0.1.2` 下载地址。

新基线及后续版本必须满足：

- `package.json`、安装包内部版本、文件名和更新清单使用同一个新版本号。
- 每次发布严格递增版本号，同一版本的文件内容不可覆盖或替换。
- beta 和 stable 使用独立目录，不跨渠道复用清单或安装包。

## 3. 本地构建

无正式签名时使用本地打包入口：

```bash
npm run package:local:beta
# 或
npm run package:local:stable
```

macOS 包使用 ad-hoc 签名且不公证；Windows 包不带受信任发布者签名。操作系统仍可能显示 Gatekeeper、未知开发者、SmartScreen 或企业安全策略提示。

不要运行 `package:beta` 或 `package:stable` 冒充无签名构建；这两个入口设计为正式签名发布，凭据不完整时应失败。

## 4. 准备发布清单

对 builder 输出执行：

注意：默认打包命令只构建宿主平台。此清单工具要求两平台产物完整；先在各构建环境使用相同版本、渠道的代码打包，再将 Windows x64 与 macOS 双架构的产物和各自清单汇总到一个独立目录。不要直接拿只有 Mac 产物的目录生成跨平台发布计划。

```bash
npm run release:prepare-download-update -- dist/local/stable stable .release/download-update-<version>-stable
```

beta 示例：

```bash
npm run release:prepare-download-update -- dist/local/beta beta .release/download-update-<version>-beta
```

输出目录必须提前不存在，并且必须与输入目录相互独立。工具会：

- 复用现有校验器验证两个平台清单、文件大小和 SHA-512。
- 要求 Windows x64 EXE，以及 macOS arm64/x64 的 DMG、ZIP 和各自 blockmap 全部存在。
- 将清单中的 `files[].url` 和兼容字段 `path` 改为 `<version>/<原文件名>`。
- 生成根目录清单 `latest.yml`、`latest-mac.yml` 和 `upload-plan.json`。
- 不复制大型安装包、不上传文件、不检查签名，也不授予发布资格。

## 5. 上传顺序

目标渠道根目录分别是：

- beta：`https://download.longdaosep.cn/sep-client/beta/`
- stable：`https://download.longdaosep.cn/sep-client/stable/`

严格按以下顺序发布：

1. 根据 `upload-plan.json`，把 EXE、DMG、ZIP 和 blockmap 上传到渠道下的 `<version>/` 目录。
2. 逐个核对公网文件的状态码、大小和内容哈希；版本目录文件应设置为长期缓存且不可变。
3. 最后才把准备目录中的 `latest.yml` 和 `latest-mac.yml` 发布到渠道根目录；根清单应避免长期缓存。
4. 从旧基线客户端分别验证 Windows x64、macOS arm64 和 macOS x64 的版本提示及浏览器下载地址。

不得先发布根清单，否则客户端可能检测到一个尚未完整上传的版本。不得只上传 DMG/EXE；清单引用的 ZIP 及相关 blockmap 也必须保留，为以后切回应用内更新提供完整产物。

## 6. 回滚与限制

回滚只恢复上一个版本的两个根清单，并核验它们引用的旧版本目录仍完整。不要删除已上传的版本目录，也不要让已升级客户端降级；修复问题时发布更高版本。

该过渡方案依赖 HTTPS 和服务器清单，缺少正式代码签名提供的发布者身份保证。适合受控内测和早期分发；面向广泛外部用户前，仍应完成 Developer ID、公证、Windows 代码签名及三平台真实升级验收。

## 7. 验证

使用 npm run test:updates 检查清单和本地准备工具，使用 npm run test:updates:runtime 检查主进程更新逻辑。npm run test:updates:ui 会启动临时本地 Vite 服务和隔离的无头 Chrome，验证登录页与工作台的检查、下载按钮；需要本机已安装 Google Chrome。测试使用受控 IPC，不登录真实账号、不打开系统下载器、不安装更新、不修改线上更新源，不能代替发布后的真实安装验收。
