# 普通会话耗时优化

## 问题

普通会话每轮响应耗时长，尤其在多轮对话、恢复任务和带知识库的场景中，等待时间会持续增长。

## 已确认根因

- 每轮无条件执行知识库查询，即使用户没有检索意图。
- 共享 Pi session 历史持续增长，恢复时可能拼接全部历史。
- 知识库查询、上下文组装、模型请求和事件收尾缺少独立阶段计时。
- 每次模型请求前同步持久化计数，增加串行 IO。

## 目标方案

1. 增加轻量 knowledge gate：只有明确询问公司资料、历史文档或要求检索时才查询。
2. 对相同规范化 query、任务和知识库版本使用短期缓存；查询失败或取消时不阻塞首轮回答。
3. 增加上下文预算：`maxInputTokens`、`maxMessages`、`recentMessageWindow`、`summaryTriggerRatio`、`maxKnowledgeChars`。
4. 达到阈值时写入摘要 checkpoint，后续只注入摘要、最近消息、当前问题和必要工具状态。
5. 恢复时读取摘要和最近窗口，不再拼接全部历史。
6. 请求计数改为内存累计、批量异步持久化，任务结束时强制 flush。

## 主要改动

- `electron/runtime/conversation-executor.ts`
- `electron/runtime/task-runtime.ts`
- `electron/service/knowledge-service.ts` 或现有知识库查询入口
- `electron/data/task-run-store.ts`、conversation/session store
- `src/components/workspace/TaskCenterHomePage.tsx` 及会话等待状态

## 实施顺序

1. 先增加阶段计时，建立无知识库、短会话、长会话基线。
2. 上线 knowledge gate、缓存和取消降级。
3. 上线上下文预算与摘要 checkpoint。
4. 最后切换异步计数持久化，并验证重启和崩溃恢复不丢最终计数。

## 验收

- 无检索意图的会话知识库查询为 0 次。
- 长会话输入 token 和消息数受预算限制。
- 恢复不会拼接全部历史。
- 知识库慢或取消不阻塞普通首轮响应。
- 计数最终一致，且不阻塞每次模型请求。
