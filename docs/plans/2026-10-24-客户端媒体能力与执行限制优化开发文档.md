# 客户端媒体能力与执行限制优化开发文档

日期：2026-10-24

状态：本轮取消域、默认值、重复上传校验、交付预检、错误投影和报价恢复已在工作区实现。C01/C03/C04/C05/C06 的本轮实现与未覆盖范围见第 12 节；C02 已取消数量截断，新增真实规格仍需后台契约和联调；C07 为 P2 后续任务。

## 1. 目标与范围

消除 Electron 自行增加的重复限制和参数冲突。客户端尽量不限制业务规格：已知的通道能力只用于提示词、默认值和界面说明，当前不支持的组合在使用时明确提示；真正的权限、报价、扣费和提交判断仍由后台完成。覆盖普通会话、自动/手动编排及生产媒体界面。

以“限制尽量少”为原则：删除客户端业务规格白名单、重复上限和静默改参。输入不符合当前通道时，在提交前把限制写进提示词并显示可理解的后台原因；不得偷偷换比例、缩小尺寸、删图或截断提示词。授权、计费、幂等、文件安全不能通过删除校验规避。

配套：[Web 与后台开发文档](../../../SEP/docs/plans/2026-10-24-Web端媒体能力与授权配置优化开发文档.md)、[完整调研与证据](2026-10-24-媒体能力限制与跨层契约一致性优化.md)。后台任务只在配套文档以 B01..B04 登记，本文引用依赖，不重复实施。

跨端交接遵循配套文档第 5.5 节：Web 展示的是服务端有效能力；客户端还要与本地安全处理范围求交集，具体请求仍需报价、资金、审批和提交检查。Profile `configVersion` 不代表企业策略版本。

源码基线：本仓库 HEAD `8ecbbe6`，SEP 后台 HEAD `fc257a3`，代理 sub2api HEAD `5fd22ed0`。调研包含工作区已有未提交改动，实施前重新定位受影响代码并保留其他工作；行号可能漂移。下文未加仓库前缀的代码路径均相对于本仓库。

## 3. 调用链与事实

```text
普通会话 / 编排节点 / 生产媒体界面
  → SDK 工具或经 preload/IPC 进入媒体用例
  → service 解析参数、授权/审批、报价与任务关联
  → data gateway / platform runtime 能力
  → SEP real DTO / adapter / 供应商
  → receipt / usage / content
  → 客户端 tracker 保存资产
  → 编排匹配与交付 / 会话展示
```

renderer 只能经 preload；IPC 仍需边界校验，service 不直接导入 Pi SDK 或构造持久化路径。修复沿用现有分层和动态加载边界，不新增能力平台或升级 Pi SDK。

当前能力请求 `electron/common/platform/platform-api.ts` 已带 `mediaProtocolVersion=2&skillArtifactProtocolVersion=1&videoProtocolVersion=2`。后台已有分版本返回，扩展这套协商，不另造机制。

## 4. C01 / P0：确认并修复交接取消后台下载

对应总调研 D01。真实任务已出现图片生成成功、随后本地 `SAVE_FAILED / STOPPED`。源码链支持以下假设，但尚无可控回归证明该任务由此触发：

1. `electron/pi/sdk/pi-coding-agent-adapter.ts` 把 SDK 工具 signal 传给图片 host。
2. `electron/service/media-service.ts` 合并工具 signal 与 activity controller，异步 track 沿用合并后的 signal。
3. `electron/pi/sdk/pi-task-worker.ts` 在纯媒体提交成功的交接时调用 `session.abort()`；SDK abort 取消当前运行 signal。
4. tracker 被取消时停止保存并写入失败状态，与任务症状吻合。其他取消路径也可产生同样状态，不能仅凭状态定因。

### 开发步骤

- 先用真实 SDK、假网关和受控 content Promise 复现“工具返回/模型交接后下载停止”。视频具有不同 tracker 生命周期，单独验证，不直接套用图片结论。
- 划清工具提交取消、模型回合结束、任务停止、scope 失效和退出。job 与任务关联可靠落盘后，异步 tracker 的取消权转交 activity/task 生命周期；模型交接仅结束后续模型回合。
- 覆盖落盘后工具返回前、下载中、abort 先于后续回调等时序，避免切换所有权窗口丢失取消或产生孤儿 tracker。
- 显式停止、账号/企业失效、退出仍停止相关网络与写入。保留提交未知状态恢复，不能因 signal 变化再次生成。
- 保存失败优先恢复原 job 的 content 下载，保留 clientRequestId、receipt、报价及计费状态；结果过期时明确报过期。

### 验收

真实 SDK + 假网关下，交接后保存到 `SAVED` 并交付；同一时序用户停止和 scope 切换可取消。普通会话、纯媒体编排、混合节点均覆盖；断言生成提交一次，恢复仅查询/下载，不新建报价或消费。若专项测试排除假设，更新根因证据后再改代码，不能为满足文档强改取消域。

C01 已修复已确认的取消所有权问题，并验证现有原 job 恢复路径；C06 负责提交超时、未知提交和恢复流程的阶段化完善，两项不重复实现恢复机制。

## 5. C02 / P1：消费真实能力，删除重复规格硬编码

主要代码：

- `electron/common/platform/real-media-semantics.ts`
- `electron/common/platform/sep-media-runtime-contract.ts`
- `electron/common/platform/video-runtime-contract.ts`
- `electron/common/platform/platform-api.ts`
- `electron/data/sep-real-media-gateway.ts`
- `electron/data/sep-video-media-gateway.ts`
- `electron/pi/sdk/pi-coding-agent-adapter.ts`
- `src/shared/media-host.ts`、`src/shared/video-media.ts`

调研时 real semantics 与图片 gateway schema 为三尺寸，runtime 映射把 maxCount 截为 4。本轮已取消 runtime 数量截断、忠实保留后台下发值；真实 backend 请求/receipt 仍只有 4，不能据此宣称真实生成支持 8。真实 V1/V2 协议解析边界保留，新规格须先完成后台支持与版本协商。真实 receipt 未必支持取消，仍保留 job 级保护。

### 开发步骤

1. 依赖 B01/B02/B04 下发已实现能力与版本投影。客户端不维护固定尺寸、画幅、数量或组合白名单；动态能力只用于提示词、界面说明、默认值与后台预检请求，不能替代后台报价/提交校验。
2. 移除与后台重复且更窄的业务枚举/固定上限。保留协议解析、数值类型、文件签名/解码、实际返回规格一致性和防止资源耗尽所需的安全边界。未知业务值不得被本地静默隐藏、截断或替换；若当前协议不能表达，交给版本协商或后台返回明确原因。
3. 对图片提示词、参考图、输出限制消费后台提供的动态能力；视频复用 V2 已有 audioModes/defaults，不创建同义字段。需要联合约束的规格由后台返回预检结果，不能把独立字段列表当成任意组合都可执行。P1 消费 B01/B02 依据端到端实现发布的能力提示；协议声明不能单独证明本地具备处理大文件的资源能力。
4. 已有 strict schema 不直接接受新字段；新客户端明确协商支持版本，旧服务端保留可处理的回退。版本不支持时提示原因，不能把全部模型静默隐藏。
5. 请求的有效规格只解析一次，绑定审批、报价/hash、提交和 job 快照；后续能力更新不能改写已提交 job。

验收：旧协议继续可用；客户端不以重复的固定规格枚举拒绝业务值；能力未知或后台不支持时在报价/扣费前显示后台的具体原因；新规格只有经后台闭环验证并按版本下发后才显示为可用。真实取消/恢复能力与操作行为一致。

## 6. C03 / P1：默认值和输入校验前移

主要代码：`electron/service/media-service.ts`、`electron/common/platform/media-contract.ts`、`electron/data/media-image.ts`、SDK 工具定义与生产媒体表单；现有表单 helper 在 `src/shared/media-view.ts`。

### 6.1 默认规格统一解析

当前工具只传 aspectRatio 时，可能仍带入另一比例的 profile.defaultSize，随后 generate 又拒绝比例和尺寸不一致。这是客户端参数补全风险，独立于后台能否开放新规格。

统一规则：明确 size 与比例时必须一致；只给 size 时推导比例；只给比例时在该比例支持的尺寸中选默认；都未给时用有效默认值；策略过滤后默认失效则从合法集合重选。空集合返回具体不可用原因，不擅自换比例。

工具、生产表单和编排消费同一纯解析逻辑或相同契约用例，复用已有 helper；不要假定已正确处理比例切换的表单也存在相同 bug。

### 6.2 提示词和参考图

| 项目 | 本地当前接受 | 当前真实图片 | 当前真实视频 |
| --- | --- | --- | --- |
| 提示词长度 | 图片工具 20000 字符 | 4000 | 4000 |
| 参考图数量 | 图片工具最多 16 | 最多 4 | 1 |
| 格式 | PNG/JPEG/WebP | PNG | PNG |
| 参考图体积 | 图片本地库 32 MiB | 5 MiB | 10 MiB |
| 参考图单边 | 本地可更大，另有像素约束 | 4096 | 4096 |

表中的数字只是当前 backend real 路径观察值，不是客户端永久上限。客户端只能把它们作为使用时的提示词和说明，不得复制一份业务拒绝规则；实际能力由运行时配置及后台预检决定。提示词不是安全边界，后台必须在报价/产生费用前复验。也不把通道限制扩散为本地资产库限制。历史内容继续可读；不截断 prompt、删图、静默改格式或自动摘要。

默认值修复可独立实施。提交参数优先由当前授权能力提供默认值；完整的按模型动态提示依赖 C02 与 B01/B02/B04。若后台暂时无法预检，客户端应保留用户选择并把请求交由现有后台校验，不因缺少能力信息而猜测或静默改参。

能力提示应说明来源和版本，不把建议范围描述成永久限制。现有普通会话 system prompt 已要求模型先读取 `media_get_capabilities`，并按工具实际返回的授权 profile、规格与 `configVersion` 组织请求；工具结果本身提供动态能力快照。本文不宣称把动态快照直接注入 system prompt，也不把提示词作为安全或业务拦截。报价/提交服务端仍复验，拒绝时返回字段和恢复建议。字符计数口径应与后台一致并覆盖中文和 emoji；不截断用户输入。

JPEG/WebP 转 PNG、缩放或压缩如纳入实施，须作为明确的预处理能力：保留原图及派生图来源，记录实际转换和 hash，以最终上传 bytes 报价。不仅修改 MIME/扩展名，不静默降低质量；没有安全转换能力时先清楚说明。

验收：参数省略组合无冲突，审批/hash/提交使用同一份解析结果；客户端不通过复制 4000 字、4 张、5 MiB、4096 等业务上限提前拒绝请求；后台拒绝时费用未产生且错误能定位字段。安全解码、路径、内存、磁盘和实际文件类型检查仍在上传前执行；旧资产仍可读。

## 7. C04 / P1：规划和预检验证可执行性

主要代码：`electron/domain/arrangement-planner.ts`、`electron/domain/arrangement-plan.ts`、`electron/service/arrangement-service.ts`、`electron/runtime/arrangement-executor.ts`、`electron/data/arrangement-media-files.ts`。

已确认计划 schema 可表达 PNG/JPEG/WebP、MP4/WebM 和 workspace/either 来源；执行器仍会拒绝 workspace 媒体，交付 MIME 校验也不会自动转码。能力信息未完整进入规划和预检，容易在生成后才发现交付不成立。

### 开发步骤

- 在已有规划上下文中提供精简的有效媒体能力及版本；避免每轮塞全部模型目录增加延迟。普通会话和媒体工具已通过既有提示词要求先读取 `media_get_capabilities`，工具返回授权 profile 及 `configVersion`；不把动态快照直接注入 system prompt。
- 区分用户硬要求和可协商偏好。要求精确 16:9、JPG 或指定来源时，不把 3:2、PNG 偷当成功；偏好可以提出明确替代方案。
- 预检覆盖操作、尺寸/比例、数量、参考来源/MIME、输出格式和交付来源。优先使用后台返回的动态能力；把当前限制写进提示词和界面，不把客户端提示当强制业务边界。无权限、配置过期和能力不支持分别解释；不能全折算成“模型不可用”。
- 明确要求 workspace 来源、但执行器尚不支持时，在生成前说明不可执行。`either` 允许合法的 media-output 路径，不能一律判失败；按实际可用来源预检和验收。如新增 workspace 支持，复用既有资产校验和交付链，不随意开放路径读取。格式转换同理，先确定可执行支持再让计划通过。
- 执行前按 C05 的事件与合并规则刷新授权、企业策略，并核对 Profile configVersion，不为每次工具调用额外全量请求能力。该版本不覆盖策略变化，不能只比较版本就认定授权未变；具体报价及提交仍由服务端按最新授权复验。缓存可用于提示和默认值，不可用于放宽授权或跳过服务端判断。保留已完成产物，允许修复交付阶段而非重新生成。

验收：JPG 等交付硬要求、明确要求但不支持的 workspace 来源、缺参考图和策略无交集在付费前给出可理解的预检结果；`either` 可通过合法 media-output 路径完成；替代方案需明确接受，不能静默降级；普通会话工具也把相同的动态能力限制写入提示词。并行存在的附件开发不因本任务被重写，实施以当时实际工作区为准。

## 8. C05 / P1：能力刷新、错误分类与报价恢复

`electron/service/media-service.ts` 存在按 scope/task 缓存能力及 prepareRun/resetScope 流程。沿用它们，在新运行、配置过期、前台恢复或显式刷新等明确事件更新，不每次工具调用都全量请求；缓存遵守 scope 隔离。当前实现会在缓存缺失或上次授权失败时重试，但尚未合并同一 task 的并发刷新请求；这属于后续优化边界，本轮不扩大协议或刷新机制。

图片错误投影补齐业务 code、field、stage 和建议动作，参考视频已有做法；依赖 B04。能力不支持应返回后台当前计算的允许范围/未知原因，不能建议无限重试。下载失败走原结果恢复，结果过期要说明；未知提交先按原 clientRequestId 查询。

报价当前有效期短，人工审批可能超过窗口。使用有界重新报价：按同一需求获取新报价，检查 configVersion、内容/hash 和价格；若价格/规格变化或审批已失效，重新取得必要确认，不沿用旧审批接受涨价。保留后台过期保护，不把报价有效期简单无限拉长。

验收：账号/企业切换不串缓存；服务端撤销后新报价/提交立即按最新授权拒绝，客户端在上述刷新事件后更新展示。不承诺无推送条件下缓存界面瞬时更新；Profile 版本未变但企业策略已变也必须发现。过期审批无重复生成；新报价变化被明确确认；新任务能力更新不改旧 job。并发刷新合并属于后续优化，本轮仅记录当前未合并边界。

## 9. C06 / P1：分阶段等待与原结果恢复

当前客户端单次网络预算约 60 秒，而图片后台同步调用上游预算为 180 秒；工具结束、后端继续执行和最终结果未知必须分别处理。不能靠把所有 timeout 拉大修复。

- 把提交、查询、content 下载和持久化按既有流程分别计时与控制预算；依据真实接口时限设置提交预算，仍保留任务停止信号。
- 提交超时按未知提交处理，查询原请求；不能自动换 clientRequestId 重发。
- 生成成功而保存失败保留 receipt/原 job，提供重试查询和下载，避免再报价/生成/扣费。结果保留期限与后台能力一致。
- 有界退避和 tracker 收敛保留；网络暂时异常与确定业务失败分开，避免每次失败重新调用模型。
- 本任务以减少失败和无效等待为验收，不顺带建设独立阶段耗时统计或诊断页面。

验收：60 秒边界后后端已接收但响应丢失、慢 content、临时断网、重启恢复及显式停止；一次逻辑需求只有一次有效生成，已成功结果可恢复。

## 10. C07 / P2：资源上限与多产物匹配

以下独立后续交付，不阻塞 C01/C03 等修复，也不作为一次实现整篇文档的理由。

### 10.1 资源策略

当前活动存在共享并发上限，tracker 有数量/保留时间边界；文件也有本地、协议、存储多套限制。后台视频 DTO 允许值与实际存储上限不同，图片本地 32 MiB 与真实输出 25 MiB 等属于不同入口边界。P1 的 B01/B02/B04 与 C02/C03 先发布、消费各入口可兑现的有效限制并提前解释；本节 P2 仅评估扩容和资源调度，不把本地资产库无差别收窄为真实生成入口限制。

区分上传、等待生成、下载和用户任务并发，不用一个活动名额无限占全部资源。全局资源上限是本地容量与安全保护，可按容量证据调整，但不能与模型规格白名单混为一谈。扩容需测内存、磁盘、解码像素及停止恢复；保留文件签名、路径、解码和授权检查。

### 10.2 多需求与多产物

`electron/service/arrangement-media-service.ts` 当前关联和自动选择较依赖 operation 与单候选。一个 count=3 job 与三次不同需求不等价，不能直接放宽复用次数来解决。

按 requirementId、已解析输入、有效参数、job、输出建立稳定映射，保留原幂等键和历史恢复。歧义时明确选择；无歧义一对多可自动交付。验收多图、多 job、同 operation 不同输入、部分成功和只恢复一个需求，不重复消费。

## 11. 实施顺序与发布

1. C01 先专项复现并独立修复；C03 默认值与移除重复业务校验可以独立实施。
2. 后台 B01/B02/B04 准备契约与旧版投影，C02 完成消费和同源 fixture，联调后按版本开放新规格。
3. C04/C05/C06 分别交付，覆盖普通会话与编排；C07 单独立项，不扩大前序修复范围。
4. 入口 schema 更新与历史读取 schema 分开评估。既有请求快照、报价/hash、clientRequestId、receipt 不被迁移脚本改写。
5. 灰度停用新规格时继续支持其历史查询、content 和结算。旧客户端不能表达新 job 时，先隔离支持版本，不宣称任意版本可回滚。
