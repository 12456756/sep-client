# 任务中心完整设计方案

> 状态：历史产品设计记录。文中 `src/components/workspace/` 与 `src/features/workspace/`
> 已从当前实现删除；当前页面以企业工作空间和 `安排工作` 模块为准，不按本文恢复旧任务中心。

## 1. 文档目的

本文档定义 SEP 客户端“任务中心”的产品定位、信息架构、页面布局、交互流程、状态模型、视觉规范、数据结构和分阶段开发范围。

本方案基于当前实现整理，当前相关代码主要位于：

- `src/pages/WorkspaceHomePage.tsx`
- `src/components/workspace/WorkspaceComposer.tsx`
- `src/components/workspace/WorkflowView.tsx`
- `src/features/workspace/useWorkspaceDemo.ts`

本次方案只描述产品和前端设计，不包含代码修改。

## 2. 产品定位

任务中心不应是一个复杂的配置中心，而应是一个“工作安排与跟进中心”。

核心流程：

```text
用户描述目标
    -> 系统生成可编辑的工作计划
    -> 用户确认员工、职责和顺序
    -> 启动任务
    -> 查看接单、执行、交接和审批
    -> 获取最终交付物
```

用户不需要在开始时理解 workflow、runtime、session、DAG、模型 ID 等技术概念。

推荐的用户文案：

- 工作目标
- 工作计划
- 步骤
- 员工交接
- 交付物
- 等待你的确认
- 需要处理

不建议将以下词作为用户主文案：

- Workflow
- Runtime
- Session
- DAG

## 3. 当前实现问题

当前页面和数据结构存在以下不一致：

1. 页面标题承诺“安排一组员工”，但当前创建逻辑只使用 `workflow.employeeIds[0]`。
2. “工作方案”和“员工编排”混在同一个输入区域，用户不容易理解两者的区别。
3. “可安排的员工”目前更像静态名单，无法表达员工的职责、顺序和输入输出。
4. 执行页主要展示单个员工、日志和产物，无法表达多员工交接。
5. 工作目录、模型、技能和权限等技术配置过早暴露，增加了首次使用门槛。
6. 失败时容易让用户认为整个任务失败，实际上通常只需要重试某一个步骤。

因此，第一版应采用线性步骤编排，不做任意节点连线的 DAG 编辑器。

## 4. 信息架构

任务中心建议拆为三个主要页面：

| 页面 | 主要任务 |
| --- | --- |
| 任务中心首页 | 查看正在处理、待确认和已完成的任务 |
| 新建工作计划 | 描述目标、安排员工、调整步骤、确认启动 |
| 执行详情页 | 查看员工状态、交接、审批和最终产物 |

左侧导航建议保持：

```text
工作台
任务中心
硅基员工
技能与资源
```

## 5. 任务中心首页

### 5.1 页面目标

用户进入页面后，应能快速判断：

- 哪些任务正在运行；
- 哪些任务需要自己确认；
- 哪些任务失败了；
- 最近有哪些交付结果；
- 是否可以从常用方案快速开始。

### 5.3 页面区域

#### 顶部区域

- 标题：`任务中心`
- 说明：`管理正在执行的工作，查看员工交接和最终交付`
- 唯一主按钮：`安排新工作`

不要在顶部放置多个同等权重的主按钮。

#### 需要你处理

优先显示：

- 等待审批；
- 等待用户补充信息；
- 执行失败；
- 权限确认。

这是用户最需要优先关注的区域。

#### 正在进行

每个任务显示：

- 工作目标；
- 当前步骤；
- 已完成步骤数；
- 总进度；
- 当前员工；
- 最近一次状态变化；
- 查看详情按钮。

#### 最近交付

支持：

- 打开任务详情；
- 查看交付物；
- 复制为新任务；
- 保存为常用方案。

#### 常用工作方案

推荐方案：

- 竞品分析；
- 市场报告；
- 内容审核；
- 周报生成；
- 代码审查；
- 从目标开始。

常用方案是快捷入口，不应取代“从目标开始”的主流程。

## 6. 新建工作计划

新建页面采用三步向导：

```text
1. 描述目标  ->  2. 确认工作计划  ->  3. 检查并启动
```

顶部显示轻量进度，不使用大型营销式步骤卡。

### 6.1 第一步：描述目标

```text
┌────────────────────────────────────────────────────────────┐
│ <- 任务中心                              1 描述目标 · 2 计划 · 3 启动 │
├────────────────────────────────────────────────────────────┤
│                                                            │
│ 你希望完成什么工作？                                       │
│                                                            │
│ ┌────────────────────────────────────────────────────────┐ │
│ │ 例如：整理本季度销售数据，并生成一份给管理层的分析报告 │ │
│ │                                                        │ │
│ └────────────────────────────────────────────────────────┘ │
│                                                            │
│ 示例目标                                                   │
│ [整理销售数据] [分析竞品] [生成周报] [审核一批文档]        │
│                                                            │
│ 工作目录                                                   │
│ [选择工作目录]                          [只读 ▼]           │
│                                                            │
│                                             [生成工作计划] │
└────────────────────────────────────────────────────────────┘
```

用户只需要填写：

- 工作目标；
- 可选附件；
- 工作目录；
- 权限模式。

模型、技能、重试策略等设置放入“高级设置”，默认收起。

### 6.2 系统生成计划

例如用户输入：

```text
整理本季度销售数据，并生成一份给管理层的分析报告。
```

系统可生成：

```text
1. 数据整理
   员工：数据分析员工
   工作：清理数据、识别缺失值、整理关键指标

2. 趋势分析
   员工：商业分析员工
   工作：提取增长趋势、异常变化和区域差异

3. 报告撰写
   员工：报告撰写员工
   工作：形成管理层可读的分析报告

4. 最终审核
   员工：审核员工
   工作：检查数字、结论和表达是否一致
```

用户可以重新生成，也可以手动编辑计划。

### 6.3 第二步：确认工作计划

```text
┌───────────────────────────────┬────────────────────────────┐
│ 工作步骤                       │ 计划摘要                   │
│                               │                            │
│ ① 数据整理                    │ 工作目标                   │
│ ┌───────────────────────────┐ │ 整理季度销售数据并生成报告 │
│ │ [头像] 数据分析员工        │ │                            │
│ │ 整理销售数据               │ │ 工作目录                   │
│ │ 清理数据并提取关键指标     │ │ sales-q2                   │
│ │ 输入：销售明细             │ │                            │
│ │ 输出：清洗后的数据表       │ │ 执行步骤                   │
│ └───────────────────────────┘ │ 4 个步骤                   │
│                               │                            │
│ ② 趋势分析                    │ [保存为常用方案]           │
│                               │                            │
│ [+ 添加步骤]                  │                            │
│                               │ [预览计划] [开始安排工作]   │
└───────────────────────────────┴────────────────────────────┘
```

步骤列表是核心区域，右侧为计划摘要。

在 960px 宽度下，右侧摘要改为顶部摘要条或抽屉，避免主区域过窄。

### 6.4 工作步骤卡片

每个步骤至少包含：

- 步骤编号；
- 员工头像和名称；
- 员工职责；
- 步骤名称；
- 给员工的具体指令；
- 输入内容；
- 预期输出；
- 对前序步骤的依赖；
- 更多操作菜单。

操作包括：

- 上移；
- 下移；
- 编辑；
- 复制；
- 删除；
- 更换员工。

不能只依赖拖拽排序，必须提供上移和下移操作，以支持键盘和窄窗口使用。

步骤卡片示例：

```text
① 数据整理

[头像] 数据分析员工
整理并清洗本季度销售数据

任务说明
清理重复数据，标记缺失值，统一日期和金额格式。

输入：销售明细.xlsx
预期输出：清洗后的销售数据表和异常记录说明
依赖：无

[上移] [下移] [编辑] [更多]
```

### 6.5 添加步骤抽屉

```text
添加工作步骤

选择员工
[搜索员工或按职责筛选]

步骤名称
[例如：审核销售结论]

交代给员工的工作
[多行文本]

需要使用的输入
[选择前序步骤产物]

预期输出
[多行文本]

[取消] [添加步骤]
```

员工优先按职责展示：

- 数据分析；
- 内容撰写；
- 设计制作；
- 代码开发；
- 审核校对；
- 项目管理。

用户不应首先看到模型 ID 或底层运行时信息。

### 6.6 工作目录与权限

工作目录是计划级配置：

```text
工作目录
[ sales-q2 ] [只读 ▼]
```

权限模式：

- 只读；
- 可修改文件；
- 执行前询问。

建议默认值：

- 普通分析任务：只读；
- 需要生成报告：可修改文件；
- 代码、脚本、删除文件等高风险操作：执行前询问。

高级设置可以包含：

- 失败后是否继续后续步骤；
- 是否允许员工读取前一步的全部产物；
- 是否需要最终审核；
- 是否在每个步骤完成后暂停。

### 6.7 第三步：检查并启动

```text
┌────────────────────────────────────────────────────────────┐
│ 检查并启动                                                  │
├────────────────────────────────────────────────────────────┤
│ 工作目标                                                   │
│ 整理本季度销售数据，并生成管理层分析报告                   │
│                                                            │
│ 执行顺序                                                   │
│ 1 数据整理 -> 2 趋势分析 -> 3 报告撰写 -> 4 最终审核          │
│                                                            │
│ 工作目录：sales-q2                                         │
│ 权限：只读，修改文件前询问                                 │
│                                                            │
│ 本任务包含 4 个员工步骤，预计耗时约 20 分钟                 │
│                                                            │
│ [返回修改]                         [开始安排工作]           │
└────────────────────────────────────────────────────────────┘
```

启动后直接进入执行详情页，不停留在创建页。

## 7. 执行详情页

### 7.1 页面目标

让用户随时知道：

- 当前哪个员工在工作；
- 已经完成了什么；
- 下一步是谁；
- 是否需要用户确认；
- 最终会交付什么；
- 失败时应该重试哪一步。

### 7.2 页面布局

```text
┌────────────────────────────────────────────────────────────┐
│ <- 任务中心       整理季度销售数据             [...]         │
│ 已完成 2/4 · 正在执行 · 已运行 8 分钟                      │
├───────────────────────┬───────────────────────┬────────────┤
│ 工作计划              │ 执行时间线            │ 交付结果   │

│ 整理季度销售数据      │ ✓ 已完成              │ 数据表     │
│                       │                       │            │
│ 工作目录              │ ↓ 员工交接            │ 预期交付   │
│ sales-q2              │                       │ 分析报告   │
│                       │ ② 趋势分析            │            │
│ 计划步骤              │ ● 正在工作            │ 文件变更   │
│ ✓ 数据整理            │   商业分析员工        │ 2 个文件   │

│ ○ 报告撰写            │ ③ 报告撰写            │ 工作记录   │
```

在窄窗口下：

- 左侧计划摘要折叠为顶部信息条；
- 右侧交付结果改为抽屉；
- 中间时间线保持主区域。

### 7.3 步骤时间线

每个步骤展示：

- 步骤编号；
- 员工名称；
- 工作职责；
- 状态；
- 开始时间；
- 完成时间；
- 输出摘要；
- 产物数量；
- 操作按钮。

示例：

```text
① 数据整理
数据分析员工 · 已完成

↓ 员工交接

② 趋势分析

正在识别区域增长趋势和异常变化
[查看工作记录] [暂停]

③ 报告撰写
报告撰写员工 · 等待中

等待趋势分析完成
```

## 8. 状态设计

| 状态 | 用户看到的文案 | 主要操作 |
| --- | --- | --- |
| `draft` | 草稿 | 继续编辑、删除 |
| `queued` | 等待开始 | 取消 |
| `running` | 正在工作 | 查看进展、暂停 |
| `waiting-approval` | 等待你的确认 | 允许、拒绝 |
| `waiting-input` | 等待补充信息 | 补充信息 |
| `completed` | 已完成 | 查看交付物、复制为新任务 |
| `failed` | 需要处理 | 重试当前步骤、修改计划 |
| `cancelled` | 已取消 | 复制为新任务 |
| `skipped` | 已跳过 | 查看原因 |

状态不能只依赖颜色，需要同时使用状态文字、图标、进度或节点形状。

## 9. 失败、审批与恢复

### 9.1 失败处理

失败应局部化，只突出失败步骤：

```text
趋势分析 · 需要处理

商业分析员工未能读取输入文件：
sales-q2/summary.xlsx

[查看原因] [更换输入] [重试此步骤] [修改计划]
```

默认只重试失败步骤，不重复执行已经完成的步骤。

### 9.2 审批处理

审批出现在对应步骤中：

```text
报告撰写员工请求修改：

sales-q2/management-report.docx

原因：需要写入最终报告内容

[允许本次] [始终允许此类操作] [拒绝]
```

### 9.3 等待用户输入

员工无法继续时，步骤卡片内直接显示问题：

```text
需要补充信息

报告需要使用哪一种货币单位？

[人民币] [美元] [其他]
```

用户提交后继续当前步骤，不创建新的任务。

## 10. 建议数据结构

第一版使用“任务计划 + 计划步骤”结构：

```ts
interface TaskPlanDraft {
  goal: string
  steps: TaskPlanStep[]
  workspace: LocalWorkspaceBinding
  permissionMode: 'read-only' | 'read-write' | 'ask-before-change'
  continueOnFailure: boolean
  requireFinalApproval: boolean
}

interface TaskPlanStep {
  id: string
  order: number
  employeeInstanceId: string
  title: string
  instruction: string
  inputArtifactIds: string[]
  expectedOutput: string
  dependsOn: string[]
  status:
    | 'queued'
    | 'running'
    | 'waiting-approval'
    | 'waiting-input'
    | 'completed'
    | 'failed'
    | 'skipped'
    | 'cancelled'
  outputSummary: string | null
  artifactIds: string[]
  startedAt: number | null
  completedAt: number | null
}
```

第一版只支持：

```text
步骤 1 -> 步骤 2 -> 步骤 3 -> 步骤 4
```

保留 `dependsOn` 字段，为以后扩展并行分支和条件分支做准备，但暂时不开放任意连线编辑器。

## 11. 视觉规范

### 11.1 风格

任务中心应保持安静、紧凑、可扫描、有工作感，避免营销页式构图。

不建议使用：

- 大面积渐变；
- 过度圆润的卡片；
- 复杂背景动画；
- 多层嵌套卡片；
- 每个模块使用不同的强调色；
- 过大的空白英雄区域。

### 11.2 布局尺寸

```text
侧栏：220-260px
主内容最大宽度：1200px
主内容左右间距：24-32px
步骤卡片间距：12-16px
基础间距单位：4px
```

窗口适配：

| 窗口宽度 | 布局 |
| --- | --- |
| 1440px 以上 | 三栏布局 |
| 1120-1440px | 左侧摘要 + 主内容 + 可收起右栏 |
| 960-1120px | 主内容 + 抽屉式摘要和交付物 |
| 960px 以下 | 单列，不产生横向滚动 |

### 11.3 形状和控件

建议统一使用：

- 小圆角：4px；
- 普通控件：6px；
- 主要容器：8px；
- 普通按钮高度：32-36px；
- 主要按钮高度：36-40px；
- 图标按钮：32px 或 36px；
- 状态节点：8-10px。

### 11.4 颜色

使用语义色角色：

```text
页面背景
内容表面
弱背景
主要文字
次要文字
边框
品牌强调色
成功
警告
危险
审批
```

品牌色只用于主按钮、当前步骤和关键操作。状态必须同时显示文字或图标。

### 11.5 动画

动画用于解释状态变化，不作为装饰：

| 场景 | 建议时长 |
| --- | --- |
| 页面切换 | 200-300ms |
| 步骤状态变化 | 250-400ms |
| 员工交接 | 300-400ms |
| 抽屉展开 | 200-250ms |
| 按钮点击 | 100-150ms |
| 任务完成 | 300ms |

必须支持 `prefers-reduced-motion`。

## 12. MVP 范围

第一期实现：

1. 输入一个工作目标；
2. 生成或手动创建线性步骤；
3. 一个计划中选择多个员工；
4. 调整员工步骤顺序；
5. 编辑职责、输入和预期输出；
6. 设置工作目录和权限；
7. 启动任务；
8. 查看员工接单、工作、交接和交付；
9. 处理审批请求；
10. 只重试失败步骤；
11. 查看和下载最终产物；
12. 将完成任务保存为常用方案。

第一期暂不实现：

- 任意节点连线；
- 并行分支；
- 条件分支；
- 循环执行；
- 复杂调度器；
- 多层嵌套子任务；
- 复杂流程模板市场。

## 15. 验收标准

- 用户不需要理解 workflow 就能创建任务。
- 用户可以明确看到任务由哪些员工完成。
- 用户可以调整员工执行顺序。
- 每个步骤都有职责和预期输出。
- 执行过程中能看到当前员工和当前阶段。
- 员工交接关系清晰可见。
- 审批请求不会被埋在日志里。
- 失败时只突出失败步骤。
- 用户可以只重试失败步骤。
- 最终交付物与对应步骤有关联。
- 960×640 下不产生横向滚动。
- 状态不会只依赖颜色表达。
- 页面没有过度嵌套卡片和装饰性动画。
