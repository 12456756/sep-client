# 工作记录区分会话与编排开发方案

- 调研日期：2026-10-09。
- 状态：已按方案完成开发；实现与验证记录见第 9 节。
- 范围：工作记录的类型展示、组合筛选、分类数据可靠性及导航状态保持。
- 调研方式：核对仓库的创建、持久化、IPC、前端映射与页面实现，先形成方案，再实现并补充回归测试。

## 1. 结论

**保留一个“工作记录”页面，增加系统类型标识“会话 / 编排”，并提供独立的“全部 / 会话 / 编排”筛选。** 类型筛选与现有状态筛选、搜索取交集，不拆成两个页面，不新增用户可编辑标签或另一套记录存储。

这里的“标签”是已有工作类型的可视化标识，不是一个新业务字段。类型回答“这项工作以什么方式组织”，状态回答“现在进行到哪里”，两者同时显示，例如“编排 · 已完成”和“会话 · 需要我处理”。

调研时发现分类数据流缺口：后端已经持久化 `conversation | arrangement`，但任务查询没有把它传到前端；前端依赖异步加载的计划和历史 prompt 标记分类。**只在卡片上展示旧的 `WorkItem.kind` 不足以作为完成验收，可能把尚未加载计划的编排显示成会话。** 本次已补齐查询投影和独立读取状态。

## 3. 方案比较

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 只加类型标识 | 改动小，扫描卡片即可辨认 | 记录多时仍需逐条寻找；分类可靠性问题仍存在 | 适合原型，不作为最终方案 |
| 分为会话记录和编排记录两个入口 | 视觉隔离明确 | 查“需要我处理”或搜索全部记录需要来回切换，重复布局和状态管理 | 当前不采用 |
| 新建可编辑标签系统 | 未来可支持任意业务标签 | 会把系统工作类型混成自由标记，引入编辑、持久化与一致性成本 | 不属于本需求 |
| **统一页面 + 类型标识 + 独立类型筛选** | 保留统一待办与追溯，同时支持只看某一类；复用既有数据 | 需要补齐类型读取和筛选状态保持 | **推荐** |

不按员工数量、步骤数量、任务状态或自然语言标题推断类型。一个节点也可以是编排；会话中切换员工、参与多人，也不因此变成编排。

## 4. 页面与交互

### 4.1 布局

```text
工作记录
状态   全部(…)  进行中(…)  需要我处理(…)  已完成(…)  未完成(…)
类型   全部(…)  会话(…)  编排(…)                         搜索

工作标题                    [编排] [已完成]   最后更新 …
工作目标、参与员工、最终结果、待你处理
现有查看、复制、终止、删除等操作
```

- 卡片标题之后放类型标识，接着放状态标识；类型标识不承担点击、编辑或跳转行为。
- 类型使用现有 Lucide 图标：会话用 `MessageSquare`，编排用 `Workflow`，同时保留可读文字。
- 类型采用低强调样式，不占用表示成功、失败、待确认的状态颜色；不单凭颜色区分。
- 类型筛选使用分段选择控件，状态区沿用既有样式；无需新增侧栏入口或说明型横幅。
- 窄窗口允许工具栏和卡片头部自然换行；标题、两个标识及更新时间不重叠，按钮点击区域不随计数变化跳动。
- 分段选择提供可访问名称和选中状态，支持键盘操作；装饰图标设置 `aria-hidden`。若使用 tab 语义，应同时实现对应键盘行为，不仅添加 `role`。

### 4.2 默认值与筛选规则

- 首次进入：状态仍为“需要我处理”，类型为“全部”，搜索为空。不改变现有产品默认值。
- “全部类型”只取消类型限制，不取消状态或搜索；“全部状态”也不取消类型或搜索。
- 保持现有状态归属：进行中包含 `running/arranging`，需要我处理包含 `waiting-user` 或存在 `nextUserAction`，已完成为 `completed`，未完成包含 `failed/paused`。
- “需要我处理”不是审批专属状态，也不与其他状态桶互斥。不要要求所有状态计数相加等于总记录数。
- 搜索范围沿用标题、目标、当前员工名称，不将技术类型字符串或 prompt 标记加入用户可见搜索内容。
- 排序仍按 `updatedAt` 降序。类型解析完成不得修改业务更新时间或制造新的工作活动。

设记录集合为 `W`，当前状态匹配为 `S`，当前类型匹配为 `T`，关键词匹配为 `Q`：

```text
列表结果 = W ∩ S ∩ T ∩ Q
某状态计数 = W ∩ 该状态 ∩ T ∩ Q
某类型计数 = W ∩ S ∩ 该类型 ∩ Q
```

计数排除自身维度的当前选择，方便看见切换后的结果。此口径会改变现有“不考虑搜索”的状态计数，开发时应明确测试，不顺手保留两套计数口径。

### 4.3 空态、未就绪与错误

- 完全没有工作：沿用无记录空态。
- 有工作但当前交集为空：显示“没有符合条件的工作记录”，提供明确的重置筛选操作。
- 重置筛选：状态设为“全部”、类型设为“全部”、清空搜索；与首次进入的默认状态区分。
- 类型尚在查询：标识显示“类型加载中”，不得先显示“会话”。
- 分类无法确认：显示“类型暂不可用”，提供重试入口，不编造类型。
- 未确认类型的记录保留在“全部类型”中，不计入会话或编排；“全部”计数包含它们，必要时补充未确认数量，避免把二者之和误认为完整总数。
- 选定会话或编排时，未确认记录暂不加入结果；若仍有未确认项，应显示简短加载或错误状态，不能把暂时零条包装成已完成的空结果。
- 计划或时间线失败不应阻止有权威类型的记录展示，详情读取失败不能转成类型失败。本次解耦读取并保留 hook 的独立错误状态，不扩展详情页错误展示。

### 4.4 导航状态保持

当前不是 URL 路由，不新增路由框架。扩展 `AppRoute` 的 `records` 分支，保存 `bucket`、`workType` 和 `search`；`workType` 使用 `all | conversation | arrangement`。

筛选变化通过 `replaceRoute()` 只更新当前记录页状态，不为每次输入或点击压入导航历史。进入详情时，历史栈保存当前完整筛选；返回后恢复类型、状态、搜索。

普通的“工作记录”入口未指定筛选时采用默认值；不要求跨退出登录或应用重启永久记住上次筛选。本需求不新增本地偏好持久化。

## 5. 类型数据与兼容设计

### 5.1 类型语义

- 统一对外领域值：`conversation | arrangement`，展示为“会话 / 编排”。
- 计划模式 `conversation` 对应会话，`auto/manual` 对应编排；只接受已校验的合法模式，不能把任意非会话字符串当编排。
- 短期保留前端 `WorkItem.kind: conversation | flow` 和历史解码器，通过显式适配将 `arrangement` 转为 `flow`。新增筛选在边界转换，不让页面散落自行猜测逻辑。
- 完整重命名另行评估。[WorkDetailPage.tsx](../../src/pages/enterprise/WorkDetailPage.tsx) 和 [WorkTalkDrawer.tsx](../../src/components/enterprise/WorkTalkDrawer.tsx) 已按类型分支，不能仅改列表的枚举而遗漏详情。
- 未确认类型是读取状态，不是第三种业务类型。禁止为了消除类型错误给执行接口增加 `unknown` 工作模式。

### 5.2 已实现的数据流

```text
任务元数据 / 工作计划 / 历史兼容信息
  → data 层结构化读取结果
  → service 层只读类型解析
  → 现有 task:get / task:getAll 查询的读取 DTO
  → preload / renderer 工作区
  → work-mapping 类型适配
  → 工作记录标识、筛选和计数
```

复用现有查询，不为了两个分类新增一个大型工作聚合接口。原始任务持久化结构保持不变；查询视图组合任务字段和类型读取状态。共享类型契约如下：

```ts
type WorkKind = 'conversation' | 'arrangement';
type WorkTypeReadResult =
  | { state: 'resolved'; kind: WorkKind }
  | { state: 'unavailable' };

type TaskReadView = ClientTask & { workType: WorkTypeReadResult };
```

`ClientTask.workType` 为可选字段，兼容不携带类型的原始运行事件；`TaskReadView.workType` 必填，供服务层查询返回。前端为未读取任务补充 `loading`，通过去重的 `getTask()` 查询校准；旧后端仍不返回类型时显示 `unavailable`，不猜测会话。领域模型与读取状态分开，避免把卡片加载状态传播到执行逻辑。

service 只调用既有数据访问端口，不拼文件路径，不读取 Pi SDK。计划存储与共享创建协调器由 bootstrap 注入。控制层与 preload 复用原有查询和输入校验，不新增 IPC；新增投影只提供类型读取状态，不暴露元数据存储路径或诊断异常。

### 5.3 解析优先级

以下优先级已实现于 [work-type.ts](../../electron/service/work-type.ts)：

1. 合法的任务元数据 `kind`。
2. 合法工作计划的显式 `mode`，包括显式 `conversation`。
3. 已识别的 `[SEP_WORK_META]` 历史元信息：`conversation` 或 `flow`，后者标准化为 `arrangement`。
4. 已识别的旧 `[SEP_WORKFLOW_TASK]` 前缀，按现有历史格式判为编排。
5. 以上来源已读取完成、确认缺失且没有损坏或读取错误时，才将无类型信息的普通旧任务按会话兼容。

`[SEP_TASK_PLAN]` 当前只用于从显示文本剥离技术信息，不是独立分类依据；不要把其出现等同于合法编排计划。旧标记继续按已有兼容格式处理，不扩大为对任意正文的关键词猜测。

元数据与计划或历史标记冲突时，列表展示以元数据为准，不擅自修改持久化数据或执行路由。此次将“显式会话计划”纳入优先级，修正它无法稳定覆盖旧 `flow` 标记的行为，并以回归测试固定规则。本次不增加逐次冲突日志，读取异常仅返回 `unavailable`，避免重复查询输出完整 prompt 或敏感元数据。

### 5.4 必须处理的两个可靠性问题

**读取缺失不等于读取失败。** 当前 metadata 和 plan store 都通过 `readJsonWithBackup()` 读取，`null` 混合了缺失、损坏、读取失败。本需求如果承诺“不误标”，就不能只给现有 `null` 加一个前端判断：

- 为相关 store 提供可诊断的读取结果，区分找到、确认缺失、内容无效、读取失败，保留现有备份恢复能力。
- 有合法备份或其他合法类型来源时，可继续解析；没有合法来源且存在异常时返回 `unavailable`，不是默认会话。
- 优先新增窄范围读取能力，保留其他调用方原有行为；如复用 common helper，必须补回归测试，不全局改写所有存储读取语义。
- 不因一条记录异常让整个工作列表失败；诊断日志经共享 logger 与脱敏流程，不包含完整 prompt 或敏感元数据。

**查询投影不能被实时事件覆盖。** 当前 renderer 对单任务和全列表事件均做整体替换。只在 `getAllTasks()` 中增加字段，随后收到原始任务事件就会丢失：

- 推荐 renderer 保存按任务 ID 的类型读取缓存，与实时任务字段分开；事件没有类型字段时不清除已确认结果。
- 对首次出现且无类型的任务，触发去重的类型查询；切换账号、删除任务时清理对应缓存，异步结果核对所属上下文，避免旧账号结果回写。
- 创建任务早于元数据保存，首个事件可能早到。会话创建结果应在保存完成后携带类型；编排确认结果返回后，使用 plan 的任务 ID 补做查询或填入已确认的类型。
- 新任务尚在创建提交期间不应用“旧任务缺失信息默认会话”的兜底。不要靠固定延迟猜测写入完成，也不要对每个流式事件重新读取文件。
- 对旧版本或失败响应采用明确的兼容与重试状态；计划加载和时间线加载解耦，至少不能让时间线错误否定已确认类型。
- 若改为后端统一投影更新事件，也必须解决元数据保存前的事件顺序和异步结果乱序；事件发送仍只在 `bootstrap/renderer-bridge.ts`，不放入 service。

上述缓存/查询方案是建议实现路径；开发可选择更贴近现有代码的统一投影方式，但初次加载、创建、全列表更新和单任务更新必须满足同一契约。

## 6. 开发拆分与文件范围

### 阶段一：分类契约与回归测试

先建立解析与兼容测试，再调整数据读取和查询视图。覆盖元数据优先、显式计划模式、旧 `flow`、前缀、无信息旧任务、来源冲突及读取失败；明确新任务提交中不走旧数据默认值。

### 阶段二：可靠的读取投影

补齐相关 store 读取诊断，在现有 `TaskService.get()/list()` 中组合类型，更新共享读取 DTO、控制层及 preload 契约。实现类型缓存、创建完成后的校准查询与实时事件合并。分类只读，不自动迁移历史文件。

### 阶段三：页面展示与筛选

增加类型标识、类型分段控件、交集筛选与双维计数；保存完整筛选状态；补齐未就绪、错误和不同空态。保持详情入口、复制、终止、删除及确认流程行为不变。

### 阶段四：联调与验收

验证新旧数据、初次打开、重启、实时更新、返回导航和窄窗口；确认业务更新时间、执行状态与权限逻辑不受分类展示影响。

| 不在默认范围 | task runtime、Pi SDK、monitor 上报、完整 `flow` 重命名、详情重构 | 不应为记录分类牵动执行系统 |

后端 monitor history 虽然也有 `taskType`，但属于上报与恢复数据，不作为本地工作记录的主数据源，不绕远拉取外部历史来解决本地分类。

## 7. 测试与验收

| 场景 | 验收结果 |
| --- | --- |
| 新建普通会话、会话模式草稿 | 展示会话，不因参与员工增加而变成编排 |
| 自动编排、手动编排、单节点编排 | 均展示编排，不按节点数量猜测 |

| 类型与全部状态桶组合、搜索、重置 | 列表和计数符合交集规则，不把状态桶当互斥分类 |

| 单任务事件、全列表事件、创建期间早到事件 | 不擦除已确认类型、不早兜底会话、不过量查询、不乱序回写 |
| 删除任务、切换账号 | 不残留跨任务或跨账号类型缓存 |
| 复制、终止、删除 | 沿用原有业务契约及确认；类型展示不改变执行选择 |
| 窄窗口、长标题、键盘和屏幕阅读器 | 类型与状态可辨认、无重叠、选中状态可访问 |

## 8. 风险与非目标

- 主要风险不是标识样式，而是缺失/失败混淆、创建事件早到、实时更新覆盖类型，以及旧命名兼容遗漏。
- 单纯前端增加 badge/filter 的成本较小，但完整验收必须包括查询可靠性；不能用视觉原型掩盖类型可能错误的事实。
- 不新增自由标签、独立记录页、按类型分表、外部历史同步或历史数据批量迁移。
- 不重定义工作状态、审批策略、执行模式、重试/终止语义；不修改 Pi 依赖版本或动态导入边界。
- 不重写整个工作详情或安排工作页面；不引入新路由库、UI 库或其他依赖。

最终交付标准：用户不打开详情也能可靠辨认记录类型，能组合筛选出所需记录，往返详情不丢筛选；历史和实时数据均不因加载顺序被误标。

### 9.4 剩余边界

- 创建失败标记仅在当前进程内保存。如果任务已写入，但分类文件全部未写入，随后进程崩溃或重启，该残留任务无法与普通无类型历史会话可靠区分；跨进程事务标记属于后续独立持久化设计，本次没有引入。
- 筛选状态仅保留在当前工作区导航中，不跨重启或退出登录保存。
- 本次自动化覆盖实际工作区 hook、页面和后端存储/服务；尚未使用真实已登录 Electron 账号手动走完创建、重启与历史数据验证。
- 现有执行系统仍保留历史 `flow` 命名与原有执行类型判断，本次只改变查询和展示，不自动修复类型冲突任务的执行方式。
