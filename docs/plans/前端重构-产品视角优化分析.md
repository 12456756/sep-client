# SEP 客户端前端重构 · 产品视角优化分析

> 评估对象：`src/`（React 渲染层），分支 `refactor/backend-structure`。
> 评估方法：逐页面通读组件源码 + 数据 hook + 类型映射，沿"用户想完成什么 → 页面实际交付了什么 → 差距 → 建议"的链路分析。
> 本文聚焦**产品与信息架构**层面的优化意见，供前端重构作为输入；不含纯样式微调。
> 所有结论均标注 `文件:行`，可直接定位核验。

---

## 0. 一句话结论

这套前端的**交互骨架已经相当完整**（导航、工作流编排、详情报告、技能版本管理都齐了），但存在一个贯穿全局的产品级缺陷：

> **平台真实下发的数据被拿到手却没用，渲染层用"派生值 / 占位值"顶替，导致多个页面"看起来有数据、其实是假的或空的"。**

这比任何视觉问题都更伤产品可信度——用户会基于错误的数字（企业员工总数）和空白区块（员工能做什么）做判断。重构应优先解决"数据保真"，其次才是视觉与交互打磨。

## 1. 信息架构与导航

### 1.1 默认落地页是"组织架构"，不是工作台 ⚠️ P1

`useEnterpriseWorkspace.ts:223` 初始 `route = { name: 'organization' }`。

用户登录后第一眼看到的是**企业组织树**，而不是"我手上有哪些员工、哪些工作在等我"。对一个"我每天来干活"的桌面客户端，这是反直觉的落地页——组织架构是低频的"了解全局"场景，工作台才是高频的"开始干活"场景。

**建议**：默认落地 `home`（工作台）。组织架构作为可切换的次级视图。

### 1.2 "组织架构"的导航归属割裂 ⚠️ P1

- 侧边栏 `AppSideNav` 主导航是：首页 / 硅基员工 / 安排工作 / 工作记录 / 员工技能（5 项）。
- "组织架构"**不在侧边栏**，只藏在顶栏右上角的 `首页 / 组织架构` 切换器里（`ClientAppPage.tsx:94-115`）。

结果是同一个产品里有**两套并行的导航心智**：侧边栏一套（按功能模块），顶栏切换器一套（首页↔组织架构）。用户很难预期"组织架构"在哪——它既像一个顶级模块，又像是首页的一个视图开关。而且顶栏的"首页"按钮和侧边栏的"首页"是重复入口。

**建议**：二选一。要么把"组织架构"提升为侧边栏第 6 项，去掉顶栏切换器；要么明确它是"首页"下的一个 tab。当前的混合态最让人困惑。

### 1.3 路由用受控状态而非 URL，牺牲了可恢复性 ℹ️ P2

`ClientAppPage.tsx:9` 注释明确："路由用受控状态而不是 URL，因为桌面端不需要地址栏"。

这在桌面端可以理解，但代价是：

- 刷新 / 重开窗口总是回到默认页（见 1.1），无法恢复到上次离开的工作详情。
- 无法把"某项工作"的位置发给同事（没有可复制的定位）。
- 浏览器返回键不参与，回退完全依赖 hook 内部的历史栈（`goBack`，`useEnterpriseWorkspace.ts:512`）。

**建议**：保留无地址栏，但用 `history` 状态做会话级恢复（记住最后停留的 route），让重开窗口回到上次的工作。成本低、体验提升明显。

## 2. 逐页面产品评估

### 2.1 首页（HomePage）

**用户目标**：一眼看清"我有哪些员工、谁在忙、有什么等我处理"，并快速发起一项工作。

**做得好的**：以员工为中心的卡片墙（`EmployeeDeskCard` 轮播）+ 底部 `ArrangeBar` 快速发起，方向对——把"人"作为第一视觉主体，符合"硅基员工"的产品叙事。

**问题**：

#### 🔴 P0 — 两个统计数字恒等，且"企业员工总数"是假的

`HomePage.tsx:47-50`：

```
<Figure label="公司员工总数" value={overview.totalEmployees} onClick→ employees?scope=all />
<Figure label="我拥有的员工" value={roster.length}            onClick→ employees?scope=mine />
```

而 `useEnterpriseWorkspace.ts:364-365`：

```
totalEmployees: myEmployees.length,   // = 我拥有的
availableToMe:  myEmployees.length,   // 同一个值
```

`roster` 又是 `employees.filter(assignedToMe)`（`HomePage.tsx:24`），`myEmployees` 里每一个 `assignedToMe` 都恒为 `true`（`useEnterpriseWorkspace.ts:302`）。

**净效果**：首页两个格子永远显示**同一个数字**（=我拥有的员工数）。一个企业实际有 10 位硅基员工、分配给我 6 位时，首页显示"公司员工总数 6 / 我拥有的员工 6"——**总数是错的**，两格信息冗余。点"公司员工总数"还会跳到只显示这 6 位的页面（见 2.3）。

更关键的是：平台**已经**把真实数字下发了——`ORGANIZATION.statistics.employeeCount / activeEmployeeCount / currentUserAvailableEmployeeCount`（`platform-supplement-contracts.ts:14-17`），但全代码库**没有任何页面消费它**（`grep statistics src/pages src/features` 无业务命中）。真实数据被丢在手里，界面却用派生值造假。

**建议**：`totalEmployees` 取 `statistics.employeeCount`，`availableToMe` 取 `statistics.currentUserAvailableEmployeeCount`。两格才有对比意义（"企业 10 位，你能用 6 位"）。

### 2.2 组织架构（OrganizationPage）

**用户目标**：理解企业里"谁（人）能用哪些硅基员工"的授权关系。

**做得好的**：`mapEnterpriseOrganization`（`organization-mapping.ts:28`）把部门/成员/授权构建成一棵树，区分 root/department/member 节点，并处理了部门继承、授权过期（`isActiveGrant`）、防环（`seen` 集合）。逻辑严谨。`OrganizationPage` 还有 loading/empty/error/retry 四态。这是质量较高的一页。

**问题**：

#### 🟡 P1 — 与"硅基员工"页职责重叠，但口径不一致

组织架构页能看到**企业全员**（含未分配给我的财务/法务/市场调研员工，因为 `organizationEmployees` 走 `mapOrganizationEmployees`，基于 `organization.employees` 全量），而"硅基员工"页的"全部"只看得到分配给我的（见 2.3）。

于是用户会困惑：到底哪个页面是"看公司所有硅基员工"的地方？同一个概念（企业员工全集）在两个页面给出不同答案。

**建议**：明确分工——组织架构页讲"授权关系（谁→哪些员工）"，硅基员工页的"全部"应当也能看到企业全员（灰色不可用态），两页数据口径统一。

### 2.3 硅基员工（EmployeesPage）

**用户目标**：浏览/筛选可用的硅基员工，进入某位员工的详情或直接安排工作。

**做得好的**：搜索 + 范围切换（我的/全部）+ 可用性筛选 + 紧凑/宽松密度切换（`EmployeesPage.tsx:25-40`），筛选维度齐全；卡片有 compact/full 两种形态。交互完成度高。

**问题**：

#### 🔴 P0 — "全部员工"名不副实

`EmployeesPage.tsx:26,34`：`scope='all'` 过滤的是 `workspace.employees`，而 `employees` 由 `myEmployees` 派生（`useEnterpriseWorkspace.ts:339-354`），只含**分配给我的**员工。真正的企业全员在 `organizationEmployees` 里，但这一页没用它。

`EmployeesPage.tsx:72` 还写了提示"（灰色卡片表示尚未分配给你，只能查看介绍）"——**界面承诺了会显示未分配员工，但数据层根本没把它们送进来**。所以"我的"和"全部"两个 tab 显示同一批人，那句灰色卡片说明永远不成立。

**建议**：`scope='all'` 时数据源切到 `organizationEmployees`（已含全量 + `assignedToMe` 标记 + 灰色态逻辑，`organization-mapping.ts:134-159` 已实现），让承诺兑现。

#### 🟡 P1 — 卡片主操作标签与实际行为不一致

`EmployeesPage` 的员工卡主按钮标记"开始对话"（`EmployeeCard.tsx:61-64`），但 `onChat` 回调在这一页被接成 `id => open(id)`（`EmployeesPage.tsx:84,96`），即 `workspace.navigate({ name: 'employee', employeeId })`——实际跳到**员工详情**，不是开启对话。

用户点"开始对话"期待进入聊天输入框，结果到了介绍页。标签与行为不符。

**建议**：要么改标签为"查看详情"，要么真的调 `startConversation`。当前设计里员工详情页才有对话 textarea（`EmployeeDetailPage.tsx:73-85`），所以"开始对话"作为"进详情页准备对话"的跳板勉强讲得通，但仍是一次多余的跳转——更直接的方案是卡片上直接展开对话输入框。

### 2.4 员工详情（EmployeeDetailPage）

**用户目标**：判断"这位员工能帮我做什么、边界在哪、怎么开始"。

**做得好的**：四区块结构清晰（介绍 / 能做什么 / 使用范围 / 技能）；"使用范围"=本机操作权限，由用户自己开启且有风险提示（`PermissionPanel`）；未分配态有醒目 banner + 禁用对话入口（`EmployeeDetailPage.tsx:62-66`）。结构是对的。

**问题**：

#### 🔴 P0 — "能做什么 / 不做这些"永远是空的

`EmployeeDetailPage.tsx:89-98` 渲染 `employee.goodAt` 和 `employee.cannotDo`，但这两个字段在 `myEmployees` 构造时**被硬编码为空数组**（`useEnterpriseWorkspace.ts:304-305`）：

```
goodAt: [],
cannotDo: [],
```

"能做什么"是用户决定要不要用这位员工的**核心信任信息**，现在永远显示两个空列表。这等于详情页最重要的决策依据缺失。

**建议**：从平台/模板补 `goodAt`/`cannotDo`（哪怕先用 `placeholder.ts` 里按角色的 `PROFILE_BY_ROLE` 兜底——该数据已存在但未被消费）。在真实数据接通前，至少显示"暂无能力说明"而非两个空 `<ul>`。

#### 🟡 P1 — 返回链接文案与目标不一致

`EmployeeDetailPage.tsx:34-37`：返回按钮文字是"全部员工"，但 `navigate({ name: 'employees' })` 不带 scope，落到默认 `mine`（"我的"）。文案说"全部"、实际回"我的"。

**建议**：文案改"返回员工列表"，或带上 `scope` 与来源一致。

#### ℹ️ P2 — 残留空标签

`EmployeeDetailPage.tsx:129-130`：技能卡里有一个空的 `<span>`（内含空白行），是删改后没清理的残留。重构时一并清掉。

### 2.5 安排工作（ArrangeWorkPage）

**用户目标**：选员工、定方式、确认开干。

**做得好的**：入口屏（`mode='pick'`）用 `ModeCards` 呈现**三种**编排方式——对话式 / 自动编排 / 自己编排，每张卡都带场景化说明（`ModeCards.tsx:33,40,48`，如"对话式：与一个员工直接沟通，边聊边完成工作"），三张卡视觉刻意一致、只用一条极淡顶部线标记 `featured`（自动编排），切换有淡出过渡。模式引导设计是合格的，新手不至于"不知道选哪个"。运行设置有独立抽屉（`RunSettingsDrawer`）；无可用员工时有 `Empty` 兜底。

**问题**：

#### 🔴 P0 — 用户填错时看到一串问号（生产代码乱码）

`useEnterpriseWorkspace.ts` 里 `arrangeWork` 的全部用户可见错误提示是**损坏的占位串**：

- `:569` `setError('????????')`（本意：请至少填写一个工作步骤）
- `:585` `setError('???????')`（本意：请选择模型）
- `:604` `'??????'`（创建草稿失败兜底）
- `:606` `'??????'` + `blockingIssues.join('?')`（运行前检查失败）
- `:608` `'????'`（员工没接单）
- `:611` `'????'`（最外层兜底）

同样的乱码还出现在：
- `src/App.tsx:66,72`（订阅加载失败 `'?????????'`）
- `src/features/workspace/useWorkspaceDemo.ts:403,419,420,436,438,440,445`（一整套）

**根因**：这些原本是中文，在某次提交里被转码损坏成 `?`。而 `npm run check:boundaries` 的 mojibake 检测**只扫 `electron/`，扫不到 `src/`**，所以漏网至今。

用户在不填步骤就点"开始"时，看到的不是"请至少填写一个工作步骤"，而是 `????????`。这是直接面向用户的破损。

**建议**：
1. 立即修复全部乱码串（恢复中文）。
2. 把 mojibake 检测的范围从 `electron/` 扩到 `src/`，纳入 `check:boundaries`，防止回归。

### 2.6 工作记录（WorkRecordsPage）

**用户目标**：找到某项工作，看结果 / 跟进 / 复用 / 清理。

**做得好的**：分桶（全部/进行中/我的/已完成/已终止）带计数 + 搜索；每条记录可展开"结果/过程"面板；操作齐全（查看结果、查看过程、复制为新工作、终止、删除）且危险操作有确认弹窗。功能完整度高。

**问题**：

#### 🟡 P1 — 单条记录操作过多，主次不清

一条记录上并列了 lead 按钮 + 查看结果 + 查看过程 + 复制为新工作 + 终止 + 删除（`WorkRecordsPage.tsx`）。6 个动作平铺，用户要扫一遍才知道点哪个。

**建议**：按状态收敛主操作——进行中→"跟进/终止"，已完成→"查看结果/复制为新工作"，已终止→"复制为新工作/删除"。次要操作收进 `⋯` 菜单。

#### ℹ️ P2 — 分桶语义已核实，"需要我处理"是有效筛选

存在 `all / active / mine / done / stopped` 五个桶。需澄清的是：`mine` 桶的实际标签是"需要我处理"（`WorkRecordsPage.tsx:47`），匹配 `work.status === 'waiting-user' || work.nextUserAction`，确实是一个**有效且不同于 `all` 的集合**——它不等于 2.3 那种"名不副实"。`stopped` 桶标签是"未完成"，覆盖 `failed` 与 `paused`。

唯一可优化处：`mine` 变量名与"需要我处理"标签不一致（`mine` 字面是"我的"，实际是"待我处理"），重构时把变量名对齐语义即可，避免维护者误读。

### 2.7 工作详情（WorkDetailPage）

**用户目标**：看一项工作的全貌——谁在做、做到哪、产出了什么、需不需要我。

**做得好的**：这是信息密度最高、设计最用心的一页。头部 + 元信息 + 三栏（执行员工/工作信息/结果 Donut）+ 两栏（过程时间线/产出文件）+ "现在需要你"行动条 + 折叠的更多信息 + 对话/计划双抽屉。完成态当"工作报告"、运行态当"实时进展"，一套布局两种用途。流程态的步骤状态来自真实事件（`arrangementStepState`），对话态来自 `decodeWorkMeta`，区分得当。

**问题**：

#### 🟡 P1 — 信息密度高，窄屏与首次理解成本需验证

三栏 + 两栏 + 抽屉 + 行动条，在 1200×800 尚可，960×640（CLAUDE.md 要求验证的尺寸）下多栏可能挤压。Donut、时间线、产出、行动条同屏，用户视线无明确落点。

**建议**：重构时按"状态"精简——运行态突出"现在需要你 + 当前进展"，完成态突出"结果 + 产出"，把时间线/更多信息默认折叠。窄屏下多栏降为单栏堆叠。需在 960×640 实测。

### 2.8 员工技能（SkillsPage / SkillDetail）

**用户目标**：看懂某项技能做什么、企业版与我的个人版差异、切换员工使用的版本。

**做得好的**：技能库工具栏 + 卡片网格；详情是带版本列表的编辑器，支持个人版本保存（Radix 保存弹窗）；版本区分 scope（PLATFORM/ENTERPRISE/PERSONAL）与审核状态；"企业标准只读、个人版可调"的权限模型清晰。功能完整。

**问题**：

#### ℹ️ P2 — 概念偏重，对非管理员用户门槛高

版本、scope、审核状态、个人版上传/重试——这套模型对"只想用员工干活"的普通成员偏重。当前 `canManage=false`（平台未开放，`ClientAppPage.tsx:37`），管理员审核入口本就隐藏，但版本管理的复杂度仍暴露给所有人。

**建议**：按角色分层——普通成员只看到"这位员工用的是哪个版本 + 切到个人偏好版"，把 scope/审核/上传等管理动作收进管理员视图。

## 3. 横切问题（跨页面）

### 3.1 🔴 数据保真——本次重构最该解决的根本问题

贯穿 2.1 / 2.3 / 2.4 的同一个病根：**平台真实数据拿到了，渲染层却用派生值/占位值顶替**。

| 现象 | 真实数据在哪 | 渲染层用了什么 | 位置 |
|------|------------|--------------|------|
| 企业员工总数=我拥有的 | `statistics.employeeCount` | `myEmployees.length` | `useEnterpriseWorkspace.ts:364` |
| "全部员工"=我的 | `organizationEmployees`（全量） | `employees`（仅已分配） | `EmployeesPage.tsx:26` |
| 员工"能做什么"空白 | 模板/角色画像（`PROFILE_BY_ROLE` 已存在） | 硬编码 `[]` | `useEnterpriseWorkspace.ts:304` |

重构应确立一条原则：**渲染层只消费平台真实字段；缺字段时显式标注"平台未提供"，绝不用派生值冒充真实值冒充。** 这能一次性消除上述三处误导。

### 3.2 🔴 用户可见文案的健壮性

- 乱码占位串（2.5）已确认遍布 `App.tsx` / `useEnterpriseWorkspace.ts` / `useWorkspaceDemo.ts`。
- 检测盲区：`check:boundaries` 的 mojibake 只覆盖 `electron/`。

**建议**：扩展到 `src/`；并把所有用户可见错误文案集中到一处常量表（类似后端 `errors/error-codes.ts` 的做法），避免散落各处的字面量再次损坏。

### 3.3 🟡 空态（Empty）的使用要一致

代码里有统一的 `Empty` 原子组件（`atoms.tsx`），多处用得不错。但 2.4 的"能做什么"用了两个**裸空列表**而非 `Empty`——同样是"没数据"，呈现不一致。

**建议**：制定空态规范：什么场景用 `Empty`（带标题+说明），什么场景用占位文案，全前端统一。

### 3.4 🟡 导航/文案一致性

- 返回链接文案与目标不符（2.4）。
- "首页"在侧边栏和顶栏重复入口（1.2）。
- 顶栏副标题"企业共 X 位，其中 Y 位已分配给你"（`ClientAppPage.tsx:65`）两个数字也恒等（同 3.1）。

**建议**：重构时做一次全量文案与导航口径梳理，建立"同一概念同一说法"的对照表。
