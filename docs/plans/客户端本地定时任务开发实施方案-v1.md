# 客户端本地定时任务开发实施方案 V1

状态：在建，待评审。

日期：2026-10-16。

范围：Electron 客户端本地定时任务；不引入云端调度服务，不重新开发 Agent 执行器。

本文是分批实施方案，不要求一次完成所有阶段。每阶段独立交付可操作的前后端闭环；尚未实现的时间规则、策略及恢复动作不得在界面开放。

## 1. 结论先行

本模块的核心不是“到点调用一次函数”，而是可靠地完成下面这条链路：

```text
定时任务配置
  -> 持久化 nextRunAt
  -> 动态定时器唤醒
  -> 生成唯一触发记录 occurrence
  -> 创建一个新的普通工作任务
  -> 复用现有 TaskRuntime 执行
  -> 记录这一次运行的状态、尝试、错误和结果
  -> 重新计算下一次触发时间
```

定时任务配置和实际执行记录必须分开：

- 定时任务配置只有一个固定 ID。用户编辑时更新原配置，增加 `revision`，不创建新的定时任务。
- 每个计划时间点必须有独立的 `occurrence`，否则无法展示历史、重试、恢复和判断是否重复。
- 每次 occurrence 创建一个新的普通 `taskId`，复用现有任务列表、工作详情、事件、检查点和执行状态。
- 自动编排只在创建定时任务时规划一次；之后只复制已确认的 `WorkPlan` 快照，不再调用规划器，不开放自动编排步骤编辑。
- 指定员工任务保存目标、员工、模型、工作目录和权限配置；每次真正执行前重新校验员工并重新装配当时有效的 Skill。
- 动态定时器只是唤醒机制，持久化的 `nextRunAt`、occurrence 和恢复扫描才是事实来源。

本方案重点保证两件事：

1. 同一个计划时间不会被调度器创建多个有效执行实例。
2. 客户端崩溃、重启、休眠、网络异常后，不会因为“不确定”而盲目重复执行有副作用的任务。

对外部副作用不能承诺真正数学意义上的 exactly-once。客户端可以做到“触发和领取有效地去重”，但在外部命令已经执行、进程随后崩溃的窗口里，只能标记结果不确定，不能假装知道它没有执行。

这里的“确保运行”指：在应用在线、当前账号有效、存储健康且资源可用时，符合策略的触发最终能进入既有执行入口；无法满足时，必须有明确的等待、跳过或失败记录与原因。它不代表一定按秒准点，也不代表模型一定完成业务目标。

## 2. 已核对的现有能力

以下是 2026-10-16 对当前工作树的静态核对结果。

| 能力 | 现有实现 | 对定时任务的结论 |
| --- | --- | --- |
| 任务保存 | `electron/data/task-store.ts` + JSON 原子写入 | 复用普通任务；定时任务需要新增专用 Store |
| 任务执行 | `electron/runtime/task-runtime.ts` | 复用 `executeTask(taskId)`，不新建 Agent 执行链 |
| 自动编排计划 | `electron/data/work-plan-store.ts`、`ArrangementExecutor` | 创建时保存快照，下一次执行复制到新 task |
| 执行记录 | `electron/data/task-run-store.ts`、`TaskEventStore` | 继续保存实际运行记录和事件 |
| 员工授权 | `electron/service/employee-authorizer.ts` | 执行前重新授权、刷新目录并装配 Skill |
| Skill 版本 | `electron/data/skill-version-store.ts`、`pi-skill-packages.ts` | 定时任务不保存替换功能，运行前按员工当前配置装配 |
| 工作目录冲突 | `electron/runtime/workspace-lock-manager.ts` | 复用；冲突不能简单视为 Agent 失败 |
| 队列 | `electron/runtime/run-queue.ts` | 复用，但需增加定时任务分发入口和容量策略 |
| 审批 | `electron/runtime/run-approvals.ts` | 复用 60 秒超时自动拒绝，不因无人值守而自动放行 |
| 中断恢复 | `TaskManager`、`TaskRunStore`、编排检查点 | 复用现有状态；定时任务不能无条件重跑中断实例 |
| 持久化基础 | `atomic-file.ts`、`WriteChain`、`ScopePath` | 可支持 V1，但必须增加调度交接和恢复规则 |
| 单实例 | 当前未发现 `requestSingleInstanceLock` | 第一阶段启用调度前补上；未取得同一 userData 的写入所有权不得启动调度 |
| 执行隔离 | PiTaskWorker 当前为主进程普通对象 | 现有动态 import 不等于进程隔离；CPU 隔离单独纵向验证后再开放长任务 |

现有 `atomic-file.ts` 存在先删除目标再 rename 的窗口，且没有显式持久化同步；现有“读不到返回 null”的部分接口不能直接作为“任务不存在、可以新建”的证据。第一阶段需以诊断式读取区分不存在、损坏、不可读和备份恢复，不宣称现有文件工具已提供数据库事务或断电保证。

当前 `ArrangementService.confirmDraft()` 会把草稿确认成一个具体 task，不能每天直接重复调用；其中已确认草稿会返回已有的 `WorkPlan`。因此必须增加“从定时任务配置创建新的普通 task 实例”的内部用例，而不是重复调用确认接口。

## 3. 模块边界

保持现有依赖方向：

```text
renderer
  -> controller / IPC
  -> ScheduledTaskService
  -> ScheduledTaskStore / OccurrenceStore
  -> Scheduler / Dispatcher
  -> TaskService / TaskRuntime
  -> Pi SDK
```

### 3.1 ScheduledTaskManager

负责：

- 创建、修改、暂停、恢复、删除定时任务。
- 校验员工、模型、工作目录、权限和已确认编排。
- 修改时增加 `revision`，不改变任务 ID。
- `expectedRevision` 不匹配时拒绝覆盖，返回当前修订，前端刷新后再确认。
- 修改成功后通知 Scheduler 立即重新扫描。
- 手动触发时复用同一条 occurrence 创建和分发流程，不另写一条执行路径。

不负责：

- 解析 Agent 输出。
- 直接调用 Pi SDK。
- 自己实现 Skill 下载或装配。
- 直接控制 Renderer。

### 3.2 ScheduledTaskScheduler

负责：

- 从 Store 加载启用任务。
- 计算最早 `nextRunAt`。
- 只设置一个动态唤醒 timer。
- timer 到期后扫描所有到期任务。
- 处理启动、登录、修改、暂停、恢复和系统唤醒后的重新扫描。
- 调用 OccurrenceStore 创建唯一触发记录。

不负责：

- 执行 Agent。
- 检查复杂员工权限。
- 直接修改普通 task 状态。

### 3.3 ScheduledTaskDispatcher

负责：

- 领取待处理 occurrence。
- 处理重叠策略、队列容量和工作目录冲突。
- 调用“从定时配置创建普通 task”的内部端口。
- 将 occurrence 与普通 task 关联。
- 处理启动前的鉴权、配置和资源错误。

### 3.4 ScheduledTaskRunnerAdapter

负责把定时任务转换成现有任务执行调用：

- 指定员工模式：创建普通 task，设置员工，然后调用 `TaskRuntime.executeTask`。
- 自动编排模式：以保存的 `WorkPlan` 快照创建新 task 和新 plan，然后调用 `TaskRuntime.executeTask`。
- 执行开始前由现有 `EmployeeAuthorizer.authorize()` 重新装配 Skill。
- 不调用自动规划器。

### 3.5 ScheduledTaskRecovery

负责：

- 启动恢复扫描。
- 休眠唤醒后的补偿扫描。
- 修复 occurrence 与普通 task 的交接状态。
- 回收过期领取租约。
- 识别普通 task 已创建但 occurrence 尚未更新的情况。
- 对状态不确定的任务阻止自动重放。
- 先核对当前身份作用域及既有任务恢复结果，再允许 Dispatcher 工作；不得以超时或租约过期直接证明 Agent 已停止。

## 4. 本地持久化设计

不引入数据库时，使用当前按企业和成员隔离的文件存储。建议目录：

```text
<userData>/task-data/v3/<enterprise>/<member>/scheduled-tasks/
  <scheduledTaskId>/
    definition.json
    occurrences/
      <occurrenceId>.json
```

### 4.1 `definition.json`

该文件是定时任务的唯一逻辑配置记录，修改时覆盖同一记录。备份、待提交文件和恢复凭据不是新建一条定时任务：

以下是逻辑字段示意，不是可直接编译的共享 DTO；实际开发按阶段生成完整 Zod/schema 与共享类型，引用既有权限、WorkPlan 等类型，不另造执行模式。

```typescript
interface ScheduledTaskDefinition {
  schemaVersion: 1
  id: string
  owner: { memberId: string; enterpriseId: string }
  name: string
  enabled: boolean
  health: 'ready' | 'blocked' | 'deleted'
  stateVersion: number
  mode: 'employee' | 'arrangement'
  prompt: string
  title: string
  subscriptionId: string | null
  modelId: string | null
  workDir: string | null
  permissions: RequestedTaskPermissionPolicy
  plan: WorkPlanSnapshot | null
  schedule: {
    type: 'once' | 'interval' | 'daily' | 'weekly' | 'monthly' | 'cron'
    expression: string
    timezone: string
    nextRunAt: string | null
    lastScheduledAt: string | null
    latenessGraceMs: number
  }
  misfirePolicy: 'skip' | 'catch_up_once' | 'catch_up_all'
  misfireWindowMs: number
  maxCatchUpRuns: number
  overlapPolicy: 'skip' | 'queue' | 'parallel'
  maxConcurrentRuns: number
  retryPolicy: {
    maxAttempts: number
    baseDelayMs: number
    maxDelayMs: number
  }
  dispatchTimeoutMs: number
  timeoutMs: number | null
  revision: number
  createdAt: string
  updatedAt: string
}
```

`plan` 只保存已经确认的执行计划快照，不允许在定时任务页面修改节点、员工分配或 DAG。时间、名称和其他获准修改的属性始终更新原 ID；如未来支持替换工作内容，必须走现有重新生成与确认流程，将新确认快照更新到原记录，不能通过编辑表单直接改计划，也不能暗中新建另一条定时任务。

`revision` 仅在用户修改配置时递增；推进游标、领取或记录错误使用单独的 `stateVersion`，避免运行中的调度更新让用户配置表单无谓冲突。每次写入均由 Store 串行地重新读取和比较版本，旧事件不能覆盖新配置或终态。

Skill 不进入该配置的固定版本字段。执行时按照员工当前可用 Skill 装配，并将实际使用的版本指纹写入 occurrence/普通 run 的诊断信息。

### 4.2 `occurrence.json`

一个 occurrence 表示一个计划时间点，不是一个新的定时任务：

```typescript
interface ScheduledOccurrence {
  schemaVersion: 1
  id: string
  scheduledTaskId: string
  scheduledTaskRevision: number
  owner: { memberId: string; enterpriseId: string }
  trigger: 'scheduled' | 'manual'
  scheduledAt: string
  executionSnapshot: ScheduledExecutionSnapshot
  reservedTaskId: string
  status:
    | 'scheduled'
    | 'dispatching'
    | 'queued'
    | 'running'
    | 'waiting_retry'
    | 'waiting_auth'
    | 'waiting_network'
    | 'waiting_approval'
    | 'succeeded'
    | 'failed'
    | 'skipped'
    | 'cancelled'
    | 'timed_out'
    | 'interrupted'
    | 'unknown'
  taskId: string | null
  currentAttempt: number
  attempts: ScheduledAttemptSummary[]
  nextRetryAt: string | null
  error: ScheduledError | null
  resultReference: { taskId: string } | null
  lease: { owner: string; generation: number; expiresAt: string } | null
  dispatchDeadlineAt: string
  cancelRequestedAt: string | null
  executionReceipt: {
    admittedRunId: string | null
    enteredExecution: boolean
    sideEffectState: 'none_observed' | 'observed' | 'unknown'
  }
  stateVersion: number
  createdAt: string
  updatedAt: string
}
```

`scheduledAt` 必须保存 UTC 时间。不能使用本地时间字符串作为唯一键，否则夏令时重复小时会造成两个不同时间被当成同一个 occurrence。

建议 occurrence ID 使用：

```text
occurrenceId = hash(canonical([scheduledTaskId, scheduledAtUtc]))
```

同一任务同一计划时刻永远得到同一个 ID，不把配置 revision 放进键中，以免编辑前后重复生成同一时刻。ID 只含现有安全路径字符，不使用冒号。手动立即运行使用带请求幂等键的随机 ID，不改变下一次计划时间，也不能绕过重叠策略。

仅保存 `scheduledTaskRevision` 不够：原配置会被更新，因此 occurrence 必须同时保存不可变 `executionSnapshot`（目标、员工/编排快照、模型、目录、权限、调度策略和截止时间），不包含 token，不包含固定 Skill 版本。快照用现有 WorkPlan 结构；运行日志和文件正文只在原任务存储保存，不复制进快照。

实际 Skill 指纹属于本次运行证据，不属于可编辑配置。每位员工/节点真正启动前重新授权、装配 Skill；已启动的节点不热替换。

`sideEffectState=none_observed` 只表示没有观察到副作用，不代表可以证明没有发生。崩溃且事件可能尚未落盘时必须按 `unknown` 处理，不能依据“没有工具完成事件”自动重放。

一次尝试的最小字段为 `attemptId/number/phase/startedAt/finishedAt/status/error/nextRetryAt/runtimeRunId`。模型 SDK 内部请求重试记录为事件及预算，不冒充新的一次整任务尝试。attempt 摘要有数量上限，不在 occurrence 无限累积流式事件。

### 4.3 写入顺序和崩溃恢复

JSON 文件不能像数据库一样对多个文件进行事务提交，因此必须规定写入顺序：

1. 在当前任务写队列内校验配置修订及启停状态，先持久化完整 occurrence（快照及预留 taskId），使用排他占位/提交协议；已存在时验证内容，不重复生成。
2. 再更新 `definition.nextRunAt` 和 `lastScheduledAt`。
3. 再将 occurrence 改为 `dispatching` 并开始分发；Agent 不能早于必要记录落盘开始。

排他创建本身不保证文件已写完整：崩溃留下的空文件/半文件不能被当成正常成功，也不能删除后自动重建执行。Store 必须使用临时完整内容、校验摘要、同目录发布、必要的文件同步和提交标记；每个 record 带 schema/stateVersion。写入成功含义、Windows 替换行为、备份回退都要用实际 Electron 运行环境验证，不盲用最新版 Node 才支持的选项。

建议为定时模块提供加固的文件提交 helper，优先复用并修复共享能力，避免无必要改动所有旧存储。强制维持一个写入方；子进程只能发事件，不能直接改定时文件。存储磁盘不支持所需排他/提交语义时关闭自动执行并告知用户，不悄悄降级。

如果第 1 步成功、第 2 步前崩溃，启动恢复扫描会看到 occurrence 已存在，并重新计算 definition 的 `nextRunAt`。不能重新创建 occurrence。

如果第 2 步成功、第 3 步前崩溃，恢复扫描会根据 occurrence 状态继续分发。

如果创建普通 task 后、关联 `taskId` 前崩溃，必须通过来源标记和 occurrence 预留的 taskId 找到已创建 task，不能再次创建。为此需要扩展普通任务的持久化对象，增加可选来源字段：

```typescript
interface ScheduledTaskOrigin {
  scheduledTaskId: string
  occurrenceId: string
}
```

在现有 `ClientTask` 上新增可选 `scheduledOrigin: ScheduledTaskOrigin`，兼容旧记录；字段必须与普通 task 在创建的第一次 commit 中一起写入，不能创建成功后才补写。需要一个内部 `createScheduledTaskOnce(reservedTaskId, origin, snapshot)` 用例，串行比较已存在的来源与配置摘要，重复请求返回同一 task。原手动创建继续使用原行为，外部 Renderer 不能指定任意 taskId 或伪造来源。

恢复时按 `scheduledOrigin.occurrenceId` 搜索已有 task：

- 找到一个：补回 occurrence.taskId；先补齐 WorkPlan/metadata，再根据准入和运行凭据决定观察、启动或标记中断。
- 找到多个：标记 occurrence 为 `unknown`，停止自动操作并报错。
- 一个都找不到：必须是健康存储的“明确不存在”，且没有已准入/执行凭据，才允许用原 reservedTaskId 补建；损坏/读取超时/备份回退不等于不存在。

这是一条必须落实的正确性不变量：**先确认是否已有普通 task，再决定是否创建。**

读取备份成功也不意味着可以自动执行：备份可能遗漏最近一次准入/成功记录。定时文件或现有 task/run 存储发生回退、丢失或校验失败时，先冻结受影响范围并交叉核对；证据不足显示“记录异常，已停止自动执行”。完成历史不能仅因游标回退再次被触发；清理 occurrence 正文必须保留精简触发凭据/终态摘要，至少覆盖时钟回拨和去重范围。

## 5. 动态定时器设计

### 5.1 一个 Scheduler、一个主 timer

不为每个任务长期维护一个 `setInterval`。Scheduler 维护一个动态 timer：

```text
load enabled definitions
  -> find minimum nextRunAt
  -> arm one timer
  -> wake and scan due definitions
  -> create occurrences
  -> dispatch eligible occurrences
  -> recompute minimum nextRunAt
  -> arm again
```

唤醒点取下一次计划、重试、等待截止、租约检查和低频校准时间中的最早值。即使所有计划都在几天后，已经失败等待重试的 occurrence 也必须能被唤醒；不能只依据 `nextRunAt`。

建议最大校准间隔初值 60 秒：只有存在启用任务或未完成 occurrence 时才启用；平时检查内存时间索引和墙钟偏差，不每分钟读取全量历史。无人登录、没有任务且没有待处理记录时停止 timer。业务状态变化立即重排，无需等 60 秒。这是待压测的技术默认值，不是高频磁盘轮询。

`setTimeout` 不保证准点且有最大延迟边界；实际 delay 分段并夹在合法范围内。不能依赖一个跨月 timer，也不能用 0ms 重试循环造成忙等。

### 5.2 必须重新扫描的事件

以下事件全部调用同一个 `scanAndRearm(reason)`，不能各自实现一套：

- 客户端启动完成后。
- 用户登录或切换成员后。
- 新建定时任务成功后。
- 编辑定时任务成功后。
- 暂停、恢复、删除定时任务后。
- 当前 timer 到期后。
- Electron `powerMonitor` 发出 resume 后。
- 系统时间或时区发生变化后。
- 认证状态恢复后。
- occurrence 进入重试、等待截止更新、普通任务完成/锁释放、取消执行后。

用户创建任务后，必须在 Store 写入成功后立即请求 `scanAndRearm('created')`，由 single-flight 扫描保证合并期间不丢请求。创建响应区分“配置已保存”与“调度健康”，调度请求失败不能让用户误以为未创建并重复点击；同一创建请求携带幂等键，返回原任务 ID。已保存未激活的任务由低频修复或启动扫描接管，前端提示状态，不要求用户再创建一条。

不假设 Electron 有跨平台统一的系统时间/时区变更事件。使用 `resume`、显式配置事件和有上限的动态唤醒校准；比较墙钟与单调时钟的增量发现回拨/前跳。账号切换递增 scope generation，取消旧 timer；扫描及网络返回在任何写入/执行前重新校验 generation，旧账号记录不得投递到新账号。

### 5.3 扫描并发控制

`scanAndRearm` 必须 single-flight：

- 同时触发多个扫描时只保留一个正在执行的扫描。
- 扫描期间有新配置变化，设置 `scanRequested=true`，当前扫描结束后再扫一次。
- 扫描不能持有长时间的文件锁等待 Agent 执行。
- 调度器只负责短事务和投递，不在扫描循环中执行网络请求、Skill 下载或 Agent。
- 每轮最多处理固定数量到期定义/occurrence，分批让出事件循环；坏文件按任务隔离，不让单条错误中断全部扫描。
- Store 缓存活跃任务索引，启动时重建，修改后更新；计时重排不读取所有历史 occurrence。

### 5.4 到期扫描

扫描条件是 `enabled && nextRunAt <= now`。每次扫描：

1. 根据 `misfirePolicy` 计算应处理的计划时间集合。
2. 对每个计划时间生成稳定 occurrence ID。
3. 只创建不存在的 occurrence。
4. 计算并保存下一次 `nextRunAt`。
5. 将可执行 occurrence 投递给 Dispatcher。
6. 重新计算全局最早时间并 arm timer。

本地时间规则依据系统墙钟和持久化 UTC 时刻，不依赖云端调度或模型判断；单调时钟用于运行耗时和墙钟跳变检测。

### 5.5 时间语义和默认策略

以下是建议默认值，后续阶段可以增量开放，不构成一次性全部实现要求：

| 问题 | 明确规则 |
| --- | --- |
| 固定周期 | 从固定锚点计算，不从上次完成时间顺延；运行耗时不改变计划 |
| 每日/每周/每月 | 保存 IANA 时区和当地时间，换算 UTC；用户改变系统时区不自动改任务时区 |
| Cron | 使用成熟解析库，先开放明确的五段格式；不手写日历解析，保存格式版本及 timezone |
| 夏令时缺失时间 | 跳过不存在的本地时刻；重复本地时刻每日/周/月默认只选较早一次；Cron 也采用同一去重规则并做专门测试 |
| 每月 29/30/31 日 | 当月无该日期时跳过，不悄悄改为月底；表单展示接下来至少 3 次时间 |
| 正常扫描延迟 | `latenessGraceMs` 建议 30 秒，容差内算正常到期；超出后进入错过策略 |
| 默认错过策略 | CatchUpOnce，建议窗口 24 小时、补跑最多 1 次；窗口外不执行 |
| CatchUpAll | 配置窗口且单次补跑最多 10 次，分批入队；超过上限跳过较旧时刻，保留摘要和原因 |
| Skip | 容差外只记跳过，不补跑；不能把每次 timer 晚几毫秒都视为错过 |
| 用户主动暂停 | 暂停期间不积累默认补跑；恢复从当前时间算下一次，已有 occurrence 另按其状态处理 |
| 修改时间 | 原已生成 occurrence 使用快照继续；尚未生成的旧时刻作废，不按新规则追溯生成旧任务 |
| 一次性到期 | 生成唯一 occurrence 后 `nextRunAt=null`，定义仍保留；失败重试属于该 occurrence，不新建一次计划触发 |
| 时钟回拨 | 已处理时刻不重复触发；查精简触发凭据，无法确认则阻塞而非重新执行 |

被跳过时刻在工作记录中应可解释；长时间关闭跨越数千个时刻时，保存有边界的跳过区间摘要，按需计算展示，不能为了补全 UI 无限创建文件。

默认重叠策略 Skip：同一定时任务有排队、等待网络/认证、运行或待核查的 occurrence 时不启动第二次；本次显示“上次尚未结束，已跳过”。Queue 需最大长度和启动截止；Parallel 受单任务及全局上限约束，并且不能绕过工作目录锁。未知副作用应阻塞同一定时任务的后续运行，不阻塞所有其他健康任务。

## 6. 创建和修改流程

### 6.1 指定员工模式

```text
Renderer 填写目标、员工、模型、目录、权限和时间
  -> IPC controller 校验输入
  -> Service 检查当前登录和员工授权
  -> Store 创建 definition.json
  -> Scheduler 重新扫描
  -> 返回定时任务详情
```

保存时检查员工和模型只是提前发现问题；实际每次运行前仍需重新检查，因为订阅、员工和权限可能已经变化。

### 6.2 自动编排模式

```text
用户先完成现有自动编排并确认
  -> 获取确认后的 WorkPlan
  -> 将 WorkPlan 深拷贝写入定时任务 definition
  -> 不保存草稿编辑入口
  -> Scheduler 重新扫描
```

之后每次运行：

```text
读取 WorkPlan 快照
  -> 为本次 occurrence 创建新的普通 task
  -> 为本次 task 保存新的 WorkPlan
  -> 调用现有 TaskRuntime.executeTask(taskId)
```

定时任务配置被修改时，已经生成的 occurrence 继续使用其不可变配置快照，未来 occurrence 使用新 revision；不能根据旧 revision 再去读已被覆盖的配置。

### 6.3 修改、暂停和删除

- 修改：原 ID 不变，`revision + 1`，更新原 `definition.json`，保存成功后重新扫描。
- 修改时间规则：旧的 `nextRunAt` 不再触发；新的下一次时间重新计算。
- 工作目录为用户指定路径时原样复用，写入冲突走原目录锁；未指定时按现有规则创建本次默认工作目录。固定文件名在指定目录中可能覆盖既有产物，创建时需明确确认，不静默修改编排交付路径。
- 暂停：停止生成未来 occurrence；已有 `queued/running` 不强制终止。
- 恢复：根据当前时间和错过策略重新扫描。
- 删除：标记删除或从列表隐藏；已有运行记录保留，正在执行的任务默认不强制终止。
- 删除后重新创建同名任务，必须生成新的任务 ID，不能复用旧 ID。
- 删除与扫描/领取在同一任务写队列中串行；删除返回后未准入的 occurrence 不得再启动。已运行任务保留历史，删除确认框允许明确选择是否另外取消正在运行的工作。
- 自动编排的节点、DAG、员工分配及任务目标不在普通编辑表单开放；指定员工任务可按获准字段编辑。所有编辑均更新原 ID，不新增定时定义。

## 7. 完整异常处理方案

所有异常都要经过后端错误分类，前端不根据字符串猜测。错误结构至少包括：

```typescript
interface ScheduledError {
  category:
    | 'schedule'
    | 'persistence'
    | 'authentication'
    | 'authorization'
    | 'employee'
    | 'skill'
    | 'model'
    | 'network'
    | 'rate_limit'
    | 'workspace'
    | 'approval'
    | 'tool'
    | 'runtime'
    | 'timeout'
    | 'cancelled'
    | 'process_crash'
    | 'side_effect_unknown'
    | 'dispatch'
    | 'unknown'
  code: string
  retryable: boolean
  retryScope: 'none' | 'storage' | 'preflight' | 'dispatch' | 'model_request' | 'checkpoint'
  executionEntered: boolean
  sideEffectUncertain: boolean
  userAction: 'none' | 'retry' | 'login' | 'fix_config' | 'review' | 'free_workspace'
  message: string
  requestId: string | null
  occurredAt: string
}
```

`message` 是安全的用户提示；堆栈、供应商响应、命令原文只在必要时经共享脱敏流程进入诊断日志，token/密钥无论普通日志还是诊断日志都不能记录。时间、允许展示的工作目录、请求 ID 不是秘密凭证，但仍受当前成员作用域控制。

错误分类接入现有 `AppError`/错误码及已验证的 HTTP 状态，扩充缺失的结构化信息，不另建一套字符串匹配器。SDK 无法可靠提供原因时使用 `RUNTIME_FAILURE`，不从模糊错误文本推断“肯定能重试”。分类先确定失败阶段和是否已进入执行，再确定根因；Skill 加载中的网络失败应归网络临时错误，而不是所有 Skill 错误一律永久失败。

### 7.1 异常处理矩阵

| 场景 | 后端处理 | 是否重试 | 定时任务记录 | 前端展示 |
| --- | --- | --- | --- | --- |
| 时间表达式/时区非法 | 创建或修改时拒绝，不落无效配置 | 否 | 任务保持旧版本 | 表单字段错误 |
| 定时配置文件损坏 | 尝试主文件、`.bak`，失败则隔离并停止该任务 | 否 | `blocked` + `persistence` | “配置无法读取”，提供导出诊断/删除 |
| 写入失败/磁盘满 | 不推进游标、不准入；保留已有提交证据，暂停受影响任务 | 仅重试同一幂等写入，建议最多 3 次 | 最后可信状态 + `STORAGE_UNAVAILABLE`，不能假写新状态 | “存储异常，自动执行已停止”，修复后核对 |
| 重复扫描同一时刻 | 通过 occurrence ID 判重 | 不需要 | 已有记录继续 | 不提示错误 |
| 普通 task 已创建但关联失败 | 按来源字段恢复关联 | 不直接重建 | `dispatching` | “正在恢复执行记录” |
| 同时发现多个关联 task | 停止自动处理 | 否 | `unknown` | “执行状态不确定，请人工核查” |
| Access Token 过期 | 复用现有刷新与并发合并，成功后重放原受保护请求一次，不重放工具副作用 | 一次，服从现有令牌模块预算 | 认证中原因 + 原 attempt | “正在重新验证身份” |
| Refresh Token 失效/退出登录 | 停止新准入，沿用已有退出清理；已执行实例不转回待启动 | 不自动反复刷新 | 启动前 `waiting_auth`；执行后 `interrupted/unknown` | 登录提示；旧账号记录切换后不可见 |
| 员工/订阅被撤销、明确 403 | 启动前拒绝，运行中停止受保护调用并取消，检查工具副作用 | 否 | `failed` 或 `unknown`，定义 `blocked` | “员工授权已失效”，查看原因，不自动换员工 |
| 模型不在允许列表 | 不启动 Agent | 否 | `failed` + 配置错误 | “模型配置已不可用” |
| Skill 内容/版本被撤销、缺失或校验失败 | 不启动对应员工/节点；禁止静默换版本；已完成前置节点不重跑 | 否 | `failed`/编排 `interrupted`，定义需处理 | “员工技能不可用，请在员工技能管理中处理” |
| Skill 装配请求超时/网络失败 | 已装配节点保持不变，未启动节点按根因处理 | 仅当前装配/前置检查有限重试 | `waiting_network/waiting_retry` | 阶段为“装配技能”，显示下次检查 |
| 启动前断网/DNS/超时 | 保留 occurrence 及 taskId；重新做前置检查，不新建 task | 有限重试且受启动截止时间约束 | `waiting_network` | “等待网络”，显示检查时间和取消本次 |
| 运行中断网/断流/缺失 finish_reason | 先使用 SDK 原会话有限请求重试；耗尽后由运行时终止，检查副作用 | 不由 Scheduler 重跑整任务 | `failed/interrupted/unknown` | “执行中连接中断”，可查看原工作 |
| 模型请求 429 | 原层读取 Retry-After；前置请求可重试，运行中由现有 SDK 预算管理 | 有限，绝不创建另一整任务 | `waiting_retry` 或原运行状态 + 重试原因 | “服务限流”，下一次允许请求时间 |
| 前置请求 5xx | 同一前置检查退避；明确无工具执行才可重新分发 | 建议新增层最多 3 次 | `waiting_retry` | 重试次数/下次时间/取消 |
| 运行中网关 5xx | SDK 原会话预算内处理，耗尽停止，不追加整任务重试层 | 沿用既有预算 | `failed/interrupted`，不确定时 `unknown` | “模型服务暂不可用”，原工作详情 |
| 配额耗尽/订阅过期等明确业务错误 | 与临时 429 区分，停止无效请求 | 否 | `failed` + 定义 `blocked` | “配额或订阅不可用”，等待用户处理 |
| 普通工具失败 | 交给 Agent 当前运行处理 | 不重跑整个 task | `failed` 或由 Agent 继续 | 显示具体工具失败 |
| 审批请求 | 复用现有审批流程 | 不自动批准 | `waiting_approval` | 显示审批状态 |
| 审批拒绝/60 秒超时 | 将拒绝结果交还原 Agent，是否还能完成由既有运行时决定；不新建审批、不默认批准 | 不重试被拒工具 | 原运行状态 + 拒绝事件，最终状态以原任务为准 | “该操作已拒绝/审批超时”，最终结果另显 |
| 工作目录占用 | 等待已有锁释放 | 在等待窗口内重试 | `queued`/`waiting_retry` | “工作目录正在使用” |
| 工作目录不可读写 | 不启动 Agent | 否 | `failed` + workspace | “工作目录不可用” |
| Agent 超时 | 记录取消意图，abort，有限等清理；隔离后可终止子进程及受管工具 | 不重跑 | 已确认停止且无不确定副作用 `timed_out`，否则 `unknown` | “超时已停止”或“超时，停止结果待核查”，不得提前显示已结束 |
| Agent 进程退出/心跳丢失 | 收集退出码和运行凭据；心跳丢失不证明已死，未确认退出不释放冲突资源 | 启动前明确未进入可重试；进入后默认不重跑 | `interrupted/unknown` | “执行进程异常/失联”，可核查不可盲重跑 |
| 外部副作用状态不确定 | 停止自动重试 | 否 | `unknown`/`side_effect_unknown` | 强提示人工核查 |
| 用户主动取消 | 先记 `cancelRequestedAt`，向既有运行时取消，清理确认后再终态 | 否 | 清理中沿用原状态；确认后 `cancelled`，副作用不明则 `unknown` | 先“正在取消”，再显示实际结果 |
| 客户端关闭 | 有序停止；未完成 run 由现有机制标为中断 | 否 | `interrupted` | 下次查看执行详情 |
| 持久化结果失败 | 重试同一结果写入，冻结自动重放；内存只作告警不是持久化成功证据 | 仅同一写入有限重试 | 最后可信状态 + 存储健康异常 | “结果记录失败，请检查磁盘”，不显示业务可重试 |
| 保存成功但 IPC 响应丢失 | 创建/手动运行幂等键查询原结果，编辑按 revision 核对 | 仅同一命令重放 | 保持同一任务/occurrence | 刷新列表，不鼓励重复新建 |
| 通知/前端事件发送失败 | 执行结果已持久化则不回滚，仅补通知 | 是，仅通知 | 不改成功/失败终态 | 重开页面从 Store 恢复，提示记录以本地为准 |
| 队列满/前序未完成 | 显式排队或按重叠策略跳过，有队列上限及截止时间 | 有限等待，不消耗模型重试 | `queued/skipped` | “等待资源”或跳过原因 |
| 扫描器单条异常 | 捕获并隔离该条，继续其他任务；异常记录可见 | 按根因 | 定义 `blocked` 或健康告警 | 列表告警，不使全部任务消失 |
| 未分类异常 | 留脱敏 cause/requestId，停止该 attempt，保留执行证据 | 不默认重试 | `failed/interrupted/unknown` | “执行异常”，诊断 ID、查看详情 |

`persistence`、`dispatch` 是错误类别，不是 occurrence 状态；`blocked` 是定义健康状态；前端不得混成一个状态枚举。网络恢复通知只是重新检查的信号，不能仅凭 Renderer 的 `navigator.onLine` 判定云端可访问。

### 7.2 执行后重试的安全门

所有自动重试先执行以下判断，不能只看 `retryable=true`：

1. 当前登录作用域仍匹配，定义未删除，occurrence 未取消/终止。
2. 前一领取者已被证明停止或释放；租约过期不是这个证明。
3. 尚未进入 Agent/工具执行：可在预算和启动截止前重试同一前置检查/交接，仍使用原 taskId。
4. 已进入执行：只允许现有 SDK 在原会话内的请求重试，或既有运行时明确支持的检查点恢复；Scheduler 不自行调用整任务 `retryTask()`。
5. 出现副作用不确定、存储回退、凭据缺失或双重来源：禁止自动恢复，进入人工核查并阻塞该定义后续运行。

SDK 的请求重试也不保证供应商只计费一次，不能对模型请求承诺 exactly-once。工具执行没有平台幂等键/明确完成凭据时，不以“错误是网络错误”作为安全重放依据。

### 7.3 重试层级与等待预算

必须区分四种重试：

1. **调度重试**：扫描失败或文件暂时不可读。
2. **分发重试**：队列满、目录锁冲突、临时资源不足。
3. **模型请求重试**：网关断流、429、临时 5xx。
4. **整个普通任务重试**：只有在确认没有产生不确定副作用时才能允许。

新增的前置/分发重试建议最多 3 次，总等待预算和启动截止时间落盘；现有 SDK 重试上限不因本模块随意改变。分别记录两层预算，SDK 耗尽后不得再套 3 次整任务重试。锁冲突和认证等待另记等待计数/截止时间，不冒充模型重试次数。

退避规则：

```text
delay = min(maxDelay, baseDelay * 2^(attempt - 1)) + random(0, jitter)
```

`Retry-After` 按秒数或 HTTP 日期解析，并校验合法范围。实际重试不得早于服务端允许时间；若它长于本地预算，则停止/等待人工，不得把等待时间截短后提前请求。没有该头时才按退避加抖动计算。

`dispatchDeadlineAt` 在 occurrence 创建时固定，建议启动宽限初值 1 小时；暂停等待不能反复延长。超出后尚未启动则标记 `skipped` 并说明“超过启动窗口”；进入执行后由 `timeoutMs` 管理，不把运行中的任务当成错过触发。

### 7.4 恢复动作和终态规则

- `scheduled -> dispatching -> queued -> running -> succeeded/failed/cancelled/timed_out/interrupted/unknown` 为主路径；等待态保留原阶段，恢复只回到该阶段。
- 启动前允许 `waiting_auth/network/retry -> dispatching`；执行后不能从等待态绕过既有恢复逻辑重新从头运行。
- `skipped`、确认的完成终态不再被调度器启动。人工重新做一次工作必须有新的明确意图及新 run，不覆盖旧证据。
- `unknown` 只能通过核查/现有安全恢复流程处理，不能靠定时器自动转为 `scheduled`。
- 所有状态更新携带 `occurrenceId/attemptId/stateVersion/runtimeRunId`；旧尝试的晚到事件不能覆盖新尝试或成功终态。
- 终态先持久化再通知界面。收到执行终态但写入失败时，阻止下一次冲突执行，有限重试结果写入并告警。
- 成功以既有执行器终态/交付校验为依据，不以 HTTP 200、已入队、Agent 发出一条文本或无异常退出为依据。

### 7.5 错误码、修复入口与影响范围

尽量复用已有 `AUTH_REQUIRED/INVALID_ARGUMENT` 等代码；新增调度专用代码至少能区分：`SCHEDULE_REVISION_CONFLICT`、`SCHEDULE_INVALID`、`STORAGE_UNAVAILABLE`、`OCCURRENCE_LINK_CONFLICT`、`DISPATCH_EXPIRED`、`EMPLOYEE_UNAVAILABLE`、`SKILL_UNAVAILABLE`、`MODEL_UNAVAILABLE`、`WORKSPACE_BUSY`、`EXECUTOR_LOST`、`SIDE_EFFECT_UNKNOWN`。实际代码名在对应阶段随共享 schema 冻结，不能把本文建议直接当作已存在的枚举。

- 配置冲突：前端保留用户输入、展示当前版本，刷新并重新确认，禁止自动覆盖。
- 修复员工/Skill/模型：跳转既有管理入口，返回后进行“重新校验”；校验通过解除 blocked，只影响未来或尚未启动的运行。
- 身份恢复：登录后只核对该成员截止前的未启动记录；已执行记录仍需安全恢复，不因为重新登录就从头执行。
- 目录忙：显示占用原因和等待截止，锁释放后重新分发；用户可取消本次。
- 结果不确定：打开原工作、事件和交付文件，允许人工确认“无需继续/已完成”或使用现有安全恢复；确认操作留审计记录，不伪造原运行成功。未实现核查流程的阶段只提供查看、保持阻塞，不展示无效按钮。
- 单任务配置/文件错误只阻塞该任务；当前账号认证失效停止该账号新准入；共享存储不可用或唯一写入权丢失暂停整个调度模块。进程致命故障退出并在下次启动恢复，不能捕获后假装继续可靠运行。

界面为每类错误显示：发生阶段、可读原因、是否会自动恢复、下次动作时间、用户可以做什么。没有下一次自动动作时明确写“需要处理”，不能永远显示“稍后重试”。

## 8. 前端展示和用户动作

前端不直接展示内部异常字符串，只消费稳定状态和错误字段。

### 8.1 定时任务列表

在现有工作记录区域增加“定时任务”视图，不改变全局导航。列表按固定定时定义分组，点击进入该定义的时间点历史；每条 occurrence 可跳转现有普通工作详情。普通工作的内部 kind 仍是 conversation/arrangement，通过可选来源字段关联，不把两种执行模式改造成第三个 Agent 模式。

每一行显示：

- 名称。
- 模式：指定员工 / 自动编排。
- 员工名称或参与员工数量。
- 时间规则和时区。
- 启用/暂停/阻塞状态。
- 下一次执行时间。
- 最近一次执行状态。
- 是否存在需要处理的异常。

状态展示建议：

| 状态 | 文案 | 操作 |
| --- | --- | --- |
| ACTIVE | 已启用 | 暂停、立即运行、编辑 |
| PAUSED | 已暂停 | 恢复、编辑 |
| BLOCKED | 配置不可用 | 查看原因、修复配置 |
| 最近一次：WAITING_AUTH | 本次等待重新登录 | 登录、重新检查 |
| 最近一次：RUNNING | 本次正在执行 | 查看详情、取消本次 |
| 最近一次：WAITING_RETRY | 本次等待重试 | 查看原因、取消本次 |
| 最近一次：UNKNOWN | 本次状态待核查 | 查看详情、人工确认 |

定义“启停/健康”与“最近一次执行状态”分列，不能把某次失败显示成整个定义已删除。没有实际 retryScope 或可恢复证据时，不展示重试按钮。

### 8.2 每个时间点的执行详情

详情页按 occurrence 展示：

- 计划执行时间。
- 实际开始时间和结束时间。
- 使用的定时任务配置 revision。
- 实际使用的员工、模型和 Skill 指纹。
- 关联普通 task。
- 当前 attempt 和重试次数。
- 当前阶段：等待认证、等待网络、排队、执行、等待审批等。
- 错误分类、用户可读原因、请求 ID。
- 下一次重试时间。
- 最终结果或关联工作详情。
- 跳过、取消和错过窗口的原因；同一工作使用的排队时长与实际运行时长分开。
- 人工恢复操作的时间、结果及新 run 引用，不覆盖原失败记录。

前端首次进入读取快照，之后通过 `bootstrap/renderer-bridge.ts` 唯一出口接收变化；事件按 stateVersion 忽略旧消息。重连、页面重新进入或版本跳号时重新查询，不将 IPC 推送当唯一事实源。历史按页读取，详情不一次加载所有日志；等待时间仅用于展示倒计时，触发和重试一律由主进程决定。

### 8.3 前端动作边界

用户可执行：

- 暂停/恢复定时任务。
- 编辑定时属性；指定员工模式按允许字段编辑执行配置，自动编排模式不得直接编辑工作内容及节点。
- 手动触发一次。
- 取消当前 occurrence。
- 查看普通工作详情。
- 对 `WAITING_AUTH` 重新登录。
- 对尚未进入执行且可安全重试的 occurrence 点击“重新检查/重试启动”；已经执行的按现有工作恢复入口及检查点安全规则操作。

用户不能执行：

- 在定时任务页面编辑自动编排节点。
- 对 `UNKNOWN` 或 `SIDE_EFFECT_UNKNOWN` 直接点击“重新执行”。
- 绕过审批或提升权限。
- 修改已经运行中的 occurrence 的员工、模型或 WorkPlan。

## 9. 保证不重复和不丢执行

### 9.0 可保证范围与不可跨越边界

| 保证 | 方法 | 不夸大的边界 |
| --- | --- | --- |
| 一个计划时刻只有一个有效触发身份 | 稳定 occurrence ID、单写入方、排他提交、去重凭据 | 文件损坏时暂停，不猜测历史重新执行 |
| 一个 occurrence 不重复创建业务工作 | 预留 taskId + 来源首次提交 + 内部幂等创建 | 不使用可返回 null 的失败读取证明不存在 |
| 已准入运行不被重复准入 | 既有 admitTask + 持久化交接凭据 + 条件状态转换 | 重启会清理 activeRunId，不能仅凭清理后的 null 再次启动 |
| 符合策略的未启动工作最终被处理 | 动态唤醒、低频校准、启动/resume/登录扫描、过期领取核对 | 必须在线、存储健康、当前账号有效且截止前有资源 |
| 启动不等于完成 | 接收入队/实际运行/业务成功分别记凭据 | 不能保证 AI 成功，也不能保证工具副作用全局只发生一次 |
| 无法处理也有交代 | 等待截止、终态或跳过原因、持久化错误告警 | 不允许永久“正在执行”却无监督或提示 |

非致命临时故障不能默默丢弃；满足安全门时自动有限恢复。恢复后仍无法判断的故障转为明确待核查，牺牲自动重跑换取不重复副作用，不同时宣称“任何故障都自动运行成功”。

### 9.1 防止重复生成 occurrence

- 一个任务一个稳定 `scheduledTaskId`。
- 一个计划时间一个稳定 `occurrenceId`。
- occurrence 文件排他创建。
- 同一 Scheduler 扫描 single-flight。
- 客户端启用单实例锁，防止两个主进程同时调度。
- 锁按实际 userData 隔离验证，测试两个安装/两个工作树是否可能指向同一目录；无法证明唯一写入方就不启用调度。仅内存 WriteChain 不是跨进程锁。

### 9.2 防止重复创建普通 task

- occurrence 先落盘，再开始分发。
- 普通 task 写入 `scheduledOrigin`，包含 `scheduledTaskId + occurrenceId`。
- Dispatcher 创建前先查 occurrence.taskId。
- 恢复时再按 `scheduledOrigin.occurrenceId` 查询普通 task。
- 查到多个关联 task 时进入 `unknown`，不选择其中一个继续执行。

### 9.3 防止任务创建后没有执行

创建普通 task 后必须按顺序：

```text
幂等创建普通 task（首次提交同时含 scheduledOrigin）
  -> 补齐 WorkPlan/metadata（完成前禁止准入）
  -> occurrence 写入 taskId
  -> occurrence 进入 queued
  -> 准入意图落盘
  -> 调用现有执行入口并持久化 run 凭据
  -> 确认开始/终态
```

任何一步失败，恢复扫描根据来源字段继续，而不是重新创建 task。

增加与现有执行入口相连的内部幂等准入端口，接收持久化的 occurrence/attempt 身份，将其与 runtimeRunId 关联并保留不可回退的已准入凭据；不创建第二个执行器。手动任务不强制使用定时字段，保持现有行为。此端口必须通过任务串行准入和运行记录测试，不能只在 Scheduler 加内存锁。

如果普通 task 已经成功 `admitTask`，但客户端在调用 `startRun` 前崩溃，现有启动恢复会把 active run 标成 interrupted 并清理 activeRunId。定时任务不能把清理后的 null 当成“从未执行”，需要依赖持久化准入凭据，将 occurrence 标记为 `interrupted`；若能证明未进入执行可安全接管，否则走已有安全恢复或人工核查。

需要启动看门狗：已交接长期没有实际开始事件，重新核对普通任务及准入凭据；未准入则继续同一交接，已准入则检查监督状态，不另起任务。看门狗发现“正在运行但无消息”只表示失联，不等于可以杀掉并重跑。

领取租约带进程启动 ID 和单调 generation；过期领取者的晚到结果一律不接受。网络前置检查超时采用可取消信号，并在返回后复核租约、scope generation 和配置启停状态。未确认旧执行者/受管工具退出前，不释放写目录锁或启动同目录的新任务。

### 9.4 副作用不确定时的原则

以下情况一律不能自动重放整个 task：

- 命令进程已经启动但没有收到结束事件。
- 文件写入已开始但结果未确认。
- 外部 API 请求已发送但客户端断线。
- Agent 进程在工具调用中退出。
- 任务运行记录和工具事件无法确定哪个先落盘。

此时前端显示“执行结果不确定，需要人工核查”，而不是“失败，点击重试”。只有现有检查点或工具幂等记录明确证明可以恢复，才允许继续。

### 9.5 典型断点恢复决策

| 崩溃位置 | 重启核对 | 自动动作 |
| --- | --- | --- |
| occurrence 尚未完整提交 | 检查临时/占位/提交标记和摘要 | 未发生执行且能证明未提交可补齐；半文件无证据则阻塞 |
| occurrence 已提交，游标未推进 | 同 ID 已存在且快照一致 | 不再生成，修复游标并处理原 occurrence |
| 普通 task 已创建，plan/metadata 未写齐 | reservedTaskId、来源、快照摘要一致 | 只补齐缺失配置，不准入半成品 |
| task 已关联，尚无准入 | 健康存储明确无准入凭据且原领取者停止 | 在同一 task 上继续交接 |
| 已准入，但开始确认丢失 | 检查持久化 run、事件与监督进程 | 观察原 run；无法证明未执行则中断/待核查，不二次准入 |
| 工具执行中退出 | 检查工具开始/结束及副作用记录 | 有明确安全检查点才恢复，否则 unknown |
| 普通工作已完成，occurrence 未更新 | 原任务终态与 run 证据一致 | 补记 occurrence 终态，不重新运行 |
| 完成记录回退/被损坏 | 比较备份、提交版本、run 和触发凭据 | 无法确认则停止自动执行，禁止以旧 pending 重跑 |

恢复扫描的职责是恢复“交接和状态”，不是默认重做“业务工作”。这张表从第一阶段开始用故障注入验证。

### 9.6 可观测性与长期监督

统一使用 `electron/common/logger.ts` 和共享脱敏，关联 `scheduledTaskId/occurrenceId/taskId/runtimeRunId/attemptId/scopeGeneration`。记录创建/编辑、重排原因、计划触发、领取/交接、等待/重试、终态、启动恢复和失联判断。没有变化的低频校准不打印 info，避免日志和磁盘开销。

健康信息至少包括最近成功扫描时间、下一次唤醒时间、逾期未处理数量、最长排队时长、待核查数量、存储健康及失败阶段。前端详情可查看“计划时间 -> 唤醒 -> 交接 -> 实际开始 -> 结束”的时间线，从而区分未触发、等待资源与运行失败。

第一阶段就要有活跃任务数、队列和等待上限，默认保守串行且让手动任务优先；后续只扩展策略和调优，不能到长期压测阶段才首次限制资源。过载时有界排队或按配置跳过并记原因，不无上限创建进程或堆积触发文件。

## 10. 纵向闭环开发步骤

每个阶段都必须包含数据、Electron 主进程、IPC、Renderer、测试和可运行验收，不按“先把所有后端写完、最后再接前端”的横向方式开发。

**单实例、去重、基础交接恢复、身份隔离和安全拒绝是第一阶段底线，不是第五阶段才添加的能力。** 后续阶段只增加场景和自动恢复能力。每阶段通过 feature flag/能力字段开放已验证功能；每次交付列明未实现项，不要求一次完成全部计划。

### 阶段一：指定员工 + 一次性任务闭环

目标：完成最小可用链路，不包含 Cron 和自动编排。

完整闭环：

```text
前端创建表单
  -> IPC 创建定时任务
  -> JSON definition 持久化
  -> Scheduler 根据一次性时间动态唤醒
  -> 创建 occurrence
  -> 创建普通 task
  -> 复用 TaskRuntime 执行
  -> 工作记录显示本次详情
```

必须实现：

- 指定员工模式；复用已有执行配置，支持一次性时间和明确时区。
- 创建、编辑原记录、列表、暂停/恢复、删除及手动触发；表单可暂不显示周期选项。
- 新建成功后立即 `scanAndRearm('created')`。
- 单实例/单写入方、加固文件提交、配置 revision 校验、occurrence 去重和不可变快照。
- occurrence 与普通 task 首次提交来源关联，预留 ID 幂等创建，WorkPlan/metadata 未补齐不执行。
- 持久化准入凭据和基础启动恢复，正常退出有界清理；恢复不能自动重跑已进入执行的任务。
- 身份失效、权限撤销、目录不可用、存储损坏、未知副作用都有明确后端状态及前端文案；先安全停止，不要求首期完成所有自动重试。
- 前端工作记录可看到每个时间点、计划/实际时间、执行状态和原工作详情；取消先显示处理中再确认结果。
- 真实执行一次、重复扫描、保存响应丢失、登出切号、崩溃窗口、成功与失败回归测试。

阶段验收：可控时钟设置 10 秒后执行一次，关闭详情页不影响执行；同一计划时间和重复创建请求不产生第二个普通 task；重启已完成记录不重跑，未交接完成记录可补齐，不确定记录明确阻塞。此阶段不声称已经解决主进程 CPU 阻塞，面向小范围验证而非重任务放行。

### 阶段二：执行隔离与取消/超时闭环

目标：保证 CPU 密集型 Agent 工作不会直接堵塞主进程，同时手动、定时工作保持同一执行逻辑。这个阶段修改共享执行承载方式，不能只把 Scheduler 放入子进程。

必须实现：

- 基于现有 TaskWorkerPort 评估 utilityProcess 适配；主进程保留调度、权限、持久化与监督，执行子进程加载锁定版本 SDK。
- 指令、事件、审批、取消、心跳、退出统一消息协议，边界校验，runId/attemptId 关联，消息大小和缓冲上限。
- Refresh Token 留在原认证模块，不经 Renderer 或普通任务文件传递；子进程使用受控认证请求接口，短期凭据仅内存使用且不记录。
- 任务启动、执行、取消/超时、进程退出和受管工具清理均有持久化回执；未知副作用不自动重跑。
- 前端仍显示原工作详情，同时能看到“正在取消/超时/执行失联”的真实状态。
- 采用有上限的进程数量，保留工作目录锁；如果使用进程池，登录作用域和会话不得跨用户残留。

阶段验收：执行子进程注入持续 CPU 计算时，主进程仍响应 IPC 和调度心跳；可取消、可监督退出；模拟异常退出不重跑副作用。手动员工、手动编排及定时任务均回归，四个 SDK POC、typecheck/build、任务测试及并发不变量通过。独立进程不能防止整机 CPU/内存耗尽，需用实际机器验证资源上限，不承诺无限负载下流畅。

### 阶段三：周期、编辑、唤醒和工作记录闭环

目标：增量开放固定周期、每天、每周、每月和 Cron；每个时间模式都从表单到时间点历史完成后再开放。

必须实现：

- 成熟规则解析库及明确的时间语义，保存时展示后续执行预览。
- 编辑同一记录，expectedRevision 冲突前端提示；修改后旧 timer 失效，新时间只生成一次。
- 新建、编辑、暂停、恢复、删除、resume、登录、重试等待变化均触发同一 single-flight 重排。
- 墙钟校准、夏令时、月底、回拨和迟到容差的确定性测试。
- 默认 Skip 重叠 + CatchUpOnce 有限补偿，启动截止和跳过原因可见。
- 时间点历史分页、跳过区间摘要和普通工作结果跳转；运行中的配置快照不随编辑改变。

阶段验收：在不同时间模式分别创建/修改/暂停/恢复并执行到结果；休眠和异常重启不会重复生成同一时刻，恢复只补符合窗口的最近一次，不无限创建历史文件。

### 阶段四：自动编排重复执行闭环

目标：复用已确认编排，不重新规划、不开放计划编辑。

必须实现：

- 创建时从现有确认结果保存 `WorkPlan` 快照。
- 每次 occurrence 创建新的普通 task 和新的 WorkPlan 文件。
- 仍使用现有 `ArrangementExecutor` 和 `TaskRuntime`。
- 节点启动前重新授权员工并装配当前 Skill。
- 原任务配置 Skill 页面不新增；校验每次装配实际使用的内容与指纹，必要时复用不可变版本文件或生成本次运行材料，避免另一任务重新装配覆盖当前节点文件。
- 前端详情显示本次使用的 revision、员工和关联工作。
- 编排失败时保留现有检查点，不自动从头重跑。

阶段验收：同一个自动编排定时任务连续触发两次，生成两个不同 taskId，均不调用规划器；修改员工 Skill 后，下一次执行使用新 Skill，但自动编排步骤不变。

### 阶段五：有限自动恢复与高级策略闭环

目标：在前几阶段已能安全停止和记录原因的基础上，逐类增加自动恢复；每类都同时交付后端策略、UI 状态、用户动作和故障测试，不集中造一个未接通的错误框架。

必须实现：

- 稳定错误类别和错误码。
- 调度、分发、模型请求、整任务重试分层。
- 429、网络、5xx、Token 刷新按阶段有限重试，遵守 SDK 已有预算，禁止整任务重试相乘。
- 权限撤销、模型不可用、Skill 失败进入明确终态。
- 审批沿用 60 秒超时拒绝。
- 未知副作用禁止自动重试。
- 前端显示下一次重试时间、错误原因、请求 ID和可用动作。
- Queue/Parallel 重叠策略、CatchUpAll 补偿、队列和补偿上限分批开放；每次新增策略覆盖其前端与恢复测试。
- 身份恢复只接管当前账号、截止前且未进入执行的 occurrence；用户操作有幂等键。
- 既有检查点明确支持时才开放恢复到原工作，确认副作用不确定不得出现“自动重试”。

阶段验收：模拟每类错误，后端状态、日志和前端文案一致；重试次数有上限；未知状态没有“直接重试”按钮。

### 阶段六：并发、资源保护和长期运行闭环

目标：确保定时任务长期运行不拖垮客户端。

必须实现：

- 定时任务与手动任务共享执行容量。
- 队列长度、单任务并发和全局并发上限。
- 工作目录锁冲突处理。
- 长时间运行的日志和 occurrence 分页。
- 动态 timer、消息通道、监听器及进程资源释放；已结束任务不残留回调。
- 客户端退出时停止调度和有界等待。
- 验证阶段二的执行隔离、IPC 流量、进程数和资源预算，避免通过无上限进程掩盖主进程问题。
- 历史归档/去重凭据保留、磁盘满及索引重建、备份陈旧恢复、通知失败补查全部有前端可见结果。

阶段验收：大量任务同时到期时主界面仍可操作；后台任务不能占满所有执行槽；退出、重启和内存增长测试通过。

### 每阶段的交付记录

每次仅推进一个经过确认的纵向阶段，交付说明包括：用户可完成的流程、主要文件、兼容变化、实跑检查、截图/操作证据、未开放能力和剩余风险。不把“代码已经写出”标成“已经可生产运行”。

公共修改运行相关检查：`typecheck`、`build`、相关 `test:tasks/test:renderer`；IPC/分层修改运行 `check:boundaries`，运行时并发修改运行 `test:invariants`；main、Pi SDK 或动态加载修改按仓库要求运行全部四个 POC。前端阶段启动本地服务，用 Playwright 验证列表、表单、详情及错误状态桌面/窄窗口布局，不能只有后端单测。

## 11. 测试要求

每个纵向阶段完成后立即运行该阶段测试，不等到全部开发结束。

### 调度正确性

- 创建后立即重新扫描。
- 编辑后立即重新扫描。
- 暂停、恢复、删除后重新扫描。
- 重复 timer 回调只生成一个 occurrence。
- 同一计划时间只生成一个普通 task。
- 时区、夏令时、月底和系统时间回拨。
- 启动、登录、resume 后补偿扫描。

### 交接正确性

- occurrence 已创建，definition 尚未推进。
- definition 已推进，occurrence 尚未 dispatch。
- 普通 task 已创建，occurrence 未写 taskId。
- occurrence 已关联，executeTask 尚未调用。
- executeTask 已 admission，客户端异常退出。
- 恢复时找不到、找到一个、找到多个关联 task。
- 备份比主文件旧、文件半写、磁盘满、正常返回前强制退出。
- 完成后 occurrence 状态未保存，重启只能补终态不能重跑。
- 旧 scope/旧 lease/旧 attempt 的晚到事件不覆盖当前状态。

### 异常和重试

- 401 刷新一次后成功/失败。
- 403 权限撤销。
- 429 遵守等待时间。
- 5xx 和网络断开退避。
- Skill 装配失败。
- 员工或模型失效。
- 工作目录冲突和超时。
- 审批 60 秒超时。
- Agent 进程退出。
- 工具副作用不确定。
- 持久化主文件和备份同时损坏。
- Retry-After 长于本地预算时不提前重试；请求预算不会相乘。
- 同一错误在装配前、进入 Agent 后、工具发出后采用不同恢复行为。

### 前端回归

- 定时任务列表与工作记录同步。
- 错误状态不会显示成成功。
- WAITING_AUTH、WAITING_RETRY、UNKNOWN 有不同文案和按钮。
- 自动编排页面没有编辑节点入口。
- 点击重试不会创建第二个 occurrence。
- 关联普通工作详情可以正常打开。

## 12. 主要风险和暂不承诺

- 本地任务在客户端完全退出或电脑关机期间不会执行。
- JSON 文件无法提供数据库级跨文件事务，必须依靠来源标记、恢复扫描和严格写入顺序补足。
- 外部副作用在崩溃窗口中无法保证 exactly-once，只能做到不盲目重放。
- 当前项目还没有 Agent 执行 utilityProcess 隔离，阶段二单独完成共享执行承载改造；未通过前不得声称 CPU 密集任务不会影响主进程。
- 当前审批机制是 60 秒超时自动拒绝，定时任务不改变这一安全规则。
- 定时任务不保存 Skill 替换配置；执行时读取员工当前 Skill 配置，实际版本通过运行诊断记录。
- 自动编排不重新规划；员工、模型或权限失效时，应报告配置/授权错误，不自动更换员工或改写计划。

## 13. 第一阶段的实施约定

以下采用方案默认值即可开展第一阶段，不要求先评审完所有未来功能或再向用户逐条追问：

1. 只开放指定员工 + 一次性时间，持久化 UTC 时刻和 IANA 时区；周期规则在阶段三落实 schema。
2. 默认 CatchUpOnce，补偿窗口建议 24 小时；一条一次性任务最多一个计划触发身份。
3. 默认不允许重叠，启动等待建议最多 1 小时；上限是建议配置，不是已验证 SLA。
4. 退出登录停止新准入；未启动记录在原账号下等待，登录后仅在截止前恢复，否则跳过并记原因。
5. 普通 task 兼容新增可选 scheduledOrigin，首次创建原子保存；旧任务不需要迁移全部历史。
6. 测试先证明文件提交/幂等交接可行，再开放执行；基础不可靠就停止放行，不增加一套假可靠的内存队列。

建议第一阶段只做“指定员工 + 一次性 + 完整执行记录”，先验证从创建、重新扫描、动态 timer 到现有 TaskRuntime 的闭环，再加入周期和自动编排。

## 14. 依据与验证边界

本方案依据第 2 章列出的本地源码及仓库 `AGENTS.md`。Node/Electron 行为可参考官方资料，具体 API 仍需以项目 Electron 内置 Node 版本验证：

- Node.js timers：`https://nodejs.org/api/timers.html`，计时不保证精确及 delay 边界。
- Node.js fs：`https://nodejs.org/api/fs.html`，排他创建、文件同步和文件操作约束。
- Electron powerMonitor：`https://www.electronjs.org/docs/latest/api/power-monitor`，resume 等生命周期信号。
- Electron utilityProcess：`https://www.electronjs.org/docs/latest/api/utility-process`，独立执行进程与消息生命周期。

本文描述目标行为，不表示模块已经实现。文件掉电语义、跨进程隔离、时区解析库、UI 和错误恢复必须在各自纵向阶段实测后才能宣称支持。本文不选用未经版本核对的第三方依赖；阶段三在选型记录中比较解析能力、DST 语义、维护状况及打包体积，固定版本后加入锁文件。
