# 媒体生成长等待与交付优化

## 问题

视频请求已经提交并产生账务记录，但页面长时间停在 50% 或“生成中”；图片/视频完成后还会继续执行多轮模型、`sleep`、状态查询和交付修正。

## 已确认根因

- 模型侧和主进程 `VideoTracker` 同时等待同一个媒体 job，形成双重轮询。
- `onResponseSettled` 把媒体等待、文件校验、manifest 检查和交付 JSON 修正绑定到模型回合。
- `SETTLED` 只表示账务完成，不能证明供应商生成完成或本地文件保存完成。
- 生成、下载、保存和交付没有统一的阶段状态，导致长等待无法解释。

## 目标方案

1. 媒体工具只负责授权、审批和幂等提交，成功后返回 `jobId`。
2. 主进程持久化 `taskId + nodeRunId + operation + idempotencyKey + jobId`。
3. 由唯一 tracker 负责退避查询、重启恢复和最终保存；模型禁止 `sleep` 和 `video_get_job` 轮询。
4. 保留现有生成、保存、账务及任务生命周期状态；聚合展示准备、已提交、供应商生成中、保存中、交付中、可用和阻塞阶段，不再用固定 50% 表示媒体进度。
5. 成功后主进程自动生成结构化 `MediaArtifactSummary` 和 delivery envelope；仅在业务选择确实失败时恢复模型一次。
6. 记录 `providerWaitMs`、`downloadMs`、`materializeMs`、`deliveryMs` 和最后一次查询时间。供应商未提供排队结束、生成开始时间，不能准确拆分 `providerQueueMs` 与 `providerGenerationMs`；`providerWaitMs` 表示客户端观测的排队及生成总等待。

## 实施顺序

1. 先给原视频请求增加状态查询、最后查询时间和阶段计时，不重新提交媒体。
2. 增加媒体运行状态和幂等键，恢复时只跟踪已有 job。
3. 移除模型侧等待，把 tracker 设为唯一等待方。
4. 增加主进程自动物化、原子保存和 delivery envelope。
5. 增加 `waiting-media` checkpoint、重启恢复、取消和超时映射。

## 验收

- 同一媒体 job 的实际提交数始终为 1。
- 供应商成功到本地完成交付为秒级，且可以定位每个阶段耗时。
- 供应商仍在 `QUEUED/RUNNING` 时展示真实等待阶段，不伪造百分比。
- tracker 超时、重启、重复点击和恢复均不创建新 job。
- 下载/保存失败可以重试交付，不重试生成。

## 实现记录（2026-10-23）

### 1. 提交后由主进程接管

- 纯媒体节点的必需操作都已取得并持久化原 job 关联后，在完整且成功的工具回合结束时停止 SDK 的后续模型回合，进入主进程等待及交付。
- 停止的是 SDK 自动继续执行，不把任务标记为用户取消；工具结果保留在会话中。真实取消、工具失败、会话保存失败仍按原错误处理。
- 原 job 由既有图片活动或视频 tracker 跟踪。`media_get_job` / `video_get_job` 提供本地快照；提示词禁止模型通过查询、脚本或 `sleep` 等待。
- 混合文档与媒体的节点继续保留模型工作，避免只生成图片就提前完成尚未写出的文档。

### 2. 文件可用不等待账务

- 交付条件为生成成功（含部分成功）且本地保存完成，不以 `SETTLED` 为前提。
- `waitForRun` 读取本地 job 状态；唯一 tracker 继续供应商查询和账务对账。等待交付不增加供应商请求。
- 图片通过短间隔本地检查识别已保存结果，避免等待仍在处理账务的 tracker 整体结束；视频使用相同的交付与账务分离原则。
- 视频交付读取本地快照，不等待供应商查询占用的 job 活动锁；单 job 查询仍串行，不同 job 不再共用显式恢复锁。批量恢复保留原有 scope 锁和鉴权失败暂停规则。
- 视频 run 完成后关闭旧工具入口，保留有限时、有限次的后台账务 tracker；用户停止任务或退出时仍能取消它。后续 run 只跟踪自己的提交和恢复关联，避免上一轮对账拖住下一轮。
- run 与 IPC 恢复 host 对同一原 job 共享主进程内的跟踪归属；已有跟踪者时其他 host 只观察本地状态，结束或停止时释放归属，不再重复查询供应商。
- 图片生成失败、取消或过期，以及视频生成/保存失败时，交付及时返回失败，不被仍未结束的账务查询拖住。恢复的图片原 job 同样纳入失败判断。
- 视频交付检查遇到 tracker 在读取期间结束或释放跟踪归属时，重新读取本地快照；观察 host 自己结束轮询后，仍等待已有跟踪者完成保存，避免把稍早的生成/保存快照误判为交付失败。
- 已保存文件的预览、导出保持可用；账务待确认单独展示。

### 3. 自动交付与原任务恢复

- 单一明确资产与交付物一一匹配时，主进程生成 delivery envelope，调用现有原子物化及文件校验流程，不再要求模型额外构造交付 JSON。
- 同一类型存在多个候选资产时不自动挑选。纯媒体节点最多进行一次模型选择修正，提供已核验资产清单；仍不明确则报错保留原任务。
- 交付前保存 `waiting-media` 阶段及 `pendingSubmission`，中断恢复继续原 job 或原清单；禁止因恢复、提示词变化、重复提交而重做已关联的媒体操作。
- 恢复关联同时验证 task、node run、subscription 等归属；缺少原关联证据时明确报错，避免通过重新生成掩盖数据问题。
- 下载、文件冲突及交付错误沿用原结果重试路径，不提交新的生成请求。任务取消和既有 tracker 超时、恢复规则继续生效。

### 4. 页面阶段与计时

- 编排详情根据本地 job、资产及 checkpoint 聚合真实阶段，不依赖滞后的 link 输出或账务状态。
- 执行中的编排每 5 秒刷新一次本地 IPC 快照，防止页面一直展示旧进度；刷新不访问供应商，且避免同任务重叠刷新。
- 旧 IPC 未返回期间切换账号范围或任务进入终态时，丢弃旧响应，并在其结束后立即补发最新快照，无需再等一个刷新周期。
- `lastQueriedAt` 在供应商查询发起前持久化，查询失败也能保留最近尝试时间。
- `providerWaitMs` 在首次收到生成终态时冻结，包含查询响应网络耗时；后续账务轮询不增加该数值。
- `downloadMs` 记录实际保存轮次；已有文件不重复下载。`materializeMs` 记录复制、发布媒体交付物的耗时，`deliveryMs` 记录最终文件验收耗时。
- 旧记录没有相应数据时不补造耗时。已交付的本地文件优先于远端结果过期状态，避免文件还在却显示不可用。

## 验证范围与性能口径

- 使用本地假网关及真实 SDK 回归：成功工具结果持久化后只发送一次模型 HTTP 请求，主进程无需模型轮询或交付 JSON 即可完成图片和视频交付。
- 后端链路回归覆盖图片到视频、混合文档节点、中断恢复、原 job 不重提、跨节点资产归属、取消、交付错误和阶段投影。
- 专项回归覆盖生成与保存已完成但账务仍待结算的情况，确保交付提前返回，同时后台继续账务处理。
- 失败回归挂起账务查询，验证图片原运行及恢复运行、视频保存失败均及时报错；账务恢复后仍只处理原请求。
- 视频竞态回归挂起旧快照及保存操作，覆盖 tracker 在读取期间结束、其他 host 仍在保存以及归属释放后重新读取的情形。
- 视频跨轮回归同时挂起旧账务查询、启动 IPC 恢复和下一轮生成，验证下一轮可完成保存、旧 job 查询次数不增加，释放挂起请求后旧账务最终结算；两轮各提交、报价和下载一次。
- 前端回归及页面检查覆盖真实媒体阶段、无假百分比、已保存资产操作及耗时展示。
- “秒级交付”是移除额外模型和账务等待后的目标，不是固定 SLA：下载文件大小、网络、磁盘及校验成本仍影响交付时间。本轮不发起真实付费生成，不能据本地假网关耗时宣称线上性能已实测。

### Review 修正

- 收窄 SDK 交接的主动中止匹配，只忽略已知的中止错误；不能仅凭 `stopReason=aborted` 忽略后续事件或 `prompt` 的真实错误。新增两种会话保存失败回归。
- 补齐失败结果与账务等待分离，以及视频跟踪归属、完成时刻的旧快照重读。保存失败重试仍使用原结果，不新增生成请求。
- 耗时展示测试按运行环境格式化查询时间，移除固定 UTC/北京时间断言，避免其他时区误报失败。

## 本次边界

本次仅处理媒体提交后等待、保存、交付和页面反馈。不扩展普通会话首字延迟优化、历史任务生命周期修复或独立诊断界面；不为完成文档而改造 `task-manager` / `task-runtime`。复用现有恢复、原子保存、交付校验及审批机制，不新增依赖。
