# 视频授权与 Skill 重复下载修复

## 问题与范围

工作记录 `7c5e45ae-6477-4874-b3ff-2092df05d258` 的三次视频调用在 Skill 下载收到 HTTP 429 后失败，没有进入视频报价或提交。视频授权接入了完整员工运行环境准备，单次文生视频路径约六次调用该准备流程；已安装的同版本 Skill 也会先下载再检查安装目录。`AuthApiError` 又被视频适配器折叠为无错误码的通用错误。

本次仅修改客户端，不改 SEP 限流规则，不访问生产接口，不重新报价或生成，不提交或推送 Git。保留工作区已有改动。

## 目标链路

```text
run 启动：获取员工 runtime -> 准备当前授权的 Skill -> 创建 run
视频查询：检查本地归属 -> 读取任务、素材和已有能力快照
视频生成：获取当前视频授权 -> 解析需求并补齐参数 -> 报价
          -> 持久化 NOT_SENT -> 审批 -> 刷新视频授权并确认配置
          -> 持久化 MAYBE_SENT -> 提交一次 -> 查询原始回执
原任务恢复：检查身份与有效订阅 -> 查询原始回执，不准备 Skill
```

## 实施设计

### 1. 拆开授权与运行环境准备

- 在现有 `EmployeeAuthorizer` 内提取共用的 runtime 读取流程，统一身份、订阅、manifest 解析及授权 revision 更新。
- 新增轻量 `authorizeRuntime()`，返回媒体能力，不准备 Skill、不依赖聊天模型的选择；不新增授权 TTL 或长期授权缓存。
- 原 `authorize()` 组合上述流程及 Skill 准备，仍供聊天 run 启动使用，保持现有技能审批与快照语义。
- 视频与图片面板中仅需媒体能力的入口接入轻量授权。原回执恢复继续使用 `authorizeRecovery()`。

### 2. 收敛视频重复检查

- `VideoRunService` 负责 run 生命周期、取消和工具转发，不在每次调用前重复授权、选 profile、补参数。
- host 负责统一生成用例；模型请求与 IPC 请求汇入同一生成流程，保留各自外部输入边界。
- 正常文生视频调用仅在报价前和审批后各刷新一次视频授权；gateway 的 quote/submit 包装不再次读取 runtime。
- `video_get_job` 只读取本地归属、历史和已有能力快照，不刷新 runtime 或下载 Skill。能力刷新仍走显式授权入口。
- 保留跨异步操作的身份/取消 fence、提交前任务策略检查、配置版本一致性、提交防重和磁盘状态转换。它们不应触发 Skill 下载。
- 对外部工具输入、SEP 响应、磁盘记录分别在边界解析；内部同一份已解析对象不逐层重复解析能力。

### 3. 下载前复用 Skill 包

- 仍从当前授权 descriptor 和已批准版本决定是否可用，磁盘缓存不代表授权。
- 按现有用户/订阅/capability/版本/artifact 哈希保存原始包；复用时从原始包重建预期快照和文件清单，再运行现有安装完整性验证，不信任磁盘清单自报的哈希。
- 原始包不存在才下载、验证、原子保存和安装；旧安装首次升级需下载一次原始包，此后复用。本地包损坏应明确失败，不静默覆盖或回退旧版本。
- 用现有 `WriteChain` 串行同作用域的准备，后续调用复用前次安装；每次保留独立授权输入，不跨版本合并结果。失败不缓存，身份变化后不得使用旧请求结果，不长期保存 token。
- 不增加第二套包索引、重试队列或自动重试机制。

### 4. 保留明确错误与脱敏诊断

- 在现有错误映射中识别平台 HTTP 异常，429 映射 `RATE_LIMITED`，401/403、网络与 5xx 使用明确业务码。
- Skill 下载限流提示说明失败资源，不误称视频模型不可用，不自动重试付费请求。
- 视频工具失败记录 runId、toolCallId、tool、固定阶段（可确定时）、异常类型、错误码和 HTTP 状态；通过已有 run 记录关联 task，不记录任意错误正文。
- 不记录提示词、图片、token、API key、请求体或任意服务端响应正文。未知异常也保留固定失败码。

## 兼容性与限制

- 旧安装未保存原始 artifact，首次进入完整聊天 run 准备时仍可能下载一次；视频工具自身的轻量授权不依赖该迁移。
- 缓存需多保留一份原始包，沿用旧版本文件不主动删除的策略；未增加自动清理和下载重试。
- 未打包安装新客户端，也未进行真实收费请求验证。运行中的旧安装需要更新后才能使用本修复。
- 未修改 SEP 后端限流规则，未提交或推送 Git。

## 后续定位：报价 403 被误报为审批拒绝

2026-10-21 19:55:59（北京时间），任务 `c63c901c-fa35-4dcc-93df-1963c7342837`、run `43380d6b-f784-458a-8fc6-ccb271694784` 的视频调用失败。客户端记录 `SepVideoGatewayError / PERMISSION_DENIED / HTTP 403`。生产日志只读核查显示：同一时刻员工 token 接口返回 200，随后 `POST /api/gateway/v1/media/video-real/quotes` 返回 403；未发现对应视频提交，本地也没有进入报价完成后的任务持久化或审批。生产日志未提供该次请求的 request ID 或拒绝正文。

视频传输层未携带 `Origin/Referer`，而现有图片链路已携带这两个头。部署后端的生产 CSRF 规则要求该视频 POST 请求提供来源；使用实际后端 guard 的离线复现中，原请求头被拒绝，补入平台来源头后通过。这次失败发生在报价阶段，尚未进入本地审批或视频生成提交。

修复复用图片链路已有的 `platformSourceHeaders()`，由配置的 `SEP_WEB_ORIGIN` 提供来源，统一用于视频传输。不增加授权检查、缓存、重试或后端例外规则。错误仅附加固定的授权、报价或提交阶段，报价 403 明确提示发生在本地审批之前，日志继续只保留脱敏字段。
