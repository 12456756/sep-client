# 开发计划 v3：多用户任务与硅基员工运行时

## 1. 背景与目标

SEP Client 是本地 Electron 桌面客户端。React renderer 只能通过 preload/contextBridge 与 Electron main 交互；Electron main 是客户端内部后端，负责认证、任务、Pi Agent、文件、运行时资源和 SEP 平台调用。

```text
React renderer
  -> preload / contextBridge IPC
  -> Electron main
      -> TaskStore / TaskScheduler / PiTaskWorker
      -> EmployeeResourceManager
      -> SEP 登录、实例、实例令牌、AI 网关
```

SEP 平台当前向客户端提供的是当前登录用户已授权的实例列表。每个实例在客户端中对应一个硅基员工。客户端不能自行创建 SEP 实例；“创建多个硅基员工”在当前语义中是平台侧创建/分配多个实例后，客户端加载并使用这些已授权实例。

本计划目标：

- 一个登录用户可拥有多个硅基员工实例。
- 一个硅基员工可创建多个独立任务。
- 不同硅基员工的任务允许并发运行。
- 同一个硅基员工同一时间最多运行一个任务。
- 每个任务、Pi 运行、Skill、工具、工作目录和审批均与当前用户隔离。
- 被打断的任务可保留历史并由用户明确选择继续或重试。
- 任务运行不依赖 renderer mock、全局 currentTaskId 或单一 Pi session。

本计划不修改 `docs/对接/SEP客户端API文档.md`。

---

## 2. 总体领域模型

系统中存在以下不同实体：

```text
SiliconEmployee
  -> SEP 返回并授权给用户使用的 instance

Task
  -> 用户交给某个员工的业务任务

TaskRun
  -> Task 的一次实际执行尝试

PiTaskWorker
  -> 承载某个 TaskRun 的 Pi AgentSession、TokenManager、ResourceLoader

EmployeeRuntime
  -> 该用户可使用的员工 Skill、工具和资源版本
```

关系如下：

```text
一个用户
  -> 多个 SiliconEmployee
      -> 多个 Task
          -> 多个 TaskRun
              -> 一个 Pi session 文件
```

示例：

```text
用户 A
├── 市场调研员·小智
│   ├── 任务 1
│   │   ├── run 1：失败
│   │   └── run 2：重试成功
│   └── 任务 2：排队
└── 代码分析员·小码
    └── 任务 3：运行中
```

任务创建时必须固定保存员工和模型快照。员工以后升级、模型列表变化或实例被撤销时，历史任务仍然能说明原始执行上下文；但新执行或重试必须重新校验当前授权。

## 3. 核心设计原则

### 3.1 Electron main 是权威执行端

renderer 只负责提交命令、展示 DTO 和订阅事件。以下能力只存在于 Electron main：

- SEP API 调用；
- refresh token 与 instance token 使用；
- 任务状态变更；
- Pi session 创建和销毁；
- Skill/工具资源校验和加载；
- 文件访问和工作目录限制；
- 工具审批；
- 本地持久化和用户隔离。

renderer 不能下载员工包、安装 Skill、创建 Pi session、读取任务文件、保存 token，也不能用定时器伪造任务执行结果。

### 3.2 任务和 Pi session 是两层历史

Pi SDK 的持久化 session 用于保存 Agent 上下文：

```text
用户消息
assistant 消息
工具调用与结果
模型变更
上下文压缩摘要
分支摘要
扩展自定义 entry
```

客户端 TaskStore 用于保存业务语义：

```text
所属用户
员工和模型绑定
任务状态和队列
TaskRun
审批记录
工件索引
工作区绑定
资源版本
UI 标题和统计
```

因此：

```text
Task
  -> TaskRun
      -> Pi Session JSONL
```

Pi session 不能替代 TaskStore，TaskStore 也不能替代 Pi 的对话上下文。

### 3.3 显式上下文，不使用全局当前任务

每个执行动作、Pi 事件、工具调用和审批都必须关联：

```text
owner
employeeInstanceId
taskId
runId
sequence
```

不再使用全局 `currentTaskId` 来推断事件属于哪个任务。

### 3.4 默认拒绝和最小权限

- 未授权员工、模型、Skill、工具、工作目录和 taskId 默认拒绝。
- 未知工具默认拒绝。
- Skill/资源只能从 main 已验证目录加载。
- token、密码和未脱敏原始异常不能写入任务数据、日志或 IPC。

## 4. 阶段一：统一领域模型和接口边界

### 要解决的问题

当前项目中存在多套任务模型：Electron task manager、legacy task board、workspace mock 以及 PiHost 内部状态。它们的字段、状态和职责不一致，后续开发会形成重复数据源。

### 采用的编程思想

- **领域建模**：明确 SiliconEmployee、Task、TaskRun、TaskMessage、TaskEvent、ApprovalRecord、Artifact、EmployeeRuntime 的职责。
- **单一事实来源**：任务状态和运行状态只由 Electron main 管理。
- **命令查询分离**：创建、取消、重试等为命令；列表、详情、事件流为查询。
- **显式上下文**：每项运行数据都使用 taskId/runId 关联。

### 主要工作

1. 统一 `src/shared/types.ts`、`src/shared/task-types.ts`、workspace 模型和 main 模型。
2. 定义统一状态：

```text
queued
preparing
running
waiting_approval
completed
failed
cancelled
stopped
interrupted
```

3. 定义 renderer-safe DTO 与 main 内部持久化模型的转换边界。
4. 明确 SEP instance 是授权员工资源，EmployeeRuntime 是客户端本地准备结果。
5. 明确同一任务不可更换员工绑定；模型切换需要单独命令与权限校验。

### 完成标准

- 后续模块不再新增另一套同义任务类型。
- 每个任务都能表达所属用户、员工、模型、Skill、工作区、run 和状态。
- 任务、员工实例、Pi worker 的关系被代码类型表达清楚。

## 5. 阶段二：用户隔离和任务持久化

### 要解决的问题

任务、消息、Pi 运行数据和员工资源需要跨重启保存，同时不同 SEP 用户和企业之间绝不能互相访问。

### 采用的编程思想

- **多租户隔离**：`enterpriseId + memberId` 是所有数据读写的作用域。
- **Repository/Store 模式**：文件读写集中在 main 内部 TaskStore，不在 IPC handler 或 renderer 分散处理。
- **版本化 schema**：每类持久化数据带版本，支持可重复迁移。
- **原子写入和容错恢复**：临时文件写入后 rename；单条损坏数据不影响登录。
- **追加式事件记录**：消息和事件使用 JSONL 或等价追加存储，避免频繁重写巨大任务文件。

### 主要工作

1. 将用户目录从全局 `tasks.json` 演进为用户作用域目录：

```text
<userData>/
  auth/

  task-data/
    <enterpriseId>/
      <memberId>/
        index.json
        tasks/
          <taskId>/
            task.json
            messages.jsonl
            events.jsonl
            approvals.jsonl
            artifacts.json
            runs/
              <runId>.json
```

2. 保存 `Task`：

```text
taskId
owner
employee snapshot
modelId
skillIds
workspace
status
createdAt
updatedAt
activeRunId
error
```

3. 保存 `TaskRun`：

```text
runId
taskId
instanceId
modelId
runtimeKey
sessionFile
startedAt
endedAt
outcome
usage
error
```

4. 保存消息、事件、工具调用摘要、审批决策和工件元数据。
5. 不保存 token、密码、未脱敏敏感工具输入或原始异常对象。
6. 旧任务迁移：缺少员工/模型的旧任务只保留历史展示，不允许自动运行。

### 完成标准

- 用户 A 无法读取或修改用户 B 的任务、消息、资源和审批。
- enterpriseId 不同即使 memberId 相同也无法互相访问。
- 退出登录保留磁盘历史，清除内存任务视图和活跃运行时。
- 损坏的任务文件不会阻塞登录或其他任务恢复。
- 所有持久化任务均可明确定位所属用户和企业。

## 6. 阶段三：员工级并发调度

### 要解决的问题

产品目标不是全局串行：不同硅基员工的任务可以并发；但同一员工暂不允许并发。还要考虑全局 CPU、内存、进程和工作目录冲突。

### 采用的编程思想

- **Actor/Worker 隔离**：每个 active TaskRun 有独立 worker。
- **资源锁**：员工运行槽位、工作目录锁和全局资源预算共同决定任务能否启动。
- **状态机**：任务状态只能按合法转移变化。
- **队列调度**：同一员工任务默认 FIFO；不同员工可被独立调度。
- **幂等命令**：重复 start/retry 不创建重复 run。

### 主要工作

1. 新增 `TaskScheduler`，维护：

```text
TaskRegistry
RunRegistry
EmployeeSlotRegistry
WorkspaceLockRegistry
GlobalResourceBudget
```

2. 每个员工实例维护一个运行槽位：

```text
employeeInstanceId -> activeRunId | null
```

3. 调度条件：

```text
任务为 queued
AND 当前员工无 active run
AND 工作目录无冲突
AND 当前用户仍有权限
AND 全局资源预算允许
```

4. 同一员工多个任务排队：

```text
员工 A / 任务 1 -> running
员工 A / 任务 2 -> queued
员工 A / 任务 3 -> queued
```

5. 不同员工并发：

```text
员工 A / 任务 1 -> running
员工 B / 任务 2 -> running
员工 C / 任务 3 -> preparing
```

6. 默认工作区策略：读写任务对相同目录、父目录、子目录互斥；后续再考虑只读共享策略。

### 状态机

```text
queued -> preparing -> running
preparing -> failed | cancelled | interrupted
running -> waiting_approval -> running
running -> completed | failed | cancelled | stopped | interrupted
queued -> cancelled
```

### 完成标准

- 同一员工同一时间只有一个 active run。
- 不同员工可以并发运行。
- 一个任务只能有一个 active run。
- 取消、失败或完成后，当前员工队列可以继续调度。
- 退出、崩溃或认证失效时 active run 标记为 interrupted，不能被标记为 completed。

## 7. 阶段四：PiTaskWorker 和 Pi session 持久化

### 要解决的问题

现有 PiHost 只有一个全局 `AgentSession` 和 `currentTaskId`，无法正确支持不同员工并发运行，也无法通过 Pi session 恢复对话上下文。

### 采用的编程思想

- **组合优于全局对象**：用 coordinator + worker 替代全局单 session PiHost。
- **依赖注入**：worker 显式获得 task/run/employee/model/workspace/resource/token 配置。
- **事件驱动与事件溯源**：Pi event 先规范化和持久化，再通过 IPC 推送。
- **显式生命周期管理**：worker 必须可以 start、abort、dispose。

### Pi SDK 的关键事实

项目锁定使用 `@earendil-works/pi-coding-agent@0.83.0`。使用方式必须遵循 SDK 的实际 API：

```ts
const { session } = await createAgentSession({
  modelRuntime,
  model,
  resourceLoader,
  sessionManager,
})
```

`createAgentSession()` 返回结果对象，不能直接把返回值当成 session。

`DefaultResourceLoader` 必须提供 `cwd`、`agentDir`，并且必须执行：

```ts
await resourceLoader.reload()
```

session 事件使用：

```ts
session.subscribe(listener)
```

而不是 `session.on()`。

### Pi session 的持久化策略

当前 `SessionManager.inMemory()` 不适用于可恢复任务。每个 TaskRun 应使用自己的持久化 session：

```ts
const sessionManager = SessionManager.create(
  task.workspace.path,
  runSessionDir,
  { id: runId },
)
```

Pi session 会以追加式 JSONL 保存消息、工具结果、模型变化、上下文压缩和自定义 entry。

建议目录：

```text
<task-data>/<enterpriseId>/<memberId>/tasks/<taskId>/
  runs/<runId>.json
  sessions/<runId>/...
```

每个 worker 具有：

```ts
interface PiTaskWorker {
  taskId: string
  runId: string
  employeeInstanceId: string
  session: AgentSession
  sessionManager: SessionManager
  resourceLoader: DefaultResourceLoader
  tokenManager: InstanceTokenManager
  dispose(): Promise<void>
}
```

### Pi 事件处理

每个 Pi 事件规范化为：

```ts
interface TaskEvent {
  taskId: string
  runId: string
  employeeInstanceId: string
  sequence: number
  type: string
  occurredAt: number
  payload: unknown
}
```

处理顺序：

```text
Pi session event
  -> 绑定 worker 的 taskId/runId
  -> 脱敏、截断、规范化
  -> TaskStore append event/message/tool summary
  -> renderer IPC event
```

不能通过全局 `getCurrentTask()` 判断事件归属。

### 中断、继续和重试

#### 用户停止当前生成

使用：

```ts
await session.abort()
```

已有持久化 session 历史保留。对话型任务可以继续使用同一 session；工作流任务通常需要建立新的 run。

#### 应用退出、崩溃或认证失效

当前 run 标记为：

```text
interrupted
```

下次登录后只恢复历史显示，不自动运行。

#### 用户选择继续

继续前必须重新校验：

```text
实例仍属于当前用户
实例仍为 ACTIVE
模型仍被允许
Skill/工具仍可用
工作目录仍存在且符合策略
旧运行时版本仍可加载
```

通过后可打开旧 session：

```ts
const sessionManager = SessionManager.open(
  run.sessionFile,
  run.sessionDir,
  task.workspace.path,
)
```

然后重新创建 AgentSession。

#### 用户选择重试

重试创建新的 TaskRun 和新的 Pi session，不覆盖旧 run。

### 完成标准

- 每个 run 有独立 session 文件、token manager、resource loader 和 event subscription。
- 不同 worker 的事件不会串线。
- session 结束后迟到事件不能写入任务。
- `abort()`、`dispose()`、token refresh、审批 waiter 和工作区锁均能被正确释放。
- 历史对话和工具上下文可通过 Pi session 文件恢复。

## 8. 阶段五：实例授权、模型校验和任务 IPC

### 要解决的问题

一个用户可拥有多个员工实例，每个实例的 `allowedModels` 不同。renderer 选择员工、模型和 Skill 只是 UI 请求，不能作为权限依据。

### 采用的编程思想

- **主进程权威校验**：main 每次执行前检查授权，不信任 renderer。
- **不可变绑定**：任务创建后员工绑定不可直接更换。
- **命令查询分离**：明确区分修改状态的命令和读取状态的查询。
- **故障安全**：不合法输入、实例撤销、模型变化默认拒绝而不是继续执行。

### 建议 IPC

资源查询：

```text
resources:list
task:list
task:get
task:get-timeline
task:list-artifacts
```

任务命令：

```text
task:create-conversation
task:create-workflow
task:send-message
task:stop
task:cancel
task:retry
task:switch-model
task:resolve-approval
```

创建任务请求至少包含：

```ts
interface CreateTaskRequest {
  title: string
  prompt: string
  taskType: 'conversation' | 'workflow'
  employeeInstanceId: string
  modelId: string
  skillIds?: string[]
  workDir?: string
}
```

main 必须校验：

```text
用户已登录
实例属于当前用户
实例状态为可用
modelId 在实例 allowedModels 中
Skill 已授权且已安装
工作目录存在并符合权限策略
任务状态允许当前命令
```

### 完成标准

- 未授权实例、错误模型、跨用户 taskId 和非法工作目录均被拒绝。
- 同一实例可创建多个任务。
- 同一任务不能更换员工。
- 用户必须先选员工，renderer 才显示对应模型列表；main 仍重新校验。

## 9. 阶段六：声明式 Skill 和客户端工具注册

### 要解决的问题

SEP 实例的 `allowedTools` 只是授权声明，不代表客户端可以下载或执行任意同名代码。`packageRef` 也不是已经定义完善的可信安装协议。

### 采用的编程思想

- **能力白名单**：最终可用工具是多层策略的交集。
- **默认拒绝**：未知工具、未授权 Skill、非法资源路径都拒绝。
- **声明式资源优先**：先支持 `SKILL.md`、提示词和配置，暂不执行第三方扩展代码。
- **内容寻址缓存**：资源按用户、实例、版本和 digest 隔离保存。

### 工具策略

客户端工具由 main 内置注册表提供：

```text
web_search
calculator
...其他经审计的客户端工具
```

实例只能授予使用权：

```text
客户端注册工具
∩ instance.allowedTools
∩ task tool policy
∩ 用户审批结果
= 当前 worker 可用工具
```

Pi 内置工具可使用 `allowedToolNames`、`excludedToolNames` 和 `initialActiveToolNames` 进行限制。`bash`、`write`、`edit` 保持现有审批原则；未知工具默认拒绝。

### Skill 加载

每个 worker 使用经过验证的 Skill 路径：

```ts
const resourceLoader = new DefaultResourceLoader({
  cwd: task.workspace.path,
  agentDir: taskAgentDir,
  extensionFactories,
  additionalSkillPaths: verifiedSkillPaths,
  noContextFiles: true,
})
await resourceLoader.reload()
```

规则：

- `cwd` 是任务允许的工作目录，不是 `process.cwd()`。
- `agentDir` 是 task/run 专用目录，不是共享项目 `.pi`。
- `additionalSkillPaths` 只能来自 main 验证后的缓存。
- `noContextFiles: true` 继续保留，避免自动加载工作目录中的未知文件。
- Skill 不能由 renderer 提供任意路径。

### 用户隔离缓存

资源缓存键至少包含：

```text
enterpriseId
+ memberId
+ instanceId
+ lockedVersion
+ packageDigest
```

目录示例：

```text
<userData>/employee-resources/
  <enterpriseId>/<memberId>/<instanceId>/<version>/<digest>/
    manifest.json
    skills/
    tools/
```

退出登录只销毁内存 runtime，不删除用户资源历史。删除账号或清理资源应是单独的显式操作。

### 完成标准

- 用户 A 不能加载用户 B 的 Skill 或员工资源。
- 重复安装返回幂等结果。
- 安装失败不污染当前有效版本。
- Skill/工具不能绕过 workspace、审批或 token 边界。
- 不存在于注册表的工具不会被静默启用。

## 10. 阶段七：远程员工包安装协议

### 要解决的问题

npm、Git 或 ZIP 员工包可能包含任意 Node.js 代码。直接加载到 Electron main，相当于授予第三方代码文件、网络、进程和运行时访问能力。

当前 SEP API 尚未确认完整的包下载、签名、manifest、撤销和版本兼容协议，因此本阶段不能提前假设已经具备。

### 采用的编程思想

- **零信任下载**：不信任 renderer URL、包自身声明、mutable tag 或 branch。
- **供应链验证**：版本、来源、hash、签名和 manifest 都必须可验证。
- **隔离安装**：下载到 quarantine，验证后原子激活。
- **默认拒绝**：协议或校验缺失时拒绝安装。
- **可执行扩展隔离**：把可执行扩展视为高权限代码，不当作普通 Skill。

### 正式支持远程包前的必需协议

```text
固定版本
可信来源
SHA-256/integrity
数字签名
manifest
Pi 版本兼容信息
Skill/工具声明
大小限制
超时限制
更新和撤销语义
```

### 安装流程

```text
下载到 quarantine
  -> 校验来源、版本、digest、签名
  -> 校验 manifest
  -> 拒绝 zip-slip、绝对路径、symlink 越界
  -> 校验 Skill 布局
  -> 原子移动到 active cache
  -> 写入用户安装记录
```

npm lifecycle scripts 默认不执行。

如果未来必须支持可执行员工扩展，应运行在独立 sandbox worker process 中，通过受限 RPC 与 Electron main 通信；不得直接获得 refresh token、任意 shell、任意文件系统或不限网络权限。

### 完成标准

- 缺少正式协议时，`packageRef` 只展示或明确拒绝安装。
- 校验失败不污染活动缓存。
- 资源只从已验证的内容地址加载。
- 可执行扩展不会直接拥有 Electron main 全部权限。

## 11. 阶段八：Renderer 和产品流程迁移

### 要解决的问题

当前 workspace 仍使用静态员工、静态模型、本地 timer 和模拟状态，与 main 权威状态冲突；同时 legacy task board 也保留旧 IPC 路径。

### 采用的编程思想

- **单向数据流**：renderer command -> main -> store -> event -> renderer。
- **事件驱动 UI**：renderer 订阅真实 task event，而不是自行模拟运行。
- **权威回放**：挂载时先 list/get，再订阅事件。
- **兼容适配后删除**：旧接口暂时适配到新实现，最终删除重复路径。

### 产品流程

```text
登录成功
  -> 进入工作台
  -> 显示硅基员工列表

创建任务
  -> 选择硅基员工
  -> 根据该员工 allowedModels 选择模型
  -> 选择已授权/已安装 Skill
  -> 输入任务内容
  -> 选择工作目录
  -> 提交任务
```

员工卡片仅展示：

```text
市场调研员·小智
状态：可用
版本：1.2.0
```

### 完成标准

- renderer 不创建 Pi session、不读任务文件、不安装资源、不接触 token。
- renderer 不使用 timer 模拟执行状态。
- 不同员工并发任务可以分别正确展示。
- 断线或重新挂载后可以通过 list/get/timeline 同步真实状态。
- legacy mock 状态和重复任务模型被移除。

## 12. 阶段九：迁移、测试和上线门槛

### 要解决的问题

多用户隔离、并发 worker、文件系统边界、工具审批、资源安装和中断恢复均属于高风险边界，不能只依赖手动测试。

### 采用的编程思想

- **契约测试**：验证 IPC DTO、错误码和权限边界。
- **故障注入**：模拟损坏文件、网络失败、Pi 初始化失败、token 失效、审批超时等。
- **渐进式迁移**：旧 tasks.json 可重复迁移，旧任务保留但不自动运行。
- **可观测性**：日志记录 taskId/runId/instanceId/sequence，不记录敏感凭据。

### 测试矩阵

#### 数据隔离

- 用户 A 无法读取、更新、取消、删除用户 B 的任务。
- enterpriseId 不同即使 memberId 相同也不能互相访问。
- 用户资源目录隔离。
- logout 不删除历史。

#### 调度

- 同一员工任务 FIFO。
- 不同员工任务可并发。
- 同任务重复 start 不创建重复 run。
- 工作区冲突被阻止。
- 取消、失败后可继续调度。
- auth invalidation 和退出将 active run 标记为 interrupted。
- retry 创建新 run。

#### Pi Worker

- 每个事件带 taskId/runId。
- worker 事件不会串线。
- session、token manager、approval waiter 均能释放。
- 迟到事件被忽略。
- 正确使用对应 instance token。
- Pi session 历史可以恢复。

#### Skill 和工具

- 未授权 Skill 被拒绝。
- 重复安装幂等。
- hash/signature 不符被拒绝。
- ZIP 路径穿越和 symlink 越界被拒绝。
- 未知工具默认拒绝。
- Skill/工具不能绕过审批与工作区边界。

#### 回归验证

```text
npm run typecheck
npm run build
npm run poc:01
npm run poc:02
npm run poc:03
npm run poc:04
```

`npm run lint` 需要先补充 ESLint 9 flat config 后才能作为上线通过条件。

## 13. 推荐实施顺序

```text
阶段一：统一领域模型和接口边界
  -> 阶段二：用户隔离和任务持久化
  -> 阶段三：员工级并发调度
  -> 阶段四：PiTaskWorker 和 session 持久化
  -> 阶段五：实例、模型和任务 IPC
  -> 阶段六：声明式 Skill 和客户端工具
  -> 阶段七：远程员工包安装协议
  -> 阶段八：Renderer 迁移
  -> 阶段九：迁移、测试和上线
```

关键顺序约束：

```text
先建立用户隔离、任务隔离和 worker 隔离
再加载 Skill 和工具
最后才支持远程员工包
```

不能在运行时边界、资源验证和权限策略未建立前，直接下载或执行员工包。
