# 意图识别与员工编排闭环开发文档

## 1. 文档目的

本文定义 SEP 客户端“用户目标 -> 意图识别 -> 员工能力匹配 -> 授权申请 -> 订阅刷新 -> 执行 DAG -> 任务运行”的完整闭环。

本文以接口文档《SEP客户端完整接口对接文档-v1》第 7 节为接口依据，并结合当前 `sep-client` 的实现边界，作为后续开发、联调、测试和验收标准。

## 2. 目标与非目标

### 2.1 目标

- 从自然语言目标中识别用户意图，拆解为有依赖关系的步骤。
- 为每个步骤提取稳定、可匹配的能力摘要。
- 按固定优先级匹配员工：当前用户已授权且有效的订阅、企业内未授权员工、平台可申请员工。
- 已订阅员工可以直接生成执行节点；未授权员工只能作为候选推荐，不能进入执行 DAG。
- 申请员工后可查询申请状态；申请批准后刷新订阅并复用原意图继续规划。
- 只有有效订阅、允许模型和通过权限预检的节点才能启动任务。
- 任一步骤无法覆盖时，保留意图快照和未解决步骤，用户可以继续申请或重新检查。

### 2.2 非目标

- 意图识别阶段不执行用户任务，不调用联网、文件或其他业务工具。
- 不把企业目录或平台目录中的员工对象当作可执行订阅。
- 不把 Skill Markdown 全文发送给意图识别模型。
- 不由客户端伪造企业 ID、成员 ID、申请人 ID 或 Employment Token。

## 3. 现状审计

### 3.1 已有能力

- `electron/domain/arrangement-planner.ts` 已定义意图快照、未解决步骤和候选员工匹配结果。
- `electron/service/arrangement-service.ts` 已按授权员工、企业候选、平台候选顺序规划。
- `candidateMatches` 已支持企业员工和平台员工申请。
- `POST /client/employee-access-requests` 与申请状态查询已接入。
- 申请批准后会刷新员工目录，前端提供“重新检查”。
- 执行前已有订阅、模型和权限预检。

### 3.2 当前阻塞点

1. 已授权订阅映射到规划器时没有加载 `/enterprise/employees/:employeeId/skills`，因此 `capabilities` 为空。
2. 企业候选来自 `/enterprise/overview`，当前映射没有携带能力摘要。
3. 平台目录接口的 `keyword` 当前只搜索名称、职位、简介和行业，不搜索能力名称；不能把能力名称直接当作唯一查询条件。
4. 规划器虽然收到 `intentAnalysis`，但候选匹配仍主要依赖模型自行判断，缺少客户端能力交集校验和确定性排序。
5. 推荐结果为空时，界面只能显示“暂无找到可申请的员工”，缺少“已查询哪些目录、匹配依据、下一步动作”的诊断信息。

## 4. 端到端流程

```text
用户输入目标
  -> 创建 auto draft
  -> 读取当前有效订阅
  -> 加载已订阅员工能力摘要
  -> 意图识别与步骤拆解
  -> 已订阅员工能力匹配
  -> 生成可执行节点
  -> 对未解决步骤查询企业目录
  -> 对未解决步骤查询平台目录
  -> 展示候选员工和申请入口
  -> 创建/查询授权申请
  -> 申请批准后刷新 /client/subscriptions
  -> 复用 intentAnalysis 重新匹配
  -> 仅用有效订阅生成 DAG
  -> preflight
  -> 用户确认
  -> 创建任务并执行
```

规则：任何阶段失败都必须保留 draft、`intentAnalysis`、`unresolvedSteps` 和申请记录；不得把失败结果清空成一个新的目标。

## 5. 数据模型

### 5.1 意图快照

```ts
interface ArrangementIntentAnalysis {
  summary: string
  steps: Array<{
    id: string
    title: string
    requiredCapabilities: string[]
    dependsOn: string[]
  }>
}
```

`requiredCapabilities` 需要优先使用平台能力 ID；当模型只能识别自然语言能力时，同时保留标准化名称，供目录搜索和展示使用。能力名称不能被当作能力 ID 发送给申请接口，除非服务端明确允许。

### 5.2 员工能力摘要

```ts
interface ArrangementPlannerCapability {
  id: string
  name: string
  description: string
  type?: string
}
```

Skill 正文只在实际执行时通过现有 Skill 加载流程获取，规划器只接收摘要。

### 5.3 候选匹配

```ts
interface ArrangementCandidateMatch {
  stepId: string
  employeeId: string
  subscriptionId: string | null
  source: 'enterprise' | 'platform'
  name: string
  rationale: string
  canExecute: false
  canApply: true
}
```

已授权员工不进入 `candidateMatches`，而是直接生成节点。候选员工没有有效订阅时，`canExecute` 必须为 `false`。

## 6. 接口调用与字段映射

### 6.1 已授权订阅

调用：`GET /client/subscriptions`

用途：获取当前用户可执行的有效订阅、`subscriptionId`、`employeeId`、允许模型。

随后按 `employeeId` 调用：`GET /enterprise/employees/:employeeId/skills`

映射规则：

- `skills[].capability` -> `ArrangementPlannerCapability`。
- 只保留 `id/name/description/type`。
- 接口失败时不能静默伪造空能力；应记录该员工能力加载失败，并将相关步骤标记为待确认或未解决。
- 规划节点只能使用订阅原有的 `allowedModels`。

### 6.2 企业候选员工

调用：企业员工目录接口，当前客户端使用 `GET /enterprise/overview` 返回的员工目录。

必须补齐能力摘要字段，至少包含 `employeeId`、`subscriptionId`、`name`、`description`、`position`、`capabilities`、`status`、`canApply`。

企业目录员工只能产生企业授权申请，不能直接生成执行节点。

### 6.3 平台候选员工

调用：`GET /client/platform-employees`

查询策略：

1. 前两轮后仍有未解决步骤时进入第三轮，不再由能力名称交集提前跳过平台匹配。
2. 不传任务关键词或能力 ID；按每页 100 条连续加载，直到 `hasNextPage=false`，跨页按员工 ID 去重，不限制总候选数。
3. 只保留 `employeeStatus=APPROVED`、`availability=AVAILABLE`、`canApply=true` 的员工，不按任务内容预筛选。
4. 将完整可申请员工目录（包括名称、职位、描述、能力摘要）放入第三轮提示词，由模型判断匹配关系。平台员工只能作为申请候选，不能直接执行。
5. 企业及平台待授权员工阶段使用独立的推荐提示词和 JSON 示例：仅通过 `candidateMatches` 返回员工；`nodes` 必须为空；即使已选中候选，也须保留 `unresolvedSteps` 并注明等待授权。已有意图快照保持不变，已有执行节点由服务层保留，不由模型重复输出。执行节点的非空模型及员工授权校验保持严格，不补造字段或丢弃错误节点。
5. 任意一页请求失败时整体报错，不将部分目录当作全量目录，也不伪造空候选结果。

### 6.4 申请接口

创建：`POST /client/employee-access-requests`

- 企业候选：`targetType=ENTERPRISE_SUBSCRIPTION`，发送 `subscriptionId`。
- 平台候选：`targetType=PLATFORM_EMPLOYEE`，发送 `employeeId`。
- 不发送企业 ID、成员 ID 或申请人 ID。
- `requestedCapabilities` 使用能力 ID；未知能力 ID 不应伪造。
- 使用由 `draftId + stepId + employeeId` 派生的稳定幂等键。

查询：`GET /client/employee-access-requests/:requestId`

- `PENDING`：保留当前草稿，允许查询状态。
- `APPROVED`：刷新订阅目录，然后重新规划。
- `REJECTED/CANCELLED`：保留记录，允许选择其他候选或重新编排。

## 7. 匹配算法

### 7.1 能力匹配

对每个步骤计算：

```text
required = step.requiredCapabilities
provided = employee.capabilities
coverage = required 与 provided 的 ID/名称标准化交集比例
```

匹配规则：

- `coverage = 1`：可覆盖，进入可执行或候选排序。
- `0 < coverage < 1`：只能作为部分覆盖候选，必须说明缺失能力。
- `coverage = 0`：不推荐。
- 能力描述只用于解释和辅助模型，不可绕过 ID、状态和权限校验。

### 7.2 优先级

排序键按以下顺序比较：

1. 来源：`authorized` > `enterprise` > `platform`。
2. 能力覆盖率：完整覆盖优先。
3. 能力摘要匹配分：ID 精确匹配 > 名称匹配 > 描述语义匹配。
4. 员工状态：有效、可执行或可申请优先。
5. 稳定更新时间和名称，保证结果可复现。

同一个步骤可生成多个候选，但只能选择一个员工进入执行节点。候选列表必须保留排序依据，便于 UI 展示和问题定位。

### 7.3 已订阅员工优先的硬约束

- 只要存在覆盖率为 1 的已订阅员工，不得推荐企业或平台员工。
- 已订阅员工覆盖部分能力时，优先补充其他已订阅员工；只有仍有未覆盖步骤时才查企业和平台目录。
- 企业和平台候选不能因为模型偏好而替代可执行订阅。
- 模型返回的 `subscriptionId`、`employeeId`、`modelId` 必须经过目录白名单校验。

## 8. 编排器职责边界

### 8.1 模型负责

- 从用户目标抽取意图。
- 拆解步骤和依赖关系。
- 为步骤给出能力需求和匹配理由。
- 在传入目录范围内提出候选计划。

### 8.2 客户端负责

- 加载真实能力摘要。
- 确定性匹配和优先级排序。
- 校验员工来源、订阅状态、模型白名单和 DAG 合法性。
- 阻止未授权员工进入执行节点。
- 管理申请、状态刷新、重规划和失败恢复。

模型不能创建目录中不存在的员工、订阅或模型，也不能自行决定绕过申请流程。

## 9. 状态机

```text
editing
  -> planning
  -> ready
  -> confirmed
  -> running

planning
  -> awaiting-employee   (存在未解决步骤)
  -> planning-failed     (模型/接口/解析失败)

awaiting-employee
  -> awaiting-employee   (申请待处理或拒绝)
  -> planning            (申请批准并重新检查)
  -> ready                (所有步骤已有有效订阅)

ready
  -> preflight-failed
  -> confirmed
```

规划失败和能力缺口必须区分：

- `planning-failed`：模型响应无效、接口错误、解析错误或内部异常。
- `awaiting-employee`：意图有效，但当前目录无法提供可执行员工。

## 10. 实施任务分解

### P0：能力数据闭环

- 在 `ArrangementService` 中加载已授权员工 Skill 能力摘要。
- 扩展企业候选映射，保留能力摘要。
- 为能力摘要加载增加缓存、超时、认证失败和部分失败处理。
- 增加能力 ID、名称和描述的标准化匹配函数。

### P1：确定性推荐

- 实现授权员工、企业员工、平台员工统一候选模型。
- 按 7.2 节排序并在模型结果后做客户端二次校验。
- 平台目录按能力 ID 查询；名称查询结果必须二次过滤。
- 将匹配分、覆盖率和缺失能力写入候选理由。

### P2：申请与重规划闭环

- 申请按钮只对 `candidateMatches` 中的合法候选开放。
- 申请状态批准后刷新 `/client/subscriptions` 和能力摘要。
- 重新规划时复用 `intentAnalysis`，只处理 `unresolvedSteps`。
- 申请拒绝、取消、重复申请和网络重试均保持幂等。

### P3：执行安全与体验

- 规划完成后执行 DAG 校验、模型白名单校验和权限预检。
- UI 区分“规划失败”“缺少员工”“申请中”“已批准待重新检查”。
- 展示推荐依据和下一步操作，不展示内部 Token 或 Skill 正文。

## 11. 测试与验收

### 11.1 单元测试

- 已授权员工能力完整覆盖时，平台员工不会出现在推荐列表。
- 已授权员工部分覆盖时，只为缺失步骤查询企业/平台目录。
- 能力 ID 精确匹配优先于名称和描述匹配。
- 平台 `keyword` 不命中但返回目录后，客户端能力二次过滤仍可推荐正确员工。
- 无效候选、伪造订阅、未允许模型、不可申请员工均被丢弃。
- 申请幂等键稳定，重复提交不创建重复申请。
- `APPROVED` 状态会刷新订阅并重新规划；不会直接执行申请响应中的员工。
- 模型无效 JSON、非法 DAG、异常工具调用进入 `planning-failed`。

### 11.2 集成测试

1. 创建“搜索 AI 新闻”目标。
2. 返回意图步骤：关键词规划、联网搜索、事实核查。
3. 已订阅员工覆盖关键词规划，企业候选覆盖事实核查，平台候选覆盖联网搜索。
4. UI 只展示后两步候选，不重复推荐已订阅员工。
5. 提交平台员工申请，验证幂等键和申请状态。
6. 模拟批准后刷新订阅，重新检查得到完整 DAG。
7. 执行前验证所有节点均来自有效订阅，且模型在 `allowedModels` 中。

### 11.3 验收标准

- 任何可由已订阅员工完成的步骤都不会被推荐到市场员工。
- 能力缺口可解释，用户能看到推荐员工、来源、理由和申请动作。
- 申请批准后无需重新输入目标即可继续编排。
- 未授权、过期或不可申请员工永远不会进入执行 DAG。
- 规划异常不会跳转登录页；认证错误只通过统一认证失效流程处理。
- 不向日志、IPC 或模型提示词暴露 refresh token、employment token 或 Skill 正文。

## 12. 观测与排障

每次规划记录以下非敏感字段：

- `planningId`、`draftId`、`draftRevision`；
- 意图步骤数量、未解决步骤数量；
- 各目录查询次数、返回候选数量、过滤后候选数量；
- 选中来源：`authorized/enterprise/platform`；
- 失败阶段：`intent/skills/catalog/match/parse/preflight`；
- API `requestId` 和错误类型。

禁止记录访问令牌、刷新令牌、Employment Token、完整 Skill 内容和模型原始敏感上下文。

## 13. 完成定义

当以下条件全部满足时，视为该功能闭环完成：

1. 意图快照能够稳定生成并持久化。
2. 已订阅员工能力摘要真实来自员工 Skill 接口。
3. 推荐顺序符合授权优先、企业其次、平台最后。
4. 企业和平台候选可以申请，申请状态可查询且幂等。
5. 批准后自动刷新订阅并复用原意图重新规划。
6. 只有有效订阅节点可以通过 preflight 并执行。
7. 单元、集成、IPC、边界和构建检查全部通过。
