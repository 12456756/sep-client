# 客户端视频提交错误与账务展示修复方案

- 日期：2026-10-22。
- 状态：客户端已实施，视频专项验证通过；最终全仓类型检查被并行素材编排改动阻塞。未进行真实报价或生成验收，未发布。
- 配套文档：[SEP 视频定价、预算与错误链路收敛开发方案](../../../SEP/docs/plans/2026-10-22-SEP视频定价预算与错误链路收敛开发方案.md)，位于相邻 SEP 仓库。
- 范围：Electron 视频网关、任务恢复、工具输出、运行结束处理和成果面板。
- 原则：复用现有本地状态、账务枚举、错误与审批机制；调试和验收不发送真实报价或生成请求。

## 1. 为什么客户端必须改

SEP 取消独立视频预算，只能解除这一个拦截条件。客户端仍存在以下独立问题：

| 现状 | 后果 |
| --- | --- |
| 非成功 HTTP 响应直接丢弃正文，402 没有对应业务处理 | 资金不足、预算不足等原因变成通用服务错误 |
| submit 捕获异常后统一保存不确定状态 | 明确被拒绝的请求也显示 `SUBMISSION_UNKNOWN` |
| 无回执查询 404 覆盖原错误 | 原因丢失，并重复查询不存在的回执 |
| 无回执的真实任务默认 `NOT_RESERVED` | AI 可能错误宣称没有扣费 |
| Pi 视频工具把全部错误改成 `Video job reported an error.` | 模型看不到可安全展示的业务错误码 |
| `VideoRunService.waitForRun()` 对非成功结果统一抛 `INVALID_STATE` | 上层仍可能只得到通用失败，覆盖已经查明的原因 |

因此，SEP 修复负责“是否允许提交”，客户端修复负责“准确理解和展示结果，并正确恢复”。两端都需要开发。

## 2. 开发范围

| 文件 | 修改内容 |
| --- | --- |
| `electron/data/sep-video-media-gateway.ts` | 有界解析错误响应，保留安全业务码、阶段、HTTP 状态和关联 ID |
| `electron/service/video-service.ts` | 区分可信的明确拒绝与提交未知；所有恢复入口遵守相同判定 |
| `electron/domain/video-media.ts` | 按需补充状态判定与校验，保持原请求身份和状态单调性 |
| `electron/service/mock-video-host-service.ts` | 修正 `jobView()`、恢复适配和启动筛选；该文件也承载真实模式 |
| `electron/service/video-tracker.ts` | 核对停止和退避行为，不为已拒绝任务继续安排查询 |
| `electron/service/video-run-service.ts` | 传递明确失败原因，保留交付成功条件 |
| `electron/pi/sdk/pi-coding-agent-adapter.ts` | 白名单保留视频工具错误，防止通用文案覆盖 |
| `src/components/workspace/VideoArtifactsPanel.tsx` | 准确展示拒绝、未知、账务及可执行操作 |
| `src/shared/video-media.ts` | 仅在有必要时调整共享视图契约；首版复用已有枚举 |

共享错误类型优先放在现有共享或 domain 层，供 service 消费；service 不通过导入具体 HTTP adapter 来识别错误，避免新增层间耦合。不为这次修复搭建通用错误框架。

## 3. 错误从 HTTP 到工具完整保留

### 3.1 网关只读取受控字段

复用当前 JSON 读取的大小限制、MIME 检查和中断处理。错误响应只提取：

- 白名单 `error.code`，不接受任意字符串作为可执行状态依据。
- `source`，用于区分 SEP 平台业务错误和上游错误。
- 请求阶段，例如 `video-quote`、`video-submit`；查询和下载错误不能冒充提交错误。
- HTTP 状态及经过长度、字符校验的 `requestId`。

`clientRequestId` 从冻结的本地请求取得，不从未校验的错误正文覆盖。错误文案由客户端静态映射生成；任意 message、HTML、原始响应、提示词和凭据都不进入日志、工具或 UI。

报价失败时可能还没创建本地 job，直接返回报价阶段的安全错误，不伪造 jobId、runId 或 receipt。提交后才进入下面的状态判定。

### 3.2 可信的明确拒绝

只对白名单业务码、预期 HTTP 状态、可信平台来源和已测试的“本次请求尚未派发”语义建立映射：

| 状态与业务码 | 安全文案 |
| --- | --- |
| 402 `INSUFFICIENT_FUNDS` | 可用资金不足，视频提交被拒绝 |
| 402 `VIDEO_BUDGET_EXCEEDED` | 企业视频预算不足，视频提交被拒绝 |
| 409 `QUOTE_EXPIRED` | 本次报价已过期，视频未提交至生成服务 |
| 409 `VIDEO_CONCURRENCY_LIMIT` | 企业视频并发已满，视频提交被拒绝 |

这些映射必须与 SEP HTTP 测试共同验证。不能只凭 HTTP 402、403、409 就判定未派发；重复身份、原回执恢复失败或上游返回同状态不属于提交前拒绝。

`MEDIA_FORBIDDEN` 只保留安全的授权错误提示，不纳入确定拒绝白名单：SEP 可能在资金预占后再次检查授权并返回此码。无回执时仍显示账务待确认，并查询原请求。

旧 SEP 若缺少证明来源或阶段语义的字段，可以保留已知错误码并显示安全原因，但不能据此断言没有提交或没有费用。未知错误不自动重试。

### 3.3 保留业务码，不被其他层覆盖

`SepVideoGatewayError` 的应用错误分类与平台业务码含义不同。service 必须读取受控的业务信息，不能只保存 `SERVICE_UNAVAILABLE` 或 `PERMISSION_DENIED`。日志和工具可提供已脱敏的阶段、HTTP 状态、关联 ID；不能保存原始响应体。

Pi 视频工具仅允许白名单错误码和静态文案通过。非白名单错误继续返回安全的通用错误；不把当前全量字符串透传给模型，也不把所有已知码统一替换成一句话。

## 4. 任务状态与恢复

首版保留 `NOT_SENT / MAYBE_SENT / RECEIPTED`，不新增提交状态机，不倒退原状态，不制造服务端回执。

| 证据 | 本地保存 | 对外展示 | 恢复行为 |
| --- | --- | --- | --- |
| 尚未发送 POST | `NOT_SENT` | 未提交 | 按现有审批和提交流程处理 |
| 本次原始 POST 收到可信明确拒绝，且无 receipt | `MAYBE_SENT + STOPPED + 白名单拒绝码` | `generationStatus: FAILED`，说明提交被拒绝 | 停止自动和手工恢复查询，不自动重提 |
| POST 超时、断网、响应不可信 | `MAYBE_SENT + INTERRUPTED` | 提交结果待确认 | 只查询原 clientRequestId |
| 获取原 receipt | `RECEIPTED` | 优先使用 receipt | 沿用原回执、账务和下载恢复 |

`MAYBE_SENT` 描述客户端已进入可能发送 POST 的阶段，不能因收到拒绝而写回 `NOT_SENT`。确定拒绝由受控错误码和停止状态共同表达；查询、下载和普通异常不得写入这组确定拒绝标记。

必须共用同一个判定，覆盖：

1. `VideoService.submit()` 的错误保存。
2. `resumeOriginal()`、`resume()` 和 `recover()` 的提前返回。
3. Host tracker 的 `recover` 适配，它目前直接遍历任务并调用 `service.resume()`。
4. `resumePending()` 启动恢复及 tracker 的筛选。
5. `jobView()`、运行恢复筛选和面板按钮。

只修改 tracker 的 `pollable()` 不够：它调用 `recover()` 后才筛选，而 recover 可能已经请求服务端。判定应在实际查询之前生效，重启后也一样。

对于原有未知任务，查询返回 404 仍然只是“当前未找到回执”。不得回退状态、清除原身份、自动重新报价或再次 submit。保留已有可信错误，不让后续查询错误覆盖原始提交证据。

## 5. 账务、价格和操作展示

### 5.1 账务按证据展示

| 情况 | 展示规则 |
| --- | --- |
| 有服务端 receipt | 使用 receipt 的账务状态，不由输出数量推断 |
| 真实模式 `NOT_SENT` | 尚未提交，尚未预占 |
| 可信提交前拒绝，已确认未预占 | `NOT_RESERVED`，尚未预占 |
| 无 receipt 且提交未知 | 复用 `RECONCILING`，显示账务待确认 |
| Mock | 继续 `MOCK_NOT_CHARGED`，明确不收费 |

“未派发”不总等于“从未预占”。若某错误路径可能已经预占，仍须由回执或账务证据确认是否释放，不得仅凭拒绝码展示未扣费。具体白名单必须在 SEP 测试中证明其账务语义。

### 5.2 价格只展示，不重算

`amountUsd` 来自 Sub2 经 SEP 返回的客户报价，`amountCny` 是 SEP 冻结金额；客户端不计算第二套汇率、倍率或时长价格，也不写死 `$4.00`、`¥28.80`。

报价、已预占和已结算分开表达；只有有效实际结算证据才能说“实付”或“已扣费”。预算设置下线不影响费用展示及审批策略。

### 5.3 按钮与 AI 文案

- 明确拒绝：显示具体原因，不提供无效的“恢复跟踪”。
- 提交未知：保留查询原请求的入口，说明账务待确认，不提供会重新生成的快捷重试。
- 已生成但保存失败：只提供原输出的重新保存或下载，不能创建新任务。
- 收到资金或授权错误时，AI 不建议修改提示词、品牌词或改走图生视频来绕过。
- 用户明确重新发起才创建新请求并重新走报价和审批；不把“查进度”理解为新付费授权。

## 6. 运行结束处理

当前 `VideoRunService.waitForRun()` 在 job 未成功保存或账务待核对时统一抛 `INVALID_STATE`。修复要求：

1. 提交被拒绝时，沿现有应用错误通道保留安全的业务原因，不在等待结束时覆盖成通用状态错误。
2. 明确失败不能成为成功交付；提交未知也不能伪装成生成失败或成功。
3. 已成功且已保存、账务满足现有条件的任务继续正常完成，不能受同任务下历史拒绝记录误伤。
4. 按 run 内实际发起的 job 处理交付，保留现有成功验收；不要为修复文案而整体跳过 `waitForRun()`。
5. 任务是否继续对话或终止沿用现有运行时策略，本次只修复错误语义，不重新设计任务生命周期。

## 7. 实施与验收

开发顺序：先补网关错误分类和 service 状态回归，再修所有恢复入口，随后改 host 视图、Pi 工具与面板，最后验证运行结束时原因仍保留。可以独立于 SEP 预算下线开发；若旧 SEP 无可信明确拒绝信息，继续保守显示待确认。

优先扩展现有测试：

- `electron/data/sep-real-video-gateway.test.ts`、`sep-video-media-gateway.test.ts`：错误解析及协议边界。
- `electron/service/video-service.test.ts`、`video-tracker.test.ts`：拒绝停止、未知查询及重启恢复。
- `electron/service/mock-video-host-service.test.ts`、`video-run-service.test.ts`：host 恢复入口、视图及 run 错误。
- `electron/pi/sdk/pi-video-tools.test.ts`、`pi-coding-agent-adapter.test.ts`：错误码与脱敏。
- `src/shared/video-view.test.ts` 及按需增加的面板测试：账务和操作可见性。

必须证明：

| 场景 | 验收结果 |
| --- | --- |
| 可确认的资金或预算拒绝 | 原因保留，后续 recover/resume/启动恢复不增加查询或提交调用 |
| 未知或伪造错误体 | 不判定未派发，不宣称未收费 |
| POST 响应丢失，随后查询成功 | 同一 clientRequestId 接受原回执，submit 总调用次数为 1 |
| 查询原请求持续 404 | 保留未知，遵守既有退避和次数限制，quote/submit 均无新增调用 |
| 无回执且提交未知 | 工具和面板均为账务待确认 |
| run 结束遇到明确拒绝 | 失败原因不变成 `INVALID_STATE` 或通用视频报错 |
| 旧任务、Mock、已成功输出 | 可正常读取和恢复，不改写身份、报价或已保存文件 |
| 原输出重新保存 | 不触发报价和生成 |
| 敏感内容注入错误响应 | 日志、工具、IPC 和 UI 无原文泄漏 |

完成针对性测试后运行 `npm run typecheck`、变更文件 ESLint、`npm run check:boundaries` 和 `npm run build`；修改 Pi SDK 适配器补齐 `npm run poc:01` 至 `npm run poc:04`。若触及运行时并发或生命周期，追加 `npm run test:invariants`。

测试使用 mock gateway、临时任务存储和合成响应，不调用生产视频报价或生成。最终视频专项回归 268 项通过，变更文件 ESLint 和架构边界检查通过；实现阶段的构建及四项 SDK PoC 也已通过。业务回归覆盖网关、持久化恢复、host、run、Pi 工具和面板。

最终全仓 `typecheck` 未通过：并行素材编排改动中的 `arrangement-media-link-store.test.ts` 存在参数数量不匹配，`media-store.test.ts` 引用尚未实现的 `deriveReferenceFromOutput`。本轮保留这些其他工作改动，未将全仓类型检查标记为通过。生产部署后的联调仍需单独安排，不通过重新生成历史任务验收。

## 8. 历史任务与发布限制

不根据旧 `SUBMISSION_UNKNOWN / NOT_RESERVED` 批量修复历史任务；缺少原始错误证据的任务仍按原身份核对。已成功的视频不能重新生成来修复显示。

客户端发布不需要修改 Sub2 定价配置，也不能代替 SEP 删除预算执行逻辑。兼容老 SEP 的错误输出，保留保守恢复策略；不为了追求更确定的文案放宽未派发和未收费的判定。
