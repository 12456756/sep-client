## 1. 目标与边界

工作安排模块负责把用户意图变成可校验、可确认、可恢复的工作执行计划。模块需要同时支持：

- 对话式工作：多个员工共享一个对话上下文，可以在同一工作内切换员工。
- 自动编排：用户点击后由客户端后端 AI 生成可编辑 DAG 草稿。
- 手动编排：用户编辑真正的 DAG，而不是被强制转换为线性链。
- 任务级执行设置：共享工作区、任务权限、节点模型和确认策略。
- 执行前检查：员工状态、模型白名单、技能、工作区和订阅有效期阈值。
- 运行控制：节点失败等待用户选择重试或停止。
- 断点恢复：客户端退出、崩溃或运行时异常后，从中断节点继续。

模块不负责：

- 直接访问 SEP 数据库。
- 在 renderer 中执行 AI 编排、权限判断或路径安全检查。
- 把 Pi SDK 对象、Employment Token 或文件路径协议暴露给 renderer。
- 修改已经执行或已经完成的 `WorkPlan`。

## 2. 已冻结的业务决策

### 2.1 生命周期

```text
ArrangementDraft
  -> validate
  -> preflight
  -> confirm
  -> WorkPlan
  -> WorkExecution
```

- 草稿永久保存，只有用户主动删除才删除。
- 页面切换、抽屉关闭、客户端重启和异常退出都不删除草稿。
- 确认后的工作计划是不可变快照。
- 确认后原草稿继续保留，作为用户可复用的安排方案；修改草稿会产生新的 revision，不影响历史计划。
- 正式工作进入现有任务/工作记录体系，草稿不进入首页工作统计。

### 2.2 执行模型

- 工作目录为整个工作共享的一个 workspace。
- 模型绑定到 DAG 节点；同一员工在不同节点可以使用不同模型。
- 权限是整个工作一份任务级策略，所有节点和员工共享。
- DAG 依赖由 `dependsOn` 表达，数组中的排列顺序不代表执行顺序。
- 任意节点失败后停止继续调度，所有尚未开始的分支保持等待。
- 失败后的用户动作只有“重试失败节点”和“停止整个工作”。
- 不允许跳过失败节点，不允许单独放行独立分支。
- 客户端退出、崩溃或运行时异常时，运行中的节点和执行实例必须标记为 `interrupted`。
- 恢复时已完成节点不重复执行，中断节点重新创建 attempt；失败节点必须先重试成功，后继节点才可解除阻塞。

### 2.3 订阅有效期

预检查按每个节点绑定的订阅员工执行，但同一订阅在一个计划中只检查一次：

```text
Subscription.status = ACTIVE
且 endDate 为空，或 endDate - 当前时间 >= thresholdTimeMs
```

这里检查的是订阅有效期的最低剩余时间，不估算单个任务的运行时长，也不把余额、token 或算力额度换算成时间。阈值由客户端后端配置或 SEP 策略提供，renderer 不能降低阈值。

## 3. 总体架构

继续使用仓库现有依赖方向：

```text
renderer
   │ window.electronAPI / IPC
   ▼
controller/routes/arrangement.ts
   ▼
service/arrangement-service.ts
   ├── data/arrangement-draft-store.ts
   ├── data/workflow-store.ts
   ├── data/task-run-store.ts
   ├── service/employee-authorizer.ts
   ├── service/plan-preflight-service.ts
   └── runtime ports
          ▼
runtime/workflow-runner.ts
runtime/task-execution-coordinator.ts
          ▼
pi/sdk/
```

### 3.1 Controller

`controller/routes/arrangement.ts` 只负责：

- 为每个 IPC channel 声明 Zod schema。
- 校验 `draftId`、revision、nodeId、idempotencyKey 等输入。
- 调用 `ArrangementService` 或工作执行服务。
- 返回服务层结果，由统一 router 负责错误信封。

controller 不负责：

- DAG 合法性判断。
- 订阅有效期计算。
- 权限合并。
- 读取或拼接本地文件。
- 直接调用 Pi SDK 或 SEP HTTP。

### 3.2 Service

新增 `service/arrangement-service.ts`，负责安排工作用例：

- 创建、读取、更新、删除草稿。
- 启动和取消自动编排。
- 调用纯领域校验和预检查。
- 在 revision 和幂等键约束下冻结 `WorkPlan`。
- 将确认后的计划交给执行端口，不持有 worker 或 Pi session。

服务依赖端口而不是 runtime/Pi 具体对象：

```ts
interface PlanGeneratorPort {
  generate(input: PlanGenerationInput): Promise<PlanGenerationResult>
  cancel(planningId: string): Promise<void>
}

interface WorkExecutionPort {
  start(planId: string, idempotencyKey: string): Promise<WorkExecution>
  retryFailedNode(workId: string, nodeId: string, idempotencyKey: string): Promise<WorkExecution>
  resumeInterrupted(workId: string, idempotencyKey: string): Promise<WorkExecution>
  stop(workId: string, reason?: string): Promise<WorkExecution>
}
```

### 3.3 Domain

扩展 `domain/workflow-graph.ts` 或增加 `domain/work-plan.ts`，保持零 IO：

- 校验节点 ID、员工绑定、模型字段、依赖存在性和 DAG 无环。
- 计算节点的 `ready`、`blocked` 和终态。
- 根据失败节点计算直接/间接后继。
- 根据重试成功结果解除可执行节点。
- 校验对话参与员工和共享上下文规则。
- 生成规范化的不可变计划对象。

领域函数不读取 SEP、不读取文件、不访问 Electron，也不决定如何发 IPC。

### 3.4 Runtime

新增或拆分以下运行时协作者：

| 协作者 | 职责 |
|---|---|
| `WorkflowRunner` | 按 DAG 状态调度节点，处理失败屏障和恢复 |
| `NodeScheduler` | 从 ready 节点中选择可运行节点，获取共享 workspace 锁 |
| `ExecutionCheckpoint` | 在节点状态和 attempt 变化时持久化检查点 |
| `PlanGeneratorRuntime` | 执行后端 AI 编排请求，发布规划进度 |
| `TaskExecutionCoordinator` | 保持现有公共方法和 Pi 运行兼容，编排普通任务/对话任务/工作流执行 |

`TaskExecutionCoordinator` 继续保持现有八个公共方法，工作流能力通过协作者或内部端口接入，不能重新把队列、事件和 worker 状态全部塞回协调器。

### 3.5 Pi SDK

Pi SDK 仍只能出现在 `electron/pi/sdk/`。节点执行时由 runtime 传入：

- 该节点的 `subscriptionId`。
- 该节点的 `modelId`。
- 任务级有效权限策略。
- 任务共享 workspace。
- 当前节点输入和前置节点输出摘要。

Pi adapter 负责把这些客户端领域数据转换成 SDK session 配置；service 不得导入 Pi 类型。

## 4. 领域数据模型

### 4.1 安排草稿

```ts
interface ArrangementDraft {
  id: string
  schemaVersion: 1
  revision: number
  mode: 'conversation' | 'auto' | 'manual'
  status: 'editing' | 'planning' | 'planning-failed' | 'ready' | 'preflight-failed' | 'confirmed'
  title: string
  goal: string
  confirmedInputs: string[]
  sharedSkillIds: string[]
  conversation: ConversationArrangement | null
  nodes: ArrangementNode[]
  workspace: SharedWorkspace
  permissions: RequestedTaskPermissionPolicy
  createdAt: number
  updatedAt: number
  lastPlanning: PlanningSummary | null
}
```

草稿写入采用完整文档替换，而不是多个字段分别写入。每次成功更新：

```text
expectedRevision 匹配
  -> 写入完整新文档
  -> revision + 1
  -> 原子替换
```

### 4.2 对话式计划

```ts
interface ConversationArrangement {
  participants: Array<{
    subscriptionId: string
    modelId: string
  }>
  activeSubscriptionId: string | null
}
```

正式工作只拥有一个共享会话上下文。切换员工时：

- 不创建新工作 ID。
- 不创建新的任务级会话文件。
- 将新员工作为当前参与者写入对话上下文。
- 后续消息带新的 `subscriptionId` 和对应 `modelId`，历史消息保持原员工归属。

### 4.3 DAG 节点

```ts
interface ArrangementNode {
  id: string
  subscriptionId: string
  modelId: string
  title: string
  instruction: string
  expectedOutput: string
  dependsOn: string[]
  skillIds: string[]
  requiresUserConfirmation: boolean
}
```

`x/y` 画布坐标只属于草稿展示数据，不参与执行判断。执行顺序只由 `dependsOn` 决定。

### 4.4 任务级权限

用户请求的权限和后端计算出的有效权限分开：

```ts
interface RequestedTaskPermissionPolicy {
  preset: 'read-only' | 'workspace-edit' | 'full-local'
  allowedPaths?: string[]
  deniedPaths?: string[]
  commandPolicy?: 'disabled' | 'restricted' | 'confirm-each'
}

interface EffectiveTaskPermissionPolicy {
  preset: 'read-only' | 'workspace-edit' | 'full-local'
  allowedTools: string[]
  allowedPaths: string[]
  deniedPaths: string[]
  requireApprovalFor: string[]
  commandPolicy: 'disabled' | 'restricted' | 'confirm-each'
}
```

有效策略计算：

```text
平台/企业能力上限
  ∩ 任务请求的 preset
  ∩ 工作区路径限制
  -> EffectiveTaskPermissionPolicy
```

renderer 只提交产品档位和必要的路径选择，不能提交任意 `allowedTools` 来扩大权限。`allowedTools`、`requireApprovalFor` 和最终路径由主进程计算。

### 4.5 共享工作区

```ts
interface SharedWorkspace {
  mode: 'shared'
  path: string | null
}
```

主进程负责：

- 将空路径解析为当前用户的默认工作区。
- 规范化绝对路径和相对路径。
- 拒绝系统敏感目录、凭据目录和工作区之外的写入。
- 将最终路径写入 `WorkPlan`，但不通过事件 payload 暴露敏感路径细节。
- 在所有节点之间使用同一 workspace lock key。

## 5. 草稿持久化设计

### 5.1 Store

新增 `data/arrangement-draft-store.ts`，职责仅限：

- 按当前 scope 读写草稿。
- 使用 `atomic-file.ts` 原子写和备份恢复。
- 校验 schemaVersion、revision、owner scope 和基本字段。
- 以 `WriteChain` 串行化同一草稿写入。
- 支持用户主动删除和删除正在规划的草稿。

草稿文件路径由 `ScopePath` 派生，例如：

```text
task-data/v3/<enterprise>/<member>/arrangement-drafts/<draftId>.json
```

具体路径必须由 `ScopePath` 提供，业务层不得拼接路径。草稿不使用 `localStorage` 作为权威存储。

### 5.2 Revision 和冲突

所有更新、规划回写、预检查和确认都携带 revision：

```text
旧 revision -> 用户更新 -> 新 revision
```

自动编排结果只能写回发起时相同的 revision。如果用户在 AI 运行期间修改草稿，AI 结果必须丢弃或作为待用户选择的建议返回，不能覆盖用户内容。

### 5.3 删除语义

删除草稿是幂等命令：

- 草稿不存在时返回成功或稳定的 `NOT_FOUND`，由接口约定统一处理。
- 正在规划时先取消规划，再使迟到结果失效。
- 已确认草稿仍可删除，但不能删除已经生成的正式 `WorkPlan` 和运行记录。
- 删除不影响由该草稿生成的历史工作。

## 6. 自动编排设计

### 6.1 规划调用

`arrange.generateAutoPlan` 只接收 `draftId + expectedRevision`。后端从草稿读取：

- 工作目标。
- 已确认材料。
- 候选员工。
- 可用技能。
- 企业/客户端规划模型配置。

这样可以防止 renderer 传入一份与已保存草稿不同的目标。

### 6.2 Planner Port

AI 编排通过 `PlanGeneratorPort` 抽象，默认实现运行在客户端后端，不把 LLM 调用放到 renderer：

```ts
interface PlanGenerationInput {
  planningId: string
  draftId: string
  goal: string
  confirmedInputs: string[]
  employees: PlanningEmployeeContext[]
  sharedSkillIds: string[]
}
```

实现可以选择：

1. 通过客户端已有模型网关调用规划模型。
2. 通过 Pi SDK 的独立 planner adapter 调用模型。
3. 在后续接入 SEP 规划接口时替换 outbound adapter。

无论使用哪种实现，IPC 草稿协议和确认协议不变。规划请求必须是显式的单次用例，不允许隐藏的第二次修复模型或无契约重试循环。

### 6.3 规划结果处理

AI 返回后按以下顺序处理：

```text
解析结构化 JSON
  -> schema 校验
  -> DAG 领域校验
  -> 员工/模型/技能引用校验
  -> revision 仍匹配？
  -> 写回草稿并递增 revision
```

规划失败时保留草稿和用户已有内容，只更新 `planning-failed` 状态及可展示的错误摘要。不得清空用户输入。

## 7. 手动 DAG 设计

### 7.1 前端提交规则

前端提交完整节点数组和每个节点的 `dependsOn`。后端不根据数组位置自动补依赖，也不把 DAG 转换成线性链。

后端必须检查：

- 节点 ID 唯一且满足安全格式。
- 依赖节点存在。
- 不允许自依赖和环。
- 一个节点可依赖多个节点。
- 无依赖节点可以并行 ready。
- 员工、模型和技能引用在预检查阶段仍需再次验证。

### 7.2 画布布局

布局坐标属于展示状态：

- 可写入草稿，便于用户下次继续编辑。
- 不决定执行顺序。
- 自动布局只在缺少坐标时执行。
- 后端不根据坐标推断依赖关系。

### 7.3 运行时调度

`WorkflowRunner` 使用拓扑可执行性而不是数组顺序：

```text
pending + 所有依赖 completed
  -> ready
ready + workspace/resource 可用
  -> running
running -> completed / failed / interrupted
```

共享 workspace 下允许逻辑并行，但真正启动前仍需经过 workspace lock。后续若要支持文件级并发，需要新增文件冲突策略，不能默认为“最后写入者覆盖”。

## 8. 计划确认与执行

### 8.1 预检查

`PlanPreflightService` 聚合以下检查：

1. 草稿 revision 和 DAG 合法性。
2. 每个唯一订阅的当前状态。
3. `Subscription.endDate` 剩余时间是否超过阈值。
4. 每个节点的模型是否属于对应订阅 `allowedModels`。
5. 节点技能是否存在、版本是否可用。
6. 任务权限是否超过平台/企业上限。
7. 共享 workspace 是否可访问、是否满足路径策略。
8. 是否存在会阻止启动的本地资源冲突。

检查结果必须逐节点返回，并带 `preflightId`、revision、检查时间和过期时间。

### 8.2 确认

确认时后端不能只相信旧的 `preflightId`：

```text
锁定草稿 revision
  -> 重新读取实时员工目录
  -> 重新检查订阅 ACTIVE/endDate 阈值
  -> 重新计算有效权限
  -> 生成 planHash
  -> 写入不可变 WorkPlan
```

`planHash` 覆盖目标、节点、依赖、节点模型、workspace、权限和材料。任何字段改变都必须产生新的计划哈希。

### 8.3 创建执行实例

`confirmAndStart` 需要在一个应用级用例内完成：

```text
WorkPlan 写入
  -> WorkExecution 初始化
  -> 初始节点状态写入
  -> 初始事件写入
  -> 入队
```

使用 `idempotencyKey` 防止用户重复点击创建多个正式工作。计划已写入但入队失败时，保留未启动计划，允许再次调用 `work.start`，不能重新创建一份不同的计划。

## 9. 对话式多员工工作

对话式工作仍属于同一个 `WorkPlan` 和 `WorkExecution`：

- `conversation.participants` 保存可切换员工及其模型。
- 所有轮次共享一个 task-level Pi session 文件和一份规范化消息投影。
- 当前员工切换必须通过服务层授权，并在切换成功后更新当前参与者。
- 每轮消息记录实际 `subscriptionId`、`modelId` 和 runId。
- 切换员工不会清空上下文，不会创建新的工作记录。
- 新员工必须通过当前目录和技能包授权后才能加入。

现有 `conversation-service.ts` 可以继续承载多轮消息用例；安排工作服务只负责创建其初始计划和参与者配置，避免复制对话恢复逻辑。

## 10. 失败、停止与恢复

### 10.1 失败屏障

任一节点失败时：

```text
记录 node.failed
停止接纳新的 ready 节点
直接/间接后继 -> blocked
未开始的独立分支 -> hold/pending
执行实例 -> waiting-user
```

默认让已经开始运行的其他节点完成当前 attempt，完成后不再启动新的节点；这样可以避免为了一个失败节点强制中止其他已经产生副作用的操作。所有尚未开始的分支都必须等待用户决定。

如果运行中的其他节点也失败，记录全部失败节点，但用户操作仍只有：逐个重试失败节点，或停止整个工作。不能通过跳过其中一个失败节点继续。

### 10.2 重试失败节点

`work.retryFailedNode` 只能用于 `waiting-user` 状态下的 `failed` 节点：

1. 重新检查该员工、模型、技能、权限和订阅有效期。
2. 新建该节点 attempt，不清除历史失败记录。
3. 失败节点进入 `running`，其后继暂时保持 `blocked`。
4. 成功后重新计算所有节点：依赖全部完成的节点进入 ready，独立分支恢复调度。
5. 再次失败则回到 `waiting-user`。

不允许把失败节点改成 `skipped` 或伪造完成输出。

### 10.3 客户端退出和异常

主动退出、窗口关闭、进程崩溃恢复都遵循同一数据语义：

```text
停止新节点 admission
请求 worker abort
有限等待
所有仍为 running 的节点 -> interrupted
所有仍为 running 的 execution -> interrupted
写入 interruptionReason
```

下次启动时扫描持久化记录，将遗留的 `running` 记录幂等修正为 `interrupted`。不能因为没有收到错误而把它们当成 completed。

### 10.4 断点恢复

`work.resumeInterrupted` 的默认行为：

- 已完成节点保持原输出。
- 中断节点创建新的 attempt，从该节点重新执行。
- 失败节点仍需先调用 `retryFailedNode`，不能被恢复接口绕过。
- 被失败节点阻塞的节点继续保持 blocked。
- 中断节点之后的节点重新根据 DAG 计算 ready。
- 恢复前再次进行员工、模型、技能、权限、workspace 和订阅检查。

## 11. 数据持久化与一致性

### 11.1 复用现有数据层

| 数据 | 主要 Store | 说明 |
|---|---|---|
| 安排草稿 | `ArrangementDraftStore` | 永久保留，用户主动删除 |
| 正式计划 | `WorkflowStore` + `TaskMetadataStore` | 计划不可变，按 task scope 隔离 |
| 执行实例 | `TaskRunStore` | 每次执行和每个 attempt 的结果 |
| 节点检查点 | `TaskRunStore` 扩展或独立 checkpoint store | 状态、attempt、输出和最后事件序号 |
| 执行事件 | `TaskEventStore` | 事件序列、失败、恢复和中断记录 |
| 对话消息 | 现有 conversation context store | task-level 共享上下文 |

所有写入都必须：

- 通过 `ScopePath` 派生路径。
- 通过 `atomic-file.ts` 或事件追加的既有实现写入。
- 通过 `WriteChain` 串行化同一 scope/task 的更新。
- 使用 schema 读取校验，损坏数据进入备份/隔离流程。

### 11.2 事件顺序

节点状态和事件写入顺序必须可恢复：

```text
先写节点/执行状态
  -> 再写状态变化事件
  -> 再向 renderer 推送
```

如果推送失败，不回滚已经落盘的业务状态；renderer 重载后通过 Query 重新取得权威状态。

### 11.3 幂等性

以下命令必须支持幂等键：

- `arrange.confirmDraft`
- `arrange.confirmAndStart`
- `work.start`
- `work.retryFailedNode`
- `work.resumeInterrupted`
- `work.stop`

幂等键绑定 scope、目标 ID、revision/节点 ID 和动作类型，不能跨用户复用。

## 12. SEP 适配设计

### 12.1 必需的目录字段

现有 `GET /client/subscriptions` 需要至少提供：

```text
subscriptionId
employeeId
status
startDate
endDate
allowedModels
templateVersion
employee summary
当前用户可见的授权信息
```

数据库依据是 `Subscription.status/startDate/endDate/employeeId`。客户端不把 `DigitalEmployee` 总数当成企业订阅总数，也不把数字员工固有属性和 `EmployeeGrant.departmentId` 混为一谈。

### 12.2 权威订阅预检查

建议新增批量接口：

```http
POST /client/subscriptions/preflight
```

请求只包含订阅 ID 和节点所选模型 ID，不包含 refresh token 或客户端文件路径。响应返回每个订阅的：

- 当前状态。
- `endDate`。
- 剩余时间。
- 服务端阈值。
- 允许模型。
- 当前用户授权是否有效。
- 不通过时的稳定原因码。

该接口只负责 SEP 权威数据检查；本地 DAG、workspace 和任务权限仍由客户端后端检查。

### 12.3 技能和模型

复用现有：

- `/enterprise/subscriptions/:subscriptionId/package`
- `/enterprise/employees/:employeeId/skills`
- `/enterprise/skill-versions/:versionId/preview`
- `/gateway/v1/chat/completions`

如果企业规划模型不在某个员工订阅的 `allowedModels` 中，SEP 需要额外暴露客户端可用的规划模型策略，例如：

```http
GET /client/enterprise/model-policy
```

否则由客户端后端使用已有、且被授权的规划模型适配器完成 AI 编排。无论规划模型来自何处，规划结果都不能绕过客户端的最终员工/模型校验。

## 13. 安全设计

### 13.1 输入与权限

- 所有 IPC 参数由 controller 使用 Zod 校验。
- 所有 `draftId`、`workId`、`nodeId` 先验证当前 scope，再做业务操作。
- renderer 不能提交 token、Pi session、任意工具白名单或任意系统路径作为可信策略。
- 工具白名单由权限档位计算，未知工具默认拒绝。
- `read`、`grep`、`find`、`ls` 可在路径策略内直接执行。
- `write`、`edit`、`bash` 仍需逐次审批；审批超时自动拒绝。

### 13.2 路径和命令

- `read/write/edit` 的路径必须在共享 workspace 和允许路径内。
- 拒绝 `.env`、凭据、token、系统目录等敏感路径。
- `bash` 需要执行命令风险检查，拒绝删除、格式化、权限修改、远程脚本和工作区外操作，具体规则由 Pi guard 和主进程共同执行。
- 任务权限只能缩小企业/平台上限，不能扩大。

### 13.3 日志和事件

- 不记录 access token、Employment Token、refresh token、Authorization header。
- 不把完整 prompt、完整 AI 响应、工具输入或敏感路径写入普通日志。
- 规划进度只发送阶段、数量和用户可见摘要，不发送思维链。
- 所有错误经过统一 error mapper 和 redact 流程。

## 14. 当前前端实现迁移

安排工作后端接入后，需要移除以下前端临时权威逻辑：

| 当前实现 | 迁移目标 |
|---|---|
| `planAutoArrange()` 本地规则匹配 | 调用 `arrange.generateAutoPlan`，显示后端规划事件 |
| `ManualArrange.chain()` 强制线性依赖 | 维护用户编辑的完整 `dependsOn` DAG |
| `RunSettings.model` 单一工作模型 | 每个节点保存 `modelId` |
| `permissionOverrides` 前端状态 | 使用任务级 `RequestedTaskPermissionPolicy`，后端返回有效策略 |
| `savedFlows` localStorage | 迁移为持久化 `ArrangementDraftStore` |
| prompt 尾部 `[SEP_WORK_META]` | 后端正式保存 `WorkPlan`/metadata，旧 prompt 仅兼容读取 |
| 前端过滤和推导工作状态 | 消费后端 `WorkExecution`/summary 状态 |

迁移期间可以保留旧 IPC channel 作为兼容适配，但新页面不得新增对 prompt 元数据的依赖。

## 15. 测试设计

### 15.1 Domain 单元测试

- 多前置节点全部完成后才 ready。
- 任意环都被拒绝。
- 失败节点的直接和间接后继全部 blocked。
- 独立节点在失败屏障下不自动运行。
- 失败节点重试成功后正确解除后继阻塞。
- 完成节点不会因恢复重复执行。
- 对话参与者切换不改变共享上下文 ID。

### 15.2 Service 测试

- 草稿 revision 冲突不会覆盖新数据。
- 自动规划结果在草稿被修改后被丢弃。
- 删除规划中的草稿会取消规划并拒绝迟到回写。
- 预检查能报告每个节点的订阅状态、endDate、阈值和模型问题。
- 权限策略只允许缩小平台/企业上限。
- 确认和启动幂等，不产生重复 WorkPlan/WorkExecution。

### 15.3 Runtime 测试

- 多个无依赖节点可以进入 ready，但共享 workspace 锁生效。
- 一个节点失败后不再 admission 新节点。
- 已运行 sibling settle 后执行进入 waiting-user。
- retry 只增加失败节点 attempt。
- stopAll 将所有 running 节点持久化为 interrupted 或 stopped。
- 启动恢复能把遗留 running 记录修正为 interrupted，且重复恢复无副作用。

### 15.4 Adapter/IPC 测试

- SEP 响应缺字段或类型错误时被拒绝，不进入会话状态。
- SEP 订阅 endDate、status 和 allowedModels 正确归一化。
- 每条安排工作 IPC route 都有 schema。
- 跨 scope 访问草稿、计划、执行和节点都返回安全的 NOT_FOUND。
- 权限策略、路径策略和审批请求不会泄露 token 或完整敏感输入。

### 15.5 真机流程

至少覆盖：

1. 自动编排 -> 修改 DAG -> 修改节点模型 -> 配置任务权限 -> 预检查 -> 确认启动。
2. 手动创建多分支 DAG -> 一个节点失败 -> 全部等待 -> 重试失败节点 -> 继续执行。
3. 客户端退出时节点中断 -> 重启 -> 恢复中断节点 -> 已完成节点不重复。
4. 同一对话切换多个员工 -> 消息上下文连续且员工归属正确。
5. 订阅剩余时间低于阈值 -> 阻止启动并显示具体员工。

## 16. 实施顺序

### 阶段一：契约和领域模型

## 17. 验收标准

- 自动编排由客户端后端 AI 触发，用户可以修改生成的 DAG 后再确认。
- 手动编排支持多前置节点、并行分支和环检测。
- 对话式工作可以切换多个员工，所有员工共享同一个上下文。
- 每个节点可以独立选择模型，并经过员工订阅模型白名单检查。
- 一个工作只有一份任务级权限，权限不能越过平台/企业上限。
- 所有节点使用一个共享 workspace，并有路径和并发保护。
- 启动前能逐员工检查 ACTIVE 状态和订阅剩余时间阈值。
- 任意节点失败后，所有未开始分支等待；用户只能重试失败节点或停止工作。
- 客户端退出/崩溃后，running 节点和执行实例不会被伪装成完成，能够从中断节点恢复。
- 草稿跨页面、跨重启永久保留，只有用户删除才消失。
- 计划确认和执行启动幂等，不产生重复正式工作。
- `npm run typecheck`、`npm run check:boundaries`、后端测试、并发测试、构建和 Pi PoC 全部通过。

## 18. 非目标与后续扩展

当前设计暂不包含：

- 跳过失败节点并伪造替代输出。
- 节点级权限覆盖任务级权限。
- 每个节点独立工作目录。
- 文件级协作锁和自动合并冲突。
- 跨客户端进程共享同一运行实例。
- 将客户端本地草稿同步到 SEP 云端。

这些能力如果未来需要，必须先扩展接口和状态模型，不能通过在现有 payload 中添加未定义字段临时实现。
