# 客户端自动更新签名与跨平台验收手册

> 状态：在建，Phase 3 执行手册。配置与自动化检查不等于真实平台验收。
>
> 日期：2026-10-09。依据：[客户端自动更新开发方案](./客户端自动更新开发方案.md)。

## 1. 发布边界

- `npm run package:beta` / `npm run package:stable` 是正式签名打包入口。先检查签名条件，再写运行配置和构建；签名或产物验证失败即停止，不生成本次发布校验和及说明。
- macOS 原生机器生成 arm64、x64 的 DMG 和 ZIP；Windows x64 原生机器生成 NSIS EXE。Linux 本阶段不进入签名发布链。
- 正式输出为 `dist/beta` / `dist/stable`；本地调试使用 `npm run package:local:beta` / `npm run package:local:stable`，输出隔离在 `dist/local/<channel>`。本地产物不能用作正式升级基线或发布源。
- 所有入口保留 `--publish never`，不上传。候选更新域名尚未验收；生产部署、版本提升和证书使用须由发布负责人安排。
- 包版本目前仍为 `0.1.2`。本次开发不自动改成 `0.1.3`，也不自动导入证书或调用 Apple 公证服务。
- 不把凭据写进 JSON、命令参数、截图、测试报告或仓库。使用受控环境变量、系统钥匙串或证书库；`.p8`、`.p12`、`.pfx` 已加入忽略规则，仍应存放在仓库外。

## 2. macOS 签名准备

当前锁定 builder 为 `25.1.8`；前置检查按其公证凭据选择顺序处理，不能用低优先级完整配置掩盖高优先级残缺配置。

| 条件 | 配置 |
| --- | --- |
| 固定签名团队 | `SEP_MAC_TEAM_ID`：10 位大写字母/数字；两个版本、两种架构必须一致 |
| 应用签名 | 钥匙串中有效的 `Developer ID Application` 私钥身份，团队与上项一致；或 `CSC_LINK` 和显式 `CSC_KEY_PASSWORD` 导入身份 |
| 公证方式 1 | `APPLE_ID`、`APPLE_APP_SPECIFIC_PASSWORD`、`APPLE_TEAM_ID`；团队必须与 `SEP_MAC_TEAM_ID` 一致 |
| 公证方式 2 | `APPLE_API_KEY`（可读的本地 `.p8` 文件）、`APPLE_API_KEY_ID`、`APPLE_API_ISSUER` |
| 公证方式 3 | `APPLE_KEYCHAIN_PROFILE`；非默认钥匙串可另外设置 `APPLE_KEYCHAIN` |
| 本机工具 | Xcode command-line tools，含 `codesign`、`security`、`xcrun notarytool`、`stapler`、`spctl`、`hdiutil`、`ditto` |

公证选择顺序为 Apple ID、API key、钥匙串 profile。只配置所选方式需要的值，避免残留账号凭据干扰；前置检查不验证服务器登录或 profile 是否有效，实际公证步骤会验证。`CSC_IDENTITY_AUTO_DISCOVERY=false` 和 PR 构建不允许走正式签名入口。

正式配置强制 `forceCodeSigning`、`mac.type=distribution`、团队限定身份、Hardened Runtime、公证及 DMG 签名。主程序与辅助程序使用 `build/entitlements.mac.plist`，只开放 JIT 与 unsigned executable memory，不默认开放调试附加或禁用 library validation。真实签名包仍须验证 Pi SDK、原生模块及浏览器工具启动；失败时按证据调整，不预先扩大权限。

配置凭据后执行：

```bash
npm run release:preflight
npm run package:beta
npm run verify:release-signatures -- beta
npm run verify:update-manifest -- dist/beta
```

稳定渠道须另外显式配置批准的 `SEP_BASE_URL` 和 `SEP_GATEWAY_URL`，再执行 `npm run package:stable`。先在 beta 验收。

最终验证针对**当前包版本**的两个 DMG 和两个 ZIP，不接受旧文件代替缺失架构。验证 DMG 自身签名、只读挂载后的应用及 ZIP 中实际应用：严格签名、应用标识、Developer ID、团队、Hardened Runtime、Gatekeeper 与已附加公证票据。DMG 仅要求签名，应用必须带有效票据；从浏览器下载并带 quarantine 的首装检查仍是必测项。

ZIP 验证使用 Electron 工具链已安装的 `yauzl` 检查实际条目和符号链接，再调用本机工具提取；拒绝越界、循环链接和大小写/Unicode 名称冲突，声明的总解压大小上限为 8 GiB。该工具只用于本项目构建产物，不是任意不可信归档的安全沙箱。DMG 正常卸载失败会尝试强制卸载；两次均失败则停止并保留临时挂载，须由测试人员处理，不递归删除仍挂载的卷。

## 3. Windows 签名准备

| 条件 | 配置 |
| --- | --- |
| 固定发布者 | `SEP_WINDOWS_PUBLISHER`，与证书 CN 完全一致；旧版和新版一致 |
| 文件证书方式 | `WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD`，或 builder 通用的 `CSC_LINK` / `CSC_KEY_PASSWORD` |
| 硬件/证书库方式 | `SEP_WINDOWS_CERTIFICATE_SHA1`，40 位证书指纹；证书库中须有唯一、当前有效、含私钥的 Code Signing 身份，驱动/令牌由管理员准备 |
| 环境 | Windows x64 原生构建机、PowerShell、证书签名工具及时间戳服务可达 |

只选择一个证书来源。指纹中的 SHA-1 用于选择证书，不是文件签名算法；正式文件签名使用 SHA-256。禁止通过旧的 `certificateFile`、自定义 `sign` 或 Azure 配置覆盖本阶段签名策略；这些来源需单独审批和适配。

```powershell
npm run release:preflight
npm run package:beta
npm run verify:release-signatures -- beta
npm run verify:update-manifest -- dist/beta
```

验证当前版本 NSIS 安装器及 `win-unpacked` 主 EXE 的 Authenticode 信任、发布者和时间戳。更新配置保留 `verifyUpdateCodeSignature=true`，明确写入发布者。有效代码签名不保证新证书立即具有 SmartScreen 信誉；记录信誉警告和未签名/签名损坏警告的区别，不通过关闭系统防护完成验收。

macOS 工具同时核对包内版本和实际 Mach-O 架构；Windows 当前工具只核对当前版本文件名及签名，不核对 EXE 内部版本资源。Windows 安装后的实际版本必须在下面的原生验收中记录，不能仅凭文件名放行。

## 4. 真实升级矩阵

必须逐个平台填写结果，不能将跨架构构建成功等同于另一架构运行成功。每个平台至少有一个首次安装的干净账户/VM 和一个升级账户；只用专门测试账户，不操作真实用户数据。

| 平台 | 首装 0.1.2 | 0.1.2 → 0.1.3 | 签名与系统信任 | 数据保留 | 网络/磁盘异常 |
| --- | --- | --- | --- | --- | --- |
| macOS arm64 | 待执行 | 待执行 | 待执行 | 待执行 | 待执行 |
| macOS x64 | 待执行 | 待执行 | 待执行 | 待执行 | 待执行 |
| Windows x64 | 待执行 | 待执行 | 待执行 | 待执行 | 待执行 |

1. 固定应用 ID `cn.longdao.longsilicon`、包名 `longsilicon`、产品名、渠道和签名主体；分别准备包含 P1/P2 更新能力的签名 `0.1.2` 基线与 `0.1.3` 目标包。早期无更新能力或未签名的 `0.1.2` 必须先人工安装合规基线，不能冒充在线升级测试。
2. 验证三个平台全部产物和清单哈希。在授权的隔离 HTTPS 源部署，不临时开放 renderer 任意源或忽略证书检查；如需替换计划中的候选源，应先审查固定 builder 配置。
3. 从浏览器下载首次安装器，保持系统下载隔离标记；macOS 安装进 `/Applications` 并弹出 DMG 后启动，Windows 用标准账户安装。检查签名/来源提示、Pi 会话和工具运行。
4. 登录测试账户，产生一条普通会话、一条工作编排与对应任务记录；设置主题/侧栏状态，记录窗口尺寸与位置。记录逻辑内容，不复制令牌、钥匙串密文或完整用户目录到报告。
5. 从 `0.1.2` 手动检查并下载 `0.1.3`；核对版本、说明、进度、取消/重试。活跃、排队或待审批任务必须阻止安装；等待任务结束后再次显式确认重启。
6. 重启后确认实际运行版本为 `0.1.3`，登录身份与记录一致，主题/侧栏保留，工具仍能运行，无后台安装循环；重复启动不能回到旧版。再以首次安装方式验证 `0.1.3`。
7. 本仓库主窗口当前固定为 1200×800 居中，未持久化位置/尺寸。窗口设置保留是原方案的未完成项，不能记为“通过”或用默认尺寸代替验收；需要后续实现及重启测试。

## 5. 异常测试

| 注入条件 | 必须观察的结果与证据 |
| --- | --- |
| 防火墙阻断源、DNS/TLS 错误、清单 404 | 业务仍可使用；更新错误安全显示，恢复网络后可重试；不泄漏 token/路径 |
| 系统代理/企业代理、慢网 | 使用真实系统代理配置验证检查与下载；记录 OS、代理类型和耗时，不记录代理凭据 |
| 下载中断网后恢复、取消后重试、退出后重开 | 可恢复可校验的完整产物；记录是否实际复用部分下载及传输字节，不能把从头重下称为断点续传 |
| 磁盘空间不足 | 仅在可回滚 VM/专用受限卷制造；旧版本及用户数据保持可用，错误后释放空间再试 |
| 安装目录权限不足/文件占用 | 安装失败可恢复旧版，无循环退出；记录权限和错误类别，不禁用安全检查 |
| 清单哈希不匹配、安装器签名错误/主体不符 | 拒绝更新，不退出安装；只在隔离测试源执行，测试结束恢复原清单 |
| 下载 100%、确认前新增任务 | 100% 不等于已通过校验；只有 downloaded 状态可确认，最终任务检查仍阻止安装 |

## 6. 证据与放行

每个矩阵结果至少记录日期、测试人、OS/架构、旧新版本、渠道、构建提交、产物 SHA-256、签名主体的非敏感标识、工具退出码、用户可见结果和脱敏截图。前置检查、mock 单元测试、未签名本地包以及文本 fixture 都不能充当签名或真实升级证据。

2026-10-09 本机证据：macOS arm64；`notarytool` 可用；钥匙串有效签名身份为 0；未配置签名及 Apple 公证环境变量。**当前禁止将阶段 3 标为完成**。下一步需要发布负责人的证书/公证环境、两种 macOS 测试机及 Windows x64 测试机、已授权的更新源和窗口状态保留实现。Phase 4 上传与发布自动化不在本次范围。
